# Solution 2 — Configuration calculée et outputs

[Énoncé](../2.Exercice%202.md) · [Guide commun](../readme.md)

## 1. Workflow complet

Créer `.github/workflows/exercice-2.yml` :

```yaml
name: Exercice 2 - Configuration par cible
on:
  workflow_dispatch:
    inputs:
      cible:
        description: Environnement simule
        required: true
        type: choice
        options: [dev, staging, prod]
        default: dev

permissions: {}
defaults:
  run:
    shell: bash

jobs:
  preparer_configuration:
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    outputs:
      cible: ${{ steps.configuration.outputs.cible }}
      api_url: ${{ steps.configuration.outputs.api_url }}
      db_name: ${{ steps.configuration.outputs.db_name }}
    steps:
      - name: Calculer les valeurs
        id: configuration
        env:
          EXO_CIBLE: ${{ inputs.cible }}
        run: |
          set -euo pipefail
          case "$EXO_CIBLE" in
            dev) api_url="https://dev.example.test"; db_name="dev_db" ;;
            staging) api_url="https://staging.example.test"; db_name="staging_db" ;;
            prod) api_url="https://prod.example.test"; db_name="prod_db" ;;
            *) echo "Cible invalide" >&2; exit 1 ;;
          esac
          {
            printf 'cible=%s\n' "$EXO_CIBLE"
            printf 'api_url=%s\n' "$api_url"
            printf 'db_name=%s\n' "$db_name"
          } >> "$GITHUB_OUTPUT"

  simuler_dev:
    needs: preparer_configuration
    if: ${{ needs.preparer_configuration.outputs.cible == 'dev' }}
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    env:
      EXO_API_URL: ${{ needs.preparer_configuration.outputs.api_url }}
      EXO_DB_NAME: ${{ needs.preparer_configuration.outputs.db_name }}
    steps:
      - run: |
          printf 'Simulation dev : %s / %s\n' "$EXO_API_URL" "$EXO_DB_NAME"

  simuler_staging:
    needs: preparer_configuration
    if: ${{ needs.preparer_configuration.outputs.cible == 'staging' }}
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    env:
      EXO_API_URL: ${{ needs.preparer_configuration.outputs.api_url }}
      EXO_DB_NAME: ${{ needs.preparer_configuration.outputs.db_name }}
    steps:
      - run: |
          printf 'Simulation staging : %s / %s\n' "$EXO_API_URL" "$EXO_DB_NAME"

  simuler_prod:
    needs: preparer_configuration
    if: ${{ needs.preparer_configuration.outputs.cible == 'prod' }}
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    env:
      EXO_API_URL: ${{ needs.preparer_configuration.outputs.api_url }}
      EXO_DB_NAME: ${{ needs.preparer_configuration.outputs.db_name }}
    steps:
      - run: |
          printf 'Simulation prod : %s / %s\n' "$EXO_API_URL" "$EXO_DB_NAME"
```

## 2. Chemin des données

Le script écrit dans `GITHUB_OUTPUT`. L'identifiant `configuration` rend ces sorties accessibles à `steps.configuration.outputs`. La section `outputs` du job les expose ensuite à ses consommateurs, qui déclarent `needs`. [Outputs entre jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/pass-job-outputs)

Il ne faut pas remplacer `GITHUB_OUTPUT` par `GITHUB_ENV` : ce dernier ne fournit qu'un environnement aux étapes suivantes du même job. [Fichiers d'environnement](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#environment-files)

Les valeurs sont courtes, contrôlées et non secrètes. Aucun rapport dotenv ni artefact n'est nécessaire pour cet échange. Aucun checkout n'est nécessaire non plus : aucun fichier du dépôt n'est lu.

## 3. Différence de calendrier avec GitLab

Dans le corrigé GitLab, `rules` utilise l'input connu avant l'exécution ; le dotenv n'existe pas encore à ce moment. Ici, le job dépendant peut utiliser l'output du job terminé dans sa condition. Les jobs non sélectionnés sont ignorés dans le graphe.

Les noms `dev`, `staging` et `prod` sont ici des cibles de simulation. Nous ne déclarons pas `environment` : aucun environnement GitHub ou déploiement réel n'est créé par cet exemple.

## 4. Essais

| Input | Job exécuté après préparation | Base affichée |
| --- | --- | --- |
| `dev` | `simuler_dev` | `dev_db` |
| `staging` | `simuler_staging` | `staging_db` |
| `prod` | `simuler_prod` | `prod_db` |

Les deux autres simulations sont ignorées. Un échec de préparation empêche les trois simulations. Pour tester la garde du script, reproduire localement le `case` avec `EXO_CIBLE=invalide` : le statut doit être non nul.
