# Options d'exécution dans GitHub Actions

## Objectif

Reprendre les options Jenkins sans supposer l'existence d'un bloc global `options`.

## 1. Correspondances et limites

| Jenkins | GitLab CI/CD | GitHub Actions |
| --- | --- | --- |
| `disableConcurrentBuilds()` | `resource_group` au niveau job | `concurrency` au niveau workflow ou job |
| `abortPrevious: true` | Annulation de pipelines redondants | `cancel-in-progress: true` |
| `buildDiscarder` | Rétention et expiration | Réglages du dépôt, `retention-days` pour les artefacts |
| `quietPeriod` | Pas d'équivalent général | Pas de délai de regroupement identique |
| `skipStagesAfterUnstable` | Pas d'état identique | Pas d'état `UNSTABLE` identique |
| `retry` | `retry` de job | Boucle bornée ou relance explicite |
| `timestamps` | Journaux horodatés selon configuration | Horodatage consultable dans les logs |
| `timeout` | Timeout de job | `timeout-minutes` de job ou d'étape |

## 2. Annuler l'ancienne exécution

Fichier `.github/workflows/options.yml` :

```yaml
name: Concurrence
on:
  workflow_dispatch:
permissions: {}
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
jobs:
  demo:
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    steps:
      - run: |
          echo "Operation de demonstration"
          sleep 60
```

Lancez deux fois sur la même branche : la nouvelle exécution demande l'annulation de l'ancienne. Le groupe inclut le nom du workflow pour éviter de bloquer involontairement d'autres workflows.

## 3. Faire attendre plusieurs exécutions

Remplacez uniquement le bloc `concurrency` précédent :

```yaml
concurrency:
  group: livraison-production
  cancel-in-progress: false
  queue: max
```

La documentation actuelle distingue `queue: single` (défaut : une seule attente, remplacée par la nouvelle) et `queue: max` (jusqu'à 100 attentes). `queue: max` ne se combine pas avec `cancel-in-progress: true`. L'ordre suit l'entrée dans l'attente du groupe, pas nécessairement l'ordre de déclenchement.

Avec le comportement par défaut, `cancel-in-progress: false` seul ne conserve donc pas toutes les exécutions en attente comme on pourrait l'attendre d'une file Jenkins. Le groupe est partagé au sein du dépôt. [Concurrence et file d'attente](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

Pour sérialiser uniquement les déploiements, placez ce bloc dans le job de déploiement. Vérifiez la prise en charge de `queue` sur GitHub Enterprise Server.

## 4. Timeout et attente

Fragment de job :

```yaml
jobs:
  controle:
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    steps:
      - name: Operation courte
        timeout-minutes: 2
        run: sleep 5
```

Le timeout d'étape ne remplace pas celui du job. Il n'existe pas de `timeout-minutes` à la racine imposant une durée totale à tout le workflow. [Syntaxe des timeouts](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idtimeout-minutes)

`sleep` consomme du temps sur un runner et ne fusionne pas les événements. Un minuteur d'environnement retarde un job selon ses règles de déploiement ; il ne reproduit pas `quietPeriod`. Voir [environnements](16.environnements%20et%20protections.md).

## 5. Relancer une opération

Il n'existe pas de clé générale `retry: 3` équivalente à GitLab. Cette étape Bash simule trois tentatives, dont les deux premières échouent :

```yaml
- name: Trois tentatives au maximum
  shell: bash
  run: |
    operation() {
      [ "$1" -ge 3 ]
    }
    for attempt in 1 2 3; do
      echo "Tentative $attempt"
      if operation "$attempt"; then
        echo "Operation reussie"
        exit 0
      fi
      if [ "$attempt" -eq 3 ]; then
        exit 1
      fi
      sleep 2
    done
```

Remplacez `operation` par une commande adaptée. Répéter un téléchargement est différent de répéter une publication ou une migration déjà partiellement appliquée.

Une relance depuis **Re-run jobs** réutilise le commit et la référence initiaux ; ce n'est pas un nouveau build du dernier commit de la branche. [Relance de jobs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)

## 6. Échec toléré et absence de UNSTABLE

`continue-on-error: true` permet de tolérer une erreur. Pour empêcher une livraison après un contrôle facultatif échoué, publiez un output à partir de `steps.controle.outcome` puis conditionnez la livraison. Le résultat global vert ne suffit pas à représenter une qualité dégradée.

La tolérance et `strategy.fail-fast` d'une matrice sont deux mécanismes distincts ; voir [matrices](13.matrices.md).

## 7. Rétention et journaux

Les réglages Actions du dépôt pilotent la rétention des logs et artefacts. Une étape d'upload peut demander `retention-days: 7`, dans les limites de la politique applicable. Ce réglage ne signifie pas « conserver les sept derniers builds » et ne supprime pas les workflows eux-mêmes. [Rétention des artefacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts)

Pour un repère explicite dans une commande, utilisez `date -u`. Les options d'affichage des logs permettent aussi d'afficher les horodatages ; aucun plugin `timestamps` n'est nécessaire. [Journaux d'exécution](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs)

## Exercice

Comparez deux lancements avec annulation, puis trois avec `queue: max` sans annulation. Réduisez ensuite le timeout de l'étape de démonstration et observez la différence entre échec de commande et arrêt par timeout.

Les essais sont à réaliser dans votre dépôt ; aucune exécution GitHub n'a été effectuée ici.
