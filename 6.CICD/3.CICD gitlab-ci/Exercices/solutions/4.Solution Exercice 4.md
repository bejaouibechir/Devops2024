# Solution 4 — Deux passages avec un job différé

[Énoncé](../4.Exercice%204.md) · [Prérequis communs](../readme.md)

## 1. Configuration complète

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "web"'
    # Exclut ce pipeline ou ce job lorsque cette règle est retenue.
    - when: never

# Applique ces réglages aux jobs qui ne les redéfinissent pas.
default:
  # Choisit l'image utilisée par l'exécuteur compatible ; un exécuteur Shell ne la lance pas.
  image: alpine:3.22

# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [premier, second]

# Déclare le job « essai_1 » et sa configuration propre.
essai_1:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: premier
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Passage 1 du pipeline %s\n' "$CI_PIPELINE_ID"
      # Affiche l'heure demandée pour situer cette étape dans les journaux.
      date -u '+%Y-%m-%dT%H:%M:%SZ'
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      echo "Operation de demonstration reussie"

# Déclare le job « essai_2 » et sa configuration propre.
essai_2:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: second
  # Diffère ce job selon start_in, sans occuper immédiatement un runner.
  when: delayed
  # Retarde le démarrage du job différé selon la durée indiquée.
  start_in: 1 minute
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Passage 2 du pipeline %s\n' "$CI_PIPELINE_ID"
      # Affiche l'heure demandée pour situer cette étape dans les journaux.
      date -u '+%Y-%m-%dT%H:%M:%SZ'
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      echo "Deuxieme operation de demonstration reussie"
```

Le délai commence après la réussite du stage précédent. Une fois ce délai écoulé, la disponibilité du runner peut ajouter de l'attente. Le runner n'est pas occupé par un `sleep` pendant ce délai. [Jobs différés](https://docs.gitlab.com/ci/jobs/job_control/#run-a-job-after-a-delay)

## 2. Vérifier le comportement

Lancez une fois depuis **New pipeline**. Observez :

1. Le premier job réussit.
2. Le second est différé, sans bouton de validation à cliquer.
3. Il s'exécute après le délai et le pipeline se termine.
4. Les deux logs affichent le même `CI_PIPELINE_ID`.

Ne comparez pas les horaires comme si les débuts étaient garantis exactement à 60 secondes d'écart : le premier job a sa durée propre.

## 3. Variante distincte : reprise après échec

Ce second YAML remplace le précédent ; il démontre une reprise, pas l'intervalle demandé :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "web"'
    # Exclut ce pipeline ou ce job lorsque cette règle est retenue.
    - when: never

# Applique ces réglages aux jobs qui ne les redéfinissent pas.
default:
  # Choisit l'image utilisée par l'exécuteur compatible ; un exécuteur Shell ne la lance pas.
  image: alpine:3.22

# Déclare le job « operation_en_echec » et sa configuration propre.
operation_en_echec:
  # Configure les nouvelles tentatives après les échecs ciblés ; ce n'est pas une planification périodique.
  retry:
    max: 1
    when: script_failure
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      echo "Tentative volontairement en echec"
      # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
      exit 1
```

**Résultat attendu :** une tentative initiale et une seule reprise automatique, puis un pipeline en échec. Aucune minute d'attente n'est configurée.

GitLab compte les reprises : `max: 1` signifie au plus deux tentatives au total, `max: 2` au plus trois. Un premier succès empêche toute reprise. [Retry GitLab](https://docs.gitlab.com/ci/yaml/#retry)

## 4. Différence avec le corrigé Jenkins

Le couple `timeout`/`retry` présenté dans le support ne garantit ni la répétition après succès ni l'intervalle. La variante principale rend les deux passages explicites.

Si le besoin devient « créer deux pipelines distincts », il faut une orchestration externe ou des déclenchements API/schedules limités. Ce n'est pas ce que réalise le job différé.

## Validation attendue
