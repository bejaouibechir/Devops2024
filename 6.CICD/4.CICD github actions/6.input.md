# Saisie et approbation manuelle dans GitHub Actions

## Objectif

Reprendre le choix Yes/No du support Jenkins en séparant deux besoins : fournir un paramètre au départ et autoriser une livraison après le build.

## 1. Trois mécanismes différents

| Besoin | Jenkins | GitLab CI/CD | GitHub Actions |
| --- | --- | --- | --- |
| Choix avant lancement | `parameters` | Inputs de pipeline | `workflow_dispatch.inputs` |
| Pause avant livraison | `input` | Job manuel/approbations | Required reviewers d'un environnement |
| Nouvelle saisie dans le run en cours | `input` | Inputs de job selon version | Pas de formulaire natif équivalent dans une étape |

`workflow_dispatch` crée une exécution ; il ne remplit pas un formulaire au milieu de l'exécution précédente.

## 2. Variante Yes/No au lancement

Fichier `.github/workflows/decision.yml` :

```yaml
name: Decision de lancement
run-name: Decision ${{ inputs.decision }}
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
    # Déclare les paramètres attendus ; leur type et leurs contraintes définissent le contrat.
    inputs:
      # Définit le paramètre « decision » et les contraintes de sa valeur.
      decision:
        description: Autoriser la simulation de livraison
        type: choice
        options: ['Yes', 'No']
        # Fournit la valeur utilisée si cet input n'est pas renseigné.
        default: 'No'
        required: true
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « build » ; needs permet de préciser ses dépendances.
  build:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Build simule"
  # Déclare le job « approved » ; needs permet de préciser ses dépendances.
  approved:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: build
    # Conditionne l'exécution à cette expression évaluée par GitHub.
    if: ${{ inputs.decision == 'Yes' }}
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Branche Yes"
  # Déclare le job « rejected » ; needs permet de préciser ses dépendances.
  rejected:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: build
    # Conditionne l'exécution à cette expression évaluée par GitHub.
    if: ${{ inputs.decision == 'No' }}
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Branche No, choix valide"
```

**Résultat attendu :** `No` sélectionne une branche normale et n'est pas un échec. Une seule des deux branches est exécutée. Les valeurs sont citées pour éviter toute ambiguïté avec les interprétations YAML des mots Yes/No.

Placez le fichier sur la branche par défaut puis utilisez **Run workflow**. `run-name` décrit l'exécution à partir du choix initial ; ce n'est pas une affectation tardive à `currentBuild.description`. [Lancement manuel](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

## 3. Variante : approbation après build

Avant l'essai, créez **Settings > Environments > production** et configurez **Required reviewers**. Déclarer uniquement `environment: production` dans le YAML ne crée pas cette règle.

```yaml
name: Validation apres build
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « build » ; needs permet de préciser ses dépendances.
  build:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Build simule"
  # Déclare le job « deploy » ; needs permet de préciser ses dépendances.
  deploy:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: build
    # Conditionne l'exécution à cette expression évaluée par GitHub.
    if: ${{ github.ref == 'refs/heads/main' }}
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Associe le job à l'environnement et à ses secrets ou règles de protection.
    environment: production
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Livraison simulee apres approbation"
```

Lancez sur `main`. Après le build, ouvrez **Review deployments**, puis approuvez ou refusez.

- **Approve and deploy** autorise la suite si les autres règles sont satisfaites.
- **Reject** fait échouer le workflow : ce n'est pas la branche `No` réussie de la première variante.
- Les secrets d'environnement ne sont accessibles qu'après passage des protections.

Sur les offres Free, Pro et Team, reviewers obligatoires et minuteur d'attente sont réservés aux dépôts publics. Les environnements des dépôts privés/internes et leurs protections dépendent de l'offre ; vérifiez vos droits avant l'atelier. [Revue des déploiements](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments)

## 4. Si le choix doit arriver après la compilation

Deux solutions répondent à des besoins différents :

1. Autoriser ou refuser la livraison du même run : environnement protégé.
2. Choisir une version et de nouveaux paramètres : workflow de livraison séparé, lancé manuellement.

Dans le second cas, demandez un identifiant précis d'exécution/artefact, vérifiez sa provenance et sa réussite, puis téléchargez cet artefact. Ne reconstruisez pas silencieusement la tête d'une branche qui a pu changer depuis la revue. Voir [artefacts](7.artefact.md).
