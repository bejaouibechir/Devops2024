# Milestone 4 — GitLab CI/CD et publication des modules

> **Ateliers couverts :** A12

---

## Objectif du milestone

Le projet est entièrement piloté par GitLab CI. Les modules sont publiés sur le **GitLab Module Registry** et consommés depuis le registry plutôt que localement. Un push sur `main` déclenche automatiquement `terraform apply` sur Azure.

---

## Architecture finale

```
GitLab
├── terraform-fil-rouge/          # projet principal
│   ├── .gitlab-ci.yml            # pipeline CI/CD
│   ├── versions.tf               # modules depuis GitLab registry
│   └── ...
├── terraform-local-networking/   # dépôt du module networking publié
└── terraform-local-compute/      # dépôt du module compute publié
```

```
Pipeline GitLab CI
│
├── Merge Request → job "plan"
│   └── terraform plan (commentaire sur la MR)
│
└── Push main → job "apply"
    └── terraform apply → Azure
```

## Convention de nommage des modules publiés

GitLab Registry impose :

```
terraform-<PROVIDER>-<NOM>
```

| Module local | Dépôt GitLab | Source dans versions.tf |
|---|---|---|
| `modules/networking` | `terraform-local-networking` | `gitlab.com/<namespace>/terraform-local-networking` |
| `modules/compute` | `terraform-local-compute` | `gitlab.com/<namespace>/terraform-local-compute` |

Structure attendue à la racine de chaque dépôt de module :

```
terraform-local-networking/
├── main.tf
├── variables.tf
├── outputs.tf
└── README.md
```

## Pipeline GitLab CI

> **Comment lire ce fichier ?** GitLab CI lit un unique fichier `.gitlab-ci.yml` à
> la racine du projet. À chaque `git push` (ou création de Merge Request), GitLab
> lance des **jobs** dans des conteneurs Docker jetables, selon des **règles** qui
> décident quel job tourne dans quelle situation. Les commentaires ci-dessous
> expliquent chaque ligne.

```yaml
# .gitlab-ci.yml

# Image Docker de base : chaque job démarre dans un conteneur qui contient
# déjà la commande `terraform` (version 1.9). Pas besoin de l'installer.
image: hashicorp/terraform:1.9

# Variables réutilisées dans tout le pipeline.
variables:
  # Répertoire racine où se trouve le code Terraform ("." = à la racine du dépôt).
  TF_ROOT: "."
  # Adresse du state distant, hébergé par GitLab lui-même (backend HTTP).
  # CI_API_V4_URL et CI_PROJECT_ID sont fournies automatiquement par GitLab.
  TF_ADDRESS: "${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/terraform/state/fil-rouge"

# Les "stages" définissent l'ordre d'exécution : d'abord tous les jobs
# "validate", puis "plan", puis "apply". Un stage ne démarre que si le
# précédent a réussi.
stages:
  - validate
  - plan
  - apply

# Bloc réutilisable (ancre YAML "&terraform_init"). Ce n'est PAS un job :
# c'est un morceau de config qu'on réinjecte dans les jobs avec "<<: *terraform_init".
# Il contient le "before_script" : les commandes lancées AVANT le script principal.
.terraform_init: &terraform_init
  before_script:
    # `terraform init` initialise le projet et connecte Terraform au state distant.
    # Toutes les options -backend-config indiquent OÙ et COMMENT lire/écrire le state.
    - terraform init
        # Adresse du fichier de state.
        -backend-config="address=${TF_ADDRESS}"
        # Adresse utilisée pour poser/retirer le verrou (évite deux applies simultanés).
        -backend-config="lock_address=${TF_ADDRESS}/lock"
        -backend-config="unlock_address=${TF_ADDRESS}/lock"
        # Authentification auprès de GitLab : un token de job temporaire,
        # généré et détruit automatiquement à chaque pipeline (jamais stocké).
        -backend-config="username=gitlab-ci-token"
        -backend-config="password=${CI_JOB_TOKEN}"
        # Méthodes HTTP attendues par le backend GitLab pour verrouiller/déverrouiller.
        -backend-config="lock_method=POST"
        -backend-config="unlock_method=DELETE"

# JOB 1 — VALIDATE : vérifie que le code Terraform est syntaxiquement correct.
validate:
  <<: *terraform_init        # réinjecte le before_script (terraform init) défini plus haut
  stage: validate            # rattache ce job au stage "validate"
  script:
    - terraform validate     # contrôle la syntaxe et la cohérence, sans rien déployer
  rules:                     # QUAND ce job s'exécute-t-il ?
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"   # sur une Merge Request
    - if: $CI_COMMIT_BRANCH == "main"                    # ou sur un push vers main

# JOB 2 — PLAN : calcule les changements que Terraform ferait, sans les appliquer.
plan:
  <<: *terraform_init
  stage: plan
  script:
    # `-out=tfplan` enregistre le plan dans un fichier, pour que le job "apply"
    # applique EXACTEMENT ce qui a été calculé ici (pas de recalcul).
    - terraform plan -out=tfplan
  artifacts:                 # fichiers conservés et transmis aux jobs suivants
    paths:
      - tfplan               # on garde le plan pour le réutiliser dans "apply"
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"

# JOB 3 — APPLY : applique réellement les changements sur Azure.
apply:
  <<: *terraform_init
  stage: apply
  script:
    # `-auto-approve` évite la question interactive (impossible en CI).
    # On applique le fichier "tfplan" produit par le job "plan".
    - terraform apply -auto-approve tfplan
  dependencies:
    - plan                   # récupère l'artefact "tfplan" du job "plan"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"   # uniquement sur la branche main (jamais sur une MR)
  when: manual   # le job attend un clic humain dans GitLab avant de déployer (sécurité)
```

## Variables CI/CD à configurer dans GitLab

Dans **Settings → CI/CD → Variables** du projet :

| Variable | Description | Protégée | Masquée |
|---|---|---|---|
| `ARM_CLIENT_ID` | Service Principal Azure | ✅ | ✅ |
| `ARM_CLIENT_SECRET` | Secret du Service Principal | ✅ | ✅ |
| `ARM_SUBSCRIPTION_ID` | ID de l'abonnement Azure | ✅ | ✅ |
| `ARM_TENANT_ID` | ID du tenant Azure AD | ✅ | ✅ |
| `GITLAB_TOKEN` | Token GitLab pour le provider | ✅ | ✅ |

Créer le Service Principal Azure :

```bash
az ad sp create-for-rbac \
  --name "sp-terraform-fil-rouge" \
  --role Contributor \
  --scopes /subscriptions/<SUBSCRIPTION_ID>
```

## Critères de validation du milestone

- [ ] Les modules `networking` et `compute` sont publiés sur GitLab avec un tag `v1.0.0`
- [ ] Le projet principal consomme les modules depuis le registry (plus de `./modules/`)
- [ ] Un push sur une branche feature → pipeline `validate` + `plan` s'exécute
- [ ] Une MR vers `main` → le plan est visible dans les commentaires de la MR
- [ ] Un merge sur `main` → job `apply` disponible et déploiement Azure fonctionnel
- [ ] Aucune credential Azure n'est présente dans le code — tout passe par les variables CI/CD
- [ ] `terraform destroy` peut être déclenché depuis la CI (job optionnel)
