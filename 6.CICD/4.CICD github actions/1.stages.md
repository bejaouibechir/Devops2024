# Organiser les jobs et les étapes dans GitHub Actions

## Objectif

Construire Build → tests parallèles → Deploy, en comprenant pourquoi GitHub Actions n'a pas de bloc `stages`.

## 1. Du stage au graphe de jobs

| Jenkins | GitLab CI/CD | GitHub Actions |
| --- | --- | --- |
| `pipeline` | Pipeline | Exécution d'un workflow |
| `stage` | Stage contenant des jobs | Job, ou groupe relié par `needs` |
| `steps` | Commandes de `script` | Étapes `run` ou `uses` |
| Stages ordonnés | Ordre de `stages` | Dépendances explicites |
| Bloc `parallel` | Jobs du même stage | Jobs sans dépendance entre eux |

L'ordre d'écriture des jobs ne définit pas leur ordre d'exécution. Les étapes d'un job sont séquentielles et partagent ses fichiers ; chaque étape `run` démarre toutefois un nouveau processus de shell. [Organisation des jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs)

## 2. Exemple complet

Créez `.github/workflows/stages.yml` sur la branche par défaut. Les opérations sont simulées : aucun projet applicatif n'est nécessaire.

```yaml
name: Build Tests Deploy
on:
  workflow_dispatch:
permissions: {}
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Construction simulee"
  unit_tests:
    needs: build
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Tests unitaires simules"
  integration_tests:
    needs: build
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Tests integration simules"
  deploy:
    needs: [unit_tests, integration_tests]
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Deploiement simule"
```

**Résultat attendu :**

1. `build` termine avec succès.
2. Les tests deviennent exécutables ; les ressources disponibles déterminent leur simultanéité réelle.
3. `deploy` attend la réussite des deux tests.
4. Si un test échoue, `deploy` est ignoré par défaut.

Dans **Actions**, ouvrez l'exécution pour voir le graphe et les journaux. Aucun plugin équivalent à Blue Ocean n'est nécessaire. [Graphe des workflows](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-the-visualization-graph)

## 3. Exécuter un script du dépôt

Créez `scripts/test.sh` :

```sh
#!/usr/bin/env bash
set -euo pipefail
test -f README.md
echo "Le README est present"
```

Workflow indépendant `.github/workflows/script.yml` :

```yaml
name: Script du depot
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - shell: bash
        run: bash scripts/test.sh
```

`run` lance une commande ; `uses` appelle une action. `checkout` récupère le code. L'appel `bash scripts/test.sh` ne nécessite pas de bit exécutable sur le script. [Action checkout](https://github.com/actions/checkout)

## 4. Partager des données

| Besoin | Mécanisme |
| --- | --- |
| Fichier entre étapes du même job | Répertoire de travail |
| Petite valeur entre jobs | Output lu avec `needs` |
| JAR, archive, rapport entre jobs | Upload puis download d'artefact |

`needs: build` attend le build, mais ne télécharge rien. Voir [les artefacts](7.artefact.md).

Un `export VERSION=1` dans une étape ne transmet pas la variable à la suivante. Utilisez `GITHUB_ENV` ou des outputs, détaillés dans [environnement et paramètres](2.environnement%20et%20params.md).

## 5. Jobs facultatifs et matrices

Une dépendance ignorée peut entraîner l'ignorance de ses successeurs. Pour un bilan après réussite ou échec, voir [post](3.post.md). Ne rendez pas un déploiement systématique pour contourner une dépendance mal conçue.

Une [matrice](13.matrices.md) crée plusieurs variantes d'un job ; elle ne définit pas un stage.
