# Déclenchement des pipelines : équivalents des `triggers` Jenkins

## Objectif

Reprendre les scénarios du support Jenkins : polling, planification, pipeline amont, push GitHub/GitLab, fichiers modifiés et Merge Request. Distinguer l'événement déclencheur des règles qui autorisent le pipeline et ses jobs.

## 1. De l'événement aux jobs : les mécanismes à distinguer

| Mécanisme | Rôle |
| --- | --- |
| Événement : push, MR, horaire, appel API… | Provoque une demande de création de pipeline. |
| `workflow:rules` | Autorise ou refuse le pipeline pour cette demande. |
| `rules` dans un job | Sélectionne les jobs à ajouter au pipeline. |
| `trigger` dans un job | Demande la création d'un autre pipeline. |

Écrire une règle `schedule` ne crée pas de planification. Écrire une règle `push` ne configure pas un webhook externe. Les règles filtrent des événements existants. [Workflow GitLab](https://docs.gitlab.com/ci/yaml/workflow/), [règles des jobs](https://docs.gitlab.com/ci/jobs/job_rules/)

| Jenkins | GitLab CI/CD |
| --- | --- |
| `pollSCM(...)` | Push natif si le dépôt est hébergé sur GitLab ; pas de sondage à configurer. |
| `cron(...)` | Pipeline schedule dans GitLab, en dehors du YAML. |
| `build job: ...` / déclenchement amont | Job `trigger:project` ou `trigger:include`. |
| Webhook GitLab vers Jenkins | Événement push natif dans le projet GitLab. |
| `githubPush()` | Intégration GitHub externe, si le code reste sur GitHub. |
| `when { branch ...; changeset ... }` | `rules:if` combiné à `rules:changes`. |
| Événement MR via plugin Jenkins | Pipeline `merge_request_event`. |

## 2. Préparer le dépôt de démonstration

Prérequis : un projet GitLab, une branche `main`, un runner Linux avec `sh`, `date` et la possibilité d'exécuter les jobs sans tags. Sinon, ajoutez les tags appropriés.

Créez `scripts/test.sh` dans le dépôt utilisé pour les essais, avec des fins de ligne LF :

```sh
#!/bin/sh
set -eu
# Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
printf 'OK - tests simules le %s\n' "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"
```

Les exemples appellent `sh scripts/test.sh` : le droit d'exécution du fichier n'est pas nécessaire. Le runner récupère normalement le dépôt avant `script`, sans job `Checkout` à ajouter.

Les variantes ci-dessous remplacent le contenu de `.gitlab-ci.yml`. Ne les concaténez pas. Les exemples à plusieurs fichiers ou plusieurs projets précisent leur emplacement.

## 3. `pollSCM` et webhook GitLab : exécuter après un push

Pour un dépôt hébergé dans GitLab, utilisez son événement natif :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == "main"'

# Déclare le job « tests » et sa configuration propre.
tests:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh scripts/test.sh
```

**Essai :** modifiez `README.md`, puis poussez le commit sur `main`. Le pipeline devient éligible immédiatement, puis attend un runner disponible. Un push sur `dev` est refusé par ce workflow.

Cela remplace les scénarios 1 et 5 du support pour un dépôt GitLab natif. Un pipeline planifié toutes les deux minutes serait différent de `pollSCM` : il pourrait tourner sans nouveau commit.

`push` couvre aussi les tags ; le test sur `CI_COMMIT_BRANCH` les exclut ici. Pour accepter toutes les branches, utilisez `&& $CI_COMMIT_BRANCH` à la place de la comparaison à `main`. [Sources des pipelines](https://docs.gitlab.com/ci/jobs/job_rules/#ci_pipeline_source-predefined-variable)

## 4. `cron` : planifier indépendamment des commits

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "schedule"'

# Déclare le job « verification_periodique » et sa configuration propre.
verification_periodique:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh scripts/test.sh
```

Après avoir enregistré le fichier sur `main` :

1. Ouvrez **Build > Pipeline schedules > New schedule**.
2. Choisissez `main` comme référence cible.
3. Pour un essai périodique, saisissez `*/5 * * * *` et le fuseau **Europe/Paris**.
4. Enregistrez la planification, puis attendez une échéance ou utilisez son bouton d'exécution.

Le `H/5` de Jenkins répartit les horaires par hachage ; ne le recopiez pas. `*/5` désigne les minutes 0, 5, 10, etc. La fréquence effective dépend des limites et du traitement des planifications sur l'instance.

La planification s'exécute avec les droits de son propriétaire. Elle peut aussi fournir les inputs du thème précédent. Un lancement via **New pipeline** a la source `web` et sera refusé par cet exemple, réservé à `schedule`. [Pipelines planifiés](https://docs.gitlab.com/ci/pipelines/schedules/)

## 5. Déclenchement amont : lancer un autre pipeline

Le support Jenkins combine un appel explicite `build job: 'app-deploy'` avec un déclenchement configuré dans le job cible. Choisissez un mécanisme unique pour éviter deux demandes de lancement.

### A. Deux projets : `trigger:project`

Prérequis : les projets A et B existent, `main` existe dans B, et l'utilisateur lançant A peut démarrer un pipeline dans B. Le projet B doit avoir son runner et ses fichiers de test.

Dans `.gitlab-ci.yml` du **projet A**, remplacez `mon-groupe/app-deploy` par le chemin réel du projet B :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "web"'

# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [build, declenchement]

# Déclare le job « build_application » et sa configuration propre.
build_application:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: build
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Build simule reussi"

# Déclare le job « lancer_projet_b » et sa configuration propre.
lancer_projet_b:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: declenchement
  # Déclenche le pipeline cible au lieu d'exécuter un script local.
  trigger:
    project: mon-groupe/app-deploy
    branch: main
    # Définit les variantes du job et leur politique d'exécution.
    strategy: mirror
```

Dans `.gitlab-ci.yml` du **projet B** :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "pipeline"'

# Déclare le job « deployer » et sa configuration propre.
deployer:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Deploiement simule demande par le projet A"
    - sh scripts/test.sh
```

Lancez A avec **Build > Pipelines > New pipeline**. Après son build, A demande B. Un push direct sur B ne crée pas de pipeline avec cette configuration.

`strategy: mirror` nécessite **GitLab 18.2 ou plus récent** : le job attend B et reflète son résultat. Sans `strategy`, il peut réussir dès la création de B, avant le résultat de ses tests ; c'est plus proche de l'intention Jenkins `wait: false`. [Stratégie du déclenchement](https://docs.gitlab.com/ci/yaml/#triggerstrategy)

### B. Même projet : `trigger:include`

Dans `.gitlab-ci.yml` :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "web"'

# Déclare le job « lancer_enfant » et sa configuration propre.
lancer_enfant:
  # Sérialise les jobs utilisant cette même ressource logique.
  resource_group: sequence-demo
  # Déclenche le pipeline cible au lieu d'exécuter un script local.
  trigger:
    # Charge une configuration complémentaire lors de la construction du pipeline.
    include:
      - local: .gitlab/ci/enfant.yml
    # Définit les variantes du job et leur politique d'exécution.
    strategy: mirror
```

Créez `.gitlab/ci/enfant.yml` dans le **même commit** :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "parent_pipeline"'

# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [verification, publication]

# Déclare le job « verifier » et sa configuration propre.
verifier:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: verification
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh scripts/test.sh

# Déclare le job « publier » et sa configuration propre.
publier:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: publication
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Publication simulee"
```

L'enfant utilise le même projet, la même référence et le même commit que le parent. Un pipeline multi-projet, lui, utilise la référence du projet cible. Un simple `include` global fusionnerait de la configuration dans le pipeline courant ; `trigger:include` crée un pipeline séparé. [Pipelines en aval](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/)

Cet exemple complète [4.options.md](4.options.md) : le verrou `sequence-demo` est conservé pendant l'enfant grâce à `mirror`. Deux parents peuvent exister, mais leurs séquences enfants ainsi verrouillées ne se chevauchent pas. Ne remettez pas ce même verrou sur les jobs enfants, ce qui pourrait les bloquer en attendant le parent. [Verrouillage d'une séquence](https://docs.gitlab.com/ci/resource_groups/)

## 6. Code conservé sur GitHub : intégration externe

Un dépôt GitHub ne produit pas automatiquement des événements dans GitLab. L'intégration **Run CI/CD for external repository** connecte le dépôt, configure un miroir et les notifications nécessaires. La fonctionnalité officielle GitHub est proposée en **Premium/Ultimate** ; les autorisations et étapes dépendent de GitHub.com ou GitHub Enterprise. [Intégration GitHub](https://docs.gitlab.com/ci/ci_cd_for_external_repos/github_integration/)

Une fois l'intégration configurée, un pipeline de Pull Request externe utilise une source différente d'une Merge Request GitLab :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "external_pull_request_event"'

# Déclare le job « tests_pr_github » et sa configuration propre.
tests_pr_github:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "external_pull_request_event"'
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh scripts/test.sh
```

Le YAML seul ne crée ni le miroir ni les webhooks. La variante n'accepte que les PR externes ; la prise en charge des push doit être ajoutée séparément si souhaitée. Elle remplace le scénario GitHub PR, sans le confondre avec une MR GitLab.

## 7. `main` et fichiers modifiés : filtrer les jobs

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH'

# Déclare le job « afficher_contexte » et sa configuration propre.
afficher_contexte:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - 'echo "Push sur $CI_COMMIT_BRANCH"'

# Déclare le job « tests_readme_main » et sa configuration propre.
tests_readme_main:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_COMMIT_BRANCH == "main"'
      changes:
        - README.md
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh scripts/test.sh
```

Le job de contexte conserve un pipeline visible même lorsque les tests sont exclus.

| Push sur une branche existante | Fichiers modifiés | Tests ajoutés |
| --- | --- | --- |
| `main` | `README.md` | Oui |
| `main` | `README.md` et `src/app.py` | Oui |
| `main` | `src/app.py` seulement | Non |
| `dev` | `README.md` | Non |

`if` et `changes` dans une même règle doivent tous deux être satisfaits. Pour un push de branche, GitLab compare au commit précédent de la branche ; pour une MR, à sa branche cible. Sans `compare_to`, un nouveau pipeline de branche ou un événement sans push peut faire correspondre `changes` sans le différentiel attendu. [Référence changes](https://docs.gitlab.com/ci/yaml/#ruleschanges)

Le filtre signifie « README figure parmi les fichiers modifiés », pas « README est le seul fichier modifié ». Exclure tout changement contenant README exclurait aussi un commit modifiant du code et README. Pour un filtre orienté code, listez plutôt les chemins utiles, par exemple `src/**/*` et `tests/**/*`.

Pour tous les push sur `main`, retirez simplement `changes`. Une fusion vers `main` produit alors un pipeline de branche après la fusion ; ce n'est pas le pipeline de MR lancé avant fusion.

## 8. Merge Request GitLab `dev` vers `main`

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_SOURCE_BRANCH_NAME == "dev" && $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"'

# Déclare le job « tests_mr » et sa configuration propre.
tests_mr:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - 'echo "MR de $CI_MERGE_REQUEST_SOURCE_BRANCH_NAME vers $CI_MERGE_REQUEST_TARGET_BRANCH_NAME"'
    - sh scripts/test.sh
```

1. Ajoutez les fichiers de démonstration à la branche `dev`.
2. Créez une MR de `dev` vers `main`.
3. Poussez un nouveau commit sur `dev` et observez le pipeline de MR.

`CI_COMMIT_BRANCH` n'est pas disponible dans un pipeline de MR ; utilisez ses variables source/cible. Pour accepter toutes les branches vers `main`, retirez la comparaison de la branche source à `dev`. [Variables prédéfinies](https://docs.gitlab.com/ci/variables/predefined_variables/)

Un pipeline de MR standard teste le contenu de la branche source. Tester le résultat de fusion avec la cible relève des **merged results pipelines**, fonctionnalité distincte. [Pipelines de Merge Request](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/)

## 9. Éviter les doubles pipelines push et MR

Un push sur une branche ayant une MR ouverte peut conduire à deux pipelines si les deux sources sont autorisées. Voici une variante générale pour privilégier les MR, quel que soit leur nom de branche :

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS'
      # Exclut ce pipeline ou ce job lorsque cette règle est retenue.
      when: never
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH'

# Déclare le job « tests » et sa configuration propre.
tests:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "push"'
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh scripts/test.sh
```

Sans MR ouverte, le push de branche est accepté. Avec MR ouverte, le pipeline de MR est accepté et celui du push est refusé. Cette variante exclut les tags, horaires et lancements manuels ; ajoutez explicitement leurs sources si vous en avez besoin. [Alternance branche/MR](https://docs.gitlab.com/ci/yaml/workflow/#switch-between-branch-pipelines-and-merge-request-pipelines)

## 10. Reconnaître la source et diagnostiquer

| Action | `CI_PIPELINE_SOURCE` |
| --- | --- |
| Push de branche ou de tag | `push` |
| MR GitLab | `merge_request_event` |
| Horaire planifié | `schedule` |
| Bouton New pipeline | `web` |
| API de création de pipelines | `api` |
| API de déclenchement avec un trigger token | `trigger` |
| Pipeline multi-projet via `trigger` | `pipeline` |
| Pipeline enfant | `parent_pipeline` |
| Pull Request externe GitHub | `external_pull_request_event` |

Le token de déclenchement API et le mot-clé YAML `trigger` sont deux mécanismes distincts. Avec un `CI_JOB_TOKEN`, l'API de déclenchement peut aussi produire la source `pipeline`. Le workflow cible doit autoriser la bonne source. [API de déclenchement](https://docs.gitlab.com/ci/triggers/)

Si rien ne démarre, vérifiez dans cet ordre : l'événement a-t-il eu lieu, le workflow l'autorise-t-il, au moins un job est-il sélectionné, puis un runner est-il disponible ? Un job `pending` a déjà été créé : cherchez alors du côté des runners.

## 11. Exercices

1. Comparez un push sur `main`, un push sur `dev` et New pipeline avec la variante du chapitre 3.
2. Configurez une planification et vérifiez qu'elle fonctionne sans nouveau commit.
3. Dans B, provoquez un échec avec `exit 1` : comparez le résultat de A avec puis sans `strategy: mirror`.
4. Lancez deux parents avec le pipeline enfant verrouillé et observez leur exécution.
5. Testez les quatre lignes du tableau `README.md`, après la création initiale des branches.
6. Créez une MR puis poussez un nouveau commit avec la variante anti-doublons.

Les exemples ont été relus à partir des documentations officielles. Ils n'ont pas été exécutés sur GitLab ; aucune planification, intégration GitHub ni connexion entre projets n'a été créée. Validez chaque variante dans l'éditeur de pipeline du projet utilisé pour les essais.
