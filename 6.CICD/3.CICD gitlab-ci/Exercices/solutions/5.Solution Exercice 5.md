# Solution 5 — Pipeline nocturne et notification simulée

[Énoncé](../5.Exercice%205.md) · [Prérequis communs](../readme.md)

## 1. Configuration complète

```yaml
# Déclare le contrat des inputs avant le séparateur YAML de la configuration.
spec:
  # Déclare les valeurs validées puis interpolées avant la création du pipeline.
  inputs:
    # Définit le paramètre « cible » et les contraintes de sa valeur.
    cible:
      type: string
      description: Cible du pipeline nocturne
      options: [dev, staging, prod]
      # Fournit la valeur utilisée si cet input n'est pas renseigné.
      default: dev
---
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "web"'
    # Exclut ce pipeline ou ce job lorsque cette règle est retenue.
    - when: never

# Applique ces réglages aux jobs qui ne les redéfinissent pas.
default:
  # Choisit l'image utilisée par l'exécuteur compatible ; un exécuteur Shell ne la lance pas.
  image: alpine:3.22

# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [prepare, simulation]

# Déclare le job « preparer_configuration » et sa configuration propre.
preparer_configuration:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: prepare
  # Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
  variables:
    EXO_CIBLE_INPUT: "$[[ inputs.cible ]]"
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Sélectionne le cas correspondant à la valeur ; la branche de repli traite les valeurs non prévues.
      case "$EXO_CIBLE_INPUT" in
        dev)
          # Prépare une valeur locale au shell ; elle ne devient pas automatiquement disponible dans un autre job.
          api_url="https://dev.api.example.test"
          db_name="dev_db"
          notify="dev@example.test"
          ;;
        staging)
          api_url="https://staging.api.example.test"
          db_name="staging_db"
          notify="recette@example.test"
          ;;
        prod)
          api_url="https://api.example.test"
          db_name="prod_db"
          notify="exploitation@example.test"
          ;;
        *)
          # Écrit le diagnostic sur la sortie d'erreur pour distinguer l'erreur des résultats normaux.
          echo "Cible invalide" >&2
          # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
          exit 1
          ;;
      esac
      {
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        printf 'EXO_CIBLE=%s\n' "$EXO_CIBLE_INPUT"
        printf 'EXO_API_URL=%s\n' "$api_url"
        printf 'EXO_DB_NAME=%s\n' "$db_name"
        printf 'EXO_NOTIFY=%s\n' "$notify"
      } > configuration.env
      # Affiche le contenu ou la liste des fichiers pour vérifier le résultat de l'étape précédente.
      cat configuration.env
  # Conserve les fichiers ou rapports du job pour consultation ou transmission.
  artifacts:
    # Déclare des rapports que GitLab interprète selon leur type.
    reports:
      # Expose les valeurs non secrètes de ce fichier aux jobs consommateurs ; ce rapport n'est pas un coffre à secrets.
      dotenv: configuration.env
    # Sélectionne les fichiers du workspace à publier comme artefacts.
    paths:
      - configuration.env
    # Fixe la durée de conservation demandée pour ces artefacts.
    expire_in: 1 day

# Déclare le job « simuler_deploiement » et sa configuration propre.
simuler_deploiement:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: simulation
  # Limite les jobs antérieurs dont les artefacts seront récupérés.
  dependencies:
    - preparer_configuration
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Interrompt le script si cette configuration obligatoire est absente ou vide.
      : "${EXO_CIBLE:?Cible absente}"
      : "${EXO_API_URL:?URL absente}"
      : "${EXO_DB_NAME:?Base absente}"
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Deploiement simule vers %s\n' "$EXO_CIBLE"
      printf 'API : %s\nBase : %s\n' "$EXO_API_URL" "$EXO_DB_NAME"
      printf 'Source du pipeline : %s\n' "$CI_PIPELINE_SOURCE"
      # Affiche l'heure demandée pour situer cette étape dans les journaux.
      date -u '+%Y-%m-%dT%H:%M:%SZ'

# Déclare le job « notifier_succes » et sa configuration propre.
notifier_succes:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: .post
  # Exécute ce traitement si les étapes antérieures requises ont réussi.
  when: on_success
  # Limite les jobs antérieurs dont les artefacts seront récupérés.
  dependencies:
    - preparer_configuration
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Interrompt le script si cette configuration obligatoire est absente ou vide.
      : "${EXO_NOTIFY:?Destinataire absent}"
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Notification SIMULEE pour %s\n' "$EXO_NOTIFY"
      printf 'La simulation %s du pipeline %s a reussi\n' \
        "$EXO_CIBLE" "$CI_PIPELINE_ID"
```

Le job de notification attend la fin des stages précédents. `dependencies` lui fournit la configuration sans autoriser un démarrage anticipé comme pourrait le faire un `needs` mal placé.

Les quatre variables envoyées dans le dotenv sont des données fictives non secrètes. Aucun appel réseau applicatif ni envoi d'email n'est effectué.

## 2. Tester manuellement

Commitez le fichier et lancez trois pipelines depuis **New pipeline**, avec les trois cibles. Vérifiez les URL, les bases et les destinataires affichés.

La création d'un pipeline sur push n'est pas autorisée par ce YAML ; cela évite de confondre les essais manuels et le planning nocturne.

## 3. Créer la planification dans GitLab

Dans **Build > Pipeline schedules > New schedule**, configurez :

| Réglage | Valeur |
| --- | --- |
| Description | Atelier nocturne |
| Intervalle cron | `0 2 * * *` |
| Fuseau horaire | `Europe/Paris` |
| Branche cible | Branche contenant ce YAML, par exemple `main` |
| Input `cible` | `staging`, ou la cible voulue |
| État | Actif pendant les essais |

Le planning est conservé dans GitLab, pas dans le fichier YAML. Il utilise les droits de son propriétaire pour ses exécutions planifiées. Ce compte doit rester autorisé sur la branche et les ressources nécessaires.

Le bouton de lancement immédiat d'un schedule permet d'en tester la configuration sans attendre 2 h ; ses permissions d'exécution peuvent différer de celles d'un déclenchement programmé. [Schedules GitLab](https://docs.gitlab.com/ci/pipelines/schedules/)

## 4. Horaire et absence d'interaction

La cible est choisie dans le schedule. Il n'y a pas d'étape de saisie nocturne, contrairement à une boîte `input` laissée dans un pipeline Jenkins.

L'horaire exprime une heure locale. Les changements d'heure et les délais d'ordonnancement doivent être pris en compte si un traitement métier exige une cadence stricte.

## 5. Cas négatifs

- Une cible hors liste est refusée à la création du pipeline.
- Un échec de la simulation empêche la notification de succès.
- Un propriétaire de schedule sans droits suffisants peut empêcher l'exécution.

Désactivez le schedule à la fin de l'atelier. Le corrigé ne crée pas automatiquement ce schedule et aucun pipeline n'a été exécuté sur GitLab pendant la rédaction.
