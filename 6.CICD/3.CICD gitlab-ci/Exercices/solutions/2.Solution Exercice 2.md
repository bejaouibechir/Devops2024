# Solution 2 — Configuration selon l'environnement

[Énoncé](../2.Exercice%202.md) · [Prérequis communs](../readme.md)

## 1. Configuration complète

```yaml
spec:
  inputs:
    cible:
      type: string
      description: Environnement de simulation
      options: [dev, staging, prod]
      default: dev
---
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - when: never

default:
  image: alpine:3.22

stages: [prepare, simulation]

preparer_configuration:
  stage: prepare
  variables:
    EXO_CIBLE: "$[[ inputs.cible ]]"
  script:
    - |
      set -eu
      case "$EXO_CIBLE" in
        dev)
          api_url="https://dev.api.example.test"
          db_name="dev_db"
          ;;
        staging)
          api_url="https://staging.api.example.test"
          db_name="staging_db"
          ;;
        prod)
          api_url="https://api.example.test"
          db_name="prod_db"
          ;;
        *)
          echo "Cible invalide" >&2
          exit 1
          ;;
      esac
      printf 'EXO_API_URL=%s\nEXO_DB_NAME=%s\n' \
        "$api_url" "$db_name" > configuration.env
      printf 'Configuration pour %s\n' "$EXO_CIBLE"
      cat configuration.env
  artifacts:
    reports:
      dotenv: configuration.env
    paths:
      - configuration.env
    expire_in: 1 day

.simulation:
  stage: simulation
  dependencies:
    - preparer_configuration
  script:
    - |
      set -eu
      : "${EXO_API_URL:?Configuration API absente}"
      : "${EXO_DB_NAME:?Configuration base absente}"
      printf 'Simulation %s\n' "$EXO_COMPORTEMENT"
      printf 'API : %s\nBase : %s\n' "$EXO_API_URL" "$EXO_DB_NAME"

simuler_dev:
  extends: .simulation
  variables:
    EXO_COMPORTEMENT: "DEV avec diagnostics detailles"
  rules:
    - if: '"$[[ inputs.cible ]]" == "dev"'

simuler_staging:
  extends: .simulation
  variables:
    EXO_COMPORTEMENT: "STAGING avec verification avant recette"
  rules:
    - if: '"$[[ inputs.cible ]]" == "staging"'

simuler_prod:
  extends: .simulation
  variables:
    EXO_COMPORTEMENT: "PROD avec journal de livraison"
  rules:
    - if: '"$[[ inputs.cible ]]" == "prod"'
```

## 2. Lecture du pipeline

L'input détermine les jobs lors de la création du pipeline. `preparer_configuration` calcule ensuite les valeurs. Le rapport dotenv injecte les valeurs non secrètes dans le job de simulation retenu.

`dependencies` sélectionne les artefacts à recevoir ; l'ordre des stages assure l'attente de la préparation. Le modèle caché `.simulation` mutualise le script sans s'exécuter lui-même.

Ne tentez pas une condition `rules:if` fondée sur `EXO_API_URL` produit dans ce job : cette valeur n'existe pas encore lors de l'évaluation des règles. [Règles de jobs](https://docs.gitlab.com/ci/jobs/job_rules/), [rapport dotenv](https://docs.gitlab.com/ci/yaml/artifacts_reports/#artifactsreportsdotenv)

## 3. Essais et résultats

| Input | Jobs ordinaires attendus |
| --- | --- |
| `dev` | `preparer_configuration`, `simuler_dev` |
| `staging` | `preparer_configuration`, `simuler_staging` |
| `prod` | `preparer_configuration`, `simuler_prod` |

Pour un essai négatif, tentez une valeur hors `options` par un moyen autorisé ou modifiez temporairement le contrat : la validation d'input doit refuser les valeurs non autorisées. Le `case` garde une protection supplémentaire si la variable était écrasée par une configuration de priorité supérieure.

## 4. Portée des données

Le fichier dotenv ne remplace pas un coffre de secrets. Ses données sont téléchargeables comme artefacts dans cet atelier. Les URL sont fictives et aucune base n'est créée.

Le job ne déclare pas `environment` : il simule un comportement sans enregistrer un déploiement GitLab. Ajouter une vraie livraison demanderait ses permissions et sa configuration propres.

## Validation attendue

Trois lancements vérifient les trois configurations. Les jobs non choisis sont absents, pas des scripts vides exécutés avec succès. Aucun pipeline n'a été exécuté sur GitLab pendant la rédaction.
