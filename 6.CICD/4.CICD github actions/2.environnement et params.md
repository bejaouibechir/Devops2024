# Variables, environnement et paramètres dans GitHub Actions

## Objectif

Adapter `environment` et `parameters` de Jenkins, ainsi que les variables et inputs GitLab.

## 1. Correspondances

| Besoin | Jenkins | GitLab CI/CD | GitHub Actions |
| --- | --- | --- | --- |
| Variable des commandes | `environment` | `variables` | `env` |
| Paramètre au lancement | `parameters` | Inputs de pipeline | `workflow_dispatch.inputs` |
| Configuration centralisée | Configuration Jenkins | Variables projet/groupe | `vars` |
| Secret | Credentials | Variable/coffre | `secrets` |
| Valeur calculée | Groovy/environnement | Shell/dotenv | `GITHUB_ENV` ou outputs |
| Cible de déploiement | Convention/plugin | `environment` | `environment` du job |

`environment: production` rattache le job à un environnement GitHub et à ses règles. Ce n'est pas une déclaration de variables shell.

## 2. Les trois portées de env

Fichier `.github/workflows/variables.yml` :

```yaml
name: Portee des variables
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
env:
  MESSAGE: workflow
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « demo » ; needs permet de préciser ses dépendances.
  demo:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
    env:
      MESSAGE: job
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: printf '%s\n' "$MESSAGE"
      # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
      - env:
          MESSAGE: etape
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        run: printf '%s\n' "$MESSAGE"
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: printf '%s\n' "$MESSAGE"
```

**Résultat :** `job`, `etape`, `job`. La portée la plus précise gagne. Bash lit `$MESSAGE` ; PowerShell utilise `$env:MESSAGE`. [Variables de workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-variables)

## 3. Paramètres typés au lancement

Workflow complet indépendant, à placer sur la branche par défaut :

```yaml
name: Parametres du lancement
run-name: Essai ${{ inputs.deploy_env }} par ${{ github.actor }}
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
    # Déclare les paramètres attendus ; leur type et leurs contraintes définissent le contrat.
    inputs:
      # Définit le paramètre « deploy_env » et les contraintes de sa valeur.
      deploy_env:
        description: Cible de simulation
        type: choice
        options: [staging, production]
        # Fournit la valeur utilisée si cet input n'est pas renseigné.
        default: staging
        required: true
      # Définit le paramètre « run_tests » et les contraintes de sa valeur.
      run_tests:
        description: Executer les tests
        type: boolean
        # Fournit la valeur utilisée si cet input n'est pas renseigné.
        default: true
      # Définit le paramètre « message » et les contraintes de sa valeur.
      message:
        description: Message libre
        type: string
        # Fournit la valeur utilisée si cet input n'est pas renseigné.
        default: Bonjour
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « demo » ; needs permet de préciser ses dépendances.
  demo:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
    env:
      DEPLOY_ENV: ${{ inputs.deploy_env }}
      MESSAGE: ${{ inputs.message }}
      BUILD_VERSION: 1.0.${{ github.run_number }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: printf 'Version %s pour %s\n' "$BUILD_VERSION" "$DEPLOY_ENV"
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: printf '%s\n' "$MESSAGE"
      - name: Tests simules
        # Conditionne l'exécution à cette expression évaluée par GitHub.
        if: ${{ inputs.run_tests }}
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        run: echo "Tests demandes"
      - name: Production simulee
        # Conditionne l'exécution à cette expression évaluée par GitHub.
        if: ${{ inputs.deploy_env == 'production' }}
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        run: echo "Cible production choisie"
```

**Run workflow** propose une liste, une case à cocher et un texte. `inputs` conserve le booléen : ne le comparez pas à la chaîne `'true'`. Le choix précède l'exécution ; il ne suspend pas un pipeline en cours comme `input` Jenkins. [Lancement manuel](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

`github.run_number` compte les exécutions de ce workflow. Une relance conserve ce numéro ; `github.run_attempt` augmente. `github.run_id` identifie l'exécution dans le dépôt. [Variables prédéfinies](https://docs.github.com/en/actions/reference/workflows-and-actions/variables)

## 4. Transmettre une valeur calculée

```yaml
name: Valeurs calculees
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « prepare » ; needs permet de préciser ses dépendances.
  prepare:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Expose les valeurs produites pour les étapes, jobs ou workflows consommateurs selon cette portée.
    outputs:
      version: ${{ steps.compute.outputs.version }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - id: compute
        # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
        shell: bash
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Prépare une valeur locale au shell ; elle ne devient pas automatiquement disponible dans un autre job.
          version="1.0.$GITHUB_RUN_NUMBER"
          # Rend ces variables disponibles aux étapes suivantes de ce job, pas aux autres jobs.
          echo "VERSION=$version" >> "$GITHUB_ENV"
          # Publie une sortie d'étape ; son exposition au niveau du job permet ensuite un échange via needs.
          echo "version=$version" >> "$GITHUB_OUTPUT"
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Valeur locale : %s\n' "$version"
      # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
      - run: |
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Etape suivante : %s\n' "$VERSION"
  # Déclare le job « consume » ; needs permet de préciser ses dépendances.
  consume:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: prepare
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
    env:
      VERSION: ${{ needs.prepare.outputs.version }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
      - run: |
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Autre job : %s\n' "$VERSION"
```

`GITHUB_ENV` concerne les étapes suivantes du même job, pas rétroactivement celle qui écrit. `GITHUB_OUTPUT` publie un output d'étape ; le mapping `outputs` du job le rend accessible aux dépendants. Réservez les outputs aux petites valeurs non secrètes. [Fichiers d'environnement](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#environment-files), [outputs entre jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/pass-job-outputs)

## 5. Configuration et secrets

Dans **Settings > Secrets and variables > Actions**, ajoutez une variable `DEFAULT_ENV` et, pour une application qui le nécessite, un secret `API_TOKEN`.

Fragment d'étape :

```yaml
- name: Lire la configuration
  # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
  env:
    TARGET: ${{ vars.DEFAULT_ENV || 'staging' }}
    API_TOKEN: ${{ secrets.API_TOKEN }}
  # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
  run: |
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    printf 'Cible : %s\n' "$TARGET"
    test -n "$API_TOKEN" || { echo "Secret requis manquant"; exit 1; }
```

Le secret est transmis au processus sans être affiché. Un secret absent produit une valeur vide. Les secrets habituels ne sont pas fournis aux pull requests provenant de forks. [Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)

Passer le texte libre par `env` évite de l'insérer directement dans le programme shell. Validez néanmoins toute valeur qui sélectionne une cible ou une commande.

## 6. Divergences essentielles

- `${{ ... }}` appartient au moteur GitHub ; `$VARIABLE` appartient au shell.
- Les contexts disponibles dépendent de l'emplacement YAML.
- Un output terminé peut servir à une condition du job suivant : ce n'est pas le calendrier des `rules` GitLab.
- `||` remplace les valeurs fausses ou vides ; un repli mal choisi peut écraser un booléen `false` volontaire.

Voir [contextes et expressions](12.contextes%20et%20expressions.md).
