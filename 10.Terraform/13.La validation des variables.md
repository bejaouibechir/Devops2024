# Atelier 3 : Validation des variables et outputs structurés avec Terraform

## 1. Introduction

## Objectif général

Dans l’Atelier 2, les participants ont découvert :

**variable {}**,  
**var.xxx**,

# 3. Étape 1 : Validation simple sur une variable string

## Objectif

Empêcher une mauvaise valeur pour l’environnement.

On veut autoriser uniquement :

**dev**, **test**, **prod**.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Variable représentant l'environnement cible.
# La validation empêche les valeurs non prévues.
variable "environment" {
  type        = string
  description = "Environnement cible autorisé : dev, test ou prod."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "La variable environment doit être dev, test ou prod."
  }
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# Crée un fichier indiquant l'environnement choisi.
resource "local_file" "environment_report" {
  filename = "environment-report.txt"

  content = <<EOT
Rapport environnement

Environnement sélectionné : ${var.environment}
EOT
}
```

## Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Affiche l'environnement réellement utilisé.
output "environment" {
  description = "Environnement utilisé pour générer le fichier."
  value       = var.environment
}

# Affiche le fichier créé.
output "created_file" {
  description = "Nom du fichier créé par Terraform."
  value       = local_file.environment_report.filename
}
```

## Commandes à exécuter

```bash
# Initialise le projet.
terraform init

# Reformate les fichiers.
terraform fmt

# Vérifie la configuration.
terraform validate

# Affiche le plan.
terraform plan

# Applique la configuration.
terraform apply -auto-approve

# Affiche les outputs.
terraform output

# Vérifie le fichier généré.
cat environment-report.txt
```

## Test d’erreur volontaire

Exécuter :

```bash
# Teste une valeur interdite.
terraform plan -var="environment=preprod"
```

Résultat attendu :

```text
La variable environment doit être dev, test ou prod.
```

## Points clés

**validation** sert à bloquer une mauvaise valeur.

**contains** vérifie si une valeur existe dans une liste.

**error_message** doit expliquer clairement l’erreur.

# 4. Étape 2 : Validation sur number

## Objectif

Contrôler une valeur numérique.

On veut créer un rapport avec un **niveau de criticité** entre **1** et **5**.

---

## Remplacer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Environnement cible.
variable "environment" {
  type        = string
  description = "Environnement cible autorisé : dev, test ou prod."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "La variable environment doit être dev, test ou prod."
  }
}

# Niveau de criticité du rapport.
# La valeur doit rester entre 1 et 5.
variable "severity_level" {
  type        = number
  description = "Niveau de criticité entre 1 et 5."
  default     = 2

  validation {
    condition     = var.severity_level >= 1 && var.severity_level <= 5
    error_message = "La variable severity_level doit être comprise entre 1 et 5."
  }
}
```

## Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Crée un fichier de rapport avec un niveau de criticité.
resource "local_file" "severity_report" {
  filename = "severity-report.txt"

  content = <<EOT
Rapport de criticité

Environnement : ${var.environment}
Niveau de criticité : ${var.severity_level}
EOT
}
```

## Remplacer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Output simple.
output "environment" {
  description = "Environnement utilisé."
  value       = var.environment
}

# Output numérique.
output "severity_level" {
  description = "Niveau de criticité appliqué."
  value       = var.severity_level
}

# Output structuré.
output "report_summary" {
  description = "Résumé structuré du rapport généré."
  value = {
    file             = local_file.severity_report.filename
    environment      = var.environment
    severity_level   = var.severity_level
    resource_address = "local_file.severity_report"
  }
}
```

## Commandes à exécuter

```bash
terraform fmt
terraform validate
terraform plan
terraform apply -auto-approve
terraform output
cat severity-report.txt
```

## Test d’erreur volontaire

```bash
# Teste une valeur trop grande.
terraform plan -var="severity_level=10"
```

Résultat attendu :

```text
La variable severity_level doit être comprise entre 1 et 5.
```

## Points clés

**&&** signifie **ET logique**.

La condition suivante impose une plage :

```hcl
var.severity_level >= 1 && var.severity_level <= 5
```

Un **output structuré** peut retourner une map contenant plusieurs informations.

# 5. Étape 3 : Validation sur bool et cohérence métier simple

## Objectif

Utiliser un booléen pour activer ou désactiver un mode.

On veut :

**detailed_mode = true** en **dev** ou **test**.

**detailed_mode = false** en **prod**.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Environnement cible.
variable "environment" {
  type        = string
  description = "Environnement cible autorisé : dev, test ou prod."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "La variable environment doit être dev, test ou prod."
  }
}

# Active ou désactive le mode détaillé.
variable "detailed_mode" {
  type        = bool
  description = "Active ou désactive le mode détaillé."
  default     = true

  validation {
    condition     = var.environment != "prod" || var.detailed_mode == false
    error_message = "En production, detailed_mode doit être false."
  }
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Crée un rapport lié au mode détaillé.
resource "local_file" "mode_report" {
  filename = "mode-report.txt"

  content = <<EOT
Rapport mode détaillé

Environnement : ${var.environment}
Mode détaillé : ${var.detailed_mode}
EOT
}
```

## Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Résumé structuré de la configuration active.
output "active_configuration" {
  description = "Configuration réellement appliquée."
  value = {
    environment   = var.environment
    detailed_mode = var.detailed_mode
    file          = local_file.mode_report.filename
  }
}
```

## Commandes à exécuter

```bash
terraform fmt
terraform validate
terraform plan
terraform apply -auto-approve
terraform output active_configuration
cat mode-report.txt
```

## Test valide

```bash
terraform plan -var="environment=prod" -var="detailed_mode=false"
```

Résultat attendu :

```text
Plan valide.
```

## Test invalide

```bash
terraform plan -var="environment=prod" -var="detailed_mode=true"
```

Résultat attendu :

```text
En production, detailed_mode doit être false.
```

## Points clés

**validation** peut utiliser plusieurs variables.

Cette possibilité nécessite **Terraform 1.9 ou supérieur**.

Avec une version antérieure à Terraform 1.9, une validation de variable qui référence une autre variable peut échouer avec une erreur du type :

```text
Invalid reference in variable validation
```

Dans cet exemple, la validation de **detailed_mode** utilise aussi **var.environment**.

**||** signifie **OU logique**.

Cette condition :

```hcl
var.environment != "prod" || var.detailed_mode == false
```

signifie :

si on n’est pas en production, c’est accepté ;  
si on est en production, le mode détaillé doit être désactivé.

# 7. Étape 5 : Validation sur map

## Objectif

Valider une map de tags.

On veut imposer que la map contienne au minimum les clés :

**environment**, **owner**, **managed_by**.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Map de tags obligatoires.
variable "project_tags" {
  type        = map(string)
  description = "Tags obligatoires du projet."
  default = {
    environment = "dev"
    owner       = "training"
    managed_by  = "terraform"
  }

  validation {
    condition = alltrue([
      contains(keys(var.project_tags), "environment"),
      contains(keys(var.project_tags), "owner"),
      contains(keys(var.project_tags), "managed_by")
    ])

    error_message = "La variable project_tags doit contenir les clés environment, owner et managed_by."
  }
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Crée un rapport basé sur les tags.
resource "local_file" "tags_report" {
  filename = "tags-report.txt"

  content = <<EOT
Rapport tags

Environment : ${var.project_tags["environment"]}
Owner : ${var.project_tags["owner"]}
Managed by : ${var.project_tags["managed_by"]}
EOT
}
```

## Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Affiche tous les tags.
output "project_tags" {
  description = "Tags appliqués au projet."
  value       = var.project_tags
}

# Affiche uniquement les clés.
output "project_tag_keys" {
  description = "Liste des clés disponibles dans la map project_tags."
  value       = keys(var.project_tags)
}

# Output structuré plus lisible.
output "project_summary" {
  description = "Résumé structuré du projet."
  value = {
    environment = var.project_tags["environment"]
    owner       = var.project_tags["owner"]
    managed_by  = var.project_tags["managed_by"]
    tag_keys    = keys(var.project_tags)
  }
}
```

## Commandes à exécuter

```bash

cat tags-report.txt
```

```hcl
}
```


**keys** retourne les clés d’une map.

# 8. Étape 6 : Validation sur object

## Objectif

Valider une configuration applicative structurée.

On veut imposer :

**name** non vide,  
**version** entre 1 et 10,  
**enabled** booléen,  
**owner_email** contenant le caractère **@**.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Objet décrivant une application.
variable "app_config" {
  type = object({
    name        = string
    version     = number
    enabled     = bool
    owner_email = string
  })

  description = "Configuration structurée de l'application."

  default = {
    name        = "demo-app"
    version     = 1
    enabled     = true
    owner_email = "admin@example.com"
  }

  validation {
    condition     = length(var.app_config.name) > 0
    error_message = "app_config.name ne doit pas être vide."
  }

  validation {
    condition     = var.app_config.version >= 1 && var.app_config.version <= 10
    error_message = "app_config.version doit être comprise entre 1 et 10."
  }

  validation {
    condition     = can(regex("@", var.app_config.owner_email))
    error_message = "app_config.owner_email doit contenir le caractère @."
  }
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Crée un rapport applicatif.
resource "local_file" "app_report" {
  filename = "app-report.txt"

  content = <<EOT
Rapport application

Nom : ${var.app_config.name}
Version : ${var.app_config.version}
Active : ${var.app_config.enabled}
Contact : ${var.app_config.owner_email}
EOT
}
```

## Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Output complet de l'objet.
output "app_config" {
  description = "Configuration applicative complète."
  value       = var.app_config
}

# Output structuré personnalisé.
output "app_summary" {
  description = "Résumé structuré de l'application."
  value = {
    name        = var.app_config.name
    version     = var.app_config.version
    enabled     = var.app_config.enabled
    owner_email = var.app_config.owner_email
    file        = local_file.app_report.filename
  }
}
```

## Commandes à exécuter

```bash

```

# 9. Étape 7 : Outputs structurés

## Objectif

Apprendre à écrire des outputs plus utiles que de simples chaînes.

On va produire :

**un output simple**,  
**un output map**,  
**un output list**,  
**un output object**,  
**un output sensible**.

Terraform affiche les outputs du module racine après **apply** et permet de les consulter avec **terraform output**. Un output peut contenir n’importe quelle expression Terraform. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/values/outputs?utm_source=chatgpt.com "Use outputs to expose module data | Terraform"))

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Nom de l'application.
variable "app_name" {
  type        = string
  description = "Nom de l'application."
  default     = "structured-output-demo"

  validation {
    condition     = length(var.app_name) >= 3
    error_message = "app_name doit contenir au moins 3 caractères."
  }
}

# Environnement cible.
variable "environment" {
  type        = string
  description = "Environnement cible."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment doit être dev, test ou prod."
  }
}

# Liste des fichiers logiques à documenter.
variable "documents" {
  type        = list(string)
  description = "Liste des documents logiques."
  default     = ["readme", "architecture", "runbook"]

  validation {
    condition     = length(var.documents) > 0 && length(var.documents) <= 5
    error_message = "documents doit contenir entre 1 et 5 éléments."
  }
}

# Tags du projet.
variable "tags" {
  type        = map(string)
  description = "Tags du projet."
  default = {
    owner      = "training"
    managed_by = "terraform"
  }

  validation {
    condition     = contains(keys(var.tags), "owner")
    error_message = "tags doit contenir au minimum la clé owner."
  }
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Crée un rapport global.
resource "local_file" "structured_report" {
  filename = "${var.app_name}-${var.environment}.txt"

  content = <<EOT
Rapport structuré

Application : ${var.app_name}
Environnement : ${var.environment}

Documents
---------
1. ${var.documents[0]}

Tags
----
Owner : ${var.tags["owner"]}
Managed by : ${var.tags["managed_by"]}
EOT
}
```

## Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Output simple.
output "file_name" {
  description = "Nom du fichier créé."
  value       = local_file.structured_report.filename
}

# Output de type list.
output "documents" {
  description = "Liste des documents déclarés."
  value       = var.documents
}

# Output de type map.
output "tags" {
  description = "Tags du projet."
  value       = var.tags
}

# Output de type object.
output "deployment_summary" {
  description = "Résumé structuré du déploiement."
  value = {
    app_name     = var.app_name
    environment  = var.environment
    file         = local_file.structured_report.filename
    documents    = var.documents
    tags         = var.tags
    resource     = "local_file.structured_report"
    generated_by = "terraform"
  }
}

# Output sensible.
# La valeur sera masquée dans l'affichage CLI standard.
output "internal_note" {
  description = "Note interne masquée dans la sortie standard."
  value       = "valeur-demo-sensible"
  sensitive   = true
}
```

## Créer le fichier terraform.tfvars

Créer le fichier **terraform.tfvars** :

```hcl
app_name    = "demo-outputs"

  "readme",
  "architecture",
  "runbook"
]

  owner      = "formation"
  managed_by = "terraform"
}
```


## Tester des outputs précis


## Points clés

Un **output** peut être simple ou structuré.

Un output structuré peut contenir :

**string**, **number**, **bool**, **list**, **map**, **object**.

**sensitive = true** masque l’affichage standard, mais la valeur reste dans le state. Terraform documente que les outputs sensibles sont masqués dans la sortie CLI, mais peuvent apparaître en clair avec certaines options comme **-json** ou **-raw**. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/values/outputs?utm_source=chatgpt.com "Use outputs to expose module data | Terraform"))
