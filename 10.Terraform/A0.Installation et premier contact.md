# Atelier — Installation de Terraform sur Ubuntu et premier contact avec local-exec, file et remote-exec

## 1. Contexte et objectif

Objectif de l’atelier :

Installer **Terraform** sur Ubuntu, vérifier son fonctionnement, puis faire un premier contact sans fournisseur cloud comme **Azure**, **AWS** ou **Kubernetes**.

Dans cet atelier, on va utiliser :

**terraform_data** : ressource logique utilisée comme support de test  
**local-exec** : exécuter une commande sur la machine Terraform  
**file** : copier un fichier vers une machine distante  
**remote-exec** : exécuter une commande sur une machine distante  
**state** : observer la mémoire locale de Terraform

Point important :

Même sans cloud provider, Terraform doit avoir une ressource à gérer. Ici, cette ressource sera **terraform_data**.

# 2. Installation de Terraform sur Ubuntu

## Étape 1 — Créer le script d’installation

Créer le fichier **install-terraform-ubuntu.sh** :

```bash
#!/usr/bin/env bash

# Arrête le script dès qu'une commande échoue.
set -e

# Affiche un titre clair.
echo "Installation de Terraform sur Ubuntu"

# Vérifie que la machine utilise apt.
if ! command -v apt-get >/dev/null 2>&1; then
  echo "Erreur : ce script est prévu pour Ubuntu ou Debian."
  exit 1
fi

# Met à jour la liste des paquets.
sudo apt-get update

# Installe les outils nécessaires pour ajouter le dépôt HashiCorp.
sudo apt-get install -y gnupg software-properties-common curl wget lsb-release

# Crée le dossier des clés APT si nécessaire.
sudo mkdir -p /usr/share/keyrings

# Télécharge et installe la clé GPG officielle HashiCorp.
wget -O- https://apt.releases.hashicorp.com/gpg \
  | gpg --dearmor \
  | sudo tee /usr/share/keyrings/hashicorp-archive-keyring.gpg >/dev/null

# Ajoute le dépôt officiel HashiCorp.
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(grep -oP '(?<=UBUNTU_CODENAME=).*' /etc/os-release || lsb_release -cs) main" \
  | sudo tee /etc/apt/sources.list.d/hashicorp.list >/dev/null

# Recharge la liste des paquets avec le dépôt HashiCorp.
sudo apt-get update

# Installe Terraform.
sudo apt-get install -y terraform

# Affiche la version installée.
terraform version

# Message final.
echo "Terraform est installé correctement."
```

## Étape 2 — Exécuter le script

Exécuter sur la machine **Ubuntu** :

```bash
chmod +x install-terraform-ubuntu.sh
./install-terraform-ubuntu.sh
```

Résultat attendu :

```text
Terraform v...
Terraform est installé correctement.
```

## Étape 3 — Vérifier manuellement

Exécuter sur la machine **Ubuntu** :

```bash
terraform version
```

Résultat attendu :

```text
Terraform v...
```

# 3. Premier projet Terraform sans cloud

## Objectif

Créer un premier projet Terraform sans Azure, sans AWS et sans Kubernetes.

Le test va créer un fichier local avec **local-exec**.

---

## Étape 1 — Créer le dossier du projet

Exécuter sur la machine **Ubuntu** :

```bash
# Crée le dossier du projet Terraform.
mkdir -p ~/terraform-first-test

# Entre dans le dossier du projet.
cd ~/terraform-first-test
```

Résultat attendu :

```text
Vous êtes dans le dossier ~/terraform-first-test.
```

---

## Étape 2 — Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Configure la version minimale de Terraform attendue.
terraform {
  required_version = ">= 1.4.0"
}

# terraform_data est une ressource logique intégrée.
# Elle ne crée pas de VM, pas de réseau, pas de ressource cloud.
# Elle sert ici à déclencher un provisioner local.
resource "terraform_data" "first_contact" {

  # Valeur simple stockée dans le state Terraform.
  input = "premier-test-terraform"

  # Exécute une commande sur la machine locale.
  # Ici, Terraform crée un fichier dans le dossier du projet.
  provisioner "local-exec" {
    command = "echo 'Bonjour depuis Terraform local-exec' > terraform-local-result.txt"
  }
}

# Affiche un résultat après terraform apply.
output "message" {
  value = terraform_data.first_contact.input
}
```

---

## Note — Deux façons d'organiser les fichiers Terraform

Dans cet atelier, tout est écrit dans un seul fichier `main.tf`. C'est valide et Terraform fonctionne parfaitement ainsi.

En pratique, deux approches coexistent :

**Option 1 — Tout dans main.tf** (approche simplifiée)

```
terraform-first-test/
└── main.tf    # contient terraform {}, resource {}, output {}
```

```hcl
# main.tf — tout en un seul fichier
terraform {
  required_version = ">= 1.4.0"
}

resource "terraform_data" "first_contact" {
  input = "premier-test-terraform"
  provisioner "local-exec" {
    command = "echo 'Bonjour depuis Terraform local-exec' > terraform-local-result.txt"
  }
}

output "message" {
  value = terraform_data.first_contact.input
}
```

**Option 2 — Fichiers séparés** (bonne pratique recommandée)

```
terraform-first-test/
├── versions.tf    # bloc terraform {} avec required_version et required_providers
├── main.tf        # ressources uniquement
└── outputs.tf     # blocs output {} uniquement
```

Le contenu est identique, simplement réparti sur trois fichiers :

```hcl
# versions.tf — contraintes de version uniquement
terraform {
  required_version = ">= 1.4.0"
}
```

```hcl
# main.tf — ressources uniquement
resource "terraform_data" "first_contact" {
  input = "premier-test-terraform"
  provisioner "local-exec" {
    command = "echo 'Bonjour depuis Terraform local-exec' > terraform-local-result.txt"
  }
}
```

```hcl
# outputs.tf — outputs uniquement
output "message" {
  value = terraform_data.first_contact.input
}
```

Les deux options produisent exactement le même résultat. Terraform fusionne tous les fichiers `.tf` d'un dossier avant de les interpréter — l'ordre et la séparation des fichiers n'ont aucune importance pour lui.

La séparation en fichiers distincts est préférable dès que le projet grandit car elle facilite la lecture, la maintenance et la réutilisation. C'est la convention adoptée dans tous les ateliers suivants et dans le projet fil rouge.

Exécuter dans **~/terraform-first-test** :

```bash

```

Résultat possible :

```text
terraform.tfstate
```

Après plusieurs exécutions, vous pouvez aussi voir :

```text
terraform.tfstate
terraform.tfstate.backup
```

Explication courte :

**terraform.tfstate** : état actuel connu par Terraform  
**terraform.tfstate.backup** : sauvegarde de l’état précédent

Attention :

En backend local, **terraform.tfstate.backup** ne garde qu’une seule version précédente.

Exemple :

```text
Après apply 1 :
terraform.tfstate = état 1

Après apply 2 :
terraform.tfstate.backup = état 1
terraform.tfstate        = état 2

Après apply 3 :
terraform.tfstate.backup = état 2
terraform.tfstate        = état 3
```

Donc l’ancien backup est écrasé à chaque nouvel apply important.

# 6. Comprendre file, remote-exec et local-exec

Avant de passer à la machine distante, il faut distinguer les trois comportements.

```text
local-exec  = commande exécutée sur la machine Terraform
file        = fichier copié depuis la machine Terraform vers une machine distante
remote-exec = commande exécutée sur la machine distante
```

Exemple :

```text
Machine Terraform :
~/terraform-first-test/hello-remote.txt

Machine distante :
/tmp/hello-remote.txt
/tmp/terraform-remote-result.txt

Machine Terraform :
~/terraform-first-test/remote-deploy-status.txt
```

À retenir :

**file** ne copie pas dans le home automatiquement.  
Il copie exactement vers le chemin indiqué dans **destination**.

# 7. Atelier file et remote-exec avec une machine distante Ubuntu

## Hypothèse

Vous avez une machine distante Ubuntu accessible en SSH.

Exemple :

```text
IP distante : 16.171.25.231
Utilisateur : ubuntu
Clé privée : ~/.ssh/id_rsa
```

Adaptez ces valeurs à votre environnement.

---

## Étape 1 — Tester SSH avant Terraform

Exécuter sur la machine **Terraform** :

```bash
# Vérifie que la machine distante est accessible en SSH.
ssh ubuntu@16.171.25.231 "hostname"
```

Résultat attendu :

```text
Le nom de la machine distante s’affiche.
```

Si cette commande ne fonctionne pas, Terraform ne pourra pas faire fonctionner **file** ou **remote-exec**.

---

## Étape 2 — Créer un fichier local à copier

Créer le fichier **hello-remote.txt** :

```text
Fichier copié par Terraform avec le provisioner file.
```

Vérifier que le fichier existe dans le dossier Terraform :

```bash
ls -l hello-remote.txt
cat hello-remote.txt
```

Résultat attendu :

```text
Fichier copié par Terraform avec le provisioner file.
```

Remarque importante :

Si ce fichier n’existe pas dans le même dossier que **main.tf**, Terraform affichera une erreur du type :

```text
stat hello-remote.txt: no such file or directory
```

Dans ce cas, le problème n’est pas SSH.  
Le problème est que le fichier source local est absent.

---

## Étape 3 — Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Configure la version minimale de Terraform attendue.
terraform {
  required_version = ">= 1.4.0"
}

# Ressource logique utilisée pour déclencher file, remote-exec et local-exec.
resource "terraform_data" "remote_demo" {

  # Valeur stockée dans le state pour identifier ce test.
  input = "demo-file-et-remote-exec"

  # Connexion SSH vers la machine distante.
  connection {
    type        = "ssh"
    host        = "16.171.25.231"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
  }

  # Copie le fichier local hello-remote.txt vers /tmp sur la machine distante.
  provisioner "file" {
    source      = "hello-remote.txt"
    destination = "/tmp/hello-remote.txt"
  }

  # Exécute des commandes sur la machine distante.
  provisioner "remote-exec" {
    inline = [
      "echo 'Commande exécutée sur la machine distante' > /tmp/terraform-remote-result.txt",
      "cat /tmp/hello-remote.txt >> /tmp/terraform-remote-result.txt"
    ]
  }

  # Exécute une commande sur la machine locale Terraform.
  provisioner "local-exec" {
    command = "echo 'Déploiement distant terminé' > remote-deploy-status.txt"
  }
}

# Affiche le nom logique du test.
output "remote_demo_name" {
  value = terraform_data.remote_demo.input
}
```

Remarque importante :

Dans cet exemple :

**/tmp/hello-remote.txt** est créé sur la machine distante.  
**/tmp/terraform-remote-result.txt** est créé sur la machine distante.  
**remote-deploy-status.txt** est créé sur la machine locale Terraform.

# 11. OpenTofu — Installation et premier contact

## 11.1 Qu’est-ce qu’OpenTofu ?

En 2023, HashiCorp a changé la licence de Terraform de **Mozilla Public License (MPL)** vers la **Business Source License (BSL)**, une licence qui restreint certains usages commerciaux.

En réponse, la communauté open source a créé **OpenTofu** sous l’égide de la **Linux Foundation** :

```text
OpenTofu = fork open source de Terraform sous licence MIT
```

Points essentiels :

```text
Syntaxe HCL identique         → les fichiers .tf fonctionnent sans modification
Providers compatibles          → tous les providers Terraform fonctionnent avec OpenTofu
Commandes quasi identiques     → terraform → tofu
State compatible               → même format terraform.tfstate
Remplacement direct            → un projet Terraform s’exécute avec OpenTofu sans réécriture
```

> Pour une comparaison approfondie Terraform vs OpenTofu, voir le document `2.terraform vs opentofu.pdf` dans les ressources de l’atelier.

---

## 11.2 Installation d’OpenTofu sur Ubuntu

### Créer le script d’installation

Créer le fichier **install-opentofu-ubuntu.sh** :

```bash
#!/usr/bin/env bash

# Arrête le script dès qu’une commande échoue.
set -e

echo "Installation d’OpenTofu sur Ubuntu"

# Vérifie que la machine utilise apt.
if ! command -v apt-get >/dev/null 2>&1; then
  echo "Erreur : ce script est prévu pour Ubuntu ou Debian."
  exit 1
fi

# Installe les dépendances nécessaires.
sudo apt-get update
sudo apt-get install -y apt-transport-https curl gnupg

# Crée le dossier des clés APT.
sudo install -m 0755 -d /etc/apt/keyrings

# Télécharge et installe la clé GPG officielle OpenTofu.
curl -fsSL https://packages.opentofu.org/opentofu/tofu/gpgkey \
  | sudo gpg --no-tty --batch --dearmor \
  -o /etc/apt/keyrings/opentofu.gpg 2>/dev/null

sudo chmod a+r /etc/apt/keyrings/opentofu.gpg

# Ajoute le dépôt officiel OpenTofu.
echo "deb [signed-by=/etc/apt/keyrings/opentofu.gpg] https://packages.opentofu.org/opentofu/tofu/any/ any main
deb-src [signed-by=/etc/apt/keyrings/opentofu.gpg] https://packages.opentofu.org/opentofu/tofu/any/ any main" \
  | sudo tee /etc/apt/sources.list.d/opentofu.list > /dev/null

# Recharge la liste des paquets et installe OpenTofu.
sudo apt-get update
sudo apt-get install -y tofu

# Affiche la version installée.
tofu version

echo "OpenTofu est installé correctement."
```

### Exécuter le script

```bash
chmod +x install-opentofu-ubuntu.sh
./install-opentofu-ubuntu.sh
```

Résultat attendu :

```text
OpenTofu v1.x.x
on linux_amd64
OpenTofu est installé correctement.
```

### Vérifier manuellement


## 11.3 Premier projet avec OpenTofu

On reprend exactement le même projet que la section 3 — aucune modification du code HCL n’est nécessaire.

### Créer le dossier

```bash
mkdir -p ~/opentofu-first-test
cd ~/opentofu-first-test
```

### Créer le fichier main.tf

```hcl
# Configure la version minimale d’OpenTofu attendue.
terraform {
  required_version = ">= 1.6.0"
}

# terraform_data fonctionne de la même façon avec OpenTofu.
resource "terraform_data" "first_contact" {

  input = "premier-test-opentofu"

  provisioner "local-exec" {
    command = "echo ‘Bonjour depuis OpenTofu local-exec’ > opentofu-local-result.txt"
  }
}

output "message" {
  value = terraform_data.first_contact.input
}
```

> Le bloc `terraform {}` conserve ce nom même sous OpenTofu — c’est la syntaxe HCL standard.

### Initialiser

```bash
tofu init
```

Résultat attendu :

```text
OpenTofu has been successfully initialized!
```

### Planifier et appliquer

```bash
tofu fmt
tofu validate
tofu plan
tofu apply -auto-approve
```

### Observer

```bash
cat opentofu-local-result.txt
tofu state list
tofu output
```

Résultat attendu :

```text
Bonjour depuis OpenTofu local-exec
---
terraform_data.first_contact
---
message = "premier-test-opentofu"
```

```bash
tofu destroy -auto-approve
rm -f opentofu-local-result.txt
```

Les deux outils peuvent coexister sur la même machine sans conflit :

# 12. Points d’attention à retenir

**terraform init** peut ne pas créer de dossier **.terraform** si aucun provider externe, module externe ou backend particulier n’est nécessaire.

Le message **You didn't use the -out option** après **terraform plan** n’est pas une erreur.

Quand Terraform affiche **Enter a value**, il faut taper exactement **yes**.

**terraform.tfstate** contient l’état actuel.

**terraform.tfstate.backup** contient uniquement l’état précédent en backend local.

Le prochain **apply** peut écraser l’ancien backup.

Si Terraform affiche **stat hello-remote.txt: no such file or directory**, le fichier source local n’existe pas dans le dossier du projet.

Le provisioner **file** copie vers le chemin indiqué dans **destination**.

Dans cet atelier, le fichier distant est dans **/tmp**, pas dans **/home/ubuntu**.

**local-exec** crée les fichiers sur la machine Terraform.

**remote-exec** crée les fichiers sur la machine distante.

Changer le nom logique d’une ressource, par exemple de **local_demo** vers **remote_demo**, pousse Terraform à supprimer l’ancienne entrée du state et à créer la nouvelle.
