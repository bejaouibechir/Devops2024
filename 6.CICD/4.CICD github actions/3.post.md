# Les traitements de fin : équivalent de post

## Objectif

Exécuter un bilan ou un diagnostic après les opérations principales.

## 1. Correspondances

| Jenkins | GitLab CI/CD | GitHub Actions |
| --- | --- | --- |
| `post` avec `success` | `when: on_success` | Étape `if: success()` |
| `post` avec `failure` | `when: on_failure` | Étape `if: failure()` |
| `post` avec `always` | `after_script` ou job final | Condition de statut explicite |
| `post` global | Stage `.post` | Job de bilan avec les `needs` utiles |

Il n'existe pas de bloc `post` global de workflow. Une étape de bilan est une étape ordinaire : son échec peut faire échouer le job, contrairement au comportement habituel d'`after_script` GitLab.

## 2. Réussite et échec dans un job

Fichier `.github/workflows/post.yml` :

```yaml
name: Traitements de fin
on:
  workflow_dispatch:
    inputs:
      fail_build:
        description: Simuler un echec
        type: boolean
        default: false
permissions: {}
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - name: Operation principale
        env:
          FAIL_BUILD: ${{ inputs.fail_build }}
        run: |
          echo "Debut du build"
          if [ "$FAIL_BUILD" = "true" ]; then
            echo "Echec volontaire"
            exit 1
          fi
          echo "Build termine"
      - name: Apres succes
        if: ${{ success() }}
        run: echo "Operation reussie"
      - name: Apres echec
        if: ${{ failure() }}
        run: echo "Diagnostic de l'echec"
      - name: Bilan local
        if: ${{ always() }}
        run: echo "Fin du job"
```

**Résultat attendu :** le bilan se lance dans les deux essais ; les étapes succès et échec s'alternent. Un diagnostic réussi ne répare pas l'échec initial.

`always()` est vrai même lors d'une annulation. `!cancelled()` permet de continuer après échec tout en respectant l'annulation. Aucun ne garantit un nettoyage après perte du runner ou arrêt forcé. Réservez `always()` aux opérations courtes. [Fonctions de statut](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions)

## 3. Bilan après plusieurs jobs

Workflow indépendant :

```yaml
name: Bilan global
on:
  workflow_dispatch:
permissions: {}
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Build"
  test:
    needs: build
    runs-on: ubuntu-24.04
    steps:
      - run: exit 1
  deploy:
    needs: test
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Deploiement simule"
  bilan:
    needs: [build, test, deploy]
    if: ${{ !cancelled() }}
    runs-on: ubuntu-24.04
    env:
      BUILD_RESULT: ${{ needs.build.result }}
      TEST_RESULT: ${{ needs.test.result }}
      DEPLOY_RESULT: ${{ needs.deploy.result }}
    steps:
      - run: |
          printf 'Build : %s\n' "$BUILD_RESULT"
          printf 'Test : %s\n' "$TEST_RESULT"
          printf 'Deploy : %s\n' "$DEPLOY_RESULT"
```

**Résultat :** `success`, `failure`, `skipped`. Le workflow reste en échec malgré le bilan réussi. Ajoutez à `needs` tout nouveau job à couvrir.

`needs` expose les dépendances directes, pas toutes les dépendances transitives. [Contexte needs](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#needs-context)

## 4. Échec toléré : regarder outcome

Fragment d'étapes :

```yaml
- id: audit
  continue-on-error: true
  run: exit 1
- if: ${{ steps.audit.outcome == 'failure' }}
  run: echo "Le controle facultatif a echoue"
```

`outcome` conserve le résultat initial ; `conclusion` tient compte de `continue-on-error`. Il n'y a pas d'état Jenkins `UNSTABLE` identique. Voir [options](4.options.md).

## 5. Fichiers et nettoyage

Pour garder un rapport après un test échoué, ajoutez un upload avec `if: ${{ !cancelled() }}` et un chemin précis. Le rapport peut ne pas exister si une étape antérieure a échoué. Voir [artefacts](7.artefact.md).

Certaines actions possèdent leurs propres hooks de nettoyage. Ces hooks appartiennent à leur implémentation ; on ne peut pas ajouter un bloc `post` arbitraire dans le workflow. [Métadonnées d'actions](https://docs.github.com/en/actions/reference/workflows-and-actions/metadata-syntax)
