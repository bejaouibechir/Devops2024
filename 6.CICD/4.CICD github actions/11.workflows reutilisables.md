# Réutiliser des workflows avec workflow_call

## Objectif

Partager un ensemble de jobs, avec des inputs, outputs et permissions explicites.

## 1. Différence avec une action

Une action intervient dans `steps`. Un workflow réutilisable est appelé au niveau d'un job et peut définir plusieurs jobs. Les includes/composants GitLab répondent aussi à la réutilisation, mais ne suivent pas exactement ce modèle d'appel.

Le fichier appelé reste directement dans `.github/workflows/` et déclare `on: workflow_call`. [Workflows réutilisables](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)

## 2. Workflow appelé

Créez `.github/workflows/reusable-version.yml` :

```yaml
name: Fabrique de version
on:
  workflow_call:
    inputs:
      prefix:
        type: string
        required: true
    outputs:
      version:
        description: Version produite
        value: ${{ jobs.prepare.outputs.version }}
permissions: {}
jobs:
  prepare:
    runs-on: ubuntu-24.04
    outputs:
      version: ${{ steps.compute.outputs.version }}
    steps:
      - id: compute
        env:
          PREFIX: ${{ inputs.prefix }}
        run: |
          if [[ ! "$PREFIX" =~ ^[0-9]+\.[0-9]+$ ]]; then
            exit 1
          fi
          echo "version=$PREFIX.$GITHUB_RUN_NUMBER" >> "$GITHUB_OUTPUT"
```

## 3. Workflow appelant

Créez `.github/workflows/caller.yml` :

```yaml
name: Appeler une fabrique de version
on:
  workflow_dispatch:
permissions: {}
jobs:
  version:
    uses: ./.github/workflows/reusable-version.yml
    with:
      prefix: '3.0'
  consume:
    needs: version
    runs-on: ubuntu-24.04
    env:
      VERSION: ${{ needs.version.outputs.version }}
    steps:
      - run: |
          printf 'Version recue : %s\n' "$VERSION"
```

**Résultat attendu :** le job consommateur affiche `3.0.N`.

Le job `version` n'a ni `runs-on` ni `steps` : ils appartiennent au workflow appelé. Les outputs remontent successivement de l'étape vers le job puis vers le contrat `workflow_call`.

## 4. Secrets et permissions

Pour recevoir un secret, l'appelé le déclare sous `on.workflow_call.secrets`, puis l'appelant le transmet sous `jobs.<id>.secrets`. Préférez des noms explicites quand seuls quelques secrets sont requis.

`secrets: inherit`, disponible dans les contextes de partage autorisés, transmet plus largement les secrets ; ce n'est pas indispensable pour une action ou un workflow public.

Les permissions ne peuvent pas être augmentées au fil des appels. Un environnement déclaré dans le job appelé possède ses propres secrets et protections : il ne devient pas un input de secret ordinaire.

## 5. Référence et code récupéré

Une référence locale `./.github/workflows/...` utilise le commit de l'appelant. Pour un autre dépôt, la forme est `organisation/depot/.github/workflows/fichier.yml@reference`.

Si le workflow appelé exécute `actions/checkout` sans `repository`, il récupère le dépôt de l'appelant. Le simple fait de partager un workflow ne copie pas les scripts du dépôt qui héberge ce workflow.

Les variables `env` du workflow appelant ne sont pas un contrat de transmission automatique. Passez les paramètres par `with`. [Réutilisation et différences avec les composites](https://docs.github.com/en/actions/concepts/workflows-and-actions/avoiding-duplication)

## Exercice

Appelez deux fois la fabrique avec `1.0` et `2.0`, puis affichez les deux outputs dans un troisième job. Provoquez ensuite un préfixe invalide et observez la propagation de l'échec.

Aucun appel de workflow n'a été exécuté pendant la rédaction.
