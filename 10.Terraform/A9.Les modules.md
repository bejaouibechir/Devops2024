# Atelier 6 : Découverte des Modules Terraform et leur Importance en Pratique

## 1. Introduction

## Objectif de l'atelier

Dans les ateliers précédents, tout le code Terraform était écrit dans le même dossier, souvent dans un seul **main.tf**.

Cette approche fonctionne pour les petits projets, mais elle devient vite difficile à maintenir.

Exemple de problème :

Un même fichier contient :

- l'installation de Docker
- la configuration Docker
- la création d'un conteneur
- les outputs
- les dépendances

Le code devient moins lisible, plus fragile, plus difficile à corriger.

Les **modules Terraform** permettent de découper le projet en blocs réutilisables.

Un module Terraform est simplement un dossier contenant des fichiers Terraform. Un bloc **module** permet d'appeler les ressources définies dans ce dossier local ou distant. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/block/module?utm_source=chatgpt.com "module block reference | Terraform"))

## Message principal

Sans module :
tout est mélangé dans un seul bloc de code.

Avec modules :
chaque responsabilité est isolée.

Dans cet atelier, on va montrer une situation concrète :

1. Installer Docker sur une **machine distante** via SSH
2. Utiliser Docker avec Terraform sur cette machine distante
3. Créer un conteneur Nginx sur la machine distante

## Contexte : machine locale vs machine distante

Terraform s'exécute sur la **machine locale** (votre poste de travail).

Les commandes d'installation Docker et les conteneurs s'exécutent sur la **machine distante** (serveur Ubuntu accessible via SSH).

C'est le même principe qu'Ansible : la machine de contrôle ne fait que piloter la machine cible.

```text
Machine locale (Terraform)  ──SSH──►  Machine distante (Ubuntu)
    terraform apply                      Docker installé ici
                                         Conteneur lancé ici
```

Le provider Docker **kreuzwerker/docker** permet à Terraform d'interagir avec l'API Docker. Il supporte une connexion via SSH pour piloter un daemon Docker distant. ([Terraform Registry](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs?utm_source=chatgpt.com "Docs overview | kreuzwerker/docker - Terraform Registry"))

## Le problème à comprendre

Le provider Docker utilise l'API Docker.

Si Docker n'est pas encore installé ou démarré sur la machine distante,
le provider Docker ne peut pas créer le conteneur.

On va donc séparer le projet en deux modules :

```text
docker-install     → installe Docker sur la machine distante
docker-container   → crée un conteneur Nginx sur la machine distante
```

Puis on utilisera **depends_on** pour forcer l'ordre :

```text
docker-install doit finir avant docker-container
```

Terraform recommande **depends_on** uniquement pour les dépendances cachées que Terraform ne peut pas déduire automatiquement. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/meta-arguments/depends_on?utm_source=chatgpt.com "depends_on meta-argument reference | Terraform"))

# 3. Étape 1 : Créer un premier module simple

## 3.1 Objectif

Avant Docker, on commence avec un module très simple.

Ce module va créer un fichier local.

Il permet de comprendre :

```text
module
source
input variables
output values
```

---

## 3.2 Créer le module simple-file

Créer le fichier **modules/simple-file/variables.tf** :

```hcl
# Nom du fichier à créer.
variable "file_name" {
  type        = string
  description = "Nom du fichier local à créer."
}

# Contenu du fichier.
variable "file_content" {
  type        = string
  description = "Contenu du fichier local."
}
```

Créer le fichier **modules/simple-file/main.tf** :

```hcl
# Le module crée un fichier local.
resource "local_file" "this" {
  filename = var.file_name
  content  = var.file_content
}
```

Créer le fichier **modules/simple-file/outputs.tf** :

```hcl
# Retourne le nom du fichier créé.
output "file_name" {
  value = local_file.this.filename
}
```

## 3.3 Créer le fichier racine main.tf

Ce fichier se crée **à la racine du projet**, pas dans le dossier du module :

```bash
# Vérifier qu'on est bien à la racine du projet, pas dans modules/simple-file/
pwd
# Attendu : ~/terraform-modules-docker
```

Créer le fichier **~/terraform-modules-docker/main.tf** :

```hcl
# Déclare les providers nécessaires au projet racine.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Provider Local sans configuration obligatoire.
provider "local" {}

# Appel du module local simple-file.
module "intro_file" {
  source = "./modules/simple-file"

  file_name    = "intro-module.txt"
  file_content = "Ce fichier a été créé par un module Terraform local."
}
```

Créer le fichier **outputs.tf** :

```hcl
# Affiche le fichier créé par le module.
output "intro_file_name" {
  value = module.intro_file.file_name
}
```

Créer le fichier **variables.tf** :

```hcl
# Fichier présent pour garder une structure professionnelle.
# Les variables racines seront ajoutées dans les étapes suivantes.
```

## 3.4 Exécuter Terraform

Exécuter dans **~/terraform-modules-docker** :

```bash
# Initialise Terraform et charge les modules locaux.
terraform init

# Reformate les fichiers.
terraform fmt -recursive

# Vérifie la configuration.
terraform validate

# Affiche le plan.
terraform plan

# Applique.
terraform apply -auto-approve
```

## 3.5 Observer

```bash
# Vérifie le fichier créé.
cat intro-module.txt

# Liste le state.
terraform state list

# Affiche l'output.
terraform output
```

Résultat attendu :

```text
Ce fichier a été créé par un module Terraform local.
```

State attendu :

```text
module.intro_file.local_file.this
```

## 3.6 Points clés

Un **module local** est un dossier contenant des fichiers Terraform.

Le bloc suivant appelle un module :

```hcl
module "intro_file" {
  source = "./modules/simple-file"
}
```

Les variables du module sont des **inputs**.

Les outputs du module sont accessibles avec :

```text
module.nom_du_module.nom_output
```

# 4. Étape 2 : Comprendre le problème sans séparation propre

## 4.1 Objectif

Montrer pourquoi il est dangereux de tout mélanger.

On pourrait être tenté d'écrire :

1. installer Docker sur la machine distante

2. puis créer un conteneur

3. dans le même fichier main.tf

Le problème est que le provider Docker doit se connecter à Docker pendant le plan ou l'apply.

Si Docker n'est pas encore installé sur la machine distante ou si le service n'est pas démarré, Terraform risque d'échouer avec une erreur de connexion au daemon Docker.

## 4.2 Exemple volontairement fragile

Ne pas exécuter ce fichier dans l'atelier principal. Il sert à comprendre le problème.

```hcl
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

# Provider Docker connecté à la machine distante via SSH.
provider "docker" {
  host     = "ssh://ubuntu@192.168.1.100"
  ssh_opts = ["-i", "~/.ssh/id_rsa", "-o", "StrictHostKeyChecking=no"]
}

# Installe Docker sur la machine distante.
resource "terraform_data" "install_docker" {
  connection {
    type        = "ssh"
    host        = "192.168.1.100"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
  }

  provisioner "remote-exec" {
    inline = [
      "sudo apt-get update -y",
      "sudo apt-get install -y docker.io",
      "sudo systemctl enable --now docker",
    ]
  }
}

resource "docker_image" "nginx" {
  name = "nginx:alpine"
}

resource "docker_container" "nginx" {
  name  = "nginx-module-demo"
  image = docker_image.nginx.image_id

  ports {
    internal = 80
    external = 8080
  }
}
```

## 4.3 Pourquoi c'est fragile ?

Même si **terraform_data.install_docker** existe, le provider Docker peut être initialisé ou utilisé alors que Docker n'est pas encore prêt sur la machine distante.

Le code mélange deux responsabilités :

```text
installation système sur la machine distante
utilisation de Docker via le provider
```

La solution propre :

```text
module docker-install   → remote-exec installe Docker
module docker-container → provider Docker crée le conteneur
depends_on entre modules
```

# 5. Étape 3 : Module docker-install

## 5.1 Objectif

Créer un module qui installe Docker sur la **machine distante** via SSH.

Ce module utilise **terraform_data** avec **remote-exec**.

Le provisioner `remote-exec` exécute des commandes sur la machine distante via une connexion SSH. C'est l'équivalent d'Ansible pour les tâches d'installation système dans Terraform.

La différence avec `local-exec` :

```text
local-exec   → exécute sur la machine qui lance Terraform (machine locale)
remote-exec  → exécute sur la machine cible via SSH (machine distante)
```

---

## 5.2 Créer le fichier modules/docker-install/variables.tf

Créer le fichier **modules/docker-install/variables.tf** :

```hcl
# Nom du fichier témoin créé après installation (sur la machine distante).
variable "marker_file" {
  type        = string
  description = "Fichier témoin indiquant que le module docker-install a été exécuté."
  default     = "docker-install.done"
}

# Adresse IP ou nom DNS de la machine distante.
variable "remote_host" {
  type        = string
  description = "Adresse IP ou hostname de la machine distante."
}

# Utilisateur SSH sur la machine distante.
variable "remote_user" {
  type        = string
  description = "Utilisateur SSH pour se connecter à la machine distante."
  default     = "ubuntu"
}

# Chemin local vers la clé privée SSH.
variable "ssh_private_key_path" {
  type        = string
  description = "Chemin vers la clé privée SSH sur la machine locale."
  default     = "~/.ssh/id_rsa"
}
```

## 5.3 Créer le fichier modules/docker-install/main.tf

Créer le fichier **modules/docker-install/main.tf** :

```hcl
# Ce module installe Docker sur la machine distante via SSH.
resource "terraform_data" "install" {

  # Cette valeur force Terraform à garder une trace logique de l'installation.
  input = "docker-install"

  # Bloc connection : définit comment se connecter à la machine distante.
  connection {
    type        = "ssh"
    host        = var.remote_host
    user        = var.remote_user
    private_key = file(var.ssh_private_key_path)
  }

  # remote-exec exécute les commandes sur la machine distante via SSH.
  #
  # Toutes les commandes privilégiées sont regroupées dans un seul appel
  # "sudo bash -c '...'" pour éviter l'erreur Terraform :
  # "remote command exited without exit status or exit signal".
  #
  # Cause : inline envoie chaque commande comme une requête SSH séparée.
  # Une commande systemctl peut faire vaciller la session SSH et priver
  # Terraform du code de sortie de la commande suivante.
  # Solution : une seule requête SSH = un seul code de sortie propre.
  provisioner "remote-exec" {
    inline = [
      "sudo bash -c 'apt-get update -y && apt-get install -y docker.io && systemctl enable docker && systemctl start docker && usermod -aG docker ${var.remote_user} && chmod 660 /var/run/docker.sock && docker --version'",
      "touch ${var.marker_file}",
    ]
  }
}
```

### Pourquoi `newgrp docker` n'est plus nécessaire ici

Dans le mode distant, après l'exécution du module docker-install :

- Le `remote-exec` a ajouté l'utilisateur au groupe docker et appliqué `chmod 660` sur le socket.
- La connexion SSH que le **provider Docker** ouvre ensuite est une **nouvelle session SSH**.
- Sur une nouvelle session SSH, le groupe docker est déjà actif.

Le problème de `newgrp docker` était propre à l'exécution locale (session shell courante). Il ne se pose pas en mode distant.

### Note : l'apply en deux temps

> ⚠️ Cette note est une **prévisualisation** — ne pas exécuter ces commandes maintenant.
> Le projet racine (`main.tf`, `variables.tf`, `outputs.tf`, `terraform.tfvars`) n'est pas encore créé.
> L'exécution complète est décrite à la **section 8**.

Une fois le projet complet, on appliquera en deux temps :

```bash
# Étape 1 : installe Docker sur la machine distante uniquement.
terraform apply -target=module.docker_install

# Étape 2 : le provider Docker peut maintenant accéder au daemon distant.
terraform apply
```

`-target=module.docker_install` est une option Terraform qui limite l'apply à une seule ressource ou module. Elle est utile ici pour séparer l'installation système du déploiement applicatif.

**remarque:** Vous aurez plus d'informations sur **terraform_data** au niveau de ce lien
https://developer.hashicorp.com/terraform/language/resources/terraform-data

## 5.4 Créer le fichier modules/docker-install/outputs.tf

Créer le fichier **modules/docker-install/outputs.tf** :

```hcl
# Retourne le fichier témoin.
output "marker_file" {
  value = var.marker_file
}

# Retourne un statut logique.
output "install_status" {
  value = terraform_data.install.output
}
```

## 5.5 Point clé

Ce module ne crée pas de conteneur.

Il prépare seulement Docker sur la machine distante :

- apt-get install docker.io
- systemctl start docker
- usermod -aG docker
- chmod 660 /var/run/docker.sock

# 6. Étape 4 : Module docker-container

## 6.1 Objectif

Créer un module qui utilise Docker pour lancer un conteneur Nginx sur la **machine distante**.

Ce module utilise le provider **Docker**.

Le provider Docker permet de gérer le cycle de vie des conteneurs Docker avec l'API Docker. ([Terraform Registry](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs?utm_source=chatgpt.com "Docs overview | kreuzwerker/docker - Terraform Registry"))

Ce module ne contient aucune référence SSH directe. La connexion au daemon Docker distant est gérée par le provider configuré dans le `main.tf` racine.

---

## 6.2 Créer le fichier modules/docker-container/variables.tf

Créer le fichier **modules/docker-container/variables.tf** :

```hcl
# Nom du conteneur Docker.
variable "container_name" {
  type        = string
  description = "Nom du conteneur Docker."
  default     = "nginx-module-demo"
}

# Image Docker à utiliser.
variable "image_name" {
  type        = string
  description = "Image Docker à télécharger."
  default     = "nginx:alpine"
}

# Port externe exposé sur la machine distante.
variable "external_port" {
  type        = number
  description = "Port externe exposé sur la machine distante."
  default     = 8080

  validation {
    condition     = var.external_port >= 1024 && var.external_port <= 65535
    error_message = "external_port doit être entre 1024 et 65535."
  }
}
```

## 6.3 Créer le fichier modules/docker-container/main.tf

Créer le fichier **modules/docker-container/main.tf** :

```hcl
# Déclare le provider Docker attendu par ce module.
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

# Télécharge ou référence l'image Docker sur la machine distante.
resource "docker_image" "nginx" {
  name = var.image_name
}

# Crée le conteneur Nginx sur la machine distante.
resource "docker_container" "nginx" {
  name  = var.container_name
  image = docker_image.nginx.image_id

  ports {
    internal = 80
    external = var.external_port
  }
}
```

## 6.4 Créer le fichier modules/docker-container/outputs.tf

Créer le fichier **modules/docker-container/outputs.tf** :

```hcl
# Nom du conteneur créé.
output "container_name" {
  value = docker_container.nginx.name
}

# Image utilisée.
output "image_name" {
  value = var.image_name
}

# URL de test depuis la machine locale.
output "container_url" {
  value = "http://${docker_container.nginx.ports[0].ip}:${var.external_port}"
}
```

## 6.5 Point clé

Ce module suppose que Docker est déjà disponible sur la machine distante.

Il ne doit pas installer Docker.

Il doit seulement utiliser Docker :

```text
docker_image
docker_container
```

Créer le fichier **variables.tf** :

```hcl
# Adresse IP ou hostname de la machine distante.
variable "remote_host" {
  type        = string

  type        = string
  description = "Utilisateur SSH pour se connecter à la machine distante."
  default     = "ubuntu"
}

# Chemin local vers la clé privée SSH.
variable "ssh_private_key_path" {
  type        = string
  description = "Chemin vers la clé privée SSH sur la machine locale."
  default     = "~/.ssh/id_rsa"
}

# Nom du conteneur Docker.

  type        = string
  description = "Nom du conteneur Nginx."
  default     = "nginx-module-demo"

# Image Docker utilisée.

  type        = string
  description = "Image Docker utilisée."
  default     = "nginx:alpine"
}

variable "external_port" {
  type        = number
  description = "Port HTTP exposé sur la machine distante."
  default     = 8080

    error_message = "external_port doit être entre 1024 et 65535."
  }

```

## 7.3 Remplacer le fichier racine main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare les providers nécessaires au projet racine.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }

    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

# Provider Local.
provider "local" {}

# Provider Docker.
# Il se connecte au daemon Docker de la machine distante via SSH.
# Terraform ouvre un tunnel SSH vers le socket Docker distant.
provider "docker" {
  host = "ssh://${var.remote_user}@${var.remote_host}"

  ssh_opts = [
    "-i", var.ssh_private_key_path,
    "-o", "StrictHostKeyChecking=no",
  ]
}

# Module responsable de l'installation Docker sur la machine distante.
module "docker_install" {
  source = "./modules/docker-install"

  marker_file          = "docker-install.done"
  remote_host          = var.remote_host
  remote_user          = var.remote_user
  ssh_private_key_path = var.ssh_private_key_path
}

# Module responsable de la création du conteneur sur la machine distante.
module "docker_container" {
  source = "./modules/docker-container"

  container_name = var.container_name
  image_name     = var.image_name
  external_port  = var.external_port

  # Cette dépendance force Terraform à terminer l'installation
  # avant d'utiliser le provider Docker.
  depends_on = [
    module.docker_install
  ]
}
```

### Pourquoi `ssh://` dans le provider Docker ?

Le provider `kreuzwerker/docker` supporte plusieurs types de connexion :

```text
unix:///var/run/docker.sock  → socket local (machine locale uniquement)
tcp://host:2375              → TCP non chiffré (déconseillé en production)
ssh://user@host              → tunnel SSH (recommandé pour machine distante)
```

Avec `ssh://`, Terraform crée un tunnel SSH vers le socket `/var/run/docker.sock` de la machine distante. L'API Docker n'est jamais exposée sur le réseau — elle reste protégée par SSH.

# 8. Étape 6 : Exécuter le projet complet

## 8.0 Prérequis : connexion SSH vers la machine distante

Avant de lancer Terraform, vérifier que la connexion SSH fonctionne :

```bash
# Remplacer par l'adresse de votre machine distante et l'utilisateur.
ssh -i ~/.ssh/id_rsa ubuntu@<IP_MACHINE_DISTANTE> "echo 'SSH OK'"
```

Si la connexion échoue, vérifier :

```text
- La clé SSH est correcte et les permissions sont 600 : chmod 600 ~/.ssh/id_rsa
- L'utilisateur existe sur la machine distante
- Le port 22 est ouvert (firewall / security group)
```

## 8.1 Vérifier la structure avant d'initialiser

L'erreur `Unreadable module directory` se produit quand Terraform ne trouve pas le dossier `modules/` parce que la commande est lancée depuis le mauvais répertoire ou parce que les dossiers de modules n'ont pas encore été créés.

Vérifier l'emplacement et la structure avant tout :

```bash
# S'assurer d'être à la racine du projet.
cd ~/terraform-modules-docker
pwd
# Attendu : /home/<utilisateur>/terraform-modules-docker

# Vérifier que les dossiers des modules existent.
ls modules/
# Attendu : docker-install  docker-container  simple-file
```

```hcl
# Ce module arrête et supprime le conteneur Docker ainsi que son image

    type        = "ssh"
```

# 8.9 `terraform destroy` vs modules de nettoyage

## Pourquoi ne pas simplement utiliser `terraform destroy` ?

`terraform destroy` détruit les ressources **tracées dans le state**. Il appelle le cycle de destruction de chaque provider.

Sur ce projet, cela donne :

| Ressource                | Ce que `terraform destroy` fait                                                   |
| ------------------------ | --------------------------------------------------------------------------------- |
| `docker_container.nginx` | Arrête et supprime le conteneur ✅                                                 |
| `docker_image.nginx`     | Supprime l'image ✅                                                                |
| `terraform_data.install` | Retire l'entrée du state — **aucune commande exécutée sur la machine distante** ❌ |

**Docker reste installé sur la machine distante.** C'est la limite de `terraform destroy` ici : il gère les ressources applicatives (conteneur, image) mais pas l'installation système.

## Ce que font nos modules de nettoyage en plus

```text
docker-remove-container  →  docker stop / rm / rmi       (identique à destroy)
docker-uninstall         →  apt-get remove docker.io     (destroy ne fait pas ça)
```

## Quand utiliser quoi

```text
terraform destroy        →  nettoyage rapide des ressources Terraform
                             Docker reste installé sur la machine
                             ⚠️ échoue si le state est perdu ou si Docker est cassé

modules de nettoyage     →  désinstallation complète de l'OS
                             fonctionne même sans state
                             fonctionne même si le daemon Docker est cassé
```

## Note : la solution propre avec `when = destroy`

Il est possible d'ajouter un provisioner `when = destroy` dans `docker-install` pour que `terraform destroy` déclenche aussi la désinstallation Docker :

```hcl
provisioner "remote-exec" {
  when = destroy
  inline = [
    "sudo bash -c 'systemctl stop docker || true; apt-get remove -y docker.io || true; apt-get autoremove -y'",
  ]
}
```

Avec ce bloc, `terraform destroy` ferait tout : conteneur, image, et désinstallation Docker. Les modules de nettoyage resteraient utiles uniquement en cas de perte de state ou de daemon Docker cassé.

Cette approche est laissée en exercice — elle introduit la notion de cycle de vie complet d'une ressource Terraform.

# 9. Étape 7 : Comprendre depends_on entre modules

## 9.1 Pourquoi depends_on est nécessaire ici ?

Le module **docker_container** ne lit pas directement une valeur technique produite par le module **docker_install** pour configurer le provider Docker.

Terraform ne peut donc pas forcément deviner que Docker doit être installé avant l'utilisation du provider Docker.

La dépendance est donc une dépendance de comportement :

```text
Le conteneur dépend du fait que Docker soit installé et démarré sur la machine distante.
```

On écrit donc :

```hcl
depends_on = [
  module.docker_install
]
```

## 9.2 Point important

**depends_on** force Terraform à terminer toutes les actions du module dépendant avant de commencer l'autre module.

C'est utile ici, mais à utiliser avec prudence.

## 9.3 Attention

**depends_on** ne répare pas un mauvais design.

Il sert uniquement quand la dépendance est réelle mais invisible dans les arguments Terraform.

Bonne utilisation :

```text
Le module docker-container dépend réellement du fait que docker-install soit terminé.
```

Mauvaise utilisation :

```text
Mettre depends_on partout par sécurité.
```

# 11. Étape 9 : Module versioning de base

## 11.1 Cas des modules locaux

Pour un module local :

```hcl
source = "./modules/docker-container"
```

Il n'y a pas de version explicite dans le bloc **module**.

La version est liée au code présent dans le dossier.

## 11.2 Cas des modules Git

Plus tard, un module peut venir d'un dépôt Git :

```hcl
module "docker_container" {
  source = "git::https://gitlab.com/example/terraform-docker-container.git?ref=v1.0.0"
}
```

Ici :

```text
ref=v1.0.0
```

désigne une version Git, souvent un tag.

## 11.3 Cas du Terraform Registry

Plus tard, un module peut venir du Terraform Registry :

```hcl
module "network" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "x.y.z"
}
```

Ici, **version** fixe la version du module public.

## 11.4 Point clé

Pour débuter :

```text
module local = source ./modules/nom

module Git = source git + ref

module Registry = source + version
```

```text
le même code doit être réutilisé
un fichier main.tf devient trop long
```

```text

```

## 12.3 Organisation recommandée

```text
modules/
└── nom-du-module/
    ├── main.tf
    ├── variables.tf
    ├── outputs.tf
    └── README.md
```

| ------------------------------------------------------ | ------------------------------------------ |

Vous avez appris à :


Le cas Docker montre clairement le problème :

```text
Installer Docker et l'utiliser sont deux responsabilités différentes.
```

La séparation propre est :

```text
module docker-install
→ installe et démarre Docker sur la machine distante (remote-exec via SSH)

module docker-container
→ crée une image et un conteneur (provider Docker via tunnel SSH)
```

La relation est explicitée par :

```hcl
depends_on = [
  module.docker_install
]
```

Le bénéfice principal des modules :

- code plus lisible

- code plus réutilisable

- code plus maintenable

- moins d'erreurs de dépendance

- meilleure séparation des responsabilités

La connexion SSH centralise la gestion de l'accès distant dans le `main.tf` racine. Les modules eux-mêmes restent réutilisables et indépendants du contexte réseau.
