# Atelier 7 : Les Templates Terraform — Générer du contenu dynamique avec templatefile()

## 1. Introduction

## Objectif de l'atelier

Jusqu'ici, toutes les valeurs dans les fichiers Terraform étaient écrites en dur ou passées via des variables simples.

Mais en pratique, on a souvent besoin de **générer des fichiers de configuration** dont le contenu varie selon l'environnement, les variables, ou une liste de valeurs.

Exemples concrets :

```text
nginx.conf        → ports, server_name, locations différents selon l'env
.env              → variables d'application selon prod/staging/dev
cloud-init.yaml   → script de démarrage d'une VM
/etc/hosts        → liste d'hôtes dynamique
```

La fonction `templatefile()` répond exactement à ce besoin.

## Introduction de la notion template

Un **template** est un fichier texte qui contient des **espaces réservés** (placeholders).

`templatefile()` remplace ces espaces par des valeurs réelles au moment de l'apply.

```text
fichier .tftpl + variables  →  templatefile()  →  contenu final généré
```

Le résultat peut être :

- écrit dans un fichier local via `local_file`
- passé en argument à une ressource (`user_data`, `content`, etc.)
- retourné comme output d'un module

## Ce que couvre cet atelier

```text
Étape 1 : interpolation simple        ${ }
Étape 2 : conditionnel                %{ if } / %{ else } / %{ endif }
Étape 3 : boucle                      %{ for } / %{ endfor }
Étape 4 : cas pratique                générer un nginx.conf complet
```

# 3. Étape 1 : Interpolation simple avec ${ }

## 3.1 Objectif

Comprendre la syntaxe de base de `templatefile()` :

- comment écrire un fichier template `.tftpl`
- comment appeler `templatefile()` depuis Terraform
- comment le résultat est injecté dans une ressource

## 3.2 Créer le template

Créer le fichier **templates/message.tftpl** :

```text
Bonjour ${prenom} ${nom} !

Environnement : ${environnement}
Version de l'application : ${version}

Ce fichier a été généré automatiquement par Terraform.
Toute modification manuelle sera écrasée au prochain apply.
```

Les éléments `${prenom}`, `${nom}`, `${environnement}`, `${version}` sont des **placeholders**.

Ils seront remplacés par les valeurs passées à `templatefile()`.

## 3.3 Ajouter les variables

Ajouter dans **variables.tf** :

```hcl
variable "prenom" {
  type    = string
  default = "Alice"
}

variable "nom" {
  type    = string
  default = "Dupont"
}

variable "environnement" {
  type    = string
  default = "development"
}

variable "version_app" {
  type    = string
  default = "1.0.0"
}
```

## 3.4 Appeler templatefile() dans main.tf

Ajouter dans **main.tf** :

```hcl
# Génère le fichier message à partir du template.
resource "local_file" "message" {
  filename = "output-message.txt"

  # templatefile() prend deux arguments :
  # 1. le chemin vers le fichier .tftpl
  # 2. une map de variables à injecter
  content = templatefile("${path.module}/templates/message.tftpl", {
    prenom        = var.prenom
    nom           = var.nom
    environnement = var.environnement
    version       = var.version_app
  })
}
```

### Explication de templatefile()

```text
templatefile(chemin, variables)

chemin    : chemin vers le fichier .tftpl
            ${path.module} désigne le dossier du fichier Terraform courant

variables : map de clés/valeurs
            les clés correspondent aux ${...} dans le template
```

## 3.5 Créer le fichier terraform.tfvars

```hcl
prenom        = "Bechir"
nom           = "Bejaoui"
environnement = "staging"
version_app   = "2.3.1"
```

## 3.6 Ajouter un output

Créer le fichier **outputs.tf** :

```hcl
output "message_genere" {
  value = local_file.message.content
}
```

## 3.7 Exécuter

```bash
terraform fmt -recursive
terraform validate
terraform plan
terraform apply -auto-approve
```

## 3.8 Observer

```bash
# Lire le fichier généré.
cat output-message.txt

# Afficher l'output Terraform.
terraform output message_genere
```

Résultat attendu :

```text
Bonjour Bechir Bejaoui !

Environnement : staging
Version de l'application : 2.3.1

Ce fichier a été généré automatiquement par Terraform.
Toute modification manuelle sera écrasée au prochain apply.
```

## 3.9 Point clé

`templatefile()` est une **fonction Terraform** — pas une ressource.

Elle s'utilise partout où une valeur de type `string` est attendue :

```hcl
content   = templatefile(...)   # local_file
user_data = templatefile(...)   # aws_instance
script    = templatefile(...)   # custom resource
```

# 4. Étape 2 : Conditionnel avec %{ if }

## 4.1 Objectif

Générer un contenu **différent selon une condition**.

Exemple : le niveau de log et le cache sont différents en production et en développement.

## 4.2 Syntaxe du conditionnel

```text
%{ if condition }
  contenu si vrai
%{ else }
  contenu si faux
%{ endif }
```

La condition peut être :

```text
variable == "valeur"
variable != "valeur"
variable > 0
variable
```

## 4.3 Créer le template

Créer le fichier **templates/app_config.tftpl** :

```text
# Configuration de l'application
# Générée par Terraform — ne pas modifier manuellement.

APP_NAME=${app_name}
APP_PORT=${port}

%{ if environnement == "production" }
LOG_LEVEL=error
CACHE_ENABLED=true
MAX_CONNECTIONS=100
%{ else }
LOG_LEVEL=debug
CACHE_ENABLED=false
MAX_CONNECTIONS=10
%{ endif }

%{ if enable_https }
HTTPS_ENABLED=true
SSL_CERT=/etc/ssl/certs/${app_name}.crt
%{ else }
HTTPS_ENABLED=false
%{ endif }
```

## 4.4 Ajouter les variables

Ajouter dans **variables.tf** :

```hcl
variable "app_name" {
  type    = string
  default = "mon-app"
}

variable "app_port" {
  type    = number
  default = 3000
}

variable "enable_https" {
  type    = bool
  default = false
}
```

## 4.5 Ajouter la ressource dans main.tf

Ajouter dans **main.tf** :

```hcl
# Génère le fichier de configuration de l'application.
resource "local_file" "app_config" {
  filename = "output-app.env"

  content = templatefile("${path.module}/templates/app_config.tftpl", {
    app_name      = var.app_name
    port          = var.app_port
    environnement = var.environnement
    enable_https  = var.enable_https
  })
}
```

## 4.6 Mettre à jour terraform.tfvars

```hcl
prenom        = "Bechir"
nom           = "Bejaoui"
environnement = "production"
version_app   = "2.3.1"
app_name      = "api-service"
app_port      = 8080
enable_https  = true
```

## 4.7 Exécuter et observer

```bash
terraform apply -auto-approve
cat output-app.env
```

Résultat attendu avec `environnement = "production"` et `enable_https = true` :

```text
APP_NAME=api-service
APP_PORT=8080

LOG_LEVEL=error
CACHE_ENABLED=true
MAX_CONNECTIONS=100

HTTPS_ENABLED=true
SSL_CERT=/etc/ssl/certs/api-service.crt
```

Changer `environnement = "development"` dans `terraform.tfvars` et relancer :

```bash
terraform apply -auto-approve
cat output-app.env
```

Le bloc LOG_LEVEL et CACHE changent automatiquement.

## 4.8 Point clé

```text
%{ if } évalue une condition Terraform.
Le contenu entre %{ if } et %{ endif } est inclus ou exclu selon la condition.
%{ else } est optionnel.
```

# 5. Étape 3 : Boucle avec %{ for }

## 5.1 Objectif

Générer du contenu **répété pour chaque élément d'une liste ou d'une map**.

Exemple : générer un fichier `/etc/hosts` avec une liste de serveurs.

## 5.2 Syntaxe de la boucle

Avec une liste :

```text
%{ for item in liste }
${item}
%{ endfor }
```

Avec une liste d'objets :

```text
%{ for item in liste }
${item.attribut1}  ${item.attribut2}
%{ endfor }
```

## 5.3 Créer le template

Créer le fichier **templates/hosts.tftpl** :

```text
# Fichier /etc/hosts
# Généré par Terraform — ne pas modifier manuellement.

127.0.0.1   localhost
::1         localhost

# Serveurs de l'infrastructure
%{ for serveur in serveurs }
${serveur.ip}   ${serveur.nom}
%{ endfor }

# Serveurs de base de données
%{ for db in bases_de_donnees }
${db.ip}   ${db.nom}   # ${db.role}
%{ endfor }
```

## 5.4 Ajouter les variables

Ajouter dans **variables.tf** :

```hcl
variable "serveurs" {
  type = list(object({
    ip  = string
    nom = string
  }))
  default = []
}

variable "bases_de_donnees" {
  type = list(object({
    ip   = string
    nom  = string
    role = string
  }))
  default = []
}
```

## 5.5 Ajouter la ressource dans main.tf

Ajouter dans **main.tf** :

```hcl
# Génère le fichier hosts.
resource "local_file" "hosts" {
  filename = "output-hosts.txt"

  content = templatefile("${path.module}/templates/hosts.tftpl", {
    serveurs         = var.serveurs
    bases_de_donnees = var.bases_de_donnees
  })
}
```

## 5.6 Mettre à jour terraform.tfvars

```hcl
serveurs = [
  { ip = "10.0.1.10", nom = "web-01" },
  { ip = "10.0.1.11", nom = "web-02" },
  { ip = "10.0.1.12", nom = "web-03" },
]

bases_de_donnees = [
  { ip = "10.0.2.10", nom = "db-primary", role = "primary" },
  { ip = "10.0.2.11", nom = "db-replica", role = "replica" },
]
```

## 5.7 Exécuter et observer

```bash
terraform apply -auto-approve
cat output-hosts.txt
```

Résultat attendu :

```text
# Fichier /etc/hosts
# Généré par Terraform — ne pas modifier manuellement.

127.0.0.1   localhost
::1         localhost

# Serveurs de l'infrastructure
10.0.1.10   web-01
10.0.1.11   web-02
10.0.1.12   web-03

# Serveurs de base de données
10.0.2.10   db-primary   # primary
10.0.2.11   db-replica   # replica
```

Ajouter un serveur dans `terraform.tfvars` et relancer `terraform apply` : le fichier se met à jour automatiquement.

## 5.8 Point clé

```text
%{ for item in liste }  itère sur une liste
%{ for k, v in map }    itère sur une map (clé, valeur)
%{ endfor }             ferme la boucle

La boucle fonctionne sur :
- list(string)
- list(object({...}))
- map(string)
```

# 6. Étape 4 : Cas pratique — Générer un nginx.conf

## 6.1 Objectif

Combiner interpolation, conditionnel et boucle dans un template réaliste.

On génère un fichier `nginx.conf` complet dont le contenu s'adapte aux variables.

C'est un cas très courant en infrastructure :

```text
un seul template nginx.conf
→ généré différemment pour chaque environnement ou service
```

## 6.2 Créer le template

Créer le fichier **templates/nginx.conf.tftpl** :

```nginx
# nginx.conf
# Généré par Terraform — ne pas modifier manuellement.
# Serveur : ${server_name} | Environnement : ${environnement}

server {
    listen ${port};
    server_name ${server_name};

    access_log /var/log/nginx/${server_name}_access.log;
    error_log  /var/log/nginx/${server_name}_error.log;

    %{ if enable_gzip }
    # Compression activée.
    gzip on;
    gzip_types text/plain text/css application/json application/javascript;
    gzip_min_length 1000;
    %{ endif }

    %{ if environnement == "production" }
    # En-têtes de sécurité (production uniquement).
    add_header X-Frame-Options "SAMEORIGIN";
    add_header X-Content-Type-Options "nosniff";
    add_header X-XSS-Protection "1; mode=block";
    %{ endif }

    # Locations configurées dynamiquement.
    %{ for loc in locations }
    location ${loc.path} {
        proxy_pass ${loc.backend};
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
    %{ endfor }

    # Page d'erreur personnalisée.
    error_page 404 /404.html;
    error_page 500 502 503 504 /50x.html;
}
```

## 6.3 Ajouter les variables

Ajouter dans **variables.tf** :

```hcl
variable "nginx_port" {
  type    = number
  default = 80
}

variable "server_name" {
  type    = string
  default = "localhost"
}

variable "enable_gzip" {
  type    = bool
  default = true
}

variable "locations" {
  type = list(object({
    path    = string
    backend = string
  }))
  default = []
}
```

## 6.4 Ajouter la ressource dans main.tf

Ajouter dans **main.tf** :

```hcl
# Génère le fichier nginx.conf.
resource "local_file" "nginx_config" {
  filename = "output-nginx.conf"

  content = templatefile("${path.module}/templates/nginx.conf.tftpl", {
    port          = var.nginx_port
    server_name   = var.server_name
    environnement = var.environnement
    enable_gzip   = var.enable_gzip
    locations     = var.locations
  })
}
```

## 6.5 Mettre à jour terraform.tfvars

```hcl
prenom        = "Bechir"
nom           = "Bejaoui"
environnement = "production"
```

# 8. Bonnes pratiques

## 8.1 Extension .tftpl

Toujours utiliser l'extension `.tftpl` pour les fichiers template Terraform.

```text
nginx.conf.tftpl    ✅
nginx.conf.tmpl     ❌ (convention différente)
nginx.conf          ❌ (ambigu)
```

L'extension `.tftpl` est reconnue par les éditeurs pour la coloration syntaxique.

## 8.2 path.module

Toujours référencer les templates avec `${path.module}` :

```hcl
templatefile("${path.module}/templates/nginx.conf.tftpl", {...})
```

`path.module` désigne le dossier du fichier Terraform qui appelle `templatefile()`. Cela garantit que le chemin est correct peu importe depuis où Terraform est lancé, et surtout quand le template est utilisé **dans un module**.

## 8.3 Garder les templates lisibles

Un template doit ressembler au fichier final qu'il génère.

```text
✅  Peu de logique dans le template — la logique reste dans les variables Terraform
❌  Conditions imbriquées complexes — difficile à lire et à maintenir
```

Si le template devient trop complexe, c'est souvent le signe que la logique doit remonter côté Terraform (avec des `local`, des expressions conditionnelles, etc.).

## 8.4 templatefile() vs heredoc

Il existe deux façons de générer du contenu dynamique dans Terraform :

```hcl
# Option 1 : templatefile() — recommandée pour les fichiers longs
content = templatefile("${path.module}/templates/nginx.conf.tftpl", {...})

# Option 2 : heredoc inline — acceptable pour les contenus courts
content = <<-EOT
  Hello ${var.prenom} !
EOT
```

Pour tout fichier de plus de quelques lignes, `templatefile()` est préférable : le template est dans un fichier dédié, versionnable, et lisible séparément.

## 8.5 Pièges fréquents

| Piège                                                                            | Problème                                     |
| -------------------------------------------------------------------------------- | -------------------------------------------- |
| Oublier `${path.module}` dans le chemin                                          | Fonctionne localement, échoue dans un module |
| Utiliser `${ }` Terraform dans du contenu qui utilise aussi `${ }` (bash, nginx) | Conflit de syntaxe — échapper avec `$${ }`   |
| Passer une variable de mauvais type à la map                                     | Erreur au validate ou à l'apply              |
| Template trop complexe avec logique imbriquée                                    | Difficile à maintenir                        |

### Cas particulier : conflit avec la syntaxe `${ }` de bash ou nginx

Si le fichier généré contient des `${}` qui ne sont **pas** des placeholders Terraform (par exemple des variables bash), les échapper avec `$$` :

```text
# Dans le template .tftpl
echo "Bonjour ${prenom}"       ← remplacé par Terraform
echo "Home : $${HOME}"         ← devient $HOME dans le fichier final (variable bash)
```

# 10. Conclusion

Dans cet atelier, vous avez découvert comment `templatefile()` permet de générer du contenu dynamique à partir de fichiers templates.

Vous avez appris à :

```text
écrire un fichier .tftpl avec des placeholders ${ }
appeler templatefile() avec une map de variables
utiliser %{ if } / %{ else } / %{ endif } pour le contenu conditionnel
utiliser %{ for } / %{ endfor } pour le contenu répété
combiner les trois dans un template réaliste (nginx.conf)
utiliser ${path.module} pour des chemins portables
échapper ${ } avec $${ } en cas de conflit
```

La règle principale :

```text
templatefile() = un fichier .tftpl + une map de variables → une string générée
```

Ce résultat peut être passé à n'importe quelle ressource qui attend une string :
`local_file`, `user_data` d'une VM cloud, `content` d'un secret, argument d'un module.

Les templates deviennent particulièrement puissants combinés aux modules (atelier 17) :
un module reçoit des variables, génère sa configuration via `templatefile()`,
et produit des fichiers cohérents et reproductibles pour chaque environnement.
