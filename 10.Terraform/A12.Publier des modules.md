# Atelier 8 : Publier des Modules Terraform — HashiCorp Registry et GitLab

## 1. Introduction

## Objectif de l'atelier

Dans les ateliers précédents, les modules étaient locaux — appelés via `source = "./modules/nom"`.

En équipe ou entre projets, cette approche ne suffit plus. Un module utile doit pouvoir être **partagé, versionné et consommé depuis n'importe quel projet**.

Deux solutions principales existent :

```text
HashiCorp Registry   → registry public, accessible à tout le monde
GitLab               → registry privé, accessible à votre organisation
```

Dans cet atelier, on utilise les modules exemples du dossier `terraform-modules-practical-labs` comme base de publication.

## Ce que couvre cet atelier

```text
Étape 1 : convention de nommage et structure d'un module publiable
Étape 2 : publier sur HashiCorp Registry (public, via GitHub)
Étape 3 : publier sur GitLab au niveau projet
Étape 4 : publier sur GitLab au niveau groupe
Étape 5 : consommer un module depuis GitLab
```

# 3. Étape 1 : Convention de nommage et structure publiable

## 3.1 Convention de nommage

HashiCorp Registry et GitLab imposent tous les deux une convention :

```text
terraform-<PROVIDER>-<NOM>
```

- `PROVIDER` : le provider principal que le module configure (`aws`, `azurerm`, `google`, `local`, `null`…)
- `NOM` : nom descriptif du module

Exemples :

```text
terraform-aws-vpc
terraform-azurerm-vm
terraform-local-tags-standard     ← notre module tags_standard
terraform-local-naming-convention ← notre module naming_convention
```

> Pour nos modules qui utilisent uniquement `hashicorp/local` ou qui ne créent aucune ressource cloud, on utilise `local` ou `null` comme provider.

## 3.2 Structure attendue du dépôt

Un module publié doit avoir ses fichiers **à la racine du dépôt** :

```text
terraform-local-tags-standard/
├── main.tf          ← logique du module
├── variables.tf     ← inputs
├── outputs.tf       ← outputs
├── versions.tf      ← version Terraform requise
└── README.md        ← documentation (obligatoire pour le Registry)
```

> Le code actuellement dans `modules/tags_standard/` doit être **déplacé à la racine** du dépôt lors de la publication. Le dossier `modules/` du projet racine sert uniquement pour les appels locaux.

## 3.3 versions.tf — obligatoire pour le Registry

Créer ou vérifier le fichier **versions.tf** :

```hcl
terraform {
  required_version = ">= 1.6"
}
```

Pour un module qui utilise un provider, déclarer le provider requis :

```hcl
terraform {
  required_version = ">= 1.6"

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = ">= 2.5"
    }
  }
}
```

## 3.4 README.md — obligatoire pour le Registry

HashiCorp Registry lit le `README.md` et l'affiche sur la page du module.

Structure minimale attendue :

```markdown
# Module terraform-local-tags-standard

## Rôle

Ce module produit une map de tags standardisés.

## Utilisation

```hcl
module "tags" {
  source  = "NAMESPACE/tags-standard/local"
  version = "~> 1.0"

  project     = "mon-projet"
  environment = "production"
  owner       = "platform-team"
  cost_center = "cc-2042"
}
```

## Variables

| Nom | Type | Description |
|---|---|---|
| project | string | Nom du projet |
| environment | string | Environnement cible |
| owner | string | Responsable |
| cost_center | string | Centre de coût |
| extra_tags | map(string) | Tags additionnels |

## Outputs

| Nom | Description |
|---|---|
| tags | Map finale des tags |
```

# 4. Étape 2 : Publier sur HashiCorp Registry (public)

## 4.1 Prérequis

```text
- Un compte GitHub (https://github.com)
- Un compte Terraform Cloud (https://app.terraform.io) — gratuit
- Git installé localement
```

## 4.2 Créer le dépôt GitHub

Le nom du dépôt doit respecter la convention `terraform-<provider>-<nom>`.

Sur GitHub, créer un nouveau dépôt public nommé :

```text
terraform-local-tags-standard
```

Cloner localement et préparer le contenu :

```bash
git clone https://github.com/<votre-username>/terraform-local-tags-standard.git
cd terraform-local-tags-standard
```

Copier les fichiers du module depuis les exemples :

```bash
# Copier les fichiers du module (pas le projet racine, seulement le module lui-même)
cp <chemin-vers>/01-tags-standard/modules/tags_standard/main.tf .
cp <chemin-vers>/01-tags-standard/modules/tags_standard/variables.tf .
cp <chemin-vers>/01-tags-standard/modules/tags_standard/outputs.tf .

# Créer versions.tf
cat > versions.tf <<'EOF'
terraform {
  required_version = ">= 1.6"
}
EOF

# Créer README.md (voir section 3.4)
```

Vérifier la structure :

```bash
ls -la
# Attendu : main.tf  variables.tf  outputs.tf  versions.tf  README.md
```

## 4.3 Créer un tag de version

HashiCorp Registry utilise les **tags Git** comme versions du module.

Convention de versioning sémantique :

```text
v<MAJEUR>.<MINEUR>.<CORRECTIF>

v1.0.0   → première version stable
v1.1.0   → nouvelle fonctionnalité compatible
v1.1.1   → correctif
v2.0.0   → changement incompatible (breaking change)
```

Créer et pousser le premier tag :

```bash
# Ajouter et committer les fichiers.
git add .
git commit -m "feat: initial release tags_standard module"

# Créer un tag annoté v1.0.0.
git tag -a v1.0.0 -m "Release v1.0.0"

# Pousser le code et le tag sur GitHub.
git push origin main
git push origin v1.0.0
```

## 4.4 Connecter le dépôt au HashiCorp Registry

1. Se connecter sur [registry.terraform.io](https://registry.terraform.io)
2. Cliquer sur **Publish** → **Module**
3. Connecter le compte GitHub si ce n'est pas déjà fait
4. Sélectionner le dépôt `terraform-local-tags-standard`
5. Cliquer sur **Publish Module**

HashiCorp Registry détecte automatiquement les tags Git et les affiche comme versions.

Observation attendue :

```text
Le module est disponible à l'adresse :
registry.terraform.io/modules/<votre-username>/tags-standard/local
```

## 4.5 Utiliser le module publié

Dans n'importe quel projet Terraform :

```hcl
module "tags" {
  source  = "<votre-username>/tags-standard/local"
  version = "~> 1.0"

  project     = "mon-projet"
  environment = "production"
  owner       = "platform-team"
  cost_center = "cc-2042"
}
```

Initialiser Terraform (il télécharge automatiquement le module depuis le Registry) :

```bash
terraform init
terraform plan
```

## 4.6 Publier une nouvelle version

Modifier le module, créer un nouveau tag, pousser :

```bash
git add .
git commit -m "feat: ajouter support tags optionnels"
git tag -a v1.1.0 -m "Release v1.1.0"
git push origin main
git push origin v1.1.0
```

HashiCorp Registry détecte le nouveau tag automatiquement.

# 5. Étape 3 : Publier sur GitLab au niveau projet

## 5.1 Comment fonctionne le registry GitLab

GitLab intègre un **Terraform Module Registry** natif.

Chaque projet GitLab peut héberger un ou plusieurs modules versionnés.

La publication se fait via l'**API GitLab** ou via une **pipeline CI/CD**.

## 5.2 Prérequis

```text
- Un compte GitLab (https://gitlab.com ou instance auto-hébergée)
- Un Personal Access Token avec le scope api
- curl installé localement
```

Créer un Personal Access Token :

```text
GitLab → Settings → Access Tokens
Scopes requis : api
Conserver le token — il n'est affiché qu'une seule fois.
```

## 5.3 Créer le projet GitLab

Créer un nouveau projet GitLab nommé :

```text
terraform-local-tags-standard
```

Cloner et préparer le contenu (même structure que section 4.2) :

```bash
git clone https://gitlab.com/<votre-namespace>/terraform-local-tags-standard.git
cd terraform-local-tags-standard

# Copier les fichiers du module (main.tf, variables.tf, outputs.tf, versions.tf, README.md)
# Créer un commit et un tag
git add .
git commit -m "feat: initial release"
git tag -a v1.0.0 -m "Release v1.0.0"
git push origin main
git push origin v1.0.0
```

## 5.4 Publier le module via l'API GitLab

Récupérer l'ID du projet GitLab :

```bash
# Remplacer par votre namespace et nom de projet.
PROJECT_ID=$(curl --silent --header "PRIVATE-TOKEN: <votre-token>" \
  "https://gitlab.com/api/v4/projects/<votre-namespace>%2Fterraform-local-tags-standard" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")

echo "Project ID : $PROJECT_ID"
```

Créer une archive du module et publier :

```bash
# Créer l'archive du module.
tar -czf tags-standard-v1.0.0.tar.gz main.tf variables.tf outputs.tf versions.tf README.md

# Publier via l'API.
# Format : /projects/<id>/packages/terraform/modules/<nom>/<provider>/<version>/file
curl --header "PRIVATE-TOKEN: <votre-token>" \
     --upload-file tags-standard-v1.0.0.tar.gz \
     "https://gitlab.com/api/v4/projects/${PROJECT_ID}/packages/terraform/modules/tags-standard/local/1.0.0/file"
```

Résultat attendu :

```text
HTTP 201 Created
Le module est visible dans :
GitLab → votre-projet → Deploy → Package Registry → Terraform Modules
```

## 5.5 Utiliser le module depuis GitLab (niveau projet)

Configurer les credentials GitLab dans le fichier `~/.terraformrc` :

```hcl
credentials "gitlab.com" {
  token = "<votre-personal-access-token>"
}
```

Dans n'importe quel projet Terraform :

```hcl
module "tags" {
  source  = "gitlab.com/<votre-namespace>/tags-standard/local"
  version = "~> 1.0"

  project     = "mon-projet"
  environment = "production"
  owner       = "platform-team"
  cost_center = "cc-2042"
}
```

Initialiser :

```bash
terraform init
```

Terraform se connecte au registry GitLab avec le token et télécharge le module.

# 6. Étape 4 : Publier sur GitLab au niveau groupe

## 6.1 Différence entre projet et groupe

| Niveau | Portée | Cas d'usage |
|---|---|---|
| **Projet** | Un seul projet GitLab | Module interne à un projet |
| **Groupe** | Tous les projets du groupe | Module partagé entre équipes |

Le niveau **groupe** est celui utilisé en entreprise : un module `terraform-local-tags-standard` publié dans le groupe `infrastructure` est accessible à tous les projets sous `infrastructure/`.

## 6.2 Créer le projet dans un groupe

Créer un groupe GitLab (ou utiliser un existant) :

```text
Nom du groupe : infrastructure
```

Créer le projet `terraform-local-tags-standard` **à l'intérieur du groupe** :

```text
gitlab.com/infrastructure/terraform-local-tags-standard
```

Même préparation que la section 5.3 (clone, fichiers, commit, tag).

## 6.3 Publier au niveau groupe

Récupérer l'ID du groupe :

```bash
GROUP_ID=$(curl --silent --header "PRIVATE-TOKEN: <votre-token>" \
  "https://gitlab.com/api/v4/groups/infrastructure" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")

echo "Group ID : $GROUP_ID"
```

Publier le module dans le registry du **groupe** :

```bash
# Format : /groups/<id>/packages/terraform/modules/<nom>/<provider>/<version>/file
curl --header "PRIVATE-TOKEN: <votre-token>" \
     --upload-file tags-standard-v1.0.0.tar.gz \
     "https://gitlab.com/api/v4/groups/${GROUP_ID}/packages/terraform/modules/tags-standard/local/1.0.0/file"
```

Résultat attendu :

```text
Le module est visible dans :
GitLab → groupe infrastructure → Packages → Terraform Modules
```

## 6.4 Utiliser le module depuis le niveau groupe

```hcl
module "tags" {
  source  = "gitlab.com/infrastructure/tags-standard/local"
  version = "~> 1.0"

  project     = "mon-projet"
  environment = "production"
  owner       = "platform-team"
  cost_center = "cc-2042"
}
```

Le `~/.terraformrc` avec le token GitLab reste identique.

```bash
terraform init
```

Terraform résout le module depuis le registry du groupe `infrastructure`.

# 7. Étape 5 : Consommer un module via Git (alternative sans registry)

Si vous ne voulez pas passer par le registry GitLab, vous pouvez appeler le module directement via **Git** avec une référence de tag.

Cette approche fonctionne aussi bien au niveau projet que groupe :

```hcl
# Appel via HTTPS (token dans l'URL ou dans ~/.netrc).
module "tags" {
  source = "git::https://gitlab.com/<namespace>/terraform-local-tags-standard.git?ref=v1.0.0"

  project     = "mon-projet"
  environment = "production"
  owner       = "platform-team"
  cost_center = "cc-2042"
}
```

Avec authentification via variable d'environnement :

```bash
# Configurer Git pour passer le token automatiquement.
git config --global url."https://oauth2:<votre-token>@gitlab.com".insteadOf "https://gitlab.com"

terraform init
```

## Comparaison des méthodes de source

| Méthode | Syntaxe source | Versioning | Auth |
|---|---|---|---|
| Registry HashiCorp | `namespace/nom/provider` | `version = "~> 1.0"` | Aucune (public) |
| Registry GitLab | `gitlab.com/namespace/nom/provider` | `version = "~> 1.0"` | `~/.terraformrc` |
| Git HTTPS | `git::https://gitlab.com/...git?ref=v1.0.0` | Tag dans l'URL | `git config` ou `~/.netrc` |
| Git SSH | `git::ssh://git@gitlab.com/...git?ref=v1.0.0` | Tag dans l'URL | Clé SSH |

# 9. Bonnes pratiques

## 9.1 Versioning sémantique — règle stricte

```text
v1.0.0  → release initiale
v1.1.0  → ajout d'une variable optionnelle (non breaking)
v1.1.1  → correctif d'un output
v2.0.0  → suppression ou renommage d'une variable (breaking)
```

Ne jamais modifier un tag existant. Créer toujours un nouveau tag.

## 9.2 CHANGELOG.md

Tenir un fichier `CHANGELOG.md` dans chaque dépôt de module :

```markdown
## [1.1.0] - 2024-06-01
### Ajouté
- Variable `extra_tags` pour enrichir les tags standards.

## [1.0.0] - 2024-05-01
### Initial
- Publication initiale du module tags_standard.
```

## 9.3 Tests avant publication

Avant de créer un tag :

```bash
# Depuis le dossier du module.
terraform init
terraform fmt
terraform validate

# Tester avec un projet racine de test.
```

## 9.4 Pièges fréquents

| Piège | Conséquence |
|---|---|
| Nom de dépôt ne respectant pas `terraform-<provider>-<nom>` | Rejeté par le Registry HashiCorp |
| Modifier un tag Git existant | Brise les projets qui fixent cette version |
| Oublier `versions.tf` | Avertissement ou rejet selon le registry |
| Ne pas documenter les breaking changes | Casse les projets consommateurs |
| Mettre des secrets dans le module | Exposition dans le registry public |

# 10. Conclusion

Dans cet atelier, vous avez appris à passer d'un module local à un module partagé et versionné.

```text
Module local         →  source = "./modules/nom"
Registry HashiCorp   →  source = "namespace/nom/provider"    + version
Registry GitLab      →  source = "gitlab.com/ns/nom/provider" + version
Git HTTPS            →  source = "git::https://...git?ref=v1.0.0"
```

La progression naturelle en organisation :

```text
1. Module local dans ./modules/     → apprentissage
2. Module Git avec ref=tag          → partage simple sans registry
3. Module dans registry GitLab      → partage organisé au sein de l'équipe
4. Module dans HashiCorp Registry   → partage public avec la communauté
```

Les modules exemples de `terraform-modules-practical-labs` constituent une base prête à publier : ils sont documentés, validés et structurés selon les conventions attendues par les deux registries.
