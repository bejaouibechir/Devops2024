# Solution 7 — Génération, transfert et exécution d'un script

[Énoncé](../7.Exercice%207.md) · [Préparation SSH commune](../readme.md#prérequis-ssh-pour-les-exercices-6-à-8)

## 1. Configuration complète

La VM doit avoir Bash et un `/tmp` accessible au compte dédié. Le script et son rapport sont créés dans le même job.

```yaml
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "web" && $CI_COMMIT_REF_PROTECTED == "true"'
    # Exclut ce pipeline ou ce job lorsque cette règle est retenue.
    - when: never

# Applique ces réglages aux jobs qui ne les redéfinissent pas.
default:
  # Choisit l'image utilisée par l'exécuteur compatible ; un exécuteur Shell ne la lance pas.
  image: alpine:3.22

# Déclare le job « script_distant » et sa configuration propre.
script_distant:
  # Limite la durée du job ; ne crée ni attente ni nouvelle tentative.
  timeout: 5 minutes
  # Prépare le job avant ses commandes principales, dans le même contexte de shell.
  before_script:
    # Installe les outils requis dans l'environnement d'exécution du job.
    - apk add --no-cache openssh-client
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Interrompt le script si cette configuration obligatoire est absente ou vide.
      : "${SSH_HOST:?Configurer SSH_HOST}"
      : "${SSH_USER:?Configurer SSH_USER}"
      : "${SSH_PRIVATE_KEY:?Configurer la variable File SSH_PRIVATE_KEY}"
      : "${SSH_KNOWN_HOSTS:?Configurer la variable File SSH_KNOWN_HOSTS}"
      # Exige un fichier existant et non vide avant de l'utiliser.
      test -s "$SSH_PRIVATE_KEY"
      test -s "$SSH_KNOWN_HOSTS"
      # Applique les permissions indiquées au fichier ou au répertoire avant son utilisation.
      chmod 600 "$SSH_PRIVATE_KEY"
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Écrit le script sans substitution locale grâce au délimiteur cité ; ses commandes s'exécuteront plus tard.
      cat > infos.sh <<'SCRIPT'
      #!/usr/bin/env bash
      set -euo pipefail
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Date : %s\n' "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"
      # Évalue whoami sur la machine d'exécution puis affiche le compte courant.
      printf 'Utilisateur : %s\n' "$(whoami)"
      # Évalue hostname sur la machine d'exécution puis affiche le nom de la machine.
      printf 'Machine : %s\n' "$(hostname)"
      SCRIPT

      # Sélectionne le cas correspondant à la valeur ; la branche de repli traite les valeurs non prévues.
      case "$CI_PROJECT_ID:$CI_JOB_ID" in
        *[!0-9:]*|:*)
          # Écrit le diagnostic sur la sortie d'erreur pour distinguer l'erreur des résultats normaux.
          echo "Identifiants CI inattendus" >&2
          # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
          exit 1
          ;;
      esac
      # Prépare une valeur locale au shell ; elle ne devient pas automatiquement disponible dans un autre job.
      remote_dir="/tmp/gitlab-ci-${CI_PROJECT_ID}-${CI_JOB_ID}"

      # Centralise les options SSH pour appliquer la même identité et le même contrôle d'hôte à chaque appel.
      ssh_ci() {
        # Exécute les commandes sur la VM ; les options SSH ci-dessous règlent la clé, le port et la vérification d'hôte.
        ssh -T \
          -i "$SSH_PRIVATE_KEY" \
          -p "${SSH_PORT:-22}" \
          -o BatchMode=yes \
          -o IdentitiesOnly=yes \
          -o StrictHostKeyChecking=yes \
          -o "UserKnownHostsFile=$SSH_KNOWN_HOSTS" \
          -o ConnectTimeout=10 \
          "${SSH_USER}@${SSH_HOST}" "$@"
      }

      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Repertoire temporaire distant : %s\n' "$remote_dir"
      # Crée sur la VM le répertoire propre à cette exécution ; un dossier existant doit faire échouer cet appel.
      ssh_ci "umask 077; mkdir '$remote_dir'"

      # Transfère le fichier vers la VM ; -P désigne le port SSH pour scp.
      scp -i "$SSH_PRIVATE_KEY" \
        -P "${SSH_PORT:-22}" \
        -o BatchMode=yes \
        -o IdentitiesOnly=yes \
        -o StrictHostKeyChecking=yes \
        -o "UserKnownHostsFile=$SSH_KNOWN_HOSTS" \
        -o ConnectTimeout=10 \
        infos.sh "${SSH_USER}@${SSH_HOST}:${remote_dir}/infos.sh"

      # Rend le script distant exécutable, puis le lance sur la VM et conserve son code de retour.
      ssh_ci "chmod 700 '$remote_dir/infos.sh' && '$remote_dir/infos.sh'" \
        > execution-distante.log
      # Affiche le contenu ou la liste des fichiers pour vérifier le résultat de l'étape précédente.
      cat execution-distante.log
      # Supprime sur la VM uniquement le fichier de cette tentative, puis son répertoire devenu vide.
      ssh_ci "rm -- '$remote_dir/infos.sh' && rmdir -- '$remote_dir'"
  # Conserve les fichiers ou rapports du job pour consultation ou transmission.
  artifacts:
    # Définit selon quel résultat du job les artefacts seront collectés.
    when: always
    # Sélectionne les fichiers du workspace à publier comme artefacts.
    paths:
      - infos.sh
      - execution-distante.log
    # Fixe la durée de conservation demandée pour ces artefacts.
    expire_in: 1 day
```

## 2. Pourquoi le script affiche-t-il la VM ?

Le délimiteur `<<'SCRIPT'` est cité : le shell du runner ne remplace pas les expressions `$(...)`. Elles restent dans le fichier et sont évaluées lorsque le serveur lance le script.

La fonction `ssh_ci` regroupe les mêmes options pour toutes les commandes distantes. SCP utilise `-P` pour le port, tandis que SSH utilise `-p`. [Manuel SCP](https://man.openbsd.org/scp)

Le répertoire est dérivé des identifiants numériques CI. `mkdir` échoue si ce chemin existe déjà ; l'exemple ne réutilise pas silencieusement un répertoire préexistant.

## 3. Artefacts et statut d'erreur

La sortie est redirigée vers un rapport, puis affichée. Aucun pipe vers `tee` ne risque de masquer le statut de SSH.

`artifacts:when:always` permet de récupérer les fichiers créés même après un échec ordinaire. Si l'erreur survient avant leur création, GitLab peut signaler leur absence ; ce n'est pas la cause initiale à corriger.

La liste de chemins exclut la clé et le fichier des hôtes connus. [Artefacts de jobs](https://docs.gitlab.com/ci/jobs/job_artifacts/)

## 4. Nettoyage et échec volontaire

Après un succès, seul le script créé par cet atelier est retiré, puis son dossier vide est supprimé avec `rmdir`.

Si le transfert ou le script échoue, le job conserve l'échec et peut laisser le répertoire distant. Son chemin exact figure dans les logs. Inspectez-le avant nettoyage manuel ; ne supprimez pas globalement les répertoires `/tmp/gitlab-ci-*`.

Ajoutez temporairement `false` dans le script généré, avant la dernière ligne. Le job doit échouer et le rapport peut ne contenir que les premières sorties.
