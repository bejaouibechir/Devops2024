# Atelier 4 : Flux Conditionnels dans Terraform

## 1. Introduction

## Pourquoi utiliser des conditions ?

Dans les ateliers précédents, les ressources étaient créées de manière fixe.

Exemple :

```hcl
resource "local_file" "report" {
  filename = "report.txt"
  content  = "Rapport Terraform"
}
```

Mais dans un vrai projet, on veut souvent adapter le comportement selon un contexte :

```text
Si environment = dev       → créer un rapport simple
Si environment = prod      → créer un rapport plus strict
Si enable_debug = true      → créer un fichier debug
Si create_extra_files = true → créer des fichiers supplémentaires
```

Terraform propose plusieurs façons d’exprimer ces conditions :

```text
Opérateur ternaire
count conditionnel
for_each conditionnel
expressions for avec if
locals conditionnels
dynamic conditionnel
```

## Objectifs de l’atelier

À la fin de cet atelier, vous saurez :

```text
utiliser l’opérateur ternaire
créer une ressource conditionnellement avec count
créer plusieurs ressources conditionnellement avec for_each
filtrer une collection avec for
centraliser des décisions dans locals
comprendre la limite de dynamic avec le provider Local
éviter les pièges fréquents des conditions
```

## Prérequis

Avoir terminé :

```text
Atelier 1 : HCL
Atelier 2 : Variables
Atelier 3 : Répétition
```

## Contrainte de l’atelier

On utilise uniquement le provider **Local** :

```text
hashicorp/local
```

Cela permet de travailler sans compte cloud, sans clé API et sans authentification.

# 3. Étape 1 : L’opérateur ternaire

## 3.1 Objectif

Utiliser une condition pour choisir une valeur.

La forme générale est :

```hcl
condition ? valeur_si_vrai : valeur_si_faux
```

Exemple :

```hcl
var.environment == "prod" ? "production" : "non-production"
```

Cette expression signifie :

```text
Si environment vaut prod, retourner production.
Sinon, retourner non-production.
```

---

## 3.2 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Environnement cible.
# Valeurs autorisées : dev, test, prod.
variable "environment" {
  type        = string
  description = "Environnement cible : dev, test ou prod."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment doit être dev, test ou prod."
  }
}

# Active ou désactive le mode debug.
variable "enable_debug" {
  type        = bool
  description = "Active ou désactive le mode debug."
  default     = false
}
```

---

## 3.3 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# Crée un rapport dont le contenu dépend de conditions.
resource "local_file" "environment_report" {
  filename = "environment-report.txt"

  content = <<EOT
Rapport environnement

Environnement : ${var.environment}

Type d’environnement :
${var.environment == "prod" ? "production" : "non-production"}

Niveau de sécurité :
${var.environment == "prod" ? "strict" : "standard"}

Mode debug :
${var.enable_debug ? "activé" : "désactivé"}
EOT
}
```

---

## 3.10 Points clés

**Ternaire** : permet de choisir entre deux valeurs.

**Condition booléenne** : expression qui retourne **true** ou **false**.

**var.enable_debug** peut être utilisé directement comme condition.

---

## 3.11 Astuces

Pour une condition simple, l’opérateur ternaire est très lisible.

Exemple :

```hcl
var.enable_debug ? "debug activé" : "debug désactivé"
```

Pour une condition longue, il vaut mieux utiliser **locals** plus tard dans l’atelier.

---

## 3.12 Attention

Les deux branches du ternaire doivent produire des valeurs compatibles.

Correct :

```hcl
var.environment == "prod" ? "strict" : "standard"
```

À éviter :

```hcl
var.environment == "prod" ? "strict" : 3
```

# 4. Étape 2 : Conditions avec count

## 4.1 Objectif

Créer ou ne pas créer une ressource selon une condition.

Le mécanisme **count** accepte un nombre entier. Il peut donc être utilisé avec une condition qui retourne :

```text
1 → créer la ressource
0 → ne pas créer la ressource
```

Terraform précise que **count** permet de créer plusieurs instances d’une ressource avec un entier, chaque instance ayant son propre objet d’infrastructure associé. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/meta-arguments/count?utm_source=chatgpt.com "count meta-argument reference | Terraform"))

```hcl
Application : ${var.app_name}

EOT
}
```

## 5.3 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Liste des environnements possibles.
variable "environments" {
  type        = list(string)
  description = "Liste des environnements disponibles."
  default     = ["dev", "test", "prod"]
}

# Environnements pour lesquels on veut générer un fichier.
variable "enabled_environments" {
  type        = list(string)
  description = "Environnements activés pour la génération de fichiers."
  default     = ["dev", "prod"]
}
```

---

## 5.4 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# for_each utilise une liste filtrée.
# Seuls les environnements présents dans enabled_environments sont conservés.
resource "local_file" "environment_report" {
  for_each = toset([
    for env in var.environments :
    env if contains(var.enabled_environments, env)
  ])

  filename = "env-${each.key}.txt"

  content = <<EOT
Rapport environnement

Environnement : ${each.value}
Statut : activé
Adresse Terraform : local_file.environment_report["${each.key}"]
EOT
}
```

## 5.11 Points clés

**for_each** est très adapté aux ressources identifiées par un nom.

La condition est souvent appliquée avant **for_each** avec une expression **for** filtrante.

Forme utilisée :

```hcl
for_each = toset([
  for env in var.environments :
  env if contains(var.enabled_environments, env)
])
```

---

## 5.12 Attention

Avec **for_each**, les clés doivent être connues avant **apply**.

Il ne faut pas baser les clés de **for_each** sur des valeurs calculées seulement après création.

# 6. Étape 4 : Blocs dynamic conditionnels

## 6.1 Objectif

Comprendre ce que permet **dynamic**, et surtout ce qu’il ne permet pas avec le provider **Local**.

Un bloc **dynamic** construit automatiquement des blocs imbriqués répétables. Il est utile quand un provider définit une ressource avec des sous-blocs comme **rule**, **setting**, **ingress**, **egress**, **disk** ou autres blocs imbriqués. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/expressions/dynamic-blocks?utm_source=chatgpt.com "Dynamic Blocks - Configuration Language | Terraform"))

---

## 6.2 Limite avec le provider Local

Le provider **Local** sert principalement à créer des fichiers.

La ressource **local_file** utilise des arguments comme :

```text
filename
content
file_permission
directory_permission
```

Elle ne possède pas de sous-bloc répétable comme :

```text
rule {}
setting {}
section {}
```

Donc on ne peut pas faire un vrai exemple exécutable de **dynamic** avec **local_file**.

---

## 6.3 Exemple à ne pas faire

Le code suivant est volontairement incorrect :

```hcl
resource "local_file" "bad_dynamic" {
  filename = "bad.txt"

  dynamic "content" {
    for_each = ["ligne 1", "ligne 2"]

    content {
      value = content.value
    }
  }
}
```

Pourquoi c’est incorrect ?

**content** dans **local_file** est un argument.

**dynamic** sert à générer des blocs imbriqués, pas des arguments.

---

## 6.4 Bonne alternative avec le provider Local

Avec le provider **Local**, pour générer un contenu conditionnel et répétitif, on utilise :

```text
for
join
condition ternaire
if dans une expression for
```

## 6.12 Forme conceptuelle d’un dynamic conditionnel

Cette syntaxe devient utile avec un provider qui expose un vrai bloc imbriqué répétable :

```hcl
dynamic "rule" {
  for_each = var.enable_rules ? var.rules : []

  content {
    name  = rule.value.name
    value = rule.value.value
  }
}
```

Lecture :

```text
Si enable_rules = true  → générer les blocs rule
Si enable_rules = false → générer zéro bloc
```

## 6.14 Points clés

**dynamic** génère des blocs imbriqués.

**dynamic** ne génère pas des arguments.

Avec **local_file**, il faut utiliser **for** pour construire le contenu.

## 6.15 Attention

Ne pas utiliser **dynamic** uniquement pour rendre le code plus compliqué.

Si une expression **for** suffit, elle est souvent plus lisible.

# 7. Étape 5 : Conditions avancées dans locals

## 7.1 Objectif

Centraliser les décisions conditionnelles dans un bloc **locals**.

Quand les conditions deviennent nombreuses, les écrire directement dans chaque ressource rend le code difficile à lire.

Les **locals** permettent de calculer des valeurs intermédiaires réutilisables.

---

## 7.2 Nettoyer l’étape précédente

```bash
# Supprime les ressources suivies.
terraform destroy -auto-approve

# Supprime les fichiers générés.
rm -f *.txt
```

---

## 7.3 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Environnement cible.
variable "environment" {
  type        = string
  description = "Environnement cible."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment doit être dev, test ou prod."
  }
}

# Active ou désactive le debug.
variable "enable_debug" {
  type        = bool
  description = "Active le mode debug."
  default     = false
}

# Liste des services possibles.
variable "services" {
  type        = list(string)
  description = "Liste des services."
  default     = ["api", "web", "worker"]
}
```

---

## 7.4 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# locals centralise les décisions conditionnelles.
locals {
  # Détermine si l'environnement est production.
  is_prod = var.environment == "prod"

  # Définit le niveau de sécurité selon l'environnement.
  security_level = local.is_prod ? "strict" : "standard"

  # Le debug effectif est interdit en production.
  effective_debug = local.is_prod ? false : var.enable_debug

  # En production, seuls api et web sont documentés.
  # Dans les autres environnements, tous les services sont documentés.
  enabled_services = local.is_prod ? ["api", "web"] : var.services

  # Nom du fichier final.
  report_filename = "final-${var.environment}.txt"
}

# Rapport global.
resource "local_file" "final_report" {
  filename = local.report_filename

  content = <<EOT
Rapport final

Environnement : ${var.environment}
Production : ${local.is_prod}
Niveau de sécurité : ${local.security_level}
Debug demandé : ${var.enable_debug}
Debug effectif : ${local.effective_debug}

Services documentés :
${join(", ", local.enabled_services)}
EOT
}

# Fichiers par service activé.
resource "local_file" "service_report" {
  for_each = toset(local.enabled_services)

  filename = "service-${each.key}.txt"

  content = <<EOT
Rapport service

Service : ${each.key}
Environnement : ${var.environment}
Niveau de sécurité : ${local.security_level}
EOT
}
```

## 7.5 Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Résumé structuré de la décision.
output "decision_summary" {
  value = {
    environment      = var.environment
    is_prod          = local.is_prod
    security_level   = local.security_level
    debug_requested  = var.enable_debug
    effective_debug  = local.effective_debug
    enabled_services = local.enabled_services
    report_file      = local.report_filename
  }
}

# Fichiers de services créés.
output "service_files" {
  value = {
    for service, file in local_file.service_report :
    service => file.filename
  }
}
```

## 7.7 Exécuter en dev

```bash
# Reformate.
terraform fmt

# Valide.
terraform validate

# Prévisualise.
terraform plan

# Applique.
terraform apply -auto-approve

ls -l *.txt
```


## 7.8 Tester en prod

Modifier **terraform.tfvars** :

```hcl
environment  = "prod"
enable_debug = true
services     = ["api", "web", "worker"]
```

Puis exécuter :

```bash
# Terraform prévoit les changements liés au passage en prod.
terraform plan

# Applique.
terraform apply -auto-approve

# Vérifie le rapport global.
cat final-prod.txt

# Vérifie les services documentés.
ls -l service-*.txt

# Affiche les outputs.
terraform output
```

Résultat attendu :

```text
Debug demandé : true
Debug effectif : false
Services documentés : api, web
```

Fichiers attendus :

```text
service-api.txt
service-web.txt
```

Le fichier **service-worker.txt** est supprimé, car **worker** n’est plus dans **local.enabled_services** en production.

## 7.10 Points clés

**locals** permet de centraliser les décisions.

Une condition écrite une seule fois est plus facile à maintenir.

Les ressources utilisent ensuite les valeurs calculées :

```hcl
local.security_level
local.effective_debug
local.enabled_services
```

---

## 7.11 Astuces

Utiliser **locals** quand :

```text
la même condition revient plusieurs fois
une condition devient longue
une décision doit être réutilisée dans plusieurs ressources
```

---

## 7.12 Attention

**locals** ne sont pas des variables d’entrée.

Ils ne se passent pas avec **-var**.

Ils sont calculés à partir du code et des variables.

# 8. Comparaison et bonnes pratiques

## 8.1 Tableau récapitulatif

| Mécanisme                 | Sert à                                | Exemple                              |
| ------------------------- | ------------------------------------- | ------------------------------------ |
| **Ternaire**              | Choisir une valeur                    | prod ? strict : standard             |
| **count conditionnel**    | Créer zéro ou une ressource           | create ? 1 : 0                       |
| **for_each conditionnel** | Créer plusieurs ressources filtrées   | for item in list : item if condition |
| **for avec if**           | Transformer et filtrer une collection | garder seulement les éléments actifs |
| **locals**                | Centraliser les décisions             | local.security_level                 |
| **dynamic**               | Générer des blocs imbriqués           | rule, setting, ingress               |

---

## 8.2 Bonnes pratiques

| Situation                                            | Recommandation                |
| ---------------------------------------------------- | ----------------------------- |
| Choix simple de texte                                | **Ternaire**                  |
| Création optionnelle d’une seule ressource           | **count = condition ? 1 : 0** |
| Création optionnelle de plusieurs ressources nommées | **for_each** avec filtrage    |
| Transformation de liste ou map                       | **for**                       |
| Condition utilisée plusieurs fois                    | **locals**                    |
| Blocs imbriqués répétables                           | **dynamic**                   |

---

## 8.3 Pièges fréquents

| Piège                                            | Problème                  |
| ------------------------------------------------ | ------------------------- |
| Utiliser **count** pour des ressources nommées   | Index instables           |
| Accéder à **resource[0]** quand count vaut 0     | Erreur                    |
| Utiliser **dynamic** pour un argument            | Incorrect                 |
| Mettre toutes les conditions dans les ressources | Code difficile à lire     |
| Faire des ternaires trop longs                   | Code peu lisible          |
| Oublier de filtrer avant for_each                | Ressources créées en trop |
