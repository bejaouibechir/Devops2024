# Créer une action composite

## Objectif

Transformer plusieurs étapes répétées en une action locale avec un contrat d'entrée et de sortie.

## 1. Particularité GitHub

Une action composite regroupe des étapes et reste exécutée dans le job appelant. Elle ne choisit pas son propre runner et ne crée pas un graphe de jobs. Pour cela, utiliser un [workflow réutilisable](11.workflows%20reutilisables.md).

GitLab propose des composants/templates, mais n'interprète pas ce format `action.yml` avec `runs.using: composite`. [Actions composites](https://docs.github.com/en/actions/tutorials/create-actions/create-a-composite-action)

## 2. Créer le fichier de métadonnées

Dans le dépôt de l'atelier, créez `.github/actions/build-version/action.yml` :

```yaml
name: Calculer une version
description: Produit une version simple et la transmet au workflow
# Déclare les paramètres attendus ; leur type et leurs contraintes définissent le contrat.
inputs:
  # Définit le paramètre « prefix » et les contraintes de sa valeur.
  prefix:
    description: Prefixe numerique de la version
    required: true
    # Fournit la valeur utilisée si cet input n'est pas renseigné.
    default: '1.0'
# Expose les valeurs produites pour les étapes, jobs ou workflows consommateurs selon cette portée.
outputs:
  version:
    description: Version calculee
    value: ${{ steps.compute.outputs.version }}
# Décrit comment le runner exécute cette action réutilisable.
runs:
  # Choisit le type d'action et, pour JavaScript, son runtime Node.
  using: composite
  # Exécute les étapes de ce job dans l'ordre sur le même runner.
  steps:
    - id: compute
      # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
      shell: bash
      # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
      env:
        PREFIX: ${{ inputs.prefix }}
      # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
      run: |
        # Contrôle le format ou le contenu attendu avant d'utiliser cette donnée.
        if [[ ! "$PREFIX" =~ ^[0-9]+\.[0-9]+$ ]]; then
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          echo "Prefixe attendu : deux nombres separes par un point"
          # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
          exit 1
        fi
        # Publie une sortie d'étape ; son exposition au niveau du job permet ensuite un échange via needs.
        echo "version=$PREFIX.$GITHUB_RUN_NUMBER" >> "$GITHUB_OUTPUT"
```

Les inputs d'une composite sont lus explicitement via `inputs`. Déclarez `shell` pour ses étapes `run`. L'action valide son préfixe et ne laisse pas une saisie devenir du code shell.

## 3. Appeler l'action

Fichier `.github/workflows/composite.yml` :

```yaml
name: Tester une action composite
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions:
  # Autorise l'accès au contenu du dépôt selon le niveau indiqué.
  contents: read
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « demo » ; needs permet de préciser ses dépendances.
  demo:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Récupère les fichiers du dépôt dans le workspace du runner.
      - uses: actions/checkout@v7
        # Fournit les paramètres attendus par l'action ou le workflow appelé.
        with:
          # Choisit si checkout conserve l'authentification Git pour les commandes suivantes.
          persist-credentials: false
      - id: version
        # Appelle une action locale ; ses fichiers doivent déjà être présents après checkout.
        uses: ./.github/actions/build-version
        # Fournit les paramètres attendus par l'action ou le workflow appelé.
        with:
          prefix: '2.5'
      # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
      - env:
          VERSION: ${{ steps.version.outputs.version }}
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Version produite : %s\n' "$VERSION"
```

**Résultat attendu :** une version `2.5.N`, où N est le numéro du workflow.

Le contrat suit ce chemin : output de l'étape interne → output de l'action → output de l'étape appelante.

## 4. Faire évoluer l'action

Si l'action contient un script dans son propre dossier, utilisez `github.action_path` pour le localiser, plutôt que de présumer que le dossier courant est celui de l'action.

Ne comptez pas sur un accès implicite au contexte `secrets` dans la composite. Passez explicitement la donnée nécessaire depuis le workflow, avec un input ou une variable d'environnement appropriée, et ne l'affichez pas. [Contextes d'actions](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)

Pour la distribuer dans un autre dépôt, publiez son code et appelez une référence vérifiée. Un dépôt d'action peut rester privé si les règles de partage et d'accès l'autorisent.

## 5. Choisir le bon format

| Besoin | Format |
| --- | --- |
| Assembler des commandes/actions existantes | Composite |
| Implémenter une logique Node réutilisable | [Action JavaScript](21.actions%20javascript.md) |
| Livrer un environnement d'outils Linux | [Action Docker](22.actions%20docker.md) |
| Réutiliser plusieurs jobs et leurs permissions | Workflow réutilisable |
