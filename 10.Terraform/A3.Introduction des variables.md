## Objectif général

Dans l’Atelier 1, les valeurs étaient écrites directement dans le fichier **main.tf**.

Exemple :


# 3. Point de départ — Variables déclarées directement dans main.tf

## Objectif

Avant d'introduire `variables.tf`, il est important de savoir que les blocs `variable` peuvent être déclarés n'importe où dans le projet Terraform, y compris directement dans `main.tf`. Il n'existe aucune obligation d'avoir un fichier séparé.

## Pourquoi commencer par là ?

Terraform charge tous les fichiers `.tf` du dossier courant sans distinction de nom. Le nom `variables.tf` est une **convention**, pas une règle technique. Un seul fichier `main.tf` contenant à la fois les variables, les ressources et les outputs est parfaitement valide.

## Exemple — Tout dans main.tf

Créer le fichier **main.tf** :

```hcl
# Déclaration du provider.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Variable déclarée directement dans main.tf.
# Aucun fichier variables.tf n'est nécessaire.
variable "file_name" {
  type        = string
  description = "Nom du fichier local à créer."
  default     = "rapport-inline.txt"
}

variable "line_count" {
  type        = number
  description = "Nombre de lignes annoncé dans le rapport."
  default     = 3
}

variable "detailed_mode" {
  type        = bool
  description = "Active ou désactive le mode détaillé."
  default     = false
}

# Ressource qui utilise les variables déclarées ci-dessus.
resource "local_file" "rapport" {
  filename = var.file_name

  content = <<EOT
Rapport Terraform (variables inline)

Nom du fichier  : ${var.file_name}
Nombre de lignes: ${var.line_count}
Mode détaillé   : ${var.detailed_mode}
EOT
}

output "fichier_cree" {
  value = local_file.rapport.filename
}
```

## Commandes à exécuter

```bash
terraform init
terraform validate
terraform apply -auto-approve
cat rapport-inline.txt
```

Résultat attendu :

```text
Rapport Terraform (variables inline)

Nom du fichier  : rapport-inline.txt
Nombre de lignes: 3
Mode détaillé   : false
```

## Passer une valeur différente sans modifier main.tf

```bash
terraform apply -auto-approve -var="file_name=mon-fichier.txt" -var="line_count=10"
cat mon-fichier.txt
```

## Quand séparer dans variables.tf ?

Garder les variables dans `main.tf` convient pour un projet simple avec peu de variables. Dès que le projet grossit, la convention est de les déplacer dans `variables.tf` pour :

```text
main.tf        → ressources et outputs uniquement
variables.tf   → déclarations de variables
terraform.tfvars → valeurs des variables
```

C'est ce que les sections suivantes vont mettre en place.

## Nettoyage obligatoire avant la section suivante

Trois actions sont nécessaires dans cet ordre précis avant de passer à la section 4.

### 1 — Détruire les ressources créées

```bash
terraform destroy -auto-approve
```

Résultat attendu :

```text
Destroy complete! Resources: 1 destroyed.
```

Ne pas sauter cette étape. Si on modifie `main.tf` sans détruire d'abord, Terraform perd la trace de la ressource et le fichier local reste sur le disque sans être géré.

### 2 — Supprimer les fichiers locaux créés pendant la section 3

```bash
rm -f rapport-inline.txt mon-fichier.txt
```

### 3 — Retirer les blocs `variable` de main.tf

La section 4 crée un fichier `variables.tf` avec les mêmes noms (`file_name`, `line_count`, `detailed_mode`). Si les blocs `variable` restent dans `main.tf`, Terraform refuse de s'initialiser :

```text
Error: Duplicate variable declaration
```

Remplacer le contenu de `main.tf` par cette version épurée :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

resource "local_file" "rapport" {
  filename = var.file_name

  content = <<EOT
Rapport Terraform

Nom du fichier  : ${var.file_name}
Nombre de lignes: ${var.line_count}
Mode détaillé   : ${var.detailed_mode}
EOT
}

output "fichier_cree" {
  value = local_file.rapport.filename
}
```

Les blocs `variable` ont disparu de `main.tf`. La section 4 les déclarera dans `variables.tf`.

# 4. Étape 1 : Variables simples string, number, bool

## Objectif

Découvrir les types de base :

**string** : texte  
**number** : nombre  
**bool** : true ou false

Terraform distingue les types primitifs **string**, **number** et **bool**. Le type **string** représente du texte, **number** représente une valeur numérique et **bool** représente **true** ou **false**. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/expressions/type-constraints "Type Constraints - Configuration Language | Terraform | HashiCorp Developer"))

## Scénario

On veut créer un fichier local dont :

**le nom** vient d’une variable string,  
**le nombre de lignes simulé** vient d’une variable number,  
**l’activation du message détaillé** vient d’une variable bool.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Variable de type string.
# Elle contient le nom du fichier à créer.
variable "file_name" {
  type        = string
  description = "Nom du fichier local à créer."
  default     = "rapport-base.txt"
}

# Variable de type number.
# Elle simule un nombre de lignes dans le rapport.
variable "line_count" {
  type        = number
  description = "Nombre de lignes annoncé dans le rapport."
  default     = 5
}

# Variable de type bool.
# Elle active ou désactive un message détaillé.
variable "detailed_mode" {
  type        = bool
  description = "Active ou désactive le mode détaillé."
  default     = true
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# Crée un fichier local en utilisant des variables simples.
resource "local_file" "basic_report" {
  filename = var.file_name

  content = <<EOT
Rapport Terraform

Nom du fichier : ${var.file_name}
Nombre de lignes annoncé : ${var.line_count}
Mode détaillé activé : ${var.detailed_mode}
EOT
}

# Affiche le nom du fichier créé.
output "created_file" {
  value = local_file.basic_report.filename
}
```

## Commandes à exécuter

Exécuter dans **~/terraform-variables-local** :

```bash
# Initialise le projet et télécharge le provider Local.
terraform init

# Reformate les fichiers Terraform.
terraform fmt

# Vérifie la configuration.
terraform validate

# Affiche ce que Terraform prévoit de créer.
terraform plan

# Crée le fichier local.
terraform apply -auto-approve
```

## Observer le résultat

```bash
# Affiche le fichier créé.
cat rapport-base.txt

# Liste les ressources suivies.
terraform state list

# Affiche les outputs.
terraform output
```

Résultat attendu dans le fichier :

```text
Rapport Terraform

Nom du fichier : rapport-base.txt
Nombre de lignes annoncé : 5
Mode détaillé activé : true
```

## Questions et réponses

**Pourquoi `file_name` est-il de type `string` ?**
Parce qu’un nom de fichier est du texte. Déclarer `type = string` interdit de passer accidentellement un nombre ou un booléen, Terraform rejettera la valeur avec une erreur de type.

**Pourquoi `line_count` est-il de type `number` ?**
Parce qu’on a besoin d’une valeur numérique pour faire des calculs ou des comparaisons. Une `string` comme `"5"` ne peut pas être utilisée dans une expression arithmétique sans conversion.

**Pourquoi `detailed_mode` est-il de type `bool` ?**
Parce que cette variable représente un choix binaire : activé ou désactivé. Le type `bool` force la valeur à être `true` ou `false`, pas `"oui"` ou `"1"`.

**Où les variables sont-elles définies ?**
Dans `variables.tf` (ou directement dans `main.tf` comme montré en section 3). Le bloc `variable` déclare le nom, le type, la description et la valeur par défaut.

**Où les variables sont-elles utilisées ?**
Dans `main.tf`, via la syntaxe `var.nom_variable`. Exemple : `filename = var.file_name`. Terraform remplace `var.file_name` par la valeur effective au moment du `plan` et de l’`apply`.

## Points clés

**variable** déclare une entrée configurable.

**type** impose le type attendu.

**default** fournit une valeur si aucune autre valeur n’est donnée.

**var.file_name** permet d’utiliser la variable dans **main.tf**.

# 5. Étape 2 : Types complexes list, map, object

## Objectif

Découvrir les types complexes :

**list** : liste ordonnée de valeurs  
**map** : ensemble de paires clé-valeur  
**object** : structure composée de plusieurs champs nommés

Terraform classe **list**, **map** et **object** parmi les types complexes. Une **list** regroupe plusieurs valeurs du même type, une **map** associe des valeurs à des clés texte, et un **object** regroupe des attributs nommés avec leurs propres types. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/expressions/type-constraints "Type Constraints - Configuration Language | Terraform | HashiCorp Developer"))

## Scénario

On veut générer un fichier de description de projet.

Le fichier contiendra :

**une liste de technologies**,  
**une map de tags**,  
**un objet décrivant l’application**.

---

## Remplacer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Liste de technologies utilisées dans le projet.
variable "technologies" {
  type        = list(string)
  description = "Liste des technologies utilisées."
  default     = ["Terraform", "HCL", "Provider Local"]
}

# Map de tags.
# Chaque clé représente le nom du tag.
# Chaque valeur représente le contenu du tag.
variable "project_tags" {
  type        = map(string)
  description = "Tags descriptifs du projet."
  default = {
    environment = "dev"
    owner       = "training"
    managed_by  = "terraform"
  }
}

# Objet décrivant l'application.
# Chaque attribut possède son propre type.
variable "app_config" {
  type = object({
    name        = string
    version     = number
    enabled     = bool
    description = string
  })

  description = "Configuration principale de l'application."

  default = {
    name        = "demo-hcl"
    version     = 1
    enabled     = true
    description = "Application de démonstration pour les variables Terraform."
  }
}
```

## Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# Crée un fichier local à partir de types complexes.
resource "local_file" "complex_report" {
  filename = "rapport-types-complexes.txt"

  content = <<EOT
Rapport sur les types complexes Terraform

Application
-----------
Nom : ${var.app_config.name}
Version : ${var.app_config.version}
Active : ${var.app_config.enabled}
Description : ${var.app_config.description}

Technologies
------------
Première technologie : ${var.technologies[0]}
Deuxième technologie : ${var.technologies[1]}
Troisième technologie : ${var.technologies[2]}

Tags
----
Environnement : ${var.project_tags["environment"]}
Responsable : ${var.project_tags["owner"]}
Géré par : ${var.project_tags["managed_by"]}
EOT
}

# Affiche le nom de l'application.
output "application_name" {
  value = var.app_config.name
}

# Affiche la première technologie.
output "first_technology" {
  value = var.technologies[0]
}

# Affiche l'environnement.
output "environment" {
  value = var.project_tags["environment"]
}
```

## Commandes à exécuter

```bash
# Reformate le code.
terraform fmt

# Vérifie les types et la syntaxe.
terraform validate

# Affiche les changements prévus.
terraform plan

# Applique la configuration.
terraform apply -auto-approve
```

## Observer le résultat

```bash
# Affiche le fichier généré.
cat rapport-types-complexes.txt

# Affiche les outputs.
terraform output
```

## Résultat attendu

Le fichier doit afficher :

```text
Nom : demo-hcl
Version : 1
Active : true
Première technologie : Terraform
Environnement : dev
```

## Questions et réponses

**Pourquoi utilise-t-on `var.technologies[0]` ?**
`technologies` est une `list(string)`. Les listes sont indexées à partir de 0. `var.technologies[0]` retourne le premier élément. `var.technologies[1]` retourne le deuxième. On ne peut pas écrire `var.technologies` seul dans une interpolation si on veut une valeur précise.

**Pourquoi utilise-t-on `var.project_tags["environment"]` ?**
`project_tags` est une `map(string)`. Les maps s’accèdent par clé textuelle entre crochets. `var.project_tags["environment"]` retourne la valeur associée à la clé `"environment"`. Si la clé n’existe pas, Terraform retourne une erreur.

**Pourquoi utilise-t-on `var.app_config.name` ?**
`app_config` est un `object`. Les attributs d’un object s’accèdent avec le point. `var.app_config.name` retourne le champ `name`. Contrairement à une `map`, un `object` peut avoir des champs de types différents (`string`, `number`, `bool`).

**Quelle différence entre une `map` et un `object` ?**
Une `map(string)` est un dictionnaire dont toutes les valeurs ont le **même type**. Un `object` est une structure dont chaque champ peut avoir un **type différent**. Une map est adaptée pour des labels ou des tags. Un object est adapté pour regrouper des paramètres de configuration hétérogènes.

```text
map(string)  → toutes les valeurs sont string
object       → chaque champ a son propre type
```

## Points clés

**list(string)** contient plusieurs valeurs du même type.

**map(string)** contient des clés texte et des valeurs du même type.

**object** permet de décrire une structure avec plusieurs champs de types différents.

**[0]** accède au premier élément d’une liste.

**["environment"]** accède à une valeur dans une map.

**.name** accède à un attribut d’un object.

# 6. Étape 3 : Différents emplacements de définition des variables

## Objectif

Comprendre la différence entre :

**définir une variable**  
et  
**donner une valeur à une variable**

Terraform permet d'attribuer des valeurs aux variables via plusieurs méthodes : option **-var**, option **-var-file**, fichiers **.tfvars**, fichiers chargés automatiquement et variables d’environnement avec le préfixe **TF_VAR_**. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/values/variables "Use input variables to add module arguments | Terraform | HashiCorp Developer"))

## Idée simple

**variables.tf** déclare les variables.

**main.tf** utilise les variables.

**terraform.tfvars** donne des valeurs automatiquement.

**dev.tfvars** donne des valeurs seulement si on utilise **-var-file**.

**-var** donne une valeur directement dans la commande.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Nom du fichier généré.
variable "file_name" {
  type        = string
  description = "Nom du fichier généré."
  default     = "default-report.txt"
}

# Nom de l'environnement.
variable "environment" {
  type        = string
  description = "Nom de l'environnement."
  default     = "default"
}

# Nom du formateur ou responsable.
variable "owner" {
  type        = string
  description = "Responsable du fichier."
  default     = "default-owner"
}

# Activation du mode détaillé.
variable "detailed_mode" {
  type        = bool
  description = "Mode détaillé activé ou non."
  default     = false
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Provider Local sans configuration obligatoire.
provider "local" {}

# Crée un fichier local avec les valeurs des variables.
resource "local_file" "report" {
  filename = var.file_name

  content = <<EOT
Rapport Terraform

Fichier : ${var.file_name}
Environnement : ${var.environment}
Responsable : ${var.owner}
Mode détaillé : ${var.detailed_mode}
EOT
}

# Affiche les valeurs réellement utilisées.
output "effective_values" {
  value = {
    file_name     = var.file_name
    environment   = var.environment
    owner         = var.owner
    detailed_mode = var.detailed_mode
  }
}
```

## Créer le fichier terraform.tfvars

Créer le fichier **terraform.tfvars** :

```hcl
# Ce fichier est chargé automatiquement par Terraform.
file_name     = "terraform-tfvars-report.txt"
environment   = "terraform-tfvars"
owner         = "valeur-depuis-terraform-tfvars"
detailed_mode = true
```

## Créer le fichier dev.tfvars

Créer le fichier **dev.tfvars** :

```hcl
# Ce fichier n'est pas chargé automatiquement.
# Il sera utilisé uniquement avec -var-file.
file_name     = "dev-report.txt"
environment   = "dev"
owner         = "valeur-depuis-dev-tfvars"
detailed_mode = true
```

## Exécution 1 — Utiliser terraform.tfvars automatiquement

```bash
# Initialise si ce n'est pas encore fait.
terraform init

# Valide la configuration.
terraform validate

# Applique avec terraform.tfvars chargé automatiquement.
terraform apply -auto-approve

# Affiche le fichier créé.
cat terraform-tfvars-report.txt

# Affiche les valeurs réellement utilisées.
terraform output effective_values
```

Observation :

Terraform utilise les valeurs de **terraform.tfvars**, car ce fichier est chargé automatiquement.

## Exécution 2 — Utiliser dev.tfvars avec -var-file

```bash
# Applique en utilisant explicitement le fichier dev.tfvars.
terraform apply -auto-approve -var-file="dev.tfvars"

# Affiche le fichier créé.
cat dev-report.txt

# Affiche les valeurs réellement utilisées.
terraform output effective_values
```

Observation :

Les valeurs de **dev.tfvars** remplacent les valeurs de **terraform.tfvars** pour les variables présentes dans les deux fichiers.

## Exécution 3 — Utiliser -var en ligne de commande

```bash
# Applique en écrasant certaines valeurs directement en ligne de commande.
terraform apply -auto-approve \
  -var="file_name=cli-report.txt" \
  -var="environment=cli" \
  -var="owner=valeur-depuis-var-cli"

# Affiche le fichier créé.
cat cli-report.txt

# Affiche les valeurs réellement utilisées.
terraform output effective_values
```

Observation :

Les valeurs passées avec **-var** ont une priorité plus forte que les valeurs de **terraform.tfvars**.

## Questions et réponses

**Quel fichier est chargé automatiquement ?**
`terraform.tfvars` est le seul fichier chargé automatiquement par Terraform sans option supplémentaire. `terraform.tfvars.json` l’est aussi. Tout autre fichier `.tfvars` doit être passé explicitement avec `-var-file`.

**Pourquoi `dev.tfvars` n’est-il pas utilisé tout seul ?**
Parce que Terraform ne charge que `terraform.tfvars` automatiquement. `dev.tfvars` a un nom différent, Terraform l’ignore sauf si on lui indique explicitement avec `-var-file="dev.tfvars"`. C’est intentionnel : cela permet d’avoir plusieurs environnements (dev, staging, prod) sans risque de confusion.

**Quelle option permet d’utiliser un fichier spécifique ?**

```bash
terraform apply -var-file="dev.tfvars"
```

On peut passer plusieurs `-var-file` dans la même commande. Ils sont appliqués dans l’ordre.

**Quelle option permet d’écraser une variable directement dans la commande ?**

```bash
terraform apply -var="file_name=mon-fichier.txt"
```

`-var` a la priorité la plus haute. Il écrase toutes les autres sources : `terraform.tfvars`, `-var-file`, et la valeur `default`. C’est utile pour un test ponctuel sans modifier aucun fichier.

## Points clés

**variables.tf** déclare.

**main.tf** utilise.

**terraform.tfvars** fournit automatiquement des valeurs.

**dev.tfvars** doit être appelé avec **-var-file**.

**-var** permet une surcharge ponctuelle.

# 7. Étape 4 : Précédence des variables

## Objectif

Comprendre quelle valeur gagne lorsque la même variable est définie à plusieurs endroits.

## Tableau de priorité

Ordre du plus prioritaire au moins prioritaire :

| Priorité | Source                        | Chargement                 |
| -------- | ----------------------------- | -------------------------- |
| 1        | **-var** et **-var-file**     | explicite dans la commande |
| 2        | **.auto.tfvars**              | automatique, ordre lexical |
| 3        | **terraform.tfvars.json**     | automatique                |
| 4        | **terraform.tfvars**          | automatique                |
| 5        | **TF_VAR_nom**                | variable d’environnement   |
| 6        | **default** dans **variable** | valeur par défaut          |

Version simple à retenir :

- CLI gagne sur fichiers.

- auto.tfvars gagne sur terraform.tfvars.

- terraform.tfvars gagne sur TF_VAR.

- TF_VAR gagne sur default.

- default est le dernier recours.

Attention :

Quand plusieurs options **-var** et **-var-file** sont utilisées dans la même commande, Terraform les traite dans l’ordre donné. <u>La dernière valeur fournie pour la même variable peut donc l’emporter dans ce contexte</u>. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/values/variables "Use input variables to add module arguments | Terraform | HashiCorp Developer"))

# 8. Démonstration pratique de la précédence

## Objectif

Créer plusieurs sources de valeurs et observer qui gagne.

On va utiliser une seule variable :

**environment**

Chaque source va donner une valeur différente.

# 10. Erreurs guidées à provoquer

Chaque scénario part d’un état fonctionnel. On casse volontairement quelque chose, on observe l’erreur, on comprend pourquoi, on corrige.

---

## Scénario 1 — Passer un texte à une variable number

**Contexte** : `line_count` est déclaré `type = number` dans `variables.tf`.

**Action** : dans `terraform.tfvars`, écrire :

```hcl
line_count = "beaucoup"
```

**Commande** :

```bash
terraform plan
```

**Erreur obtenue** :

```text
Error: Invalid value for input variable
The argument "line_count" cannot be interpreted as a number.
```

**Pourquoi** : Terraform vérifie le type à l’évaluation. `"beaucoup"` est une string, pas un number.

**Correction** :

```hcl
line_count = 10
```

---

## Scénario 2 — Passer une string à une variable bool

**Contexte** : `detailed_mode` est déclaré `type = bool`.

**Action** : dans `terraform.tfvars`, écrire :

```hcl
detailed_mode = "oui"
```

**Commande** :

```bash
terraform plan
```

**Erreur obtenue** :

```text
Error: Invalid value for input variable
The argument "detailed_mode" cannot be interpreted as a boolean.
```

**Pourquoi** : `"oui"` est une string. Terraform n’accepte que `true` ou `false` pour un bool.

**Correction** :

```hcl
detailed_mode = true
```

---

## Scénario 3 — Oublier un champ obligatoire dans un object

**Contexte** : `app_config` est un object avec les champs `name`, `version`, `enabled`.

**Action** : dans `terraform.tfvars`, supprimer le champ `enabled` :

```hcl
app_config = {
  name    = "demo"
  version = 2
}
```

**Commande** :

```bash
terraform plan
```

**Erreur obtenue** :

```text
Error: Invalid value for input variable
attribute "enabled" is required
```

**Pourquoi** : un `object` en Terraform exige que tous les attributs déclarés soient présents. Aucun champ n’est optionnel sauf si déclaré avec `optional()`.

**Correction** :

```hcl
app_config = {
  name    = "demo"
  version = 2
  enabled = true
}
```

---

## Scénario 4 — Utiliser une variable non déclarée

**Contexte** : `variables.tf` contient `file_name`, `line_count`, `detailed_mode`.

**Action** : dans `main.tf`, utiliser une variable qui n’existe pas :

```hcl
filename = var.output_path
```

**Commande** :

```bash
terraform validate
```

**Erreur obtenue** :

```text
Error: Reference to undeclared input variable
An input variable with the name "output_path" has not been declared.
```

**Pourquoi** : `validate` détecte immédiatement les références à des variables non déclarées, sans avoir besoin de contacter un provider.

**Correction** : soit déclarer `output_path` dans `variables.tf`, soit corriger la référence vers `var.file_name`.

---

## Scénario 5 — Supprimer le default sans fournir de valeur

**Contexte** : `file_name` a actuellement `default = "rapport.txt"`.

**Action** : dans `variables.tf`, supprimer la ligne `default` :

```hcl
variable "file_name" {
  type        = string
  description = "Nom du fichier local à créer."
}
```

Et vider `terraform.tfvars` ou supprimer la ligne `file_name`.

**Commande** :

```bash
terraform plan
```

**Ce qui se passe** : Terraform s’arrête et demande la valeur en interactif :

```text
var.file_name
  Nom du fichier local à créer.

  Enter a value:
```

**Pourquoi** : sans `default` et sans valeur fournie par un autre moyen, Terraform attend une saisie manuelle. En CI/CD sans terminal, cette situation bloque le pipeline.

**Correction** : soit remettre un `default`, soit fournir la valeur via `terraform.tfvars` ou `-var`.

# 11. Exercices pratiques

## Exercice 1 — Variables simples

**Objectif** : créer un fichier local dont le contenu est construit à partir de quatre variables.

**variables.tf** :

```hcl
variable "file_name" {
  type    = string
  default = "fiche.txt"
}

variable "author" {
  type    = string
  default = "anonyme"
}

variable "revision" {
  type    = number
  default = 1
}

variable "published" {
  type    = bool
  default = false
}
```

**terraform.tfvars** :

```hcl
file_name = "fiche-bechir.txt"
author    = "Bechir"
revision  = 3
published = true
```

**main.tf** :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

resource "local_file" "fiche" {
  filename = var.file_name
  content  = <<EOT
Auteur   : ${var.author}
Révision : ${var.revision}
Publié   : ${var.published}
EOT
}

output "fichier" {
  value = local_file.fiche.filename
}
```

**Commandes** :

```bash
terraform init
terraform apply -auto-approve
cat fiche-bechir.txt
```

**Réponse à la question** : `author`, `revision`, `published` viennent de `terraform.tfvars` et écrasent les valeurs `default`. `file_name` vient aussi de `terraform.tfvars`.

---

## Exercice 2 — Liste et map

**Objectif** : créer un fichier affichant des éléments de liste et de map.

**variables.tf** :

```hcl
variable "technologies" {
  type    = list(string)
  default = ["terraform", "ansible", "docker"]
}

variable "tags" {
  type = map(string)
  default = {
    environment = "dev"
    owner       = "bechir"
  }
}
```

**main.tf** (resource uniquement) :

```hcl
resource "local_file" "stack" {
  filename = "stack.txt"
  content  = <<EOT
Première technologie  : ${var.technologies[0]}
Deuxième technologie  : ${var.technologies[1]}
Tag environment       : ${var.tags["environment"]}
Tag owner             : ${var.tags["owner"]}
EOT
}
```

**Réponses** :

- Accès à un élément de liste : `var.technologies[0]` — index numérique entre crochets, commence à 0.
- Accès à une valeur de map : `var.tags["environment"]` — clé textuelle entre crochets.

---

## Exercice 3 — Object

**Objectif** : créer un fichier dont le contenu vient d’un objet structuré.

**variables.tf** :

```hcl
variable "document" {
  type = object({
    title     = string
    pages     = number
    validated = bool
  })
  default = {
    title     = "Guide Terraform"
    pages     = 42
    validated = false
  }
}
```

**main.tf** (resource uniquement) :

```hcl
resource "local_file" "doc" {
  filename = "document.txt"
  content  = <<EOT
Titre     : ${var.document.title}
Pages     : ${var.document.pages}
Validé    : ${var.document.validated}
EOT
}
```

**Réponse** : `object` est plus précis qu’une `map` parce que chaque champ a son propre type (`title` est string, `pages` est number, `validated` est bool). Une `map(string)` forcerait tous les champs à être des strings, ce qui obligerait à écrire `"42"` au lieu de `42`.

## Exercice 4 — Précédence

**Objectif** : observer quelle source gagne selon la commande utilisée.

**variables.tf** :

```hcl
variable "environment" {
  type    = string
  default = "default"
}
```

**terraform.tfvars** :

```hcl
environment = "tfvars"
```

**dev.tfvars** :

```hcl
environment = "dev"
```

**main.tf** (resource uniquement) :

```hcl
resource "local_file" "env" {
  filename = "env.txt"
  content  = "environment = ${var.environment}\n"
}
```

**Tester et observer** :

```bash
# Cas 1 : terraform.tfvars est chargé automatiquement → tfvars gagne
terraform apply -auto-approve && cat env.txt

# Cas 2 : -var-file écrase terraform.tfvars → dev gagne
terraform apply -auto-approve -var-file="dev.tfvars" && cat env.txt

# Cas 3 : -var a la priorité absolue → cli gagne
terraform apply -auto-approve -var="environment=cli" && cat env.txt

# Cas 4 : -var après -var-file → cli gagne (ordre sans importance, -var prime toujours)
terraform apply -auto-approve -var-file="dev.tfvars" -var="environment=cli" && cat env.txt
```

**Réponses** :

```text
Cas 1 → tfvars   (terraform.tfvars chargé automatiquement)
Cas 2 → dev      (-var-file écrase terraform.tfvars)
Cas 3 → cli      (-var a la priorité la plus haute)
Cas 4 → cli      (-var prime toujours sur -var-file)
```
