# Solution 3 — Actions après réussite ou échec

[Énoncé](../3.Exercice%203.md) · [Prérequis communs](../readme.md)

## 1. Configuration complète

```yaml
spec:
  inputs:
    provoquer_echec:
      type: boolean
      description: Faire echouer volontairement le traitement
      default: false
---
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - when: never

default:
  image: alpine:3.22

stages: [traitement]

traitement:
  stage: traitement
  script:
    - |
      set -eu
      echo "Debut du traitement"
      if [ "$[[ inputs.provoquer_echec ]]" = "true" ]; then
        echo "Echec volontaire" >&2
        exit 1
      fi
      echo "Traitement termine"
  after_script:
    - |
      printf 'Etat du job dans after_script : %s\n' "$CI_JOB_STATUS"

bilan_succes:
  stage: .post
  when: on_success
  script:
    - echo "Le traitement a reussi"

bilan_echec:
  stage: .post
  when: on_failure
  script:
    - echo "Le traitement a echoue"

bilan_toujours:
  stage: .post
  when: always
  script:
    - echo "Bilan apres reussite ou echec du traitement"
```

## 2. Pourquoi deux mécanismes ?

L'input booléen est interpolé dans le texte du script. Son type contraint sa valeur à `true` ou `false`. Le placer seul dans une variable YAML préserverait son type booléen, alors que les variables CI attendent ici des chaînes.

`after_script` montre l'état du **job courant**. Les jobs `.post` réagissent aux stages qui les précèdent. Ils s'exécutent sur leurs propres environnements et n'ont pas automatiquement les fichiers du traitement.

`.post` n'a pas besoin d'être ajouté à `stages`. Le pipeline contient bien un stage ordinaire ; un pipeline composé uniquement de `.pre`/`.post` ne convient pas. [Référence des stages](https://docs.gitlab.com/ci/yaml/#stage-post)

Les trois jobs de bilan n'ont pas d'ordre entre eux. Le bilan de succès décrit ici le traitement précédent, pas le statut final après tous les autres bilans.

## 3. Essais

1. Lancez avec `provoquer_echec=false` : traitement, bilan de succès et bilan général réussissent.
2. Lancez avec `true` : traitement échoue, bilan d'échec et bilan général réussissent, pipeline échoué.
3. Comparez les valeurs de `CI_JOB_STATUS` dans `after_script` : `success` puis `failed`.

Ne mettez pas `allow_failure: true` sur le traitement pour cet atelier : un échec toléré change les décisions de réussite/échec des stages suivants.

## 4. Limites du nettoyage

`after_script` utilise un nouveau shell. Une variable seulement exportée par `script` n'y est pas garantie. Son propre échec ne fait normalement pas échouer un `script` réussi ; les contrôles obligatoires restent dans `script`.

Un arrêt forcé ou une perte de runner peut empêcher le nettoyage, même avec `when: always`. [Cycle du job](https://docs.gitlab.com/ci/jobs/job_execution/), [after_script](https://docs.gitlab.com/ci/yaml/#after_script)

## Validation attendue

Les deux chemins sont vérifiables sans modifier les commandes du traitement. Les résultats restent attendus : aucun pipeline n'a été exécuté sur GitLab pendant la rédaction.
