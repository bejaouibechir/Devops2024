# Atelier 6 : Découverte des Modules Terraform et leur Importance en Pratique

## 1. Introduction

## Objectif de l’atelier

Dans les ateliers précédents, tout le code Terraform était écrit dans le même dossier, souvent dans un seul **main.tf**.

Cette approche fonctionne pour apprendre, mais elle devient vite difficile à maintenir.

Exemple de problème :

```text
Un même fichier contient :
- l’installation de Docker
- la configuration Docker
- la création d’un conteneur
- les outputs
- les dépendances
```

Le code devient moins lisible, plus fragile, plus difficile à corriger.

Les **modules Terraform** permettent de découper le projet en blocs réutilisables.

Un module Terraform est simplement un dossier contenant des fichiers Terraform. Un bloc **module** permet d’appeler les ressources définies dans ce dossier local ou distant. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/block/module?utm_source=chatgpt.com "module block reference | Terraform"))

## Message principal

```text
Sans module :
tout est mélangé dans un seul bloc de code.

Avec modules :
chaque responsabilité est isolée.
```

Dans cet atelier, on va montrer une situation concrète :

```text
1. Installer Docker sur la machine
2. Utiliser Docker avec Terraform
3. Créer un conteneur Nginx
```

Le problème à comprendre :

```text
Le provider Docker utilise l’API Docker.

Si Docker n’est pas encore installé ou démarré,
le provider Docker ne peut pas créer le conteneur.
```

Le provider Docker **kreuzwerker/docker** permet à Terraform d’interagir avec l’API Docker pour gérer des images et des conteneurs. ([Terraform Registry](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs?utm_source=chatgpt.com "Docs overview | kreuzwerker/docker - Terraform Registry"))

On va donc séparer le projet en deux modules :

```text
docker-install     → prépare Docker
docker-container   → utilise Docker
```

Puis on utilisera **depends_on** pour forcer l’ordre :

```text
docker-install doit finir avant docker-container
```

Terraform recommande **depends_on** uniquement pour les dépendances cachées que Terraform ne peut pas déduire automatiquement. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/meta-arguments/depends_on?utm_source=chatgpt.com "depends_on meta-argument reference | Terraform"))

# 3. Étape 1 : Créer un premier module simple

## 3.1 Objectif

Avant Docker, on commence avec un module très simple.

Ce module va créer un fichier local.

Il permet de comprendre :

```text
module
source
input variables
output values
```

---

## 3.2 Créer le module simple-file

Créer le fichier **modules/simple-file/variables.tf** :

```hcl
# Nom du fichier à créer.
variable "file_name" {
  type        = string
  description = "Nom du fichier local à créer."
}

# Contenu du fichier.
variable "file_content" {
  type        = string
  description = "Contenu du fichier local."
}
```

Créer le fichier **modules/simple-file/main.tf** :

```hcl
# Le module crée un fichier local.
resource "local_file" "this" {
  filename = var.file_name
  content  = var.file_content
}
```

Créer le fichier **modules/simple-file/outputs.tf** :

```hcl
# Retourne le nom du fichier créé.
output "file_name" {
  value = local_file.this.filename
}
```

## 3.3 Créer le fichier racine main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare les providers nécessaires au projet racine.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Provider Local sans configuration obligatoire.
provider "local" {}

# Appel du module local simple-file.
module "intro_file" {
  source = "./modules/simple-file"

  file_name    = "intro-module.txt"
  file_content = "Ce fichier a été créé par un module Terraform local."
}
```

Créer le fichier **outputs.tf** :

```hcl
# Affiche le fichier créé par le module.
output "intro_file_name" {
  value = module.intro_file.file_name
}
```

Créer le fichier **variables.tf** :

```hcl
# Fichier présent pour garder une structure professionnelle.
# Les variables racines seront ajoutées dans les étapes suivantes.
```

## 3.4 Exécuter Terraform

Exécuter dans **~/terraform-modules-docker** :

```bash
# Initialise Terraform et charge les modules locaux.
terraform init

# Reformate les fichiers.
terraform fmt -recursive

# Vérifie la configuration.
terraform validate

# Affiche le plan.
terraform plan

# Applique.
terraform apply -auto-approve
```

## 3.5 Observer

```bash
# Vérifie le fichier créé.
cat intro-module.txt

# Liste le state.
terraform state list

# Affiche l'output.
terraform output
```

Résultat attendu :

```text
Ce fichier a été créé par un module Terraform local.
```

State attendu :

```text
module.intro_file.local_file.this
```

## 3.6 Points clés

Un **module local** est un dossier contenant des fichiers Terraform.

Le bloc suivant appelle un module :

```hcl
module "intro_file" {
  source = "./modules/simple-file"
}
```

Les variables du module sont des **inputs**.

Les outputs du module sont accessibles avec :

```text
module.nom_du_module.nom_output
```

# 4. Étape 2 : Comprendre le problème sans séparation propre

## 4.1 Objectif

Montrer pourquoi il est dangereux de tout mélanger.

On pourrait être tenté d’écrire :

```text
installer Docker
puis créer un conteneur
dans le même fichier main.tf
```

Le problème est que le provider Docker doit se connecter à Docker pendant le plan ou l’apply.

Si Docker n’est pas encore installé ou si le service n’est pas démarré, Terraform risque d’échouer avec une erreur de connexion au daemon Docker.

## 4.2 Exemple volontairement fragile

Ne pas exécuter ce fichier dans l’atelier principal. Il sert à comprendre le problème.

```hcl
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

provider "docker" {
  host = "unix:///var/run/docker.sock"
}

resource "terraform_data" "install_docker" {
  provisioner "local-exec" {
    command = "sudo apt-get update && sudo apt-get install -y docker.io && sudo systemctl enable --now docker"
  }
}

resource "docker_image" "nginx" {
  name = "nginx:alpine"
}

resource "docker_container" "nginx" {
  name  = "nginx-module-demo"
  image = docker_image.nginx.image_id

  ports {
    internal = 80
    external = 8080
  }
}
```

## 4.3 Pourquoi c’est fragile ?

Même si **terraform_data.install_docker** existe, le provider Docker peut être initialisé ou utilisé alors que Docker n’est pas encore prêt.

Le code mélange deux responsabilités :

```text
installation système
utilisation de Docker
```

La solution propre :

```text
module docker-install
module docker-container
depends_on entre modules
```

# 5. Étape 3 : Module docker-install

## 5.1 Objectif

Créer un module qui installe Docker sur la machine locale Ubuntu.

Ce module utilise **terraform_data** avec **local-exec**.

Ici, Terraform déclenche une action système locale. C’est acceptable pour l’atelier, mais en production on préférerait souvent Ansible pour l’installation système.

---

## 5.2 Créer le fichier modules/docker-install/variables.tf

Créer le fichier **modules/docker-install/variables.tf** :

```hcl
# Nom du fichier témoin créé après installation.
variable "marker_file" {
  type        = string
  description = "Fichier témoin indiquant que le module docker-install a été exécuté."
  default     = "docker-install.done"
}
```

## 5.3 Créer le fichier modules/docker-install/main.tf

Créer le fichier **modules/docker-install/main.tf** :

```hcl
# Ce module installe Docker sur la machine locale Ubuntu.
resource "terraform_data" "install" {

  # Cette valeur force Terraform à garder une trace logique de l'installation.
  input = "docker-install"

  # local-exec exécute les commandes sur la machine où Terraform tourne.
  provisioner "local-exec" {
    command = <<EOT
set -e
sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable docker
sudo systemctl start docker
sudo usermod -aG docker "$USER" || true
docker --version
touch ${var.marker_file}
EOT
  }
}
```

## 5.4 Créer le fichier modules/docker-install/outputs.tf

Créer le fichier **modules/docker-install/outputs.tf** :

```hcl
# Retourne le fichier témoin.
output "marker_file" {
  value = var.marker_file
}

# Retourne un statut logique.
output "install_status" {
  value = terraform_data.install.output
}
```

## 5.5 Point clé

Ce module ne crée pas de conteneur.

Il prépare seulement Docker :

```text
apt-get install docker.io
systemctl start docker
docker --version
```

# 6. Étape 4 : Module docker-container

## 6.1 Objectif

Créer un module qui utilise Docker pour lancer un conteneur Nginx.

Ce module utilise le provider **Docker**.

Le provider Docker permet de gérer le cycle de vie des conteneurs Docker avec l’API Docker. ([Terraform Registry](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs?utm_source=chatgpt.com "Docs overview | kreuzwerker/docker - Terraform Registry"))

---

## 6.2 Créer le fichier modules/docker-container/variables.tf

Créer le fichier **modules/docker-container/variables.tf** :

```hcl
# Nom du conteneur Docker.
variable "container_name" {
  type        = string
  description = "Nom du conteneur Docker."
  default     = "nginx-module-demo"
}

# Image Docker à utiliser.
variable "image_name" {
  type        = string
  description = "Image Docker à télécharger."
  default     = "nginx:alpine"
}

# Port externe exposé sur la machine locale.
variable "external_port" {
  type        = number
  description = "Port externe exposé sur localhost."
  default     = 8080

  validation {
    condition     = var.external_port >= 1024 && var.external_port <= 65535
    error_message = "external_port doit être entre 1024 et 65535."
  }
}
```

## 6.3 Créer le fichier modules/docker-container/main.tf

Créer le fichier **modules/docker-container/main.tf** :

```hcl
# Déclare le provider Docker attendu par ce module.
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

# Télécharge ou référence l'image Docker.
resource "docker_image" "nginx" {
  name = var.image_name
}

# Crée le conteneur Nginx.
resource "docker_container" "nginx" {
  name  = var.container_name
  image = docker_image.nginx.image_id

  ports {
    internal = 80
    external = var.external_port
  }
}
```

## 6.4 Créer le fichier modules/docker-container/outputs.tf

Créer le fichier **modules/docker-container/outputs.tf** :

```hcl
# Nom du conteneur créé.
output "container_name" {
  value = docker_container.nginx.name
}

# Image utilisée.
output "image_name" {
  value = var.image_name
}

# URL locale de test.
output "container_url" {
  value = "http://localhost:${var.external_port}"
}
```

## 6.5 Point clé

Ce module suppose que Docker est déjà disponible.

Il ne doit pas installer Docker.

Il doit seulement utiliser Docker :

```text
docker_image
docker_container
```

# 7. Étape 5 : Utiliser les modules dans le projet racine

## 7.1 Objectif

Appeler les deux modules dans le **main.tf** racine.

On veut obtenir cette chaîne :

```text
module.docker_install
        ↓
module.docker_container
```

La dépendance est explicite avec **depends_on**.

---

## 7.2 Remplacer le fichier racine variables.tf

Créer le fichier **variables.tf** :

```hcl
# Nom du conteneur Docker.
variable "container_name" {
  type        = string
  description = "Nom du conteneur Nginx."
  default     = "nginx-module-demo"
}

# Image Docker utilisée.
variable "image_name" {
  type        = string
  description = "Image Docker utilisée."
  default     = "nginx:alpine"
}

# Port externe.
variable "external_port" {
  type        = number
  description = "Port HTTP exposé localement."
  default     = 8080

  validation {
    condition     = var.external_port >= 1024 && var.external_port <= 65535
    error_message = "external_port doit être entre 1024 et 65535."
  }
}
```

## 7.3 Remplacer le fichier racine main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare les providers nécessaires au projet racine.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }

    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

# Provider Local.
provider "local" {}

# Provider Docker.
# Il se connecte au daemon Docker local.
provider "docker" {
  host = "unix:///var/run/docker.sock"
}

# Module responsable de l'installation Docker.
module "docker_install" {
  source = "./modules/docker-install"

  marker_file = "docker-install.done"
}

# Module responsable de l'utilisation de Docker.
module "docker_container" {
  source = "./modules/docker-container"

  container_name = var.container_name
  image_name     = var.image_name
  external_port  = var.external_port

  # Cette dépendance force Terraform à exécuter le module d'installation avant celui du conteneur.
  depends_on = [
    module.docker_install
  ]
}
```

## 7.4 Créer le fichier racine outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Statut du module d'installation.
output "docker_install_status" {
  value = module.docker_install.install_status
}

# Fichier témoin créé par le module d'installation.
output "docker_install_marker" {
  value = module.docker_install.marker_file
}

# Nom du conteneur.
output "container_name" {
  value = module.docker_container.container_name
}

# URL du conteneur.
output "container_url" {
  value = module.docker_container.container_url
}
```

# 9. Étape 7 : Comprendre depends_on entre modules

## 9.1 Pourquoi depends_on est nécessaire ici ?

Le module **docker_container** ne lit pas directement une valeur technique produite par le module **docker_install** pour configurer le provider Docker.

Terraform ne peut donc pas forcément deviner que Docker doit être installé avant l’utilisation du provider Docker.

La dépendance est donc une dépendance de comportement :

```text
Le conteneur dépend du fait que Docker soit installé et démarré.
```

On écrit donc :

```hcl
depends_on = [
  module.docker_install
]
```

## 9.2 Point important

**depends_on** force Terraform à terminer toutes les actions du module dépendant avant de commencer l’autre module.

C’est utile ici, mais à utiliser avec prudence.

## 9.3 Attention

**depends_on** ne répare pas un mauvais design.

Il sert uniquement quand la dépendance est réelle mais invisible dans les arguments Terraform.

Bonne utilisation :

```text
Le module docker-container dépend réellement du fait que docker-install soit terminé.
```

Mauvaise utilisation :

```text
Mettre depends_on partout par sécurité.
```

# 10. Étape 8 : Inputs et outputs de modules

## 10.1 Inputs

Dans le module **docker-container**, les inputs sont :

```text
container_name
image_name
external_port
```

Ils sont déclarés dans :

```text
modules/docker-container/variables.tf
```

Ils sont fournis depuis le projet racine :

```hcl
module "docker_container" {
  source = "./modules/docker-container"

  container_name = var.container_name
  image_name     = var.image_name
  external_port  = var.external_port
}
```

## 10.2 Outputs

Dans le module **docker-container**, les outputs sont :

```text
container_name
image_name
container_url
```

Ils sont déclarés dans :

```text
modules/docker-container/outputs.tf
```

Ils sont récupérés dans le projet racine :

```hcl
output "container_url" {
  value = module.docker_container.container_url
}
```

## 10.3 Point clé

```text
variables.tf du module = ce que le module reçoit

outputs.tf du module = ce que le module retourne
```

# 11. Étape 9 : Module versioning de base

## 11.1 Cas des modules locaux

Pour un module local :

```hcl
source = "./modules/docker-container"
```

Il n’y a pas de version explicite dans le bloc **module**.

La version est liée au code présent dans le dossier.

## 11.2 Cas des modules Git

Plus tard, un module peut venir d’un dépôt Git :

```hcl
module "docker_container" {
  source = "git::https://gitlab.com/example/terraform-docker-container.git?ref=v1.0.0"
}
```

Ici :

```text
ref=v1.0.0
```

désigne une version Git, souvent un tag.

## 11.3 Cas du Terraform Registry

Plus tard, un module peut venir du Terraform Registry :

```hcl
module "network" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "x.y.z"
}
```

Ici, **version** fixe la version du module public.

## 11.4 Point clé

Pour débuter :

```text
module local = source ./modules/nom

module Git = source git + ref

module Registry = source + version
```

# 12. Étape 10 : Bonnes pratiques des modules

## 12.1 Quand créer un module ?

Créer un module quand :

```text
un groupe de ressources représente une responsabilité claire
le même code doit être réutilisé
un fichier main.tf devient trop long
on veut séparer installation et utilisation
on veut réduire les erreurs de copier-coller
```

## 12.2 Exemples de bons modules

```text
docker-install
docker-container
postgres-database
gitlab-project
azure-linux-vm
kubernetes-namespace
```

## 12.3 Organisation recommandée

```text
modules/
└── nom-du-module/
    ├── main.tf
    ├── variables.tf
    ├── outputs.tf
    └── README.md
```

## 12.4 README minimal d’un module

Créer le fichier **modules/docker-container/README.md** :

```text
# Module docker-container

## Rôle

Ce module crée un conteneur Docker Nginx.

## Inputs

- container_name : nom du conteneur
- image_name : image Docker à utiliser
- external_port : port exposé sur la machine locale

## Outputs

- container_name : nom du conteneur créé
- image_name : image utilisée
- container_url : URL locale du conteneur
```

## 12.5 Pièges fréquents

| Piège                                                  | Problème                                   |
| ------------------------------------------------------ | ------------------------------------------ |
| Créer un module trop tôt                               | Complexité inutile                         |
| Créer un module trop gros                              | Peu réutilisable                           |
| Ne pas documenter les inputs                           | Module difficile à utiliser                |
| Ne pas exposer d’outputs utiles                        | Module difficile à chaîner                 |
| Utiliser depends_on partout                            | Plans plus conservateurs et moins lisibles |
| Mélanger installation système et ressource applicative | Dépendances fragiles                       |

# 13. Nettoyage

## 13.1 Détruire les ressources Terraform

Exécuter dans **~/terraform-modules-docker** :

```bash
# Supprime le conteneur Docker, l'image suivie par Terraform et la ressource logique d'installation.
terraform destroy
```

Taper :

```text
yes
```

## 13.2 Supprimer le fichier témoin

```bash
# Supprime le fichier témoin local.
rm -f docker-install.done
```

## 13.3 Vérifier Docker

```bash
# Vérifie les conteneurs restants.
docker ps -a

# Vérifie les images Docker.
docker images
```

## 13.4 Désinstaller Docker si nécessaire

Créer le fichier **remove-docker.sh** :

```bash
#!/usr/bin/env bash

# Arrête le script en cas d'erreur.
set -e

# Arrête Docker si le service existe.
sudo systemctl stop docker || true

# Désinstalle Docker installé par apt.
sudo apt-get remove -y docker.io || true

# Supprime les dépendances inutiles.
sudo apt-get autoremove -y

# Affiche un message de fin.
echo "Docker a été désinstallé si le paquet docker.io était présent."
```

Puis exécuter :

```bash
# Rend le script exécutable.
chmod +x remove-docker.sh

# Lance le nettoyage Docker.
./remove-docker.sh
```

```text
structurer un module avec main.tf, variables.tf, outputs.tf
appeler un module avec source
passer des inputs à un module
récupérer des outputs depuis un module
séparer les responsabilités
utiliser depends_on entre modules
comprendre les bases du versioning de modules
```

Le cas Docker montre clairement le problème :

```text
Installer Docker et l’utiliser sont deux responsabilités différentes.
```

La séparation propre est :

```text
module docker-install
→ installe et démarre Docker

module docker-container
→ crée une image et un conteneur
```

La relation est explicitée par :

```hcl
depends_on = [
  module.docker_install
]
```

Le bénéfice principal des modules :

```text
code plus lisible
code plus réutilisable
code plus maintenable
moins d’erreurs de dépendance
meilleure séparation des responsabilités
```
