# Produire, transférer et publier des artefacts

## Objectif

Adapter `archiveArtifacts`, `stash/unstash`, `copyArtifacts` et la publication Maven en distinguant stockage CI, transfert et publication de paquet.

## 1. Correspondances

| Jenkins | GitLab CI/CD | GitHub Actions |
| --- | --- | --- |
| `archiveArtifacts` | `artifacts: paths` | `actions/upload-artifact` |
| `stash/unstash` entre agents | Artefacts entre jobs | Upload puis download dans le même run |
| `copyArtifacts` d'un autre build | API/artefacts d'un autre pipeline | Download avec dépôt, `run-id` et jeton autorisé |
| Fingerprint Jenkins | Empreinte/traçabilité applicative | Digest d'artefact, checksum, attestation selon besoin |
| `mvn deploy` | Publication Maven | Publication Maven, indépendante du stockage Actions |

`needs` impose l'ordre sans copier de fichiers. Le cache accélère les builds et n'est pas un stockage de livrables.

## 2. Exemple minimal sans application

Fichier `.github/workflows/artefacts.yml` :

```yaml
name: Transfert artefact
on:
  workflow_dispatch:
permissions: {}
jobs:
  produce:
    runs-on: ubuntu-24.04
    steps:
      - run: |
          mkdir -p dist
          printf 'Livrable du run %s\n' "$GITHUB_RUN_ID" > dist/message.txt
      - uses: actions/upload-artifact@v7
        with:
          name: message
          path: dist/message.txt
          if-no-files-found: error
          retention-days: 7
  consume:
    needs: produce
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: message
          path: reception
      - run: cat reception/message.txt
```

**Résultat attendu :** le second job affiche le message du premier. Dans **Actions > exécution > Artifacts**, l'archive peut aussi être téléchargée manuellement. [Téléchargement depuis GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)

L'upload échoue volontairement si le fichier est absent. Avec les versions modernes, plusieurs jobs ne doivent pas enrichir un même artefact : choisissez des noms distincts, notamment dans une matrice. Les versions `upload-artifact@v4+` ne sont pas prises en charge sur GHES ; cette fiche vise GitHub.com. [Action upload-artifact](https://github.com/actions/upload-artifact)

## 3. Construire un JAR Maven puis vérifier son transfert

Prérequis : projet Java 21 compatible, `pom.xml`, Maven Wrapper `mvnw` et ses fichiers `.mvn/wrapper/`. L'exemple suppose un projet mono-module produisant exactement un JAR principal.

Workflow complet indépendant :

```yaml
name: JAR Maven
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Compiler et tester
        run: bash mvnw -B clean package
      - name: Selectionner le livrable
        shell: bash
        run: |
          mapfile -d '' jars < <(find target -maxdepth 1 -type f \
            -name '*.jar' ! -name '*-sources.jar' ! -name '*-javadoc.jar' -print0)
          if [ "${#jars[@]}" -ne 1 ]; then
            echo "Adapter la selection : exactement un JAR attendu"
            exit 1
          fi
          mkdir -p dist
          cp -- "${jars[0]}" dist/app.jar
          (cd dist && sha256sum app.jar > app.jar.sha256)
      - name: Archiver le JAR
        uses: actions/upload-artifact@v7
        with:
          name: application
          path: dist/
          if-no-files-found: error
          retention-days: 7
      - name: Conserver les rapports de tests
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@v7
        with:
          name: rapports-tests
          path: target/surefire-reports/
          if-no-files-found: warn
          retention-days: 7
  verify:
    needs: build
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: application
          path: reception
      - run: |
          cd reception
          sha256sum -c app.jar.sha256
          ls -lh app.jar
```

**Résultat attendu :** le JAR téléchargé correspond au checksum produit. La vérification démontre le transfert ; elle ne démarre pas l'application. `java -jar app.jar` nécessiterait un JAR exécutable et ne constituerait pas, à lui seul, un service déployé.

`setup-java` installe le JDK et configure le cache Maven. Le cache n'est pas utilisé pour transmettre `dist/app.jar`. [Action setup-java](https://github.com/actions/setup-java)

Les rapports XML sont conservés comme fichiers. Contrairement à `artifacts:reports:junit` GitLab, l'upload seul ne crée pas une vue structurée des tests ; il faut un outil de rapport adapté ou un résumé. Voir [checks et résumés](18.checks%20annotations%20et%20resumes.md).

## 4. Télécharger depuis une autre exécution

Fragment d'un job dont la permission est `actions: read` :

```yaml
- uses: actions/download-artifact@v8
  with:
    name: application
    repository: ${{ github.repository }}
    run-id: ${{ inputs.source_run_id }}
    github-token: ${{ github.token }}
    path: reception
```

Le workflow appelant doit déclarer `source_run_id` comme input obligatoire. Avant consommation, vérifiez via l'API l'état réussi du run, son workflow, sa branche et son commit attendus.

Un autre dépôt privé exige un jeton autorisé sur ce dépôt, par exemple celui d'une GitHub App adaptée. `GITHUB_TOKEN` est normalement limité au dépôt courant. Fournir un `run-id` ne fait pas attendre la fin de ce run. [Action download-artifact](https://github.com/actions/download-artifact)

## 5. Publier dans Nexus avec Maven

Dans le `pom.xml` existant, intégrez ce fragment et remplacez l'URL :

```xml
<distributionManagement>
  <repository>
    <id>nexus</id>
    <url>https://nexus.example.org/repository/maven-releases/</url>
  </repository>
</distributionManagement>
```

Dans un job de publication autorisé, après checkout, utilisez :

```yaml
- uses: actions/setup-java@v6
  with:
    distribution: temurin
    java-version: '21'
    server-id: nexus
    server-username-env-var: MAVEN_USERNAME
    server-password-env-var: MAVEN_PASSWORD
- name: Publier le paquet
  env:
    MAVEN_USERNAME: ${{ secrets.NEXUS_USERNAME }}
    MAVEN_PASSWORD: ${{ secrets.NEXUS_PASSWORD }}
  run: bash mvnw -B deploy
```

Les inputs `server-...-env-var` désignent des noms de variables, pas directement leurs valeurs. `mvn deploy` parcourt le cycle Maven et publie dans le dépôt déclaré ; cette commande n'utilise pas automatiquement un JAR téléchargé auparavant. Pour publier ce dernier, définir explicitement une procédure `deploy-file` avec ses coordonnées et son POM.

Le dépôt de snapshots doit être configuré séparément si le projet en produit. [Maven Deploy Plugin](https://maven.apache.org/plugins/maven-deploy-plugin/usage.html)

## 6. Transfert SSH, rétention et provenance

Copier un fichier avec SCP n'est ni un upload Actions ni une publication Maven. La [fiche SSH](8.ssh%20command.md) fournit un transfert utilisant une clé et des clés d'hôte vérifiées.

Les artefacts expirent et peuvent être supprimés avec leur run. Conservez les versions publiées durablement dans un registre ou dans une release selon l'usage.

Un checksum associé au fichier vérifie leur cohérence ; il ne prouve pas à lui seul qui a construit le binaire. Pour cette question, voir [attestations](20.attestations.md).

## Exercice

Testez le workflow minimal, retirez temporairement son upload, puis observez l'échec du téléchargement. Dans un projet Maven, provoquez un test échoué et vérifiez que les rapports restent téléchargeables alors que le JAR n'est pas livré.

Aucun build applicatif, upload ou accès Nexus n'a été exécuté pendant la rédaction.
