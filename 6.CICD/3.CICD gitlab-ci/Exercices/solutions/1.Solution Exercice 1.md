# Solution 1 — Input utilisateur et lecture d'un fichier

[Énoncé](../1.Exercice%201.md) · [Prérequis communs](../readme.md)

## 1. Fichier à ajouter au dépôt

Créez `data/input.txt` avec une seule ligne :

```text
Amine
```

Le fichier est une donnée d'exercice non secrète. Pour une donnée confidentielle, utiliser une variable File ou un mécanisme de secrets approprié, pas le dépôt.

## 2. Configuration complète

Copiez ce contenu dans `.gitlab-ci.yml` :

```yaml
spec:
  inputs:
    prenom:
      type: string
      description: Prenom a afficher
      default: Leila
      regex: '^[A-Za-z][A-Za-z -]{0,79}$'
---
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - when: never

default:
  image: alpine:3.22

afficher_prenoms:
  variables:
    EXO_PRENOM: "$[[ inputs.prenom ]]"
  script:
    - |
      set -eu
      if [ ! -s data/input.txt ]; then
        echo "Erreur : data/input.txt est absent ou vide" >&2
        exit 1
      fi
      cp data/input.txt /tmp/input
      nom_fichier=$(cat /tmp/input)
      if [ -z "$nom_fichier" ]; then
        echo "Erreur : le fichier ne contient aucun prenom" >&2
        exit 1
      fi
      printf 'Nom saisi : %s\n' "$EXO_PRENOM"
      printf 'Nom du fichier : %s\n' "$nom_fichier"
```

L'exemple limite volontairement le prénom à des lettres ASCII, espaces et tirets. Il peut être élargi pour les accents selon votre besoin ; cette restriction n'est pas une limite générale de GitLab.

L'input est validé à la création du pipeline puis copié dans une variable. Le shell lit cette variable sans insérer le prénom dans le texte du programme. [Inputs et validation](https://docs.gitlab.com/ci/inputs/)

## 3. Essais

1. Commitez le YAML et `data/input.txt`.
2. Depuis **Build > Pipelines > New pipeline**, choisissez la branche et `prenom=Leila`.
3. Vérifiez les deux lignes `Leila` et `Amine`.
4. Dans un autre essai, retirez ou videz le fichier source : le job doit échouer.

Un fichier contenant seulement des espaces n'est pas traité comme vide dans cette variante ; une validation métier plus stricte peut être ajoutée.

## 4. Ce qui change par rapport à Jenkins

La copie vers `/tmp/input` a lieu dans le job courant, après récupération du dépôt. Elle ne lit pas un fichier d'un autre ordinateur. Avec un executor Docker, le prochain job dispose de son propre environnement.

Le prénom est fourni au lancement ; le job n'attend aucune saisie interactive. Le corrigé rassemble explicitement les deux sources de noms, au lieu de supposer qu'une variable utilisateur a déjà été définie ailleurs.

## Validation attendue

Le cas nominal réussit ; les fichiers manquant ou vide produisent un statut en échec. Aucun pipeline n'a été exécuté sur GitLab pendant la rédaction.
