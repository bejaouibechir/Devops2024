# Milestone 3 — Architecture modulaire, state distant et Ansible

> **Ateliers couverts :** A8 · A9 · A10 · A11

---

## Objectif du milestone

Le projet est restructuré en **modules locaux réutilisables**. Les templates génèrent les scripts de configuration des VMs. Le state Terraform migre vers un **backend Azure Storage**. Ansible intervient après le `terraform apply` pour configurer les VMs.

---

```
Azure
├── Storage Account (backend tfstate)

        └── Subnet
            ├── Network Security Group
            └── VM(s) Ubuntu
```

## Module networking

**Responsabilité :** créer le réseau, le sous-réseau et les règles de sécurité.

Inputs principaux : `name_prefix`, `location`, `resource_group_name`, `address_space`, `subnet_prefix`, `nsg_rules`

Outputs : `subnet_id`, `nsg_id`

---

## Module compute

**Responsabilité :** créer les VMs avec leur NIC, leur Public IP et leur script cloud-init.

Inputs principaux : `vms`, `subnet_id`, `vm_size`, `admin_username`, `ssh_public_key`, `environment`, `cloud_init_vars`

Outputs : `vm_ids`, `public_ips`, `private_ips`

### Template cloud-init

```yaml
# templates/cloud-init.yaml.tftpl
#cloud-config
hostname: ${hostname}
package_update: true
packages:
%{ for pkg in packages ~}
  - ${pkg}
%{ endfor ~}
runcmd:
  - echo "VM ${hostname} prête — environnement ${environment}"
```

Appel dans le module :

```hcl
custom_data = base64encode(templatefile(
  "${path.module}/templates/cloud-init.yaml.tftpl",
  {
    hostname    = "vm-${each.key}"
    environment = var.environment
    packages    = ["curl", "git", "unzip"]
  }
))
```

## Backend Azure Storage

Avant de migrer le state, créer manuellement (ou via un script bootstrap) le Storage Account :

```bash
az group create --name rg-tfstate --location francecentral
az storage account create --name sttfstate<suffix> --resource-group rg-tfstate --sku Standard_LRS
az storage container create --name tfstate --account-name sttfstate<suffix>
```

Puis configurer le backend :

```hcl
# backend.tf
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "stffstate<suffix>"
    container_name       = "tfstate"
    key                  = "fil-rouge/terraform.tfstate"
  }
}
```

Migration du state local vers le backend :

```bash
terraform init -migrate-state
```

## Ansible — post-déploiement

Après `terraform apply`, Terraform expose les IPs des VMs dans ses outputs. Ansible utilise ces IPs pour configurer les VMs.

Flux :

```
terraform apply
    └── outputs → public_ips
          └── ansible-playbook -i <ip>, playbook.yml
                └── installe packages, configure services
```

Exemple d'inventaire dynamique minimal :

```ini
[web]
<ip_vm_web> ansible_user=adminuser ansible_ssh_private_key_file=./id_rsa

[api]
<ip_vm_api> ansible_user=adminuser ansible_ssh_private_key_file=./id_rsa
```

## Critères de validation du milestone

- [ ] `main.tf` racine n'appelle que des modules, aucune ressource directe
- [ ] `terraform plan` produit le même résultat qu'avant la refactorisation
- [ ] Le state est stocké dans Azure Storage (plus de `terraform.tfstate` local)
- [ ] Une autre machine peut reprendre le projet avec `terraform init` + `terraform plan`
- [ ] Le cloud-init s'exécute au boot et les packages sont installés
- [ ] Ansible se connecte aux VMs via `id_rsa` et complète la configuration
- [ ] `terraform state list` liste toutes les ressources depuis le backend distant

---

## Points de vigilance

- Ne jamais supprimer le Storage Account contenant le state — c'est la mémoire du projet.
- Le `terraform init -migrate-state` est irréversible sans backup — sauvegarder `terraform.tfstate` local avant la migration.
- `path.module` dans `templatefile()` est relatif au module, pas au projet racine.
- Ansible a besoin que le port 22 soit ouvert dans le NSG (règle SSH toujours présente depuis M2).
