# Matrices de jobs : combinaisons et parallélisme

## Objectif

Exécuter le même contrôle sur plusieurs configurations sans dupliquer tout le job.

## 1. Ce qui est spécifique

Les matrices existent aussi dans GitLab avec `parallel:matrix` et dans Jenkins. La particularité étudiée ici est `strategy.matrix`, ses contexts et ses règles d'échec.

## 2. Matrice Java complète

Fichier `.github/workflows/matrix.yml` :

```yaml
name: Matrice Java
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  compatibility:
    name: Java ${{ matrix.java }} sur ${{ matrix.os }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      max-parallel: 2
      matrix:
        os: [ubuntu-24.04, windows-latest]
        java: ['17', '21']
        exclude:
          - os: windows-latest
            java: '17'
    steps:
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: ${{ matrix.java }}
      - run: java -version
```

**Résultat attendu :** trois jobs : Linux/17, Linux/21, Windows/21. Au plus deux variantes de cette matrice s'exécutent à la fois.

L'exemple vérifie la disponibilité de Java. Il ne compile aucune application ; ajoutez checkout et une commande de test appropriée pour transformer le diagnostic en test de compatibilité.

## 3. include, exclude et échecs

`exclude` retire une combinaison. `include` ajoute ou enrichit des combinaisons selon les valeurs compatibles existantes ; ce n'est pas toujours un simple ajout de colonne.

Pour contrôler précisément chaque variante, utilisez uniquement une liste `include` :

```yaml
strategy:
  fail-fast: true
  matrix:
    include:
      - os: ubuntu-24.04
        java: '21'
        experimental: false
      - os: ubuntu-24.04
        java: '25'
        experimental: true
continue-on-error: ${{ matrix.experimental }}
```

Ce fragment remplace le bloc `strategy` et ajoute `continue-on-error` au niveau job de l'exemple précédent.

`fail-fast` peut annuler les autres variantes lorsqu'une variante non tolérée échoue. `continue-on-error` concerne le statut de la variante. `max-parallel` limite la matrice ; il ne sérialise pas les déploiements d'autres workflows. [Stratégies de matrices](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations)

## 4. Matrice dynamique

Un job de préparation peut produire un JSON contrôlé, puis un job dépendant utiliser :

```yaml
strategy:
  matrix: ${{ fromJSON(needs.prepare.outputs.matrix) }}
```

Ce fragment suppose un output `matrix` et `needs: prepare`. Une valeur possible est `{"include":[{"java":"21"},{"java":"25"}]}`. Validez les variantes autorisées pour éviter une multiplication inattendue des jobs.

## 5. Artefacts et outputs

Chaque variante doit publier un nom d'artefact distinct, par exemple `rapport-${{ matrix.os }}-${{ matrix.java }}`.

Évitez de faire écrire un même output de job par plusieurs variantes en supposant un ordre stable. Préférez des fichiers séparés puis un job d'agrégation.

## Exercice

Ajoutez Linux/25 avec `include`, puis provoquez un échec uniquement dans cette variante expérimentale. Comparez avec une erreur dans Linux/21.

Les variantes n'ont pas été exécutées sur GitHub pendant la rédaction.
