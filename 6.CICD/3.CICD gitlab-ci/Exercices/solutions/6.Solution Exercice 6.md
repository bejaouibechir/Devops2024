# Solution 6 — Diagnostic distant avec OpenSSH

[Énoncé](../6.Exercice%206.md) · [Préparation SSH commune](../readme.md#prérequis-ssh-pour-les-exercices-6-à-8)

## 1. Préparer la cible

Le compte SSH doit pouvoir exécuter `whoami`, `hostname`, `uptime` et `df`. Il n'a pas besoin de sudo. Testez sa connexion depuis un poste autorisé avant de passer au runner.

Configurez les cinq variables du guide, dont les deux variables File. Le nom utilisé dans `SSH_HOST` doit correspondre aux clés du fichier `SSH_KNOWN_HOSTS`.

## 2. Configuration complète

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "web" && $CI_COMMIT_REF_PROTECTED == "true"'
    - when: never

default:
  image: alpine:3.22

diagnostic_ssh:
  timeout: 5 minutes
  before_script:
    - apk add --no-cache openssh-client
    - |
      set -eu
      : "${SSH_HOST:?Configurer SSH_HOST}"
      : "${SSH_USER:?Configurer SSH_USER}"
      : "${SSH_PRIVATE_KEY:?Configurer la variable File SSH_PRIVATE_KEY}"
      : "${SSH_KNOWN_HOSTS:?Configurer la variable File SSH_KNOWN_HOSTS}"
      test -s "$SSH_PRIVATE_KEY"
      test -s "$SSH_KNOWN_HOSTS"
      chmod 600 "$SSH_PRIVATE_KEY"
  script:
    - |
      set -eu
      ssh -T \
        -i "$SSH_PRIVATE_KEY" \
        -p "${SSH_PORT:-22}" \
        -o BatchMode=yes \
        -o IdentitiesOnly=yes \
        -o StrictHostKeyChecking=yes \
        -o "UserKnownHostsFile=$SSH_KNOWN_HOSTS" \
        -o ConnectTimeout=10 \
        "${SSH_USER}@${SSH_HOST}" 'sh -se' <<'REMOTE'
      printf 'Utilisateur : '
      whoami
      printf 'Machine : '
      hostname
      uptime
      df -h
      REMOTE
```

Avec les variables protégées, lancez ce pipeline depuis **New pipeline** sur la branche protégée configurée. L'utilisateur ne clique pas sur un job manuel supplémentaire : le lancement du pipeline suffit.

## 3. Lire les options

| Option | Rôle |
| --- | --- |
| `-i` | Clé utilisateur issue de la variable File |
| `BatchMode=yes` | Refuser une demande interactive de mot de passe |
| `IdentitiesOnly=yes` | Utiliser les identités explicitement choisies |
| `StrictHostKeyChecking=yes` | Vérifier le serveur |
| `UserKnownHostsFile` | Désigner les clés d'hôte de confiance |
| `ConnectTimeout=10` | Limiter l'établissement de connexion |
| `timeout: 5 minutes` | Limiter la durée totale du job |

Le heredoc cité transmet le texte sans expansion locale. `sh -se` arrête les commandes simples sur erreur ; SSH renvoie le statut de la commande distante. [OpenSSH](https://man.openbsd.org/ssh), [clés SSH dans GitLab](https://docs.gitlab.com/ci/jobs/ssh_keys/)

## 4. Essais

| Cas | Résultat attendu |
| --- | --- |
| Clés, compte et réseau corrects | Informations de la VM |
| Clé d'hôte incorrecte dans une configuration d'essai | Refus de connexion |
| Compte incorrect | Échec d'authentification |
| `false` ajouté avant `df -h` | Job échoué ; la commande suivante ne doit pas s'exécuter |
| Branche non protégée | Pipeline refusé par les règles de l'atelier |

N'écrasez pas une clé d'hôte de confiance pour masquer un refus : vérifiez d'abord l'identité du serveur.

## 5. Différences avec le support Jenkins

La configuration n'utilise ni `sshCommand` ni chemin privé fixé sur une machine Jenkins. Le client est installé dans le conteneur, et les fichiers temporaires sont fournis par GitLab.

Le compte n'est pas rendu sudoer pour ces lectures. Aucun `allowAnyHosts` ni désactivation de vérification d'hôte n'est repris.

## Validation attendue

Les résultats positifs et négatifs doivent être vérifiés sur votre VM. Aucune connexion SSH n'a été effectuée pendant la rédaction.
