# Solution 2 — Configuration selon l'environnement

[Énoncé](../2.Exercice%202.md) · [Prérequis communs](../readme.md)

## 1. Configuration complète

```yaml
# Déclare le contrat des inputs avant le séparateur YAML de la configuration.
spec:
  # Déclare les valeurs validées puis interpolées avant la création du pipeline.
  inputs:
    # Définit le paramètre « cible » et les contraintes de sa valeur.
    cible:
      type: string
      description: Environnement de simulation
      options: [dev, staging, prod]
      # Fournit la valeur utilisée si cet input n'est pas renseigné.
      default: dev
---
# Décide si GitLab crée un pipeline pour cet événement.
workflow:
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '$CI_PIPELINE_SOURCE == "web"'
    # Exclut ce pipeline ou ce job lorsque cette règle est retenue.
    - when: never

# Applique ces réglages aux jobs qui ne les redéfinissent pas.
default:
  # Choisit l'image utilisée par l'exécuteur compatible ; un exécuteur Shell ne la lance pas.
  image: alpine:3.22

# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [prepare, simulation]

# Déclare le job « preparer_configuration » et sa configuration propre.
preparer_configuration:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: prepare
  # Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
  variables:
    EXO_CIBLE: "$[[ inputs.cible ]]"
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Sélectionne le cas correspondant à la valeur ; la branche de repli traite les valeurs non prévues.
      case "$EXO_CIBLE" in
        dev)
          # Prépare une valeur locale au shell ; elle ne devient pas automatiquement disponible dans un autre job.
          api_url="https://dev.api.example.test"
          db_name="dev_db"
          ;;
        staging)
          api_url="https://staging.api.example.test"
          db_name="staging_db"
          ;;
        prod)
          api_url="https://api.example.test"
          db_name="prod_db"
          ;;
        *)
          # Écrit le diagnostic sur la sortie d'erreur pour distinguer l'erreur des résultats normaux.
          echo "Cible invalide" >&2
          # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
          exit 1
          ;;
      esac
      # Écrit une valeur non secrète destinée au rapport dotenv consommé par les jobs suivants.
      printf 'EXO_API_URL=%s\nEXO_DB_NAME=%s\n' \
        "$api_url" "$db_name" > configuration.env
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Configuration pour %s\n' "$EXO_CIBLE"
      # Affiche le contenu ou la liste des fichiers pour vérifier le résultat de l'étape précédente.
      cat configuration.env
  # Conserve les fichiers ou rapports du job pour consultation ou transmission.
  artifacts:
    # Déclare des rapports que GitLab interprète selon leur type.
    reports:
      # Expose les valeurs non secrètes de ce fichier aux jobs consommateurs ; ce rapport n'est pas un coffre à secrets.
      dotenv: configuration.env
    # Sélectionne les fichiers du workspace à publier comme artefacts.
    paths:
      - configuration.env
    # Fixe la durée de conservation demandée pour ces artefacts.
    expire_in: 1 day

# Modèle de configuration réutilisable, non exécuté directement.
.simulation:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: simulation
  # Limite les jobs antérieurs dont les artefacts seront récupérés.
  dependencies:
    - preparer_configuration
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - |
      # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie.
      set -eu
      # Interrompt le script si cette configuration obligatoire est absente ou vide.
      : "${EXO_API_URL:?Configuration API absente}"
      : "${EXO_DB_NAME:?Configuration base absente}"
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Simulation %s\n' "$EXO_COMPORTEMENT"
      printf 'API : %s\nBase : %s\n' "$EXO_API_URL" "$EXO_DB_NAME"

# Déclare le job « simuler_dev » et sa configuration propre.
simuler_dev:
  # Hérite de la configuration du modèle indiqué, avec les redéfinitions locales de ce job.
  extends: .simulation
  # Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
  variables:
    EXO_COMPORTEMENT: "DEV avec diagnostics detailles"
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '"$[[ inputs.cible ]]" == "dev"'

# Déclare le job « simuler_staging » et sa configuration propre.
simuler_staging:
  # Hérite de la configuration du modèle indiqué, avec les redéfinitions locales de ce job.
  extends: .simulation
  # Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
  variables:
    EXO_COMPORTEMENT: "STAGING avec verification avant recette"
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '"$[[ inputs.cible ]]" == "staging"'

# Déclare le job « simuler_prod » et sa configuration propre.
simuler_prod:
  # Hérite de la configuration du modèle indiqué, avec les redéfinitions locales de ce job.
  extends: .simulation
  # Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
  variables:
    EXO_COMPORTEMENT: "PROD avec journal de livraison"
  # Évalue les règles dans l'ordre pour inclure ou exclure le pipeline ou le job avant l'exécution.
  rules:
    # Teste cette expression lors de la création du pipeline, avant tout calcul par script.
    - if: '"$[[ inputs.cible ]]" == "prod"'
```

## 2. Lecture du pipeline

L'input détermine les jobs lors de la création du pipeline. `preparer_configuration` calcule ensuite les valeurs. Le rapport dotenv injecte les valeurs non secrètes dans le job de simulation retenu.

`dependencies` sélectionne les artefacts à recevoir ; l'ordre des stages assure l'attente de la préparation. Le modèle caché `.simulation` mutualise le script sans s'exécuter lui-même.

Ne tentez pas une condition `rules:if` fondée sur `EXO_API_URL` produit dans ce job : cette valeur n'existe pas encore lors de l'évaluation des règles. [Règles de jobs](https://docs.gitlab.com/ci/jobs/job_rules/), [rapport dotenv](https://docs.gitlab.com/ci/yaml/artifacts_reports/#artifactsreportsdotenv)

## 3. Essais et résultats

| Input | Jobs ordinaires attendus |
| --- | --- |
| `dev` | `preparer_configuration`, `simuler_dev` |
| `staging` | `preparer_configuration`, `simuler_staging` |
| `prod` | `preparer_configuration`, `simuler_prod` |

Pour un essai négatif, tentez une valeur hors `options` par un moyen autorisé ou modifiez temporairement le contrat : la validation d'input doit refuser les valeurs non autorisées. Le `case` garde une protection supplémentaire si la variable était écrasée par une configuration de priorité supérieure.

## 4. Portée des données

Le fichier dotenv ne remplace pas un coffre de secrets. Ses données sont téléchargeables comme artefacts dans cet atelier. Les URL sont fictives et aucune base n'est créée.

Le job ne déclare pas `environment` : il simule un comportement sans enregistrer un déploiement GitLab. Ajouter une vraie livraison demanderait ses permissions et sa configuration propres.

## Validation attendue

Trois lancements vérifient les trois configurations. Les jobs non choisis sont absents, pas des scripts vides exécutés avec succès. Aucun pipeline n'a été exécuté sur GitLab pendant la rédaction.
