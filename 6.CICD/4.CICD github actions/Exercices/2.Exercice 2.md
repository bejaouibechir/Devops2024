# Exercice 2 — Environnements et partage de configuration

## Objectif

Choisir `dev`, `staging` ou `prod`, calculer sa configuration puis exécuter uniquement la simulation correspondante. Reprise de l'[exercice GitLab 2](../../3.CICD%20gitlab-ci/Exercices/2.Exercice%202.md).

## Travail demandé

1. Déclarer l'input `cible` de type `choice` avec les trois valeurs.
2. Dans `preparer_configuration`, calculer une URL fictive et un nom de base à l'aide de `case`.
3. Exposer `cible`, `api_url` et `db_name` comme outputs d'étape puis de job.
4. Créer trois jobs dépendant de la préparation avec `needs`.
5. Utiliser un `if` par job et consommer les valeurs depuis `needs`.
6. Afficher la configuration sans appeler d'API ni créer de base.

## Divergences

Les rapports dotenv GitLab n'existent pas comme mécanisme d'injection automatique ici. `GITHUB_OUTPUT` alimente les outputs ; `GITHUB_ENV` reste limité aux étapes suivantes du même job. Contrairement aux `rules` GitLab, la condition du job GitHub peut utiliser un output d'un job terminé.

## Critères et livrables

Tester les trois cibles : un job de simulation réussit, deux sont ignorés. Vérifier les valeurs `dev_db`, `staging_db`, `prod_db`. Le script doit rejeter une cible hors contrat même si l'interface propose une liste. Remettre le YAML et les trois graphes.
