# Atelier : Ansible installe PostgreSQL, Terraform administre PostgreSQL

## 1. Contexte et objectif

Cet atelier montre la complémentarité entre **Ansible** et **Terraform** à travers un cas concret :

**Ansible** installe et configure **PostgreSQL** sur un serveur Ubuntu distant.

**Terraform** se connecte ensuite à PostgreSQL et administre les objets internes de la base :

**rôles**, **bases**, **schémas**, **extensions**, **privilèges**.

Le provider **cyrilgdn/postgresql** permet de gérer avec Terraform des objets PostgreSQL comme les **databases**, **extensions** et **roles**. Il est publié sur le Terraform Registry, et la version GitHub du projet indique une release récente **v1.26.0** publiée le **1 septembre 2025**. ([GitHub](https://github.com/cyrilgdn/terraform-provider-postgresql "GitHub - cyrilgdn/terraform-provider-postgresql: Terraform PostgreSQL provider · GitHub"))

## Message principal de l’atelier

```text
Ansible prépare le serveur.
Terraform administre PostgreSQL.
```

Terraform ne doit pas remplacer Ansible pour installer des paquets Linux, modifier des fichiers système ou gérer des services.

Ansible est mieux adapté pour :

**apt**, **systemd**, **postgresql.conf**, **pg_hba.conf**.

Terraform est mieux adapté pour :

**database**, **role**, **schema**, **grant**, **extension**.

# 6. Phase 2 — Installer et configurer PostgreSQL avec Ansible

## Objectif

Ansible va :

**installer PostgreSQL**,  
**installer les dépendances utiles**,  
**activer le service**,  
**autoriser l’écoute réseau**,  
**autoriser la connexion distante**,  
**définir un mot de passe pour postgres**,  
**redémarrer PostgreSQL**.

Pour les modules Ansible liés à PostgreSQL, la documentation Ansible rappelle que les paquets **postgresql**, **libpq-dev** et **python3-psycopg2** sont nécessaires sur les hôtes Ubuntu quand on manipule PostgreSQL côté serveur. ([Ansible Documentation](https://docs.ansible.com/projects/ansible/latest/collections/community/postgresql/postgresql_set_module.html?utm_source=chatgpt.com "community.postgresql.postgresql_set module – Change a ..."))

---

## Étape 1 — Créer le playbook Ansible

Créer le fichier **ansible/install-postgres.yml** :

```yaml
---
# Ce playbook installe et configure PostgreSQL sur un serveur Ubuntu distant.
- name: Installer et configurer PostgreSQL pour un atelier Terraform
  hosts: postgres_servers
  become: true

  vars:
    # Mot de passe utilisé uniquement pour l'atelier.
    # En production, utiliser Ansible Vault.
    postgres_admin_password: "PostgresDemo123!"

    # Port PostgreSQL standard.
    postgres_port: 5432

  tasks:
    # Met à jour le cache APT pour obtenir la liste récente des paquets.
    - name: Mettre à jour le cache APT
      ansible.builtin.apt:
        update_cache: true
        cache_valid_time: 3600

    # Installe PostgreSQL et les dépendances nécessaires.
    - name: Installer PostgreSQL et les dépendances Python
      ansible.builtin.apt:
        name:
          - postgresql
          - postgresql-contrib
          - libpq-dev
          - python3-psycopg2
        state: present

    # Active et démarre le service PostgreSQL.
    - name: Démarrer et activer PostgreSQL
      ansible.builtin.service:
        name: postgresql
        state: started
        enabled: true

    # Recherche le fichier postgresql.conf.
    # Sur Ubuntu, il se trouve généralement dans /etc/postgresql/<version>/main/postgresql.conf.
    - name: Trouver postgresql.conf
      ansible.builtin.find:
        paths: /etc/postgresql
        patterns: postgresql.conf
        recurse: true
      register: postgresql_conf_files

    # Recherche le fichier pg_hba.conf.
    # Ce fichier contrôle les connexions autorisées.
    - name: Trouver pg_hba.conf
      ansible.builtin.find:
        paths: /etc/postgresql
        patterns: pg_hba.conf
        recurse: true
      register: pg_hba_conf_files

    # Arrête le playbook si les fichiers de configuration sont introuvables.
    - name: Vérifier que les fichiers de configuration existent
      ansible.builtin.assert:
        that:
          - postgresql_conf_files.files | length > 0
          - pg_hba_conf_files.files | length > 0
        fail_msg: "Les fichiers postgresql.conf ou pg_hba.conf sont introuvables."

    # Stocke le chemin de postgresql.conf dans une variable temporaire.
    - name: Définir le chemin de postgresql.conf
      ansible.builtin.set_fact:
        postgresql_conf_path: "{{ postgresql_conf_files.files[0].path }}"

    # Stocke le chemin de pg_hba.conf dans une variable temporaire.
    - name: Définir le chemin de pg_hba.conf
      ansible.builtin.set_fact:
        pg_hba_conf_path: "{{ pg_hba_conf_files.files[0].path }}"

    # Configure PostgreSQL pour écouter sur toutes les interfaces réseau.
    # Pour un atelier, c'est simple.
    # En production, il faut limiter l'écoute réseau.
    - name: Autoriser PostgreSQL à écouter sur toutes les interfaces
      ansible.builtin.lineinfile:
        path: "{{ postgresql_conf_path }}"
        regexp: "^#?listen_addresses\\s*="
        line: "listen_addresses = '*'"
        backup: true
      notify: Redémarrer PostgreSQL

    # Configure PostgreSQL pour écouter sur le port 5432.
    - name: Configurer le port PostgreSQL
      ansible.builtin.lineinfile:
        path: "{{ postgresql_conf_path }}"
        regexp: "^#?port\\s*="
        line: "port = {{ postgres_port }}"
        backup: true
      notify: Redémarrer PostgreSQL

    # Autorise les connexions distantes en mot de passe.
    # Pour un atelier, 0.0.0.0/0 simplifie le test.
    # En production, remplacer par l'adresse IP exacte de la machine Terraform.
    - name: Autoriser les connexions distantes avec mot de passe
      ansible.builtin.blockinfile:
        path: "{{ pg_hba_conf_path }}"
        marker: "# {mark} ANSIBLE TERRAFORM POSTGRES LAB"
        block: |
          host    all             all             0.0.0.0/0               md5
        backup: true
      notify: Redémarrer PostgreSQL

    # Définit un mot de passe pour l'utilisateur postgres.
    # Cela permet au provider Terraform PostgreSQL de se connecter.
    - name: Définir le mot de passe du rôle postgres
      become_user: postgres
      ansible.builtin.command:
        cmd: psql -c "ALTER USER postgres WITH PASSWORD '{{ postgres_admin_password }}';"
      changed_when: true
      no_log: true

    # Redémarre le service si une configuration a changé.
    - name: Forcer l'exécution des handlers maintenant
      ansible.builtin.meta: flush_handlers

    # Vérifie que PostgreSQL écoute bien sur le port attendu.
    - name: Vérifier que PostgreSQL écoute sur le port 5432
      ansible.builtin.command:
        cmd: ss -lnt
      register: listen_ports
      changed_when: false

    # Affiche les ports en écoute pour diagnostic.
    - name: Afficher les ports en écoute
      ansible.builtin.debug:
        var: listen_ports.stdout_lines

  handlers:
    # Handler exécuté uniquement si un fichier de configuration a changé.
    - name: Redémarrer PostgreSQL
      ansible.builtin.service:
        name: postgresql
        state: restarted
```

# 8. Phase 4 — Terraform administre PostgreSQL

## Objectif

Terraform va créer :

**un rôle applicatif**,  
**une base de données**,  
**un schéma**,  
**une extension**,  
**des privilèges**.

Le provider PostgreSQL est conçu pour gérer des objets PostgreSQL avec Terraform, notamment des bases, rôles et extensions. ([GitHub](https://github.com/cyrilgdn/terraform-provider-postgresql "GitHub - cyrilgdn/terraform-provider-postgresql: Terraform PostgreSQL provider · GitHub"))

---

## Étape 1 — Créer le fichier Terraform

Créer le fichier **terraform/main.tf** :

```hcl
# Le block terraform configure Terraform lui-même.
terraform {
  required_providers {
    postgresql = {
      source  = "cyrilgdn/postgresql"
      version = "~> 1.26"
    }
  }
}

variable "postgres_admin_password" {
  description = "Mot de passe du rôle PostgreSQL postgres."
  type        = string
  sensitive   = true
}

variable "app_user_password" {
  description = "Mot de passe du rôle applicatif créé par Terraform."
  type        = string
  sensitive   = true
}

# Le provider PostgreSQL configure la connexion au serveur PostgreSQL.
provider "postgresql" {
  host            = "192.168.100.55"
  port            = 5432
  database        = "postgres"
  username        = "postgres"
  password        = var.postgres_admin_password
  sslmode         = "disable"
  connect_timeout = 15
}

# Crée un rôle applicatif.
# login = true permet au rôle de se connecter.
resource "postgresql_role" "app_user" {
  name     = "app_user_tf"
  login    = true
  password = var.app_user_password
}

# Crée une base de données applicative.
# owner donne la propriété de la base au rôle applicatif.
resource "postgresql_database" "app_db" {
  name  = "app_db_tf"
  owner = postgresql_role.app_user.name
}

# Crée une extension dans la base applicative.
# uuid-ossp est utile pour générer des UUID côté PostgreSQL.
resource "postgresql_extension" "uuid_ossp" {
  name     = "uuid-ossp"
  database = postgresql_database.app_db.name
}

# Crée un schéma dans la base applicative.
resource "postgresql_schema" "app_schema" {
  name     = "app"
  database = postgresql_database.app_db.name
  owner    = postgresql_role.app_user.name
}

# Donne des privilèges au rôle applicatif sur le schéma.
resource "postgresql_grant" "app_schema_usage" {
  database    = postgresql_database.app_db.name
  role        = postgresql_role.app_user.name
  schema      = postgresql_schema.app_schema.name
  object_type = "schema"
  privileges  = ["USAGE", "CREATE"]
}
```

## Attention

Les mots de passe ne sont pas écrits directement dans **main.tf**.  
Ils sont fournis à Terraform avec des variables sensibles.

Pour cet atelier, définir les variables d’environnement avant `terraform plan` ou `terraform apply` :

```bash
export TF_VAR_postgres_admin_password="PostgresDemo123!"
export TF_VAR_app_user_password="AppUserDemo123!"
```

Attention : même avec `sensitive = true`, certains secrets peuvent exister dans le state selon les ressources et providers.  
En production, utiliser Vault, un secret manager ou des variables protégées CI/CD.

Elle ne désinstalle pas PostgreSQL.

Elle ne restaure pas automatiquement **postgresql.conf** ou **pg_hba.conf**.

Ces éléments relèvent d’**Ansible**.

# 14. Phase 10 — Nettoyage optionnel avec Ansible

## Objectif

Désinstaller PostgreSQL si l’atelier est terminé.

Cette phase est optionnelle.

---

## Étape 1 — Créer le playbook de nettoyage

Créer le fichier **ansible/remove-postgres.yml** :

```yaml
---
# Ce playbook désinstalle PostgreSQL du serveur Ubuntu distant.
- name: Désinstaller PostgreSQL après l'atelier
  hosts: postgres_servers
  become: true

  tasks:
    # Arrête le service PostgreSQL si présent.
    - name: Arrêter PostgreSQL
      ansible.builtin.service:
        name: postgresql
        state: stopped
      ignore_errors: true

    # Désinstalle les paquets PostgreSQL installés pour l'atelier.
    - name: Désinstaller PostgreSQL et les dépendances associées
      ansible.builtin.apt:
        name:
          - postgresql
          - postgresql-contrib
          - libpq-dev
          - python3-psycopg2
        state: absent
        purge: true
        autoremove: true

    # Supprime les répertoires de configuration et de données.
    # Attention : cette opération efface les données PostgreSQL locales.
    - name: Supprimer les répertoires PostgreSQL restants
      ansible.builtin.file:
        path: "{{ item }}"
        state: absent
      loop:
        - /etc/postgresql
        - /var/lib/postgresql
        - /var/log/postgresql
```

## Étape 2 — Exécuter le nettoyage

Depuis le dossier **~/ansible-terraform-postgres** :

```bash
# Désinstalle PostgreSQL du serveur distant.
ansible-playbook -i ansible/inventory.ini ansible/remove-postgres.yml
```

## Attention

Ce nettoyage supprime PostgreSQL et ses données locales.

Ne jamais exécuter ce playbook sur un serveur contenant des données importantes.

# 16. Questions à poser aux participants

## Question 1

Pourquoi n’installe-t-on pas PostgreSQL directement avec le provider Terraform PostgreSQL ?

Réponse attendue :

Parce que le provider PostgreSQL administre un serveur PostgreSQL déjà accessible.  
Il ne gère pas les paquets Linux ni les services système.

## Question 2

Pourquoi Ansible est-il adapté à l’installation ?

Réponse attendue :

Parce qu’Ansible sait gérer les **paquets**, **fichiers**, **services**, **redémarrages** et **configuration système**.

## Question 3

Pourquoi Terraform est-il adapté à la création des objets PostgreSQL ?

Réponse attendue :

Parce que Terraform garde un **state** des objets déclarés et peut planifier leur création, modification ou destruction.

## Question 4

Que se passe-t-il si on lance **terraform destroy** ?

Réponse attendue :

Terraform supprime les objets PostgreSQL qu’il gère, mais ne désinstalle pas PostgreSQL du serveur.

## Question 5

Pourquoi faut-il éviter de mettre les mots de passe dans **main.tf** ?

Réponse attendue :

Parce que le fichier peut être versionné, partagé ou lu par erreur.  
Les secrets doivent être externalisés.

# 17. Points clés à retenir

**Ansible** prépare le serveur.

**Terraform** administre les objets déclaratifs.

**Le provider PostgreSQL** n’installe pas PostgreSQL.

**Le provider PostgreSQL** gère des objets PostgreSQL comme les bases, rôles, schémas, extensions et droits.

**terraform state list** montre ce que Terraform suit.

**psql** montre ce qui existe réellement dans PostgreSQL.

**terraform destroy** ne remplace pas un playbook de désinstallation.

---

# 18. Conclusion

Cet atelier montre une séparation saine entre deux outils complémentaires :

```text
Ansible = installation et configuration système
Terraform = gestion déclarative des ressources PostgreSQL
```

C’est une approche beaucoup plus réaliste qu’un atelier où Terraform ferait tout avec **remote-exec**.

La bonne logique DevOps est :

```text
Préparer le serveur avec Ansible.
Administrer les ressources avec Terraform.
Vérifier avec psql.
Nettoyer chaque couche avec le bon outil.
```
