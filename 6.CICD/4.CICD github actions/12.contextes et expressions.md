# Contextes et expressions GitHub Actions

## Objectif

Savoir où calculer une condition et où lire une valeur, sans confondre le moteur GitHub avec le shell.

## 1. Les contexts principaux

| Contexte | Contenu typique |
| --- | --- |
| `github` | Événement, dépôt, référence, identifiant de run |
| `inputs` | Paramètres d'un dispatch ou appel réutilisable |
| `env` | Variables d'environnement définies pour les étapes |
| `vars` | Configuration enregistrée dans GitHub |
| `secrets` | Secrets accessibles au job |
| `runner` | Système et répertoires du runner |
| `steps` | Résultats et outputs des étapes précédentes |
| `needs` | Résultats et outputs des jobs dépendances |
| `matrix` | Valeurs de la variante de job |

Tous ne sont pas autorisés partout. Par exemple, le choix d'un job précède l'exécution de ses étapes. Le tableau officiel de disponibilité des contexts fait référence. [Contextes](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)

## 2. Expression et shell

`${{ inputs.message }}` est une expression du workflow. `$MESSAGE` est une expansion Bash ; `$env:MESSAGE` une lecture PowerShell.

Pour du texte contrôlé par un utilisateur, passez une variable d'environnement et citez son utilisation dans le shell. Évitez d'insérer le texte dans le programme `run` lui-même.

## 3. Exemple : décider après un job de préparation

Fichier `.github/workflows/expressions.yml` :

```yaml
name: Conditions et outputs
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
    # Déclare les paramètres attendus ; leur type et leurs contraintes définissent le contrat.
    inputs:
      # Définit le paramètre « execute » et les contraintes de sa valeur.
      execute:
        description: Executer le job suivant
        type: boolean
        # Fournit la valeur utilisée si cet input n'est pas renseigné.
        default: false
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « prepare » ; needs permet de préciser ses dépendances.
  prepare:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Expose les valeurs produites pour les étapes, jobs ou workflows consommateurs selon cette portée.
    outputs:
      execute: ${{ steps.choice.outputs.execute }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - id: choice
        # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
        env:
          EXECUTE: ${{ inputs.execute }}
        # Publie une sortie d'étape ; son exposition au niveau du job permet ensuite un échange via needs.
        run: echo "execute=$EXECUTE" >> "$GITHUB_OUTPUT"
  # Déclare le job « execute » ; needs permet de préciser ses dépendances.
  execute:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: prepare
    # Utilise le résultat ou les outputs des jobs terminés pour décider de cette exécution.
    if: ${{ needs.prepare.outputs.execute == 'true' }}
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Job autorise par la valeur calculee"
```

**Résultat attendu :** le job final s'exécute seulement si la case est cochée. L'input initial était booléen ; l'output transmis est une chaîne.

GitLab permet aussi des variables et des conditions, mais ses `rules` sont généralement décidées à la création du pipeline. Ce cas montre l'évaluation d'une dépendance terminée dans GitHub.

## 4. Fonctions et pièges

| Expression | Usage |
| --- | --- |
| `startsWith(github.ref, 'refs/tags/')` | Identifier une référence de tag |
| `contains(fromJSON('["main","develop"]'), github.ref_name)` | Tester une appartenance |
| `fromJSON(needs.prepare.outputs.matrix)` | Convertir un JSON en objet de matrice |
| `hashFiles('pom.xml')` | Calculer une clé dépendant d'un fichier |

Les chaînes dans les expressions utilisent des quotes simples. La chaîne `'false'` n'est pas le booléen `false`. `A && B || C` ne reproduit un ternaire que si B n'est pas lui-même faux/vide.

Une condition sans fonction de statut garde généralement le test implicite de réussite. Pour continuer après échec, choisissez explicitement la politique présentée dans [post](3.post.md). [Expressions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions)

## 5. Déboguer sans exposer les secrets

Affichez uniquement les champs nécessaires : événement, référence ou nom du runner. Évitez d'afficher tout `toJSON(github)` : ce contexte inclut notamment des données sensibles et des contenus d'événement non fiables.

Un champ vide peut être normal pour un événement : `github.head_ref` concerne une PR, pas un push ordinaire. Validez d'abord `github.event_name`.

## Exercice

Ajoutez un input `message`, transmettez-le par `env` et affichez-le avec `printf '%s\n' "$MESSAGE"`. Testez un texte contenant des guillemets pour observer la différence entre donnée et code.

Le workflow n'a pas été exécuté pendant la rédaction.
