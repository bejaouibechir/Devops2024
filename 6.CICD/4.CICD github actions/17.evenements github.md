# Automatiser les événements du dépôt GitHub

## Objectif

Utiliser GitHub Actions au-delà des pushes : issues, releases et file de fusion.

## 1. Le dépôt est une source d'événements

GitLab permet aussi des automatisations autour de son API et de ses webhooks. La particularité GitHub réside dans les événements directement déclarés sous `on`, leur payload dans `github.event` et leurs règles de permissions.

| Événement | Usage |
| --- | --- |
| `issues` | Ouverture, modification, labels d'issues |
| `issue_comment` | Commentaires d'issues et de PR |
| `release` | Publication d'une release |
| `merge_group` | Tests d'un groupe de la merge queue |
| `repository_dispatch` | Signal explicite d'un système externe |

## 2. Observer une ouverture d'issue

Fichier `.github/workflows/issues.yml`, placé sur la branche par défaut :

```yaml
name: Observer les issues
on:
  issues:
    types: [opened]
permissions: {}
jobs:
  inspect:
    runs-on: ubuntu-24.04
    steps:
      - name: Afficher une reference
        env:
          ISSUE_NUMBER: ${{ github.event.issue.number }}
        run: printf 'Nouvelle issue numero %s\n' "$ISSUE_NUMBER"
```

**Résultat attendu :** ouvrir une issue déclenche un diagnostic. Il n'ajoute aucun commentaire ni label.

Le titre et le corps d'une issue sont des données non fiables. Une commande comme `/deploy` écrite dans un commentaire n'est pas, à elle seule, une autorisation de déploiement.

## 3. Réagir à une release publiée

Workflow indépendant `.github/workflows/release.yml` :

```yaml
name: Observer une release
on:
  release:
    types: [published]
permissions: {}
jobs:
  inspect:
    runs-on: ubuntu-24.04
    steps:
      - env:
          TAG: ${{ github.event.release.tag_name }}
          PRERELEASE: ${{ github.event.release.prerelease }}
        run: |
          printf 'Tag : %s\n' "$TAG"
          printf 'Prerelease : %s\n' "$PRERELEASE"
```

La publication d'une release et le push d'un tag sont deux événements différents. Choisissez l'événement qui correspond à votre processus ; cumuler les deux peut doubler une publication. [Référence des événements](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

## 4. Prendre en charge la merge queue

Fichier `.github/workflows/ci-queue.yml`. Prérequis : une merge queue configurée et disponible pour le dépôt.

```yaml
name: CI avec merge queue
on:
  pull_request:
    branches: [main]
  merge_group:
    types: [checks_requested]
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - run: test -f README.md
```

Le job doit tester le commit préparé pour le groupe. Un contrôle configuré uniquement sur `pull_request` ne suffit pas à rendre son résultat pour une merge queue. GitLab possède une notion comparable avec les merge trains, mais les événements et références diffèrent. [Événement merge_group](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group)

## 5. Recevoir un signal externe

Fragment de déclencheur :

```yaml
on:
  repository_dispatch:
    types: [package_ready]
```

Le système externe appelle l'API avec une identité autorisée ; le workflow doit exister sur la branche par défaut. Le payload `client_payload` décrit l'événement, mais ne prouve pas à lui seul la validité d'un paquet ou l'autorisation d'une livraison.

## Exercice

Dans un dépôt de démonstration, ouvrez une issue et publiez une release d'essai. Comparez les payloads utiles et expliquez pourquoi le premier workflow n'a pas besoin de `issues: write`.

Aucune issue, release, file de fusion ni requête externe n'a été créée pendant la rédaction.
