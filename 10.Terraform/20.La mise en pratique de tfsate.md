# Atelier : Mise en pratique du State Terraform

## Objectif

Mettre en pratique les notions visibles dans votre schéma :

**rôle du state**,  
**terraform.tfstate**,  
**drift**,  
**import**,  
**state rm**,  
**state mv**,  
**state show**.

On reste d'abord sur un atelier simple avec le **provider Local**, pour éviter AWS, Azure ou toute authentification.  
Pour la partie **import**, on utilise ensuite un mini-exemple avec **Docker Desktop**, car la ressource `local_file` du provider Local ne supporte pas `terraform import`.

---

# 1. Préparation du projet

Créer le dossier de travail :

```bash
mkdir -p ~/terraform-state-lab
cd ~/terraform-state-lab
```

Nettoyer le dossier si nécessaire :

```bash
rm -f *.txt
rm -f terraform.tfstate
rm -f terraform.tfstate.backup
rm -f .terraform.lock.hcl
rm -rf .terraform
```

Créer le fichier **main.tf** :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

resource "local_file" "web" {
  filename = "web.txt"
  content  = "Fichier web géré par Terraform"
}

resource "local_file" "api" {
  filename = "api.txt"
  content  = "Fichier api géré par Terraform"
}

output "managed_files" {
  value = {
    web = local_file.web.filename
    api = local_file.api.filename
  }
}
```

Exécuter :

```bash
terraform init
terraform fmt
terraform validate
terraform plan
terraform apply -auto-approve
```

Observer :

```bash
ls -l
cat web.txt
cat api.txt
terraform state list
```

Résultat attendu :

```text
local_file.api
local_file.web
```

Point clé :

**Terraform a créé deux fichiers et les a enregistrés dans le state.**

# 2. Rôle du state

Objectif : comprendre que le **state** fait le lien entre le code Terraform et les fichiers réellement créés.

Exécuter :

```bash
terraform show
```

Puis :

```bash
terraform state list
```

Puis :

```bash
terraform state show local_file.web
```

Observation attendue :

Terraform affiche les informations connues sur la ressource **local_file.web** :

```text
filename
content
id
content_md5
content_sha256
```

Point clé :

**Le state contient la mémoire des ressources suivies par Terraform.**

# 3. Observer terraform.tfstate

Objectif : voir le fichier d’état local.

Exécuter :

```bash
ls -l terraform.tfstate
```

Afficher une partie du fichier :

```bash
cat terraform.tfstate
```

Observation :

Le fichier contient des informations sur les ressources suivies.

Point clé :

**terraform.tfstate est le fichier local où Terraform stocke l’état courant.**

Attention :

Ce fichier peut contenir des données sensibles selon les providers utilisés.  
Il ne faut pas le publier dans un dépôt Git public.

# 4. Comprendre terraform.tfstate.backup

Modifier légèrement le fichier **main.tf** :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

resource "local_file" "web" {
  filename = "web.txt"
  content  = "Fichier web modifié par Terraform"
}

resource "local_file" "api" {
  filename = "api.txt"
  content  = "Fichier api géré par Terraform"
}

output "managed_files" {
  value = {
    web = local_file.web.filename
    api = local_file.api.filename
  }
}
```

Exécuter :

```bash
terraform plan
terraform apply -auto-approve
ls -l terraform.tfstate*
```

Résultat attendu :

```text
terraform.tfstate
terraform.tfstate.backup
```

Point clé :

**terraform.tfstate** contient l’état actuel.  
**terraform.tfstate.backup** contient l’état précédent.

Attention :

En backend local, le backup ne garde qu’une seule version précédente.

# 5. Simuler un drift

Objectif : modifier une ressource en dehors de Terraform.

Modifier manuellement le fichier **web.txt** :

```bash
echo "Modification manuelle hors Terraform" > web.txt
```

Vérifier :

```bash
cat web.txt
```

Demander à Terraform de comparer :

```bash
terraform plan
```

Observation attendue :

Terraform détecte que le contenu réel ne correspond plus au contenu attendu.

Point clé :

**Le drift apparaît quand l’état réel change sans passer par Terraform.**

Corriger avec Terraform :

```bash
terraform apply -auto-approve
cat web.txt
```

Résultat attendu :

```text
Fichier web modifié par Terraform
```

Point clé :

**Terraform remet l’infrastructure dans l’état décrit par le code.**

# 6. Utiliser state show

Objectif : afficher le détail d’une ressource stockée dans le state.

Exécuter :

```bash
terraform state show local_file.api
```

Observation :

Terraform affiche le détail de la ressource **api**.

Point clé :

**terraform state show** sert à inspecter une ressource précise dans le state.

Utile pour :

```text
voir les attributs connus
vérifier l’adresse Terraform
comprendre ce que Terraform suit
```

# 7. Utiliser state rm

Objectif : retirer une ressource du state sans supprimer le fichier réel.

Exécuter :

```bash
terraform state rm local_file.api
```

Vérifier le state :

```bash
terraform state list
```

Vérifier le fichier réel :

```bash
ls -l api.txt
cat api.txt
```

Observation attendue :

Le fichier **api.txt** existe encore, mais Terraform ne le suit plus.

Point clé :

**terraform state rm retire une ressource du state sans détruire l’objet réel.**

Attention :

Après **state rm**, Terraform oublie la ressource.  
Si le code contient encore cette ressource, un prochain **terraform plan** peut proposer de la recréer.

Vérifier :

```bash
terraform plan
```

Observation attendue :

Terraform propose de gérer à nouveau **local_file.api**.

---

# 8. Après state rm : remettre api sous gestion Terraform

Objectif : comprendre une limite importante du provider Local.

Dans notre cas, **api.txt** existe encore, mais Terraform ne le suit plus depuis **state rm**.

On pourrait être tenté d'exécuter :

```bash
terraform import local_file.api api.txt
```

Mais avec le provider **hashicorp/local**, cette commande échoue :

```text
Resource Import Not Implemented
This resource does not support import.
```

Point clé :

**Toutes les ressources Terraform ne supportent pas import.**  
La commande `terraform import` dépend du provider et de la ressource.

Comme le bloc **resource** existe toujours dans **main.tf**, on peut remettre **api.txt** sous gestion Terraform avec :

```bash
terraform apply -auto-approve
terraform state list
```

Résultat attendu :

```text
local_file.api
local_file.web
```

Attention :

Dans un vrai environnement, il ne faut pas remplacer automatiquement `import` par `apply`.  
Ici c'est acceptable parce que l'objet est seulement un fichier local de laboratoire.

# 9. Utiliser state mv

Objectif : renommer une adresse Terraform sans recréer la ressource.

Situation actuelle :

```text
local_file.web
```

On veut renommer l’adresse en :

```text
local_file.frontend
```

Modifier **main.tf** :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

resource "local_file" "frontend" {
  filename = "web.txt"
  content  = "Fichier web modifié par Terraform"
}

resource "local_file" "api" {
  filename = "api.txt"
  content  = "Fichier api géré par Terraform"
}

output "managed_files" {
  value = {
    frontend = local_file.frontend.filename
    api      = local_file.api.filename
  }
}
```

Avant de lancer **plan**, déplacer l’adresse dans le state :

```bash
terraform state mv local_file.web local_file.frontend
```

Vérifier :

```bash
terraform state list
```

Résultat attendu :

```text
local_file.api
local_file.frontend
```

Puis :

```bash
terraform plan
```

Observation attendue :

Terraform ne propose pas de détruire puis recréer **web.txt** à cause du renommage.  
Il peut seulement proposer de mettre à jour la valeur de l'output `managed_files`, car la clé passe de `web` à `frontend`.

Point clé :

**terraform state mv sert à renommer ou déplacer une adresse dans le state.**

Utile lors des refactorisations.

# 10. Import d'une ressource existante avec Docker

Objectif : faire un vrai **terraform import** sur une ressource qui le supporte.

Prérequis :

```bash
docker version
terraform version
```

Créer un conteneur hors Terraform :

```bash
docker pull nginx:alpine
docker run -d --name terraform-state-lab-legacy -p 8088:80 nginx:alpine
```

Créer un nouveau dossier pour cet exercice :

```bash
mkdir -p ~/terraform-docker-import-lab
cd ~/terraform-docker-import-lab
```

Créer le fichier **main.tf** :

```hcl
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

provider "docker" {}

resource "docker_container" "legacy" {
  name  = "terraform-state-lab-legacy"
  image = "nginx:alpine"

  ports {
    internal = 80
    external = 8088
  }
}
```

Initialiser Terraform :

```bash
terraform init
terraform validate
```

Récupérer l'ID réel du conteneur :

```bash
CONTAINER_ID=$(docker inspect -f '{{.Id}}' terraform-state-lab-legacy)
```

Importer le conteneur dans le state :

```bash
terraform import docker_container.legacy "$CONTAINER_ID"
```

Vérifier :

```bash
terraform state list
terraform state show docker_container.legacy
```

Résultat attendu :

```text
docker_container.legacy
```

Observer ensuite le plan :

```bash
terraform plan
```

Point clé :

**terraform import rattache une ressource existante au state, mais il ne génère pas automatiquement un code Terraform parfaitement aligné avec la réalité.**

Il peut rester des différences entre :

```text
le conteneur réellement créé
le state importé
le bloc resource écrit dans main.tf
```

Attention :

Ne lancez pas `terraform apply` sur ce plan si Terraform propose de remplacer le conteneur.  
Dans un vrai projet, après un import, on ajuste le code jusqu'à obtenir un plan maîtrisé.

Nettoyage de l'exercice Docker :

```bash
terraform state rm docker_container.legacy
docker rm -f terraform-state-lab-legacy
```

# 11. Synthèse des commandes state

| Commande                 | Rôle                                           |
| ------------------------ | ---------------------------------------------- |
| **terraform state list** | Liste les ressources suivies                   |
| **terraform state show** | Affiche le détail d’une ressource              |
| **terraform state rm**   | Retire une ressource du state sans la détruire |
| **terraform state mv**   | Renomme ou déplace une adresse dans le state   |
| **terraform import**     | Rattache une ressource existante au state, si la ressource le supporte |
| **terraform show**       | Affiche l’état lisible complet                 |

# Résumé final de l’atelier

```text
state = mémoire de Terraform
terraform.tfstate = fichier local de cette mémoire
drift = changement fait hors Terraform
import = rattacher une ressource existante quand le provider le supporte
state rm = oublier une ressource sans la supprimer
state mv = renommer une adresse sans recréer
state show = inspecter une ressource suivie
```

Message essentiel :

**Terraform ne regarde pas seulement le code. Il compare le code, le state et l’état réel.**

Le **state** est donc indispensable pour comprendre ce que Terraform va créer, modifier ou supprimer.
