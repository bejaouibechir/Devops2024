# Variables, paramètres et environnements dans GitLab CI/CD

## Objectif

Adapter les exemples Jenkins `environment`, `params`, variables locales et conditions, en comprenant les différences de fonctionnement.

Les exemples sont indépendants : copiez un bloc YAML complet à la fois dans `.gitlab-ci.yml`. Ils utilisent un runner Linux avec Bash ou `sh`, disponible pour le projet et acceptant les jobs sans tags. Sinon, ajoutez les tags adaptés comme dans [0.runners.md](0.runners.md).

## 1. Les correspondances et leurs limites

| Dans Jenkins | Dans GitLab CI/CD | Différence à retenir |
| --- | --- | --- |
| `environment { ... }` | `variables:` | Variables d'environnement fournies aux jobs. |
| `environment` dans un stage Jenkins | `variables:` dans un job | GitLab ne définit pas les variables sur un stage entier. |
| `parameters { ... }` et `params.NOM` | `spec:inputs` et `$[[ inputs.nom ]]` | Paramètres typés, interpolés lors de la création du pipeline. |
| Paramétrage par valeurs au lancement | Variables de pipeline | Autre méthode, sans le contrat typé des inputs. |
| `env.NOM` dans Groovy | `$NOM` dans Bash ou `$env:NOM` dans PowerShell | La syntaxe dépend du shell du runner. |
| `def localVar = ...` | Variable locale du shell | Aucun contexte Groovy partagé entre les jobs. |
| `when { expression { ... } }` | `rules:if` pour sélectionner les jobs | Les règles GitLab sont évaluées avant l'exécution des jobs. |

**Attention au faux ami :** `environment:` dans GitLab représente une cible de déploiement telle que `staging` ou `production`. Il ne remplace pas le bloc Jenkins `environment`.

Deux précisions sur la fiche Jenkins d'origine : les paramètres y sont bien déclarés à l'avance, avec éventuellement une valeur par défaut ; les variables d'environnement ne sont pas des constantes immuables par nature. Leur modification et leur portée dépendent du contexte d'exécution.

## 2. Variables globales et variables de job

```yaml
variables:
  GLOBAL_VAR: "staging"
  APP_NAME: "demo-cicd"

afficher_global:
  script:
    - |
      BUILD_VERSION="1.0.${CI_PIPELINE_IID}"
      echo "Application : $APP_NAME"
      echo "Valeur globale : $GLOBAL_VAR"
      echo "Version : $BUILD_VERSION"

afficher_override:
  variables:
    GLOBAL_VAR: "production"
  script:
    - 'echo "Valeur pour ce job : $GLOBAL_VAR"'
```

Sans autre définition de ces noms dans GitLab, le premier job affiche `staging`, le second `production`. La redéfinition n'affecte que le second job.

Les variables YAML globales sont des valeurs par défaut. Une variable de projet peut prendre le dessus même sur une variable définie dans le job. Pour les sources utilisées ici, la priorité décroissante est :

**Variables de pipeline > projet > groupe > variables YAML du job > variables YAML globales.**

C'est un extrait de la hiérarchie complète, pas sa liste exhaustive. Évitez les noms identiques entre les paramètres du cours et les variables déjà configurées dans le projet. [Priorités officielles](https://docs.gitlab.com/ci/variables/#cicd-variable-precedence)

### Équivalent pratique de `BUILD_NUMBER`

| Variable GitLab | Utilité |
| --- | --- |
| `CI_PIPELINE_IID` | Numéro du pipeline unique dans le projet ; adapté à `1.0.42`. |
| `CI_PIPELINE_ID` | Identifiant du pipeline unique dans l'instance GitLab. |
| `CI_JOB_ID` | Identifiant d'un job ; différent d'un job à l'autre. |
| `CI_COMMIT_SHORT_SHA` | Identifiant court du commit, utile pour identifier le code construit. |

`CI_PIPELINE_IID` est une correspondance pratique avec le numéro de build Jenkins, sans reproduire exactement sa portée : un projet GitLab peut avoir plusieurs branches et plusieurs types de pipelines. Relancer un job du même pipeline ne crée pas un nouveau numéro de pipeline. [Variables prédéfinies](https://docs.gitlab.com/ci/variables/predefined_variables/)

## 3. Équivalent recommandé des paramètres : les inputs

Pour ce cours, utilisez **GitLab 18.1 ou plus récent**, version où les inputs de pipeline sont généralement disponibles. Ils ont été introduits en 17.11 ; les inputs de composants/templates sont une fonctionnalité antérieure. [Versions et lancement manuel](https://docs.gitlab.com/ci/pipelines/#run-a-pipeline-manually)

| Paramètre Jenkins | Déclaration GitLab |
| --- | --- |
| `string(...)` | Input avec `type: string` |
| `booleanParam(...)` | Input avec `type: boolean` |
| `choice(...)` | Input avec `options` |
| `defaultValue` | `default` |

Les inputs sont validés à la création du pipeline et restent fixes pour cette exécution. Ils ne deviennent pas automatiquement des variables d'environnement : on peut recopier un input dans `variables` pour l'utiliser dans le shell. Cette copie suit ensuite les priorités des variables.

Le séparateur `---` termine l'en-tête `spec`. Les valeurs `default` permettent aux déclenchements automatiques d'utiliser une configuration sans saisie interactive. [Inputs GitLab](https://docs.gitlab.com/ci/inputs/)

### Exemple complet : cible et activation des tests

```yaml
spec:
  inputs:
    deploy_env:
      type: string
      description: "Cible du deploiement simule"
      options: [staging, production]
      default: staging
    run_tests:
      type: boolean
      description: "Inclure le job de tests"
      default: true
---
stages:
  - prepare
  - test
  - deploy

variables:
  APP_NAME: "demo-cicd"

afficher_configuration:
  stage: prepare
  variables:
    DEMO_DEPLOY_ENV: "$[[ inputs.deploy_env ]]"
  script:
    - |
      BUILD_VERSION="1.0.${CI_PIPELINE_IID}"
      localVar="Local-${CI_JOB_ID}"
      echo "Application : $APP_NAME"
      echo "Version : $BUILD_VERSION"
      echo "Cible : $DEMO_DEPLOY_ENV"
      echo "Variable locale : $localVar"

tests:
  stage: test
  rules:
    - if: '"$[[ inputs.run_tests ]]" == "true"'
  script:
    - echo "Simulation des tests"

deployer_staging:
  stage: deploy
  rules:
    - if: '"$[[ inputs.deploy_env ]]" == "staging"'
  environment:
    name: staging
  script:
    - 'echo "Simulation vers staging, version 1.0.${CI_PIPELINE_IID}"'

deployer_production:
  stage: deploy
  rules:
    - if: '"$[[ inputs.deploy_env ]]" == "production"'
  environment:
    name: production
  script:
    - 'echo "Simulation vers production, version 1.0.${CI_PIPELINE_IID}"'
```

Ces jobs affichent des messages. Leur mot-clé `environment` crée ou référence néanmoins un environnement et enregistre le déploiement dans GitLab ; aucune application n'est installée par ces commandes.

### Lancer et comparer les résultats

1. Enregistrez le fichier dans le dépôt.
2. Ouvrez **Build > Pipelines > New pipeline**.
3. Sélectionnez la branche contenant ce fichier, puis les inputs.
4. Lancez ces deux essais :

| Valeurs choisies | Jobs présents |
| --- | --- |
| `deploy_env=staging`, `run_tests=true` | `afficher_configuration`, `tests`, `deployer_staging` |
| `deploy_env=production`, `run_tests=false` | `afficher_configuration`, `deployer_production` |

Le job exclu par ses règles est absent du pipeline. Le paramètre booléen ne met pas le pipeline en pause pour poser une question : sa valeur est connue dès le lancement.

### Quand les conditions sont-elles évaluées ?

GitLab remplace d'abord les expressions `$[[ inputs... ]]`, puis évalue les `rules`. Les guillemets dans les conditions préservent une expression valide après substitution. [Exemples d'interpolation](https://docs.gitlab.com/ci/inputs/examples/)

Une valeur calculée par `export RUN_TESTS=false` dans `afficher_configuration` ne peut donc pas supprimer le job `tests` : celui-ci a déjà été sélectionné. Pour une décision pendant l'exécution, utilisez un `if` dans le shell ; le job existe alors et son script choisit quoi faire. Les `rules` ne lisent pas non plus les variables produites ultérieurement par un rapport dotenv. [Évaluation des règles](https://docs.gitlab.com/ci/jobs/job_rules/)

## 4. Variante : paramètres avec des variables de pipeline

Cette méthode reste utile pour comprendre les configurations existantes ou une instance sans inputs de pipeline. Le projet doit autoriser votre rôle à fournir des variables au lancement.

Remplacez le fichier par cet exemple :

```yaml
variables:
  DEPLOY_ENV:
    value: "staging"
    options: ["staging", "production"]
    description: "Cible du deploiement simule"
  RUN_TESTS:
    value: "true"
    options: ["true", "false"]
    description: "Executer les tests"

stages: [test, deploy]

tests:
  stage: test
  rules:
    - if: '$RUN_TESTS == "true"'
  script:
    - echo "Simulation des tests"

deployer:
  stage: deploy
  script:
    - 'echo "Simulation vers $DEPLOY_ENV"'
```

Dans **New pipeline**, les variables décrites sont préremplies. Ici, `"true"` et `"false"` sont des **chaînes**, pas des booléens typés. Le menu `options` facilite la saisie manuelle ; il ne fournit pas le même contrat de validation qu'un input pour toutes les voies de lancement. [Variables dans le YAML](https://docs.gitlab.com/ci/yaml/#variables)

## 5. Variables locales et valeur de repli

L'équivalent Bash du choix Jenkins `params.DEPLOY_ENV ?: env.GLOBAL_VAR`, pour des valeurs textuelles, peut s'écrire :

```yaml
variables:
  GLOBAL_VAR: "staging"

demo_repli:
  script:
    - |
      targetEnv="${DEPLOY_ENV:-$GLOBAL_VAR}"
      echo "Cible retenue : $targetEnv"
```

Si `DEPLOY_ENV` est absente ou vide, ce job affiche `staging`. Sinon, il affiche la valeur fournie. Avec les inputs, préférez un `default` explicite pour choisir la valeur dès la création du pipeline.

`targetEnv` reste dans le shell de ce job. `export targetEnv` la transmettrait aux processus enfants, pas aux autres jobs. `before_script` et `script` partagent un shell ; `after_script` utilise un contexte séparé et ne récupère pas les variables créées par le script. Le thème `post` détaillera cette différence. [Contexte des scripts](https://docs.gitlab.com/ci/variables/#exporting-variables)

Sur PowerShell, une variable CI/CD se lit avec `$env:GLOBAL_VAR` et une variable locale se déclare avec `$targetEnv = ...`. Les exemples Bash de ce cours doivent être adaptés. [Syntaxe selon le shell](https://docs.gitlab.com/ci/variables/job_scripts/)

## 6. Transmettre une valeur calculée à un autre job

Les jobs GitLab n'ont pas de mémoire de variables partagée. Pour transmettre une version calculée, publiez un rapport `dotenv` :

```yaml
stages: [prepare, deploy]

calculer_version:
  stage: prepare
  script:
    - printf 'BUILD_VERSION=1.0.%s\n' "$CI_PIPELINE_IID" > build.env
  artifacts:
    reports:
      dotenv: build.env

utiliser_version:
  stage: deploy
  needs:
    - job: calculer_version
      artifacts: true
  script:
    - 'echo "Version recue : $BUILD_VERSION"'
```

Le second job reçoit `BUILD_VERSION` grâce au rapport, pas grâce à un `export` du premier job. Réservez ce mécanisme aux données non secrètes, car le rapport est un artefact consultable. Les artefacts seront approfondis dans leur propre fiche. [Transmission avec dotenv](https://docs.gitlab.com/ci/variables/dotenv_variables/)

## 7. Environnements de déploiement et secrets

`environment: name: production` associe un job à une cible suivie dans **Operate > Environments**. Ce mot-clé n'installe pas le serveur et ne sélectionne pas le runner : les `tags` gardent ce rôle.

Les variables de projet peuvent être limitées à un environnement, par exemple un même nom `API_URL` avec une valeur pour `staging` et une autre pour `production`. La portée d'environnement correspond à l'environnement du job, pas simplement au nom de la branche. Évitez d'utiliser ces variables à portée d'environnement pour construire les `rules` ou les `include`. [Environnements et portée des variables](https://docs.gitlab.com/ci/environments/)

Pour un token, utilisez **Settings > CI/CD > Variables**, pas un input ni une valeur écrite dans le dépôt. Le masquage limite son affichage dans les journaux ; la protection restreint sa disponibilité, notamment aux branches/tags protégés. Ces deux réglages ne sont pas interchangeables. [Variables sensibles](https://docs.gitlab.com/ci/variables/#cicd-variable-security)
