# Environnements GitHub et protections de déploiement

## Objectif

Séparer les contrôles d'accès à une cible de livraison des paramètres ordinaires d'un workflow.

## 1. Correspondances

GitLab possède également des environnements et des protections. La particularité GitHub est leur association aux jobs via `environment`, avec reviewers, règles de branches/tags, secrets et autres protections disponibles.

| Élément | Rôle |
| --- | --- |
| `env` | Variables fournies aux commandes |
| `environment` | Cible de déploiement et règles d'accès |
| Input `type: environment` | Sélection d'un nom au lancement |
| `concurrency` | Limitation des exécutions simultanées |

Choisir un environnement dans un input n'y rattache pas automatiquement le job : celui-ci doit déclarer `environment`.

## 2. Configurer production

Dans **Settings > Environments**, créez `production`, puis :

1. Restreignez les branches/tags de déploiement, par exemple à `main`.
2. Configurez des reviewers si votre offre le permet.
3. Activez l'interdiction d'auto-approbation si une autre personne doit valider.
4. Ajoutez une variable `APP_URL`, par exemple `https://app.example.org`.
5. Ajoutez les secrets de déploiement nécessaires à la vraie application.

Le YAML seul ne définit pas les reviewers. Référencer un nouveau nom peut créer un environnement sans les protections attendues : configurez-le avant utilisation. [Gestion des environnements](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

## 3. Exemple complet

Fichier `.github/workflows/environment.yml` :

```yaml
name: Environnement protege
on:
  workflow_dispatch:
permissions: {}
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Construction simulee"
  deploy:
    needs: build
    runs-on: ubuntu-24.04
    environment:
      name: production
      url: ${{ steps.address.outputs.url }}
    concurrency:
      group: deployment-production
      cancel-in-progress: false
      queue: max
    steps:
      - id: address
        env:
          APP_URL: ${{ vars.APP_URL }}
        run: |
          test -n "$APP_URL"
          echo "url=$APP_URL" >> "$GITHUB_OUTPUT"
          echo "Livraison simulee, aucune modification du serveur"
```

**Résultat attendu :** le job passe les règles configurées, attend une approbation si requise, puis publie l'URL dans le suivi de déploiement. Cette URL est illustrative : le workflow ne crée pas de site.

## 4. Approbation, attente et concurrence

Avec plusieurs reviewers configurés, une seule approbation parmi les reviewers requis suffit ; ce n'est pas un quorum de tous les noms.

Un minuteur retarde le job sans faire tourner un `sleep` sur le runner. `concurrency` protège une cible de livraisons simultanées ; l'environnement seul ne fournit pas ce verrou.

Les secrets d'environnement ne sont disponibles qu'après passage des protections. [Règles d'environnement](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

## 5. Disponibilité

Sur les offres Free, Pro et Team, les reviewers obligatoires et minuteurs sont limités aux dépôts publics. Les environnements de dépôts privés/internes exigent une offre adaptée ; les règles disponibles varient selon l'offre et GitHub Enterprise Server.

Si le réglage n'est pas proposé, ne considérez pas l'environnement comme protégé par une approbation qui n'existe pas. [Conditions de disponibilité](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments)

## Exercice
