# Artefacts : conserver, transmettre et publier les résultats des jobs

## Objectif

Adapter `archiveArtifacts`, `fingerprint`, `copyArtifacts` et `stash/unstash` de Jenkins à GitLab CI/CD. Reprendre aussi les usages du support : téléchargement, réutilisation d'un JAR, transfert distant et publication Maven.

Les exemples complets remplacent `.gitlab-ci.yml`. Les fragments à intégrer sont explicitement signalés. Utilisez un runner Linux avec un shell et les outils mentionnés, disponible pour le projet et acceptant les jobs sans tags ; sinon, ajoutez ses tags.

## 1. Correspondances et différences

| Jenkins | GitLab CI/CD | Différence |
| --- | --- | --- |
| `archiveArtifacts artifacts: 'target/*.jar'` | `artifacts:paths` dans le job producteur | L'envoi intervient après les scripts du job. |
| `fingerprint: true` | Pas de correspondance directe | Une somme SHA-256 peut vérifier les fichiers, sans reproduire le suivi Jenkins. |
| Réutilisation dans un autre stage | Téléchargement d'artefacts dans le job suivant | Ne pas supposer un espace de travail partagé. |
| `stash` / `unstash` | Artefacts et `needs:artifacts` | Pas de stash nommé distinct : les fichiers sont attachés à un job. |
| `copyArtifacts` | Selon le cas : `needs`, `needs:project`, API | Le choix du pipeline source est essentiel. |
| Publication Nexus / Artifactory | Commandes Maven dans `script` | Ce stockage reste distinct des artefacts de job. |

Dans l'exemple Jenkins, `archiveArtifacts` rend les fichiers téléchargeables ; il ne les restaure pas automatiquement sur n'importe quel autre agent. Le fingerprint permet un suivi d'utilisation entre builds. [Archivage Jenkins](https://www.jenkins.io/doc/pipeline/steps/core/#archiveartifacts-archive-the-artifacts)

## 2. Premier exemple sans Java : produire puis récupérer un fichier

```yaml
# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [build, verification]

# Déclare le job « produire » et sa configuration propre.
produire:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: build
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Prépare le répertoire utilisé par les fichiers de cette étape.
    - mkdir -p dist
    # Écrit ces données dans le fichier indiqué pour une étape ultérieure.
    - 'printf "Pipeline %s, commit %s\n" "$CI_PIPELINE_IID" "$CI_COMMIT_SHA" > dist/resultat.txt'
  # Conserve les fichiers ou rapports du job pour consultation ou transmission.
  artifacts:
    name: "resultat-$CI_PIPELINE_IID"
    # Sélectionne les fichiers du workspace à publier comme artefacts.
    paths:
      - dist/resultat.txt
    # Fixe la durée de conservation demandée pour ces artefacts.
    expire_in: 7 days

# Déclare le job « consommer » et sa configuration propre.
consommer:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: verification
  # Crée une dépendance directe vers ces jobs ; précise aussi la récupération de leurs artefacts.
  needs:
    - job: produire
      # Choisit si les artefacts de ce job amont doivent être téléchargés par le job courant.
      artifacts: true
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - test -f dist/resultat.txt
    # Affiche le contenu ou la liste des fichiers pour vérifier le résultat de l'étape précédente.
    - cat dist/resultat.txt
```

Le runner envoie le fichier à GitLab après `produire`. GitLab le fournit ensuite au runner de `consommer`, même si c'est une autre machine. `paths` est relatif au répertoire du projet. `name` nomme l'archive téléchargeable, sans renommer les fichiers qu'elle contient. [Création d'artefacts](https://docs.gitlab.com/ci/jobs/job_artifacts/)

## 3. Reprendre le build Maven du support Jenkins

Prérequis : un projet Maven simple, non multimodule, produisant un JAR dans `target/`, avec `pom.xml`, `mvnw` et `.mvn/` versionnés. Les runners doivent disposer du JDK adapté, de `sha256sum` et des outils nécessaires au wrapper Maven. Le réseau doit permettre de récupérer Maven et les dépendances.

```yaml
# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [build, verification]

# Déclare le job « build_maven » et sa configuration propre.
build_maven:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: build
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh ./mvnw -B clean package
    - |
      set -- target/*.jar
      # Vérifie la présence du fichier ou de la valeur avant de poursuivre le traitement.
      if [ "$#" -ne 1 ] || [ ! -f "$1" ]; then
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        echo "Cet exemple attend exactement un JAR dans target/"
        # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
        exit 1
      fi
      sha256sum "$1" > target/SHA256SUMS
  # Conserve les fichiers ou rapports du job pour consultation ou transmission.
  artifacts:
    name: "application-$CI_COMMIT_SHORT_SHA-$CI_PIPELINE_IID"
    # Sélectionne les fichiers du workspace à publier comme artefacts.
    paths:
      - target/*.jar
      - target/SHA256SUMS
    # Fixe la durée de conservation demandée pour ces artefacts.
    expire_in: 7 days

# Déclare le job « inspecter_jar » et sa configuration propre.
inspecter_jar:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: verification
  # Crée une dépendance directe vers ces jobs ; précise aussi la récupération de leurs artefacts.
  needs:
    - job: build_maven
      # Choisit si les artefacts de ce job amont doivent être téléchargés par le job courant.
      artifacts: true
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sha256sum -c target/SHA256SUMS
    - |
      set -- target/*.jar
      # Vérifie la présence du fichier ou de la valeur avant de poursuivre le traitement.
      if [ "$#" -ne 1 ] || [ ! -f "$1" ]; then
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        echo "JAR absent ou plusieurs JAR trouves"
        # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
        exit 1
      fi
      jar tf "$1"
```

Le dépôt est normalement récupéré par le runner : pas de stage `Checkout` nécessaire. L'archivage est déclaré **sur le job qui produit le JAR**, au lieu d'un job isolé qui supposerait retrouver son disque.

Si votre projet produit un WAR ou plusieurs modules, adaptez les chemins et le contrôle du nombre de fichiers. Ici, ce contrôle évite qu'un motif sans résultat ou plusieurs JAR soient utilisés silencieusement.

### Somme de contrôle et exécution Java

La vérification SHA-256 confirme que le fichier reçu correspond à la somme enregistrée. Elle ne crée pas un historique d'usage inter-jobs comme le fingerprint Jenkins et ne prouve pas l'origine du fichier si le fichier et sa somme ont tous deux été remplacés.

`jar tf` inspecte l'archive sans démarrer de service. Pour un **JAR exécutable** et un test prévu à cet effet, `java -jar chemin-exact.jar` peut le lancer. Un JAR de bibliothèque n'est pas forcément exécutable, et une application serveur peut rester active jusqu'au timeout du job. Cette commande ne constitue pas à elle seule un déploiement distant.

## 4. Télécharger et choisir les artefacts entrants

Dans **Build > Pipelines**, ouvrez le job producteur puis téléchargez ou parcourez ses artefacts. **Build > Artifacts** les regroupe également au niveau du projet. [Accès aux artefacts](https://docs.gitlab.com/ci/jobs/job_artifacts/)

| Configuration du consommateur | Effet |
| --- | --- |
| Aucune sélection explicite | Télécharge normalement les artefacts des stages précédents. |
| `dependencies: [build_maven]` | Sélectionne ce producteur d'un stage précédent, en gardant l'ordre des stages. |
| `dependencies: []` | Ne télécharge aucun artefact précédent. |
| `needs` avec `artifacts: true` | Attend les jobs indiqués et récupère leurs artefacts ; peut démarrer avant la fin des autres jobs des stages précédents. |
| `needs` avec `artifacts: false` | Attend la dépendance sans télécharger ses fichiers. |

Ne combinez pas `dependencies` et `needs` dans un même job. Avec `needs`, seuls les producteurs listés sont pris en compte pour le téléchargement. [Référence needs:artifacts](https://docs.gitlab.com/ci/yaml/#needsartifacts)

Choisissez des chemins distincts si plusieurs producteurs livrent des fichiers : deux archives contenant le même `dist/resultat.txt` peuvent se recouvrir à l'extraction.

## 5. Conserver les résultats même après un échec

Exemple complet pour un projet Maven utilisant Surefire pour ses tests :

```yaml
# Déclare le job « tests_maven » et sa configuration propre.
tests_maven:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh ./mvnw -B test
  # Conserve les fichiers ou rapports du job pour consultation ou transmission.
  artifacts:
    # Définit selon quel résultat du job les artefacts seront collectés.
    when: always
    # Sélectionne les fichiers du workspace à publier comme artefacts.
    paths:
      - target/surefire-reports/
    # Déclare des rapports que GitLab interprète selon leur type.
    reports:
      junit: target/surefire-reports/TEST-*.xml
    # Fixe la durée de conservation demandée pour ces artefacts.
    expire_in: 7 days
```

`paths` fournit les fichiers à télécharger ; `reports:junit` permet leur lecture comme résultats de tests dans GitLab. Le rapport ne remplace pas le code de sortie de Maven : le processus de test doit signaler son échec. [Rapports de tests](https://docs.gitlab.com/ci/testing/unit_test_reports/)

La collecte ordinaire se fait après réussite par défaut. `when: always` conserve les fichiers existants après réussite ou échec normal ; elle ne les crée pas et ne garantit pas leur envoi après timeout total ou perte du runner. Les rapports disposent de leur propre collecte après succès/échec. [Types de rapports](https://docs.gitlab.com/ci/yaml/artifacts_reports/)

Les fichiers produits dans `after_script` peuvent aussi être archivés, car cette étape précède l'envoi. Voir [3.post.md](3.post.md).

## 6. Autre pipeline ou autre projet : équivalent de `copyArtifacts`

### Récupérer le dernier build réussi sur une référence

Exemple complet à placer dans le projet consommateur, avec **Premium/Ultimate**. Le projet `mon-groupe/app-build` doit avoir exécuté avec succès le job `build_maven` du chapitre 3 sur `main`. Remplacez le chemin du projet et vérifiez les droits de lecture :

```yaml
# Déclare le job « recuperer_autre_projet » et sa configuration propre.
recuperer_autre_projet:
  # Crée une dépendance directe vers ces jobs ; précise aussi la récupération de leurs artefacts.
  needs:
    - project: mon-groupe/app-build
      job: build_maven
      ref: main
      # Choisit si les artefacts de ce job amont doivent être téléchargés par le job courant.
      artifacts: true
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sha256sum -c target/SHA256SUMS
    # Affiche le contenu ou la liste des fichiers pour vérifier le résultat de l'étape précédente.
    - ls -l target/
```

**Attention :** `needs:project` télécharge les artefacts du dernier job réussi pour cette référence. Il ne lance pas le producteur et n'attend pas un build en cours. Il peut donc récupérer une version précédente. [Référence needs:project](https://docs.gitlab.com/ci/yaml/#needsproject)

Pour un livrable précis, l'API permet le téléchargement par identifiant de job ; une URL du « dernier réussi sur main » est une référence mobile. L'authentification et les droits doivent correspondre à l'endpoint choisi. [API des artefacts](https://docs.gitlab.com/api/job_artifacts/)

Pour un pipeline enfant dans la même hiérarchie, `needs:pipeline:job` cible un job réussi d'un pipeline identifié. Le simple `trigger` de [5.triggers.md](5.triggers.md) ne transfère pas automatiquement tous les fichiers. [Pipelines en aval](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/)

## 7. Transférer le JAR vers un serveur

Ce **fragment** complète le pipeline Maven du chapitre 3. Ajoutez `deploy` à sa liste `stages`.

Prérequis : `scp` sur le runner, connexion SSH configurée avec une clé autorisée et une clé d'hôte vérifiée, variables `DEPLOY_USER` et `DEPLOY_HOST`, répertoire `/opt/apps/` accessible en écriture. La configuration SSH sera détaillée au prochain thème. [Clés SSH dans les jobs](https://docs.gitlab.com/ci/jobs/ssh_keys/)

```yaml
# Déclare le job « transfert_serveur » et sa configuration propre.
transfert_serveur:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: deploy
  # Attend une intervention manuelle pour lancer ce job.
  when: manual
  # Détermine si l'échec de ce job peut être toléré dans le résultat du pipeline.
  allow_failure: false
  # Limite les jobs antérieurs dont les artefacts seront récupérés.
  dependencies:
    - build_maven
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sha256sum -c target/SHA256SUMS
    # Transfère le fichier vers la VM ; -P désigne le port SSH pour scp.
    - scp target/*.jar "${DEPLOY_USER}@${DEPLOY_HOST}:/opt/apps/"
```

`dependencies` récupère le JAR déjà construit ; l'ordre des stages attend également la vérification. Le transfert manuel ne recompile pas le projet. Il copie le fichier, sans démarrer ni redémarrer l'application distante.

## 8. Publier dans Nexus, Artifactory ou GitLab Package Registry

Un artefact de job est lié à une exécution CI. Un dépôt Maven stocke un paquet identifié par ses coordonnées et sa version, destiné à être consommé durablement.

Pour Nexus ou Artifactory, le principe Maven du support reste valable. Dans le `pom.xml`, adaptez l'URL et l'identifiant du dépôt :

```xml
<!-- Définit les destinations de publication Maven, distinctes de l'archivage CI. -->
<distributionManagement>
    <repository>
        <!-- Identifiant à faire correspondre au serveur configuré dans les réglages Maven. -->
        <id>releases</id>
        <!-- Adresse du dépôt auquel Maven enverra les livrables. -->
        <url>https://nexus.example.com/repository/maven-releases/</url>
    </repository>
</distributionManagement>
```

Les versions `SNAPSHOT` peuvent nécessiter un dépôt `snapshotRepository` distinct. Les identifiants d'authentification appartiennent à `settings.xml`, avec un `server/id` correspondant au dépôt, pas au `pom.xml`. [Maven Deploy Plugin](https://maven.apache.org/plugins/maven-deploy-plugin/usage.html)

Exemple complet, à utiliser **à la place** du pipeline de build précédent : configurez une variable CI/CD de type **File** nommée `MAVEN_SETTINGS_FILE` contenant les réglages Maven appropriés.

```yaml
# Déclare le job « publier_maven » et sa configuration propre.
publier_maven:
  # Attend une intervention manuelle pour lancer ce job.
  when: manual
  # Détermine si l'échec de ce job peut être toléré dans le résultat du pipeline.
  allow_failure: false
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    - sh ./mvnw -B -s "$MAVEN_SETTINGS_FILE" clean deploy
```

Cette commande exécute le cycle Maven, construit puis publie le paquet. Un `mvn deploy` dans un second job n'est pas une simple copie du JAR récupéré : il parcourt à nouveau le cycle de build. Pour promouvoir exactement un fichier déjà testé, utilisez une publication de fichier existant avec son POM et ses coordonnées, ou un mécanisme de promotion du dépôt.

Le **GitLab Maven Package Registry** est une alternative intégrée ; ses URL et son authentification sont propres à GitLab et ne se déduisent pas d'`artifacts:paths`. [Dépôt Maven GitLab](https://docs.gitlab.com/user/packages/maven_repository/)

## 9. Artefacts, cache et durée de conservation

| Mécanisme | Usage |
| --- | --- |
| Artefacts | JAR testé, rapport ou fichier transmis à un job suivant. |
| Cache | Accélérer une exécution, par exemple en réutilisant des dépendances Maven. |
| Package Registry | Distribuer une version de paquet à d'autres projets ou outils. |

Le cache peut être absent ; le job doit pouvoir fonctionner sans lui. Il ne remplace donc pas la transmission explicite du livrable testé. Évitez de mettre `target/` simultanément dans le cache et les artefacts, afin de ne pas mélanger des sorties anciennes et nouvelles. [Cache GitLab](https://docs.gitlab.com/ci/caching/)

`expire_in` concerne les fichiers archivés, pas la suppression du pipeline. Les politiques de conservation des derniers artefacts peuvent prendre le dessus. Prévoyez une durée couvrant les validations manuelles : un job lancé trop tard peut ne plus récupérer le fichier. Voir [4.options.md](4.options.md).

## 10. Dépannage et exercices

- **No files to upload** : vérifiez que le build produit réellement le chemin déclaré. Un motif d'archivage n'est pas une vérification métier ; le contrôle explicite du JAR dans l'exemple rend son absence bloquante.
- **Artefacts introuvables** : vérifiez expiration, droits et nom du producteur, puis `needs` ou `dependencies`.
- **Mauvaise version téléchargée** : vérifiez si vous utilisez une référence mobile, comme le dernier build réussi de `main`.
- **Archive refusée** : vérifiez la limite de taille applicable à votre instance/projet et limitez les fichiers collectés. [Dépannage des artefacts](https://docs.gitlab.com/ci/jobs/job_artifacts_troubleshooting/)

1. Exécutez le premier exemple et téléchargez `dist/resultat.txt` depuis le job producteur.
2. Remplacez `artifacts: true` par `false` dans son consommateur : vérifiez l'échec du contrôle de présence, en gardant `dist/resultat.txt` hors du dépôt Git.
3. Avec Maven, comparez le JAR et sa somme dans les deux jobs.
4. Provoquez un échec de test et vérifiez les rapports Surefire encore disponibles.
5. Comparez un téléchargement par job précis et la récupération du dernier build réussi d'une branche.

Les exemples ont été relus à partir des documentations officielles. Aucun build Maven, transfert SSH ou envoi vers un dépôt de paquets n'a été exécuté. Validez la configuration et les prérequis du projet avant les essais.
