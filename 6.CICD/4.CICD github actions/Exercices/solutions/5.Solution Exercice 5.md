# Solution 5 — Planification et configuration selon la source

[Énoncé](../5.Exercice%205.md) · [Guide commun](../readme.md)

## 1. Réglage préalable

Dans **Settings > Secrets and variables > Actions > Variables**, créer la variable de dépôt `NIGHTLY_TARGET` avec `dev`, `staging` ou `prod`. Ce n'est pas un secret. Le workflow utilise `dev` si elle est absente.

Le workflow doit se trouver sur la branche par défaut. Créer `.github/workflows/exercice-5.yml` :

```yaml
name: Exercice 5 - Simulation nocturne
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
    # Déclare les paramètres attendus ; leur type et leurs contraintes définissent le contrat.
    inputs:
      # Définit le paramètre « cible » et les contraintes de sa valeur.
      cible:
        description: Cible de la simulation manuelle
        required: true
        type: choice
        options: [dev, staging, prod]
        # Fournit la valeur utilisée si cet input n'est pas renseigné.
        default: dev
  # Définit un déclenchement périodique ; les paramètres du lancement manuel ne sont pas fournis ici.
  schedule:
    # Exprime les minutes, heures, jours du mois, mois et jours de semaine de la planification.
    - cron: '0 2 * * *'
      # Interprète le cron dans ce fuseau plutôt qu'en UTC.
      timezone: Europe/Paris

# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Définit les réglages par défaut des commandes run dans cette portée.
defaults:
  # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
  run:
    # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
    shell: bash

# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « preparer_configuration » ; needs permet de préciser ses dépendances.
  preparer_configuration:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Arrête le traitement si sa durée dépasse ce nombre de minutes.
    timeout-minutes: 5
    # Expose les valeurs produites pour les étapes, jobs ou workflows consommateurs selon cette portée.
    outputs:
      cible: ${{ steps.configuration.outputs.cible }}
      api_url: ${{ steps.configuration.outputs.api_url }}
      db_name: ${{ steps.configuration.outputs.db_name }}
      notify: ${{ steps.configuration.outputs.notify }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Choisir et calculer
        id: configuration
        # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
        env:
          EXO_SOURCE: ${{ github.event_name }}
          EXO_MANUEL: ${{ inputs.cible }}
          EXO_NOCTURNE: ${{ vars.NIGHTLY_TARGET }}
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie, propage aussi les erreurs dans les pipelines de commandes.
          set -euo pipefail
          # Sélectionne le cas correspondant à la valeur ; la branche de repli traite les valeurs non prévues.
          case "$EXO_SOURCE" in
            workflow_dispatch) cible="$EXO_MANUEL" ;;
            schedule) cible="${EXO_NOCTURNE:-dev}" ;;
            *) echo "Source non prise en charge" >&2; exit 1 ;;
          esac
          case "$cible" in
            dev) api_url="https://dev.example.test"; db_name="dev_db"; notify="dev@example.test" ;;
            staging) api_url="https://staging.example.test"; db_name="staging_db"; notify="qa@example.test" ;;
            prod) api_url="https://prod.example.test"; db_name="prod_db"; notify="ops@example.test" ;;
            *) echo "Cible invalide" >&2; exit 1 ;;
          esac
          {
            # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
            printf 'cible=%s\n' "$cible"
            printf 'api_url=%s\n' "$api_url"
            printf 'db_name=%s\n' "$db_name"
            printf 'notify=%s\n' "$notify"
          # Publie une sortie d'étape ; son exposition au niveau du job permet ensuite un échange via needs.
          } >> "$GITHUB_OUTPUT"

  # Déclare le job « simuler_deploiement » ; needs permet de préciser ses dépendances.
  simuler_deploiement:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: preparer_configuration
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Arrête le traitement si sa durée dépasse ce nombre de minutes.
    timeout-minutes: 5
    # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
    env:
      EXO_CIBLE: ${{ needs.preparer_configuration.outputs.cible }}
      EXO_API_URL: ${{ needs.preparer_configuration.outputs.api_url }}
      EXO_DB_NAME: ${{ needs.preparer_configuration.outputs.db_name }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
      - run: |
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Simulation %s : API_URL=%s DB_NAME=%s\n' "$EXO_CIBLE" "$EXO_API_URL" "$EXO_DB_NAME"

  # Déclare le job « notifier_succes » ; needs permet de préciser ses dépendances.
  notifier_succes:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: [preparer_configuration, simuler_deploiement]
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Arrête le traitement si sa durée dépasse ce nombre de minutes.
    timeout-minutes: 5
    # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
    env:
      EXO_CIBLE: ${{ needs.preparer_configuration.outputs.cible }}
      EXO_NOTIFY: ${{ needs.preparer_configuration.outputs.notify }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Simuler la notification
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Notification simulee pour %s vers %s\n' "$EXO_CIBLE" "$EXO_NOTIFY"
          {
            printf '### Simulation nocturne ou manuelle\n'
            printf -- '- Cible : %s\n' "$EXO_CIBLE"
            printf -- '- Notification simulee : %s\n' "$EXO_NOTIFY"
          # Ajoute ces informations au résumé consultable dans l'interface de l'exécution.
          } >> "$GITHUB_STEP_SUMMARY"
```

## 2. Deux événements, deux sources de paramètres

La branche `workflow_dispatch` lit l'input. La branche `schedule` lit une variable de dépôt, avec un défaut explicite. Le `case` refuse une valeur incorrecte avant toute simulation. GitLab propose des inputs sur ses schedules ; on ne peut pas copier ce mécanisme dans le bloc `schedule` GitHub.

La notification dépend des **deux** jobs : elle attend le déploiement simulé et peut lire les outputs de préparation. Le contexte `needs` contient les dépendances directes. Aucune notification réseau ou email réel n'est effectué.

## 3. Heure de Paris et limites

`timezone: Europe/Paris` est la syntaxe GitHub.com documentée lors de la rédaction. Sans fuseau, le cron est en UTC. Vérifier la compatibilité sur GitHub Enterprise Server ; un cron fixe en UTC ne conserve pas toute l'année 2 h à Paris.

Le schedule utilise le dernier commit de la branche par défaut. L'heure est une intention de planification, pas une garantie de démarrage à la seconde : une forte charge peut retarder ou faire abandonner des déclenchements. Au passage à l'heure d'été, une heure locale inexistante est décalée vers la prochaine heure valide. [Comportement des schedules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 4. Essais

1. Lancer manuellement pour chaque cible et vérifier les trois valeurs calculées.
2. Mettre `NIGHTLY_TARGET=staging`, observer un déclenchement `schedule` et vérifier la cible.
3. Tester localement le script avec `EXO_SOURCE=schedule` et une cible invalide : échec attendu.
4. Faire échouer la simulation : le job de notification doit être ignoré.
5. Consulter le résumé puis désactiver le workflow ou supprimer le déclencheur planifié après l'atelier.

Ne pas demander de saisie humaine dans le job nocturne. Si un déploiement réel devait exiger une approbation, il faudrait ajouter un environnement protégé et accepter que le job attende cette approbation.
