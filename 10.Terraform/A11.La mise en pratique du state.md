# Atelier : Mise en pratique du State Terraform

## Objectif

Mettre en pratique les notions visibles dans votre schéma :

**rôle du state**,  
**terraform.tfstate**,  
**drift**,  
**import**,  
**state rm**,  
**state mv**,  
**state show**.

On reste d'abord sur un atelier simple avec le **provider Local**, pour éviter AWS, Azure ou toute authentification.  
Pour la partie **import**, on utilise ensuite un mini-exemple avec **Docker Desktop**, car la ressource `local_file` du provider Local ne supporte pas `terraform import`.

---

# 1. Préparation du projet

Créer le dossier de travail :

```bash
mkdir -p ~/terraform-state-lab
cd ~/terraform-state-lab
```

Nettoyer le dossier si nécessaire :

```bash
rm -f *.txt
rm -f terraform.tfstate
rm -f terraform.tfstate.backup
rm -f .terraform.lock.hcl
rm -rf .terraform
```

Créer le fichier **main.tf** :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

resource "local_file" "web" {
  filename = "web.txt"
  content  = "Fichier web géré par Terraform"
}

resource "local_file" "api" {
  filename = "api.txt"
  content  = "Fichier api géré par Terraform"
}

output "managed_files" {
  value = {
    web = local_file.web.filename
    api = local_file.api.filename
  }
}
```

Exécuter :

```bash
terraform init
terraform fmt
terraform validate
terraform plan
terraform apply -auto-approve
```

Observer :

```bash
ls -l
cat web.txt
cat api.txt
terraform state list
```

Résultat attendu :

```text
local_file.api
local_file.web
```

Point clé :

**Terraform a créé deux fichiers et les a enregistrés dans le state.**

# 7. Utiliser state rm

Objectif : retirer une ressource du state sans supprimer le fichier réel.

Exécuter :

```bash
terraform state rm local_file.api
```

Vérifier le state :

```bash
terraform state list
```

Vérifier le fichier réel :

```bash
ls -l api.txt
cat api.txt
```

Observation attendue :

Le fichier **api.txt** existe encore, mais Terraform ne le suit plus.

Point clé :

**terraform state rm retire une ressource du state sans détruire l’objet réel.**

Attention :

Après **state rm**, Terraform oublie la ressource.  
Si le code contient encore cette ressource, un prochain **terraform plan** peut proposer de la recréer.

Vérifier :

```bash
terraform plan
```

Observation attendue :

Terraform propose de gérer à nouveau **local_file.api**.

# 8. Après state rm : remettre api sous gestion Terraform

Objectif : comprendre une limite importante du provider Local.

Dans notre cas, **api.txt** existe encore, mais Terraform ne le suit plus depuis **state rm**.

On pourrait être tenté d'exécuter :

```bash
terraform import local_file.api api.txt
```

Mais avec le provider **hashicorp/local**, cette commande échoue :

```text
Resource Import Not Implemented
This resource does not support import.
```

Point clé :

**Toutes les ressources Terraform ne supportent pas import.**  
La commande `terraform import` dépend du provider et de la ressource.

Comme le bloc **resource** existe toujours dans **main.tf**, on peut remettre **api.txt** sous gestion Terraform avec :

```bash
terraform apply -auto-approve
terraform state list
```

Résultat attendu :

```text
local_file.api
local_file.web
```

Attention :

Dans un vrai environnement, il ne faut pas remplacer automatiquement `import` par `apply`.  
Ici c'est acceptable parce que l'objet est seulement un fichier local de laboratoire.

# 9. Utiliser state mv

Objectif : renommer une adresse Terraform sans recréer la ressource.

Situation actuelle :

```text
local_file.web
```

On veut renommer l’adresse en :

```text
local_file.frontend
```

Modifier **main.tf** :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

resource "local_file" "frontend" {
  filename = "web.txt"
  content  = "Fichier web modifié par Terraform"
}

resource "local_file" "api" {
  filename = "api.txt"
  content  = "Fichier api géré par Terraform"
}

output "managed_files" {
  value = {
    frontend = local_file.frontend.filename
    api      = local_file.api.filename
  }
}
```

Avant de lancer **plan**, déplacer l’adresse dans le state :

```bash
terraform state mv local_file.web local_file.frontend
```

Vérifier :

```bash
terraform state list
```

Résultat attendu :

```text
local_file.api
local_file.frontend
```

Puis :

```bash
terraform plan
```

Observation attendue :

Terraform ne propose pas de détruire puis recréer **web.txt** à cause du renommage.  
Il peut seulement proposer de mettre à jour la valeur de l'output `managed_files`, car la clé passe de `web` à `frontend`.

Point clé :

**terraform state mv sert à renommer ou déplacer une adresse dans le state.**

Utile lors des refactorisations.

# 10. Import d'une ressource existante avec le provider Random

Objectif : faire un vrai **terraform import** sur une ressource qui le supporte, sans quitter l'environnement local et sans aucun prérequis supplémentaire.

Le provider `hashicorp/random` supporte `terraform import`. On simule une chaîne aléatoire déjà générée hors Terraform et on l'adopte dans le state.

## Scénario

Un identifiant `app-legacy-2024` a été généré hors Terraform. L'équipe veut le rattacher au state sans le recréer.

## Préparer le projet

Créer un sous-dossier dédié :

```bash
mkdir -p ~/terraform-import-lab
cd ~/terraform-import-lab
```

Créer le fichier **main.tf** :

```hcl
terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}

resource "random_string" "legacy" {
  length  = 16
  special = false
  upper   = false
}
```

Initialiser :

```bash
terraform init
```

## Vérifier que le state est vide

```bash
terraform state list
```

Résultat attendu : liste vide — Terraform ne connaît pas encore `random_string.legacy`.

## Importer la ressource existante

```bash
terraform import random_string.legacy "app-legacy-2024"
```

Résultat attendu :

```text
Import successful!
The resources that were imported are shown above. These resources are now in
your Terraform state and will henceforth be managed by Terraform.
```

## Vérifier

```bash
terraform state list
terraform state show random_string.legacy
```

Résultat attendu :

```text
random_string.legacy
```

## Observer le plan après import

```bash
terraform plan
```

Point clé :

**terraform import rattache une ressource existante au state, mais il ne génère pas automatiquement un code Terraform parfaitement aligné avec la réalité.**

Il peut rester des écarts entre :

```text
la valeur réellement importée
le state importé
le bloc resource écrit dans main.tf (length, upper, special…)
```

Dans un vrai projet, après un import, on ajuste le code jusqu'à obtenir un `terraform plan` sans changement.

Attention :

Ne lancez pas `terraform apply` si Terraform propose de remplacer la ressource.  
Ajustez d'abord les attributs du bloc `resource` pour les aligner avec ce que `terraform state show` affiche.

## Nettoyage

```bash
cd ..
rm -rf ~/terraform-import-lab
```

# 13. Backend GitLab — Stocker le state sur GitLab

## 13.1 Pourquoi un backend distant ?

Le fichier `terraform.tfstate` local a deux problèmes fondamentaux en équipe :

```text
Partage impossible    → chaque développeur a son propre state local
Pas de verrou         → deux apply simultanés peuvent corrompre le state
```

GitLab propose un **backend HTTP natif** qui résout ces deux problèmes :

```text
State stocké dans GitLab  → partagé entre tous les membres du projet
Verrouillage automatique  → un seul apply à la fois (lock/unlock)
Historique des versions   → GitLab conserve les versions précédentes du state
Visible dans l’UI         → GitLab → projet → Operate → Terraform states
```

## 13.2 Prérequis

```text
- Un projet GitLab (https://gitlab.com ou instance auto-hébergée)
- Un Personal Access Token avec le scope api
```

Créer un Personal Access Token :

```text
GitLab → Settings → Access Tokens
Nom : terraform-state
Scopes : api
Durée : selon politique de votre organisation
```

Récupérer l’ID du projet GitLab :

La commande encode le chemin `namespace/projet` en remplaçant `/` par `%2F` dans l’URL.

Exemple concret pour le projet `https://gitlab.com/vadimaentreprise/terraform` avec le token `glpat-A_xxxxxxxxxxxxxxxxxxxx` :

```bash
curl --silent --header "PRIVATE-TOKEN: glpat-A_xxxxxxxxxxxxxxxxxxxx" \
  "https://gitlab.com/api/v4/projects/vadimaentreprise%2Fterraform" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])"
```

Résultat attendu : un nombre entier, par exemple `58473921`. C’est le `PROJECT_ID` à utiliser dans les sections suivantes.

> Remplacez `glpat-A_xxxxxxxxxxxxxxxxxxxx` par votre token réel et `vadimaentreprise/terraform` par votre namespace et nom de projet.

## 13.3 Configurer le backend HTTP GitLab

Modifier le fichier **main.tf** du projet (ici repris de l’atelier state) :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }

  # Backend HTTP GitLab — le state est stocké dans GitLab.
  backend "http" {
    # URL du state : remplacer PROJECT_ID et STATE_NAME.
    address        = "https://gitlab.com/api/v4/projects/<PROJECT_ID>/terraform/state/<STATE_NAME>"

    # URL de verrouillage (lock) — POST pour verrouiller.
    lock_address   = "https://gitlab.com/api/v4/projects/<PROJECT_ID>/terraform/state/<STATE_NAME>/lock"
    lock_method    = "POST"

    # URL de déverrouillage (unlock) — DELETE pour déverrouiller.
    unlock_address = "https://gitlab.com/api/v4/projects/<PROJECT_ID>/terraform/state/<STATE_NAME>/lock"
    unlock_method  = "DELETE"

    # Délai d’attente en secondes avant réessai si le state est verrouillé.
    retry_wait_min = 5
  }
}

provider "local" {}

resource "local_file" "web" {
  filename = "web.txt"
  content  = "Fichier web géré par Terraform avec state sur GitLab"
}
```

Valeurs à remplacer :

```text
<PROJECT_ID>  → ID numérique du projet GitLab (ex: 12345678)
<STATE_NAME>  → nom logique du state (ex: terraform-state-lab, prod, staging)
```

> Un même projet GitLab peut héberger plusieurs states en changeant uniquement `<STATE_NAME>`. C’est utile pour séparer les environnements : `prod`, `staging`, `dev`.

## 13.4 Initialiser avec les credentials

Les credentials ne se mettent **jamais** dans `main.tf` — ils sont passés au moment de `terraform init`.

**Option 1 : variables d’environnement (recommandée en CI/CD)**

```bash
export TF_HTTP_USERNAME="<votre-gitlab-username>"
export TF_HTTP_PASSWORD="<votre-personal-access-token>"

terraform init
```

**Option 2 : flags `-backend-config` (recommandée en local)**

```bash
terraform init \
  -backend-config="username=<votre-gitlab-username>" \
  -backend-config="password=<votre-personal-access-token>"
```

Résultat attendu :

```text
Initializing the backend...

Successfully configured the backend "http"!
Terraform will automatically use this backend unless the backend
configuration changes.
```

## 13.5 Utiliser le state GitLab

Une fois initialisé, toutes les commandes Terraform fonctionnent normalement. Le state est lu et écrit dans GitLab de manière transparente.

```bash
terraform plan
terraform apply -auto-approve
terraform state list
terraform state show local_file.web
```

Pendant un `apply`, Terraform pose un **verrou** sur le state dans GitLab. Si un second `apply` est lancé en parallèle, il reçoit :

```text
Error: Error locking state: Error acquiring the state lock
```

Le verrou est automatiquement libéré à la fin de l’apply.

## 13.6 Visualiser le state dans GitLab

Le state est visible dans l’interface GitLab :

```text
Votre projet GitLab
→ Operate
→ Terraform states
```

GitLab affiche :

```text
- Nom du state
- Date de dernière modification
- Qui a modifié le state
- Historique des versions (possibilité de voir les versions précédentes)
- Bouton pour forcer le déverrouillage si nécessaire (unlock forcé)
```

## 13.7 Forcer le déverrouillage

Si un `apply` a été interrompu brutalement, le verrou peut rester actif.

Depuis l’UI GitLab :

```text
Operate → Terraform states → state concerné → bouton Unlock
```

Depuis la ligne de commande :

```bash
# Récupérer le lock ID depuis le message d’erreur Terraform.
terraform force-unlock <LOCK_ID>
```

> Utiliser `force-unlock` avec précaution. Vérifier d’abord qu’aucun apply n’est en cours.

## 13.8 Migrer un state local vers GitLab

Si vous avez déjà un state local (`terraform.tfstate`) et que vous voulez le migrer vers GitLab :

```bash
# Étape 1 : ajouter le bloc backend "http" dans main.tf (section 13.3).

# Étape 2 : réinitialiser — Terraform détecte le changement de backend
#            et propose de migrer le state existant.
terraform init \
  -backend-config="username=<username>" \
  -backend-config="password=<token>"

# Terraform affiche :
# Do you want to copy existing state to the new backend?
# Taper : yes
```

Après migration, supprimer le state local :

```bash
rm -f terraform.tfstate
rm -f terraform.tfstate.backup
```

## 13.9 Utiliser le state GitLab en CI/CD GitLab

Dans une pipeline GitLab CI, les variables `CI_PROJECT_ID` et `CI_JOB_TOKEN` sont disponibles automatiquement, ce qui simplifie la configuration.

Deux points importants sur les variables d'authentification :

```text
TF_HTTP_USERNAME: "gitlab-ci-token"   → chaîne FIXE imposée par GitLab, à copier telle quelle, ne pas remplacer
TF_HTTP_PASSWORD: "${CI_JOB_TOKEN}"   → token temporaire injecté automatiquement par GitLab pour chaque job
```

GitLab exige littéralement le mot `gitlab-ci-token` comme username quand on utilise un `CI_JOB_TOKEN`. Ce n'est pas un placeholder — c'est une convention imposée par l'API GitLab. Rien à changer.

## Prérequis : structure du dépôt GitLab

Avant de lancer la pipeline, le dépôt doit contenir ces deux fichiers :

```
terraform/
├── main.tf
└── .gitlab-ci.yml
```

Sans `main.tf`, Terraform initialise un dossier vide et le job `plan` échoue avec :

```text
Error: No configuration files
Plan requires configuration to be present.
```

## main.tf

Ce fichier crée un fichier `web.txt` dont le contenu inclut un timestamp — ce qui produit quelque chose de concret et vérifiable après chaque pipeline :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
  backend "http" {}
}

provider "local" {}

resource "local_file" "web" {
  filename = "web.txt"
  content  = "Fichier web géré par Terraform via GitLab CI — pipeline ${timestamp()}"
}

output "fichier_cree" {
  value = local_file.web.filename
}
```

## .gitlab-ci.yml

```yaml
# .gitlab-ci.yml
variables:
  TF_HTTP_USERNAME: "gitlab-ci-token"
  TF_HTTP_PASSWORD: "${CI_JOB_TOKEN}"

stages:
  - validate
  - plan
  - apply

.terraform_init: &terraform_init
  - terraform init
      -backend-config="address=https://gitlab.com/api/v4/projects/${CI_PROJECT_ID}/terraform/state/production"
      -backend-config="lock_address=https://gitlab.com/api/v4/projects/${CI_PROJECT_ID}/terraform/state/production/lock"
      -backend-config="unlock_address=https://gitlab.com/api/v4/projects/${CI_PROJECT_ID}/terraform/state/production/lock"
      -backend-config="lock_method=POST"
      -backend-config="unlock_method=DELETE"

terraform_init:
  stage: validate
  image:
    name: hashicorp/terraform:1.6
    entrypoint: [""]
  script:
    - *terraform_init
    - terraform validate

terraform_plan:
  stage: plan
  image:
    name: hashicorp/terraform:1.6
    entrypoint: [""]
  script:
    - *terraform_init
    - terraform plan -out=plan.tfplan
  artifacts:
    paths:
      - plan.tfplan

terraform_apply:
  stage: apply
  image:
    name: hashicorp/terraform:1.6
    entrypoint: [""]
  dependencies:
    - terraform_plan
  script:
    - *terraform_init
    - terraform apply plan.tfplan
  artifacts:
    paths:
      - web.txt
    expire_in: 1 week
  when: manual
```

Notes techniques :

- `entrypoint: [""]` est obligatoire sur chaque job — l'image `hashicorp/terraform` a `terraform` comme entrypoint par défaut, ce qui empêche GitLab CI d'exécuter des commandes shell
- `&terraform_init` / `*terraform_init` sont des ancres YAML pour éviter de répéter la commande init dans chaque job
- `dependencies: [terraform_plan]` dans apply récupère le `plan.tfplan` généré par le job plan
- `artifacts: paths: [web.txt]` expose le fichier créé par Terraform dans l'UI GitLab

Committer et pousser :

```bash
git add main.tf .gitlab-ci.yml
git commit -m "init terraform ci"
git push origin main
```

## Ce que la pipeline produit concrètement

### Job terraform_init (stage validate)

```text
Initializing the backend...
Successfully configured the backend "http"!
Terraform has been successfully initialized!

Success! The configuration is valid.
```

Le state est maintenant stocké dans GitLab. Visible dans :

```text
Votre projet GitLab → Operate → Terraform states → production
```

### Job terraform_plan (stage plan)

```text
Terraform used the selected providers to generate the following execution plan.

  + resource "local_file" "web" {
      + content  = "Fichier web géré par Terraform via GitLab CI — pipeline 2024-01-15T10:23:45Z"
      + filename = "web.txt"
    }

Plan: 1 to add, 0 to change, 0 to destroy.
```

Le fichier `plan.tfplan` est sauvegardé comme artifact et transmis au job apply.

### Job terraform_apply (stage apply — déclenché manuellement)

```text
local_file.web: Creating...
local_file.web: Creation complete after 0s [id=...]

Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Outputs:
fichier_cree = "web.txt"
```

### Récupérer web.txt depuis GitLab

Après l'apply, `web.txt` est téléchargeable directement depuis l'UI GitLab :

```text
CI/CD → Pipelines → votre pipeline → job terraform_apply → bouton "Browse artifacts"
→ web.txt
```

Contenu du fichier :

```text
Fichier web géré par Terraform via GitLab CI — pipeline 2024-01-15T10:23:45Z
```

Après l'apply, le state est verrouillé puis déverrouillé automatiquement. GitLab enregistre une nouvelle version dans l'historique du state :

```text
Votre projet GitLab → Operate → Terraform states → production → historique des versions
```

# Résumé final de l’atelier

```text
state          = mémoire de Terraform
tfstate local  = fichier local, suffisant pour un développeur solo
backend GitLab = state partagé, verrouillé, visible dans l'UI, intégré CI/CD
drift          = changement fait hors Terraform
import         = rattacher une ressource existante quand le provider le supporte
state rm       = oublier une ressource sans la supprimer
state mv       = renommer une adresse sans recréer
state show     = inspecter une ressource suivie
```

Message essentiel :

**Terraform ne regarde pas seulement le code. Il compare le code, le state et l’état réel.**

Le **state** est donc indispensable pour comprendre ce que Terraform va créer, modifier ou supprimer.
