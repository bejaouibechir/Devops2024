# A2.1. Un premier contact avec HCL

> **Objectif de l'atelier** : comprendre les 8 types de blocs du langage HCL, savoir dans quel fichier chacun vit, et voir leur synergie sur un exemple complet.

---

## 0. Prérequis — S'authentifier auprès d'Azure

Terraform se connecte à Azure via un **Service Principal** (compte applicatif). Il a besoin de 4 valeurs que vous exportez en variables d'environnement — aucun secret n'est jamais écrit dans le code.

| Variable              | Ce que c'est                             |
| --------------------- | ---------------------------------------- |
| `ARM_SUBSCRIPTION_ID` | L'abonnement Azure cible                 |
| `ARM_TENANT_ID`       | L'identifiant de votre annuaire Azure AD |
| `ARM_CLIENT_ID`       | L'identifiant de l'application créée     |
| `ARM_CLIENT_SECRET`   | Le secret de l'application               |

### Étape 1 — Récupérer Subscription ID et Tenant ID

Depuis le **portail Azure** :

- `subscription_id` → **Abonnements** → colonne *ID d'abonnement*
- `tenant_id` → **Microsoft Entra ID** → *Vue d'ensemble* → *ID de locataire*

Ou via Azure CLI (si installé) :

```bash
az login
az account show --query "{subscription_id:id, tenant_id:tenantId}" --output table
```

### Étape 2 — Créer le Service Principal

Depuis le portail : **Microsoft Entra ID → App registrations → New registration**

1. Donnez un nom (ex : `sp-terraform-atelier`) et validez
2. Notez l'**Application (client) ID** → `ARM_CLIENT_ID`
3. Allez dans **Certificates & secrets → New client secret** → notez la valeur → `ARM_CLIENT_SECRET` (affiché une seule fois)
4. Allez dans **Subscriptions → votre abonnement → Access control (IAM) → Add role assignment** → rôle **Contributor** → assignez à votre app

Ou via CLI :

```bash
az ad sp create-for-rbac \
  --name "sp-terraform-atelier" \
  --role Contributor \
  --scopes /subscriptions/$(az account show --query id -o tsv)
# Sortie : appId = ARM_CLIENT_ID, password = ARM_CLIENT_SECRET, tenant = ARM_TENANT_ID
```

### Étape 3 — Exporter les variables avant chaque session Terraform

**Linux / macOS / WSL :**

```bash
export ARM_SUBSCRIPTION_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export ARM_TENANT_ID="yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
export ARM_CLIENT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export ARM_CLIENT_SECRET="votre-secret"
```

**Windows PowerShell :**

```powershell
$env:ARM_SUBSCRIPTION_ID = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:ARM_TENANT_ID       = "yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
$env:ARM_CLIENT_ID       = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:ARM_CLIENT_SECRET   = "votre-secret"
```

Le provider `azurerm` lit ces variables automatiquement — le bloc `provider` reste vide :

```hcl
provider "azurerm" {
  features {}
}
```

> **Sécurité** : ne commitez jamais ces valeurs dans Git. Pour les persistre entre sessions, ajoutez les exports dans `~/.bashrc` (Linux) ou un fichier `.env` exclu via `.gitignore`.

## 1. Organisation des fichiers Terraform

Terraform ne vous impose qu'une seule règle : tous les fichiers doivent avoir l'extension `.tf` et se trouver dans le même répertoire. Par convention, la communauté adopte cette structure :

```
projet/
├── terraform.tf        ← bloc terraform  (version, backend)
├── providers.tf        ← bloc provider
├── variables.tf        ← blocs variable
├── locals.tf           ← bloc locals
├── main.tf             ← blocs resource, data, module
├── outputs.tf          ← blocs output
└── terraform.tfvars    ← valeurs des variables (pas un bloc HCL, fichier de valeurs)
```

> **Règle pratique** : pour un petit projet, tout peut tenir dans `main.tf`. Dès que le fichier dépasse 100 lignes, on éclate selon la convention ci-dessus.

## 2. Les 8 blocs HCL — tour d'horizon

---

### Bloc 1 — `terraform`

**Fichier habituel :** `terraform.tf` ou `versions.tf`

Définit la configuration **globale du projet** : version minimale de Terraform, backend de stockage du state, et providers requis avec leurs contraintes de version.

```hcl
# terraform.tf
terraform {
  required_version = ">= 1.5.0"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.0"
    }
  }

  # Backend distant — stocke le state dans Azure Blob Storage
  backend "azurerm" {
    resource_group_name  = "rg-terraform-state"
    storage_account_name = "stterraformstate"
    container_name       = "tfstate"
    key                  = "projet.terraform.tfstate"
  }
}
```

> Sans bloc `terraform`, Terraform accepte n'importe quelle version et n'impose aucun provider — pratique pour tester, risqué en production.

---

### Bloc 2 — `provider`

**Fichier habituel :** `providers.tf`

Configure **comment Terraform se connecte** à une plateforme. Chaque provider a ses propres arguments (credentials, région, features…).

```hcl
# providers.tf
provider "azurerm" {
  features {
    resource_group {
      prevent_deletion_if_contains_resources = false
    }
  }
  # Terraform lit automatiquement les variables d'environnement :
  # ARM_SUBSCRIPTION_ID, ARM_CLIENT_ID, ARM_CLIENT_SECRET, ARM_TENANT_ID
}
```

> Un même projet peut avoir **plusieurs providers** : azurerm + random + local, par exemple.

---

### Bloc 3 — `variable`

**Fichier habituel :** `variables.tf`

Déclare un **paramètre d'entrée** qui peut être fourni via `terraform.tfvars`, la ligne de commande (`-var`), ou une variable d'environnement (`TF_VAR_*`).

```hcl
# variables.tf
variable "location" {
  description = "Région Azure cible"
  type        = string
  default     = "France Central"
}

variable "environment" {
  description = "Environnement (dev, staging, prod)"
  type        = string

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Valeur autorisée : dev, staging ou prod."
  }
}

variable "tags" {
  description = "Tags communs à appliquer aux ressources"
  type        = map(string)
  default     = {}
}
```

Valeurs dans `terraform.tfvars` :

```hcl
# terraform.tfvars
location    = "France Central"
environment = "dev"
tags = {
  projet = "atelier-hcl"
  owner  = "bechir"
}
```

---

### Bloc 4 — `locals`

**Fichier habituel :** `locals.tf` (ou en tête de `main.tf`)

Déclare des **valeurs calculées internes** — ni des entrées (variable) ni des sorties (output). Évite la répétition et centralise la logique de nommage.

```hcl
# locals.tf
locals {
  prefix      = "atelier"
  full_prefix = "${local.prefix}-${var.environment}"

  common_tags = merge(var.tags, {
    managed_by = "terraform"
    env        = var.environment
  })
}
```

> Référence : `local.full_prefix` (singulier `local`, pas `locals`).

---

### Bloc 5 — `data`

**Fichier habituel :** `main.tf` ou `data.tf`

**Lit** une ressource existante dans la plateforme **sans la créer ni la gérer**. Utile pour récupérer l'ID d'un réseau déjà existant, l'image d'une VM, etc.

```hcl
# main.tf
data "azurerm_resource_group" "existant" {
  name = "rg-shared-services"
}

data "azurerm_subnet" "existant" {
  name                 = "snet-default"
  virtual_network_name = "vnet-prod"
  resource_group_name  = data.azurerm_resource_group.existant.name
}
```

Référence dans une ressource : `data.azurerm_subnet.existant.id`

---

### Bloc 6 — `resource`

**Fichier habituel :** `main.tf`

Le bloc **le plus courant** — crée, modifie, ou détruit un objet d'infrastructure. Terraform compare l'état déclaré à l'état réel et calcule le delta.

```hcl
# main.tf
resource "azurerm_resource_group" "rg" {
  name     = "${local.full_prefix}-rg"
  location = var.location
  tags     = local.common_tags
}

resource "azurerm_storage_account" "st" {
  name                     = "${local.prefix}${var.environment}st"
  resource_group_name      = azurerm_resource_group.rg.name
  location                 = azurerm_resource_group.rg.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
  tags                     = local.common_tags
}
```

> `azurerm_resource_group.rg.name` → Terraform crée automatiquement une **dépendance implicite** entre les deux ressources.

---

### Bloc 7 — `output`

**Fichier habituel :** `outputs.tf`

**Expose** une valeur après `terraform apply` — affichée dans le terminal, utilisable par un module parent ou par un pipeline CI/CD.

```hcl
# outputs.tf
output "resource_group_name" {
  description = "Nom du resource group créé"
  value       = azurerm_resource_group.rg.name
}

output "storage_account_id" {
  description = "ID du storage account"
  value       = azurerm_storage_account.st.id
  sensitive   = false
}
```

> Marquer `sensitive = true` masque la valeur dans les logs — utile pour les connexion strings.

---

### Bloc 8 — `module`

**Fichier habituel :** `main.tf`

**Appelle** un ensemble de fichiers `.tf` réutilisables (local ou registre Terraform). Un module reçoit des variables et expose des outputs.

```hcl
# main.tf
module "network" {
  source              = "./modules/network"
  location            = var.location
  resource_group_name = azurerm_resource_group.rg.name
  environment         = var.environment
  tags                = local.common_tags
}
```

## 3. Exemple pratique complet — tous les blocs en synergie

> L'exemple provisionne : un Resource Group, un Storage Account, un fichier de configuration généré localement.

Il existe **deux styles d'écriture** acceptés par Terraform — commencez par le style compact pour comprendre la logique, passez au style multi-fichiers dès que le projet grandit.

---

### Style 1 — Tout dans `main.tf` (compact, idéal pour débuter)

Tous les blocs cohabitent dans un seul fichier. Terraform s'en fiche de la répartition — ce qui compte c'est l'extension `.tf`.

#### Option A — Azure (style compact)

```hcl
# main.tf — tous les blocs dans un seul fichier

# ── terraform ─────────────────────────────────────────────────────────────────
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 3.0" }
    local   = { source = "hashicorp/local",   version = "~> 2.0" }
    null    = { source = "hashicorp/null",     version = "~> 3.0" }
  }
  backend "local" { path = "terraform.tfstate" }
}

# ── provider ──────────────────────────────────────────────────────────────────
# Les variables ARM_* sont lues automatiquement (voir section 0)
provider "azurerm" {
  features {}
}

# ── variables ─────────────────────────────────────────────────────────────────
# Attention : HCL n'accepte pas les ; ni les blocs imbriqués sur une seule ligne
variable "location" {
  type    = string
  default = "France Central"
}
variable "environment" {
  type    = string
  default = "dev"
}
variable "tags" {
  type    = map(string)
  default = {}
}

# ── locals ────────────────────────────────────────────────────────────────────
locals {
  full_prefix = "atelier-${var.environment}"
  common_tags = merge(var.tags, { managed_by = "terraform", env = var.environment })
}

# ── resource ──────────────────────────────────────────────────────────────────
resource "azurerm_resource_group" "rg" {
  name     = "${local.full_prefix}-rg"
  location = var.location
  tags     = local.common_tags
}

resource "azurerm_storage_account" "st" {
  name                     = "atelierst${var.environment}"
  resource_group_name      = azurerm_resource_group.rg.name
  location                 = azurerm_resource_group.rg.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
  tags                     = local.common_tags
}

resource "local_file" "config" {
  filename = "${path.module}/config-${var.environment}.txt"
  content  = "storage=${azurerm_storage_account.st.name}\nenv=${var.environment}"
}

resource "null_resource" "post_deploy" {
  depends_on = [local_file.config]
  provisioner "local-exec" {
    command = "echo 'Déploiement terminé - fichier : ${local_file.config.filename}'"
  }
  triggers = { hash = local_file.config.content_md5 }
}

# ── data ──────────────────────────────────────────────────────────────────────
data "azurerm_resource_group" "verify" {
  name       = azurerm_resource_group.rg.name
  depends_on = [azurerm_resource_group.rg]
}

# ── outputs ───────────────────────────────────────────────────────────────────
output "rg_name"       { value = azurerm_resource_group.rg.name }
output "storage_name"  { value = azurerm_storage_account.st.name }
output "config_file"   { value = local_file.config.filename }
output "rg_location"   { value = data.azurerm_resource_group.verify.location }
```

#### Avant de lancer — authentification Azure

Les 4 paramètres d'auth ne sont **nulle part dans `main.tf`** — c'est voulu. Le provider `azurerm` les détecte automatiquement via des **variables d'environnement** standard qu'il connaît par convention (`ARM_*`). Vous les exportez une fois dans votre terminal, et le provider les consomme en coulisses sans que vous n'ayez rien à écrire dans le code.

```bash
# Linux / macOS / WSL — dans le même terminal avant terraform
export ARM_SUBSCRIPTION_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export ARM_TENANT_ID="yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
export ARM_CLIENT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export ARM_CLIENT_SECRET="votre-secret"
```

```powershell
# Windows PowerShell
$env:ARM_SUBSCRIPTION_ID = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:ARM_TENANT_ID       = "yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
$env:ARM_CLIENT_ID       = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:ARM_CLIENT_SECRET   = "votre-secret"
```

> **Pourquoi ces variables n'apparaissent pas dans `main.tf` ?**
> Ce ne sont pas des variables Terraform (`variable "..."`) — ce sont des variables d'environnement système lues directement par le binaire du provider `azurerm`. Le bloc `provider "azurerm" { features {} }` suffit : le provider sait où chercher les credentials tout seul.

#### Séquence d'exécution

```bash
# 1. Exporter les variables d'auth (voir ci-dessus)
# 2. Puis lancer Terraform
terraform init      # Télécharge les providers azurerm, local, null
terraform validate  # Vérifie la syntaxe
terraform plan      # Prévisualise : 4 ressources à créer
terraform apply     # Crée le RG, le Storage Account, le fichier local
terraform output    # Affiche les 4 outputs
terraform destroy   # Nettoie tout
```

#### Option B — 100% local (style compact, Plan B sans Azure)

```hcl
# main.tf — style compact, aucune connexion cloud requise

# ── terraform ─────────────────────────────────────────────────────────────────
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    local = { source = "hashicorp/local", version = "~> 2.0" }
    null  = { source = "hashicorp/null",  version = "~> 3.0" }
  }
  backend "local" { path = "terraform.tfstate" }
}

# ── providers ─────────────────────────────────────────────────────────────────
provider "local" {}
provider "null"  {}

# ── variables ─────────────────────────────────────────────────────────────────
variable "environment"   { type = string; default = "dev" }
variable "project_name"  { type = string; default = "atelier-hcl" }

# ── locals ────────────────────────────────────────────────────────────────────
locals {
  output_dir  = "${path.module}/output-${var.environment}"
  config_file = "${local.output_dir}/config.txt"
}

# ── resources ─────────────────────────────────────────────────────────────────
resource "null_resource" "create_dir" {
  provisioner "local-exec" { command = "mkdir -p ${local.output_dir}" }
  triggers = { dir = local.output_dir }
}

resource "local_file" "config" {
  depends_on = [null_resource.create_dir]
  filename   = local.config_file
  content    = "project=${var.project_name}\nenv=${var.environment}\nmanaged_by=terraform"
}

resource "null_resource" "post_deploy" {
  depends_on = [local_file.config]
  provisioner "local-exec" {
    command = "echo 'OK - fichiers dans : ${local.output_dir}' && ls ${local.output_dir}"
  }
  triggers = { hash = local_file.config.content_md5 }
}

# ── data ──────────────────────────────────────────────────────────────────────
data "local_file" "config_verify" {
  depends_on = [local_file.config]
  filename   = local.config_file
}

# ── outputs ───────────────────────────────────────────────────────────────────
output "output_dir"      { value = local.output_dir }
output "config_path"     { value = local_file.config.filename }
output "config_md5"      { value = local_file.config.content_md5 }
output "config_content"  { value = data.local_file.config_verify.content }
```

#### Séquence d'exécution (Option B — aucun prérequis Azure)

```bash
terraform init      # Télécharge les providers local + null uniquement
terraform validate
terraform plan      # 3 ressources + 1 data source
terraform apply     # Crée le dossier et les fichiers localement
terraform output    # Affiche les 4 outputs dont le contenu du fichier
terraform destroy   # Supprime les ressources du state
```

### Style 2 — Fichiers séparés (convention professionnelle)

Même logique, même résultat — les blocs sont simplement répartis dans des fichiers dédiés pour la lisibilité et la maintenabilité.

### Structure du projet

```
atelier-hcl/
├── terraform.tf
├── providers.tf
├── variables.tf
├── locals.tf
├── main.tf
├── outputs.tf
└── terraform.tfvars
```

### Option A (Style 2) — Provider Azure — fichiers séparés

#### Étape 0 — Obtenir les credentials Azure

Terraform se connecte à Azure via un **Service Principal** (compte applicatif). Il a besoin de 4 valeurs :

| Variable              | Ce que c'est                              |
| --------------------- | ----------------------------------------- |
| `ARM_SUBSCRIPTION_ID` | L'abonnement Azure cible                  |
| `ARM_TENANT_ID`       | L'identifiant de votre annuaire Azure AD  |
| `ARM_CLIENT_ID`       | L'identifiant de l'application créée      |
| `ARM_CLIENT_SECRET`   | Le mot de passe / secret de l'application |

##### Prérequis

```bash
# Vérifier que Azure CLI est installé
az --version

# Se connecter à Azure (ouvre un navigateur)
az login
```

##### 1. Récupérer Subscription ID et Tenant ID

```bash
# Liste tous vos abonnements
az account list --output table

# Sélectionner l'abonnement à utiliser
az account set --subscription "NOM_OU_ID_DE_LABONNEMENT"

# Afficher les valeurs dont on a besoin
az account show --query "{subscription_id:id, tenant_id:tenantId}" --output table
```

Exemple de sortie :

```
Subscription_Id                       Tenant_Id
------------------------------------  ------------------------------------
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx  yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy
```

##### 2. Créer le Service Principal et obtenir Client ID + Secret

```bash
# Crée le Service Principal avec le rôle Contributor sur l'abonnement
az ad sp create-for-rbac \
  --name "sp-terraform-atelier" \
  --role Contributor \
  --scopes /subscriptions/$(az account show --query id -o tsv)
```

Terraform affiche automatiquement les 4 valeurs :

```json
{
  "appId":       "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",   ← ARM_CLIENT_ID
  "displayName": "sp-terraform-atelier",
  "password":    "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx", ← ARM_CLIENT_SECRET
  "tenant":      "yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"     ← ARM_TENANT_ID
}
```

> **Important** : copiez le `password` immédiatement — il n'est affiché qu'une seule fois.

##### 3. Exporter les variables d'environnement

**Linux / macOS / WSL :**

```bash
export ARM_SUBSCRIPTION_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export ARM_TENANT_ID="yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
export ARM_CLIENT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export ARM_CLIENT_SECRET="xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

**Windows PowerShell :**

```powershell
$env:ARM_SUBSCRIPTION_ID = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:ARM_TENANT_ID       = "yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
$env:ARM_CLIENT_ID       = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
$env:ARM_CLIENT_SECRET   = "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

**Windows CMD :**

```cmd
set ARM_SUBSCRIPTION_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
set ARM_TENANT_ID=yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy
set ARM_CLIENT_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
set ARM_CLIENT_SECRET=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

##### 4. Vérifier la connexion avant de lancer Terraform

```bash
# Teste que le Service Principal peut bien s'authentifier
az login --service-principal \
  --username $ARM_CLIENT_ID \
  --password $ARM_CLIENT_SECRET \
  --tenant $ARM_TENANT_ID

# Si OK, vous verrez votre abonnement s'afficher
az account show --output table
```

> **Astuce** : pour ne pas re-saisir ces variables à chaque session, ajoutez les exports dans `~/.bashrc` ou `~/.zshrc` (Linux/macOS), ou créez un fichier `.env` que vous sourcez avec `source .env`.
> Ne commitez **jamais** un fichier `.env` contenant ces secrets dans Git — ajoutez-le à `.gitignore`.

```hcl
# ─── Resource Group ───────────────────────────────────────────────────────────
resource "azurerm_resource_group" "rg" {

  tags     = local.common_tags
}

# ─── Storage Account ──────────────────────────────────────────────────────────

  resource_group_name      = azurerm_resource_group.rg.name

# ─── Génère un fichier de config local ────────────────────────────────────────
resource "local_file" "config" {
  content  = <<-EOT
    # Configuration générée par Terraform
    environment = "${var.environment}"
    location    = "${var.location}"
    storage     = "${azurerm_storage_account.st.name}"
  EOT
  filename = "${path.module}/config-${var.environment}.txt"
}

# ─── Upload le fichier vers Azure Blob via local-exec ─────────────────────────
resource "null_resource" "upload_config" {
  depends_on = [azurerm_storage_container.configs, local_file.config]

  provisioner "local-exec" {
    command = <<-EOT
      az storage blob upload \
        --account-name ${azurerm_storage_account.st.name} \
        --container-name configs \
        --name config-${var.environment}.txt \
        --file ${local_file.config.filename} \
        --auth-mode login
    EOT
  }

  # Redéclenche l'upload si le contenu du fichier change
  triggers = {
    config_hash = local_file.config.content_md5
  }
}

# ─── Data source — lit le RG après création (exemple de data) ─────────────────
data "azurerm_resource_group" "verify" {
  name       = azurerm_resource_group.rg.name
  depends_on = [azurerm_resource_group.rg]
}
```

### Option B (Style 2) — Plan B 100% local — fichiers séparés

> Remplace Azure par le provider `local` + `null_resource`. Même logique HCL, zéro dépendance réseau.
> Idéal pour apprendre, tester en offline, ou débloquer un atelier en cas de problème de connexion Azure.

#### `terraform.tf`

```hcl
terraform {
  required_version = ">= 1.5.0"

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.0"
    }
    null = {
      source  = "hashicorp/null"
      version = "~> 3.0"
    }
  }

  backend "local" {
    path = "terraform.tfstate"
  }
}
```

```hcl

```

```hcl
    command = "mkdir -p ${local.output_dir}"
  }

  triggers = {
    dir = local.output_dir
  }
}

# ─── Génère un fichier de configuration ───────────────────────────────────────
resource "local_file" "config" {
  depends_on = [null_resource.create_dir]

  filename = local.config_file
  content  = <<-EOT
    # Fichier généré par Terraform — ${timestamp()}
    project     = "${var.project_name}"
    environment = "${var.environment}"
    managed_by  = "terraform"
    output_dir  = "${local.output_dir}"
  EOT
}

# ─── Génère un fichier README ─────────────────────────────────────────────────
resource "local_file" "readme" {
  depends_on = [null_resource.create_dir]

  filename = local.readme_file
  content  = <<-EOT
    # Projet : ${var.project_name}
    Environnement : ${var.environment}
    Fichiers générés par Terraform (provider local).
    Supprimer ce dossier avec : terraform destroy
  EOT
}

# ─── Simule un provisioner "remote-exec" avec local-exec ──────────────────────
resource "null_resource" "post_deploy" {
  depends_on = [local_file.config, local_file.readme]

  provisioner "local-exec" {
    command = <<-EOT
      echo "=== Déploiement terminé ===" && \
      echo "Fichiers créés dans : ${local.output_dir}" && \
      ls -lh ${local.output_dir}
    EOT

  triggers = {
    config_hash = local_file.config.content_md5
    readme_hash = local_file.readme.content_md5
  }
}

  filename   = local.config_file
}
```

## 4. Style compact vs fichiers séparés — quand choisir ?

| Critère          | Style compact (1 fichier)   | Style multi-fichiers             |
| ---------------- | --------------------------- | -------------------------------- |
| Taille du projet | < 50 lignes, 1-3 ressources | Tout projet sérieux              |
| Lisibilité       | Facile à lire d'un coup     | Chaque fichier a un rôle clair   |
| Navigation       | Tout au même endroit        | On sait où chercher chaque bloc  |
| Collaboration    | Conflits Git fréquents      | Chaque devops touche son fichier |
| Modules          | Difficile à réutiliser      | Naturellement séparable          |
| Débutant         | ✅ Idéal pour apprendre      | ✅ Idéal dès qu'on maîtrise       |

> **Règle pratique** : commencez compact pour comprendre, passez multi-fichiers dès que vous avez plus de 3 ressources ou plusieurs contributeurs.

## 5. Récapitulatif — blocs, rôles et fichiers

| Bloc        | Rôle                               | Fichier habituel | Référence            |
| ----------- | ---------------------------------- | ---------------- | -------------------- |
| `terraform` | Version, backend, providers requis | `terraform.tf`   | —                    |
| `provider`  | Connexion à une plateforme         | `providers.tf`   | —                    |
| `variable`  | Paramètre d'entrée                 | `variables.tf`   | `var.nom`            |
| `locals`    | Valeur calculée interne            | `locals.tf`      | `local.nom`          |
| `data`      | Lecture d'une ressource existante  | `main.tf`        | `data.TYPE.NOM.attr` |
| `resource`  | Création/gestion d'infrastructure  | `main.tf`        | `TYPE.NOM.attr`      |
| `output`    | Valeur exposée après apply         | `outputs.tf`     | `module.NOM.output`  |
| `module`    | Appel d'un bloc réutilisable       | `main.tf`        | `module.NOM.attr`    |

## 6. Points clés à retenir

- L'**ordre des blocs dans les fichiers n'a pas d'importance** — Terraform construit lui-même le graphe de dépendances.
- Les **dépendances implicites** (`azurerm_resource_group.rg.name`) sont préférées aux dépendances explicites (`depends_on`).
- `depends_on` est réservé aux cas où Terraform ne peut pas détecter la dépendance seul (ex : `null_resource`, `local-exec`).
- Un `local_file` ou `null_resource` **ne détruit pas le fichier/dossier physique** automatiquement — seul le state est nettoyé.
- Le provider `local` + `null` est toujours disponible sans credentials — c'est votre filet de sécurité en formation.
