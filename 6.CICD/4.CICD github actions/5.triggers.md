# Déclencher les workflows GitHub Actions

## Objectif

Adapter les triggers Jenkins et les sources de pipeline GitLab à la déclaration `on`.

## 1. Correspondances

| Besoin                        | Jenkins                  | GitLab CI/CD             | GitHub Actions        |
| ----------------------------- | ------------------------ | ------------------------ | --------------------- |
| Réagir au code poussé         | Webhook ou polling       | Pipeline push            | `push`                |
| Tester une contribution       | Plugin PR                | `merge_request_event`    | `pull_request`        |
| Planification                 | `cron`                   | Pipeline schedule        | `schedule`            |
| Lancement humain              | Build with Parameters    | Run pipeline             | `workflow_dispatch`   |
| Appel réutilisable            | Shared Library/autre job | Include/composant/enfant | `workflow_call`       |
| Réagir à la fin d'un workflow | `upstream`               | Déclenchement aval       | `workflow_run`        |
| Événement externe             | API/webhook              | API/trigger              | `repository_dispatch` |

Il n'y a pas de `pollSCM` natif à transposer : un dépôt GitHub peut déclencher directement sur `push`.

## 2. Push sur main avec README modifié

Fichier `.github/workflows/trigger.yml` :

```yaml
name: README sur main
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Déclenche le workflow pour les pushes correspondant aux filtres ci-dessous.
  push:
    branches: [main]
    paths: [README.md]
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions:
  # Autorise l'accès au contenu du dépôt selon le niveau indiqué.
  contents: read
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « test » ; needs permet de préciser ses dépendances.
  test:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Récupère les fichiers du dépôt dans le workspace du runner.
      - uses: actions/checkout@v7
        # Fournit les paramètres attendus par l'action ou le workflow appelé.
        with:
          # Choisit si checkout conserve l'authentification Git pour les commandes suivantes.
          persist-credentials: false
      # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
      - run: test -f README.md
```

Les filtres branche et chemin doivent être satisfaits. Cela signifie « README fait partie des changements », et non « README est le seul fichier changé ». Les filtres de chemins ont des limites de calcul du diff : ne les utilisez pas comme contrôle d'autorisation. [Filtres de déclenchement](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#using-filters)

## 3. Pull request dev vers main

Workflow complet indépendant :

```yaml
name: PR dev vers main
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Déclenche le workflow pour les activités de pull request sélectionnées.
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions:
  # Autorise l'accès au contenu du dépôt selon le niveau indiqué.
  contents: read
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « test » ; needs permet de préciser ses dépendances.
  test:
    # Conditionne l'exécution à cette expression évaluée par GitHub.
    if: ${{ github.head_ref == 'dev' }}
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Récupère les fichiers du dépôt dans le workspace du runner.
      - uses: actions/checkout@v7
        # Fournit les paramètres attendus par l'action ou le workflow appelé.
        with:
          # Choisit si checkout conserve l'authentification Git pour les commandes suivantes.
          persist-credentials: false
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Test de la proposition de fusion"
```

`branches` filtre la destination ; `github.head_ref` décrit la branche source. Une PR depuis un fork peut nécessiter une autorisation d'exécution et ne reçoit normalement pas les secrets du dépôt. Ne remplacez pas simplement `pull_request` par `pull_request_target` pour obtenir ces secrets.

Pour tester toutes les PR, retirez la condition sur `dev`. [Événements de pull request](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)

## 4. Planification avec fuseau horaire

```yaml
name: Controle programme
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
  # Définit un déclenchement périodique ; les paramètres du lancement manuel ne sont pas fournis ici.
  schedule:
    # Exprime les minutes, heures, jours du mois, mois et jours de semaine de la planification.
    - cron: '17 8 * * 1-5'
      # Interprète le cron dans ce fuseau plutôt qu'en UTC.
      timezone: Europe/Paris
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « diagnostic » ; needs permet de préciser ses dépendances.
  diagnostic:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Affiche l'heure demandée pour situer cette étape dans les journaux.
      - run: date -u
```

Cette variante vise 8 h 17 du lundi au vendredi à Paris. La documentation actuelle autorise `timezone` avec un identifiant IANA ; sans cette clé, l'horaire est UTC. Contrairement au `H` Jenkins, les minutes sont explicites.

Les schedules utilisent la branche par défaut, peuvent être retardés et ne constituent pas une garantie de temps réel. L'intervalle minimal est cinq minutes. Sur un dépôt public inactif, les schedules peuvent être désactivés après 60 jours. Vérifiez `timezone` sur votre version GHES. [Planification](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 5. Deux formes de chaînage à ne pas confondre

`workflow_call` intègre des jobs réutilisables à l'exécution appelante ; sa configuration est détaillée dans [workflows réutilisables](11.workflows%20reutilisables.md).

`workflow_run` lance une autre exécution après un workflow identifié par son `name`. Exemple de bilan sans accès aux artefacts ni exécution du code amont :

```yaml
name: Bilan apres CI
# Déclare les événements qui peuvent lancer ce workflow.
on:
  workflow_run:
    workflows: [CI]
    types: [completed]
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « bilan » ; needs permet de préciser ses dépendances.
  bilan:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
    env:
      RESULT: ${{ github.event.workflow_run.conclusion }}
      SOURCE_RUN: ${{ github.event.workflow_run.id }}
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: printf 'Execution %s terminee avec %s\n' "$SOURCE_RUN" "$RESULT"
```

Prérequis : un autre workflow est nommé exactement `CI`, et le workflow de bilan existe sur la branche par défaut. Il réagit aussi à un échec. Pour ne traiter que les réussites, ajoutez au job :

```yaml
# Conditionne l'exécution à cette expression évaluée par GitHub.
if: ${{ github.event.workflow_run.conclusion == 'success' }}
```

Cette nouvelle exécution n'hérite ni du workspace ni automatiquement du commit à checkout. Elle peut posséder des privilèges supérieurs à l'amont : ne lui faites pas exécuter du code ou un artefact non fiable. [Chaînage workflow_run](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)

## 6. Éviter les doubles exécutions

Déclarer `push` sur toutes les branches et `pull_request` peut produire deux exécutions pour une branche possédant une PR. Une organisation simple consiste à déclencher `push` uniquement sur `main` et les tests de contributions sur `pull_request`.

Un push effectué avec `GITHUB_TOKEN` ne redéclenche généralement pas un workflow `push`. Les événements dispatch et certains cas de PR automatisées suivent des règles spécifiques, détaillées dans [GITHUB_TOKEN](14.github%20token%20et%20permissions.md).

## Exercice

Testez un changement de README sur `main`, un changement d'un autre fichier, puis une PR `dev` vers `main`. Pour la planification, utilisez aussi le bouton manuel afin de vérifier les commandes sans attendre l'horaire.

La fiche [événements GitHub](17.evenements%20github.md) couvre issues, releases et merge queue. Aucun événement n'a été envoyé pendant cette rédaction.
