# Authentifier un workflow avec OpenID Connect

## Objectif

Obtenir des identifiants temporaires auprès d'un fournisseur compatible, sans stocker une clé cloud permanente dans GitHub.

## 1. Particularité du modèle GitHub

OIDC existe aussi dans GitLab. Ici, on étudie l'émetteur GitHub, `id-token: write` et les claims du job.

Le déroulement est :

1. Le job demande une preuve d'identité à GitHub.
2. Le fournisseur vérifie sa signature, son audience et les conditions de confiance.
3. Il délivre une session temporaire limitée par le rôle associé.
4. Les commandes du job utilisent cette session.

`id-token: write` autorise la demande de jeton ; cette permission ne crée aucun droit cloud à elle seule. [OIDC dans GitHub Actions](https://docs.github.com/en/actions/concepts/security/openid-connect)

## 2. Prérequis pour l'exemple AWS

Un administrateur doit préparer :

- un fournisseur OIDC pour `https://token.actions.githubusercontent.com` ;
- l'audience attendue `sts.amazonaws.com` ;
- un rôle autorisant `sts:AssumeRoleWithWebIdentity` pour ce fournisseur ;
- une condition de confiance limitant précisément le sujet au dépôt et au contexte autorisés ;
- les permissions AWS minimales pour les opérations prévues.

Ajoutez au dépôt deux variables : `AWS_ROLE_ARN` et `AWS_REGION`. L'ARN du rôle est une configuration, pas une clé secrète. [Configuration OIDC avec AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)

## 3. Choisir le bon sujet de confiance

Ne copiez pas une condition `sub` sans vérifier le format utilisé par votre dépôt.

Exemple historique pour une branche :

```text
repo:organisation/depot:ref:refs/heads/main
```

La documentation actuelle décrit aussi un format avec identifiants immuables pour les dépôts concernés :

```text
repo:organisation@OWNER_ID/depot@REPO_ID:ref:refs/heads/main
```

Un job rattaché à un environnement utilise un contexte de sujet différent, par exemple `environment:production` dans la configuration standard. Une personnalisation des claims peut encore modifier ce format.

Vérifiez les réglages OIDC et les claims attendus avant d'écrire la relation de confiance. La documentation indique une évolution des valeurs par défaut depuis juillet 2026 ; GHES n'a pas nécessairement le même comportement. [Claims et sujets OIDC](https://docs.github.com/en/actions/reference/security/oidc)

## 4. Workflow complet de diagnostic

Fichier `.github/workflows/oidc.yml`. L'exemple suppose une confiance pour `main` sans environnement GitHub.

```yaml
name: Diagnostic OIDC AWS
on:
  workflow_dispatch:
permissions: {}
jobs:
  identity:
    if: ${{ github.ref == 'refs/heads/main' }}
    runs-on: ubuntu-24.04
    permissions:
      id-token: write
    steps:
      - name: Obtenir une session temporaire
        uses: aws-actions/configure-aws-credentials@v6.3.0
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}
          role-session-name: actions-${{ github.run_id }}
      - name: Verifier l'identite
        run: aws sts get-caller-identity
```

**Résultat attendu :** le compte AWS et l'ARN d'une session du rôle configuré. La commande vérifie l'identité sans déployer de ressource. Le runner doit disposer d'AWS CLI ; c'est le cas de l'image Ubuntu hébergée visée, à vérifier pour un runner autonome.

L'action échange le jeton GitHub contre une session temporaire et expose les identifiants aux étapes suivantes. [Action officielle AWS](https://github.com/aws-actions/configure-aws-credentials)

## 5. Diagnostic

| Erreur | Vérification |
| --- | --- |
| Impossible d'obtenir le jeton GitHub | `id-token: write` et contexte du job |
| Refus de prise de rôle | Émetteur, audience, sujet, ARN, relation de confiance |
| Identité correcte, opération refusée | Permissions du rôle sur la ressource |
| Fonctionne sur main mais pas en environnement | Sujet OIDC changé par `environment` |

La condition `if` du workflow ne remplace pas les restrictions de confiance côté fournisseur. N'affichez pas le JWT complet ni les identifiants temporaires.

## Exercice

Sur un compte d'exercice configuré, vérifiez l'identité puis lancez depuis une branche non autorisée. Expliquez la différence entre job ignoré par `if` et refus de confiance par AWS.

Aucun rôle, fournisseur ni appel AWS n'a été créé ou exécuté pendant la rédaction.
