# Choisir les runners dans GitHub Actions

## Objectif

Retrouver le rôle des agents Jenkins et des runners GitLab, puis choisir la machine qui exécutera chaque job.

## 1. Correspondances

| Jenkins | GitLab CI/CD | GitHub Actions |
| --- | --- | --- |
| Agent exécutant les commandes | GitLab Runner | GitHub Actions runner |
| `agent any` | Runner éligible, éventuellement sans tags | Choix explicite par `runs-on` |
| `agent { label 'linux' }` | `tags: [linux]` | Labels de runner hébergé ou autonome |
| `agent none` puis agents par stage | Runner choisi par job | `runs-on` dans chaque job contenant des `steps` |
| Agent Docker | `image` avec executor compatible | `container` sur un runner Linux compatible |

Il n'existe pas de `runs-on: any`. Un job appelant un workflow réutilisable utilise `uses` ; ses jobs internes choisissent leurs runners. [Choix du runner](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job)

## 2. Prérequis

Utilisez un dépôt GitHub avec Actions autorisé. Les fichiers de workflow sont placés dans `.github/workflows/`, contrairement au fichier GitLab situé à la racine.

Les exemples sont des variantes indépendantes. Pour utiliser **Run workflow**, placez le fichier sur la branche par défaut, puis ouvrez **Actions > nom du workflow > Run workflow**.

La collection cible GitHub.com. Sur GitHub Enterprise Server, vérifier les fonctionnalités et versions d'actions compatibles avec la version installée.

## 3. Runner hébergé par GitHub

Fichier `.github/workflows/runners.yml` :

```yaml
name: Decouvrir un runner
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « diagnostic » ; needs permet de préciser ses dépendances.
  diagnostic:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Identifier la machine
        # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
        shell: bash
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Affiche les informations système du runner effectivement sélectionné.
          uname -a
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Repertoire : %s\n' "$GITHUB_WORKSPACE"
          printf 'Systeme : %s\n' "$RUNNER_OS"
```

**Résultat attendu :** le job affiche Linux et son répertoire de travail. Le contenu du dépôt n'est pas encore récupéré : cette opération demande une étape `actions/checkout`.

Les runners standards hébergés fournissent un environnement neuf par job. Un runner autonome est maintenu par votre équipe ; son état peut persister. Ne présumez pas qu'un dossier créé par un job sera disponible dans un autre. [Runners hébergés](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners), [runners autonomes](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners)

## 4. Linux puis Windows

```yaml
name: Linux puis Windows
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « build_linux » ; needs permet de préciser ses dépendances.
  build_linux:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      - run: echo "Construction simulee sur Linux"
  # Déclare le job « test_windows » ; needs permet de préciser ses dépendances.
  test_windows:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: build_linux
    # Sélectionne la machine qui exécutera ce job.
    runs-on: windows-latest
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
      - shell: pwsh
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          Write-Output "Test simule sur Windows"
          Write-Output $env:RUNNER_OS
```

`needs` impose l'ordre. Sans lui, les jobs sont éligibles en parallèle. `windows-latest` désigne une image qui évolue ; ce nom ne fixe pas définitivement la version de Windows.

## 5. Runner autonome

Dans **Settings > Actions > Runners**, enregistrez un runner Linux dédié et attribuez-lui le label `atelier-ci`.

```yaml
name: Runner autonome
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « diagnostic » ; needs permet de préciser ses dépendances.
  diagnostic:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: [self-hosted, linux, x64, atelier-ci]
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Affiche les informations système du runner effectivement sélectionné.
      - run: uname -a
```

Le runner doit satisfaire tous les labels et être accessible au dépôt. Un label personnalisé n'installe aucun logiciel. L'absence de runner disponible ou autorisé laisse le job en attente.

Évitez d'exécuter des contributions non fiables sur un runner autonome contenant des accès sensibles. [Ajout d'un runner](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)

## 6. Job dans un conteneur

```yaml
name: Job conteneurise
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « diagnostic » ; needs permet de préciser ses dépendances.
  diagnostic:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Exécute les commandes du job dans ce conteneur sur le runner sélectionné.
    container: alpine:3.22
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
      - shell: sh
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Affiche le contenu ou la liste des fichiers pour vérifier le résultat de l'étape précédente.
          cat /etc/os-release
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          echo "Commandes executees dans Alpine"
```

Le runner reste nécessaire : il héberge le conteneur. L'image détermine les outils disponibles à l'intérieur. Ce n'est pas une action Docker, étudiée dans [les actions personnalisées](10.actions%20personnalisees.md). [Jobs conteneurisés](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/run-jobs-in-a-container)
