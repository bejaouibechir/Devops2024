# Checks, annotations et résumés d'exécution

## Objectif

Rendre les résultats lisibles dans GitHub sans demander au lecteur de parcourir tous les logs.

## 1. Trois sorties différentes

| Sortie | Utilité |
| --- | --- |
| Statut du job/check | Indiquer réussite, échec, annulation ou étape ignorée |
| Annotation | Signaler un problème, éventuellement lié à une ligne |
| Résumé Markdown | Présenter un bilan sur la page du run |

GitLab possède des rapports et vues de tests. GitHub utilise notamment les commandes `::warning::`, `::error::` et le fichier `GITHUB_STEP_SUMMARY`. L'upload d'un XML JUnit n'est pas à lui seul un import de résultats de tests.

## 2. Exemple complet

Fichier `.github/workflows/report.yml` :

```yaml
name: Rapport lisible
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  documentation:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - name: Verifier le README
        id: check
        run: |
          if [ ! -s README.md ]; then
            echo "::error file=README.md,line=1,title=Documentation::README absent ou vide"
            exit 1
          fi
          echo "::notice title=Documentation::README present"
      - name: Produire une synthese
        if: ${{ !cancelled() }}
        env:
          RESULT: ${{ steps.check.outcome }}
        run: |
          {
            echo "## Verification de la documentation"
            echo ""
            echo "| Controle | Resultat |"
            echo "| --- | --- |"
            printf '| README | %s |\n' "$RESULT"
          } >> "$GITHUB_STEP_SUMMARY"
```

**Résultat attendu :** la page du run affiche un tableau. Un README absent ou vide provoque un échec et une annotation.

Émettre `::error::` signale le problème ; le `exit 1` établit l'échec de cette commande. Ne supposez pas qu'un texte « erreur » suffit à bloquer le pipeline. [Annotations et résumés](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands)

## 3. Un résumé n'est pas une variable partagée

`GITHUB_STEP_SUMMARY` est propre à l'étape. Les contributions sont affichées sur la page du run ; une étape suivante ne doit pas compter sur ce chemin pour modifier le résumé d'une étape terminée.

Pour transmettre un état, utilisez un output. Pour conserver un rapport téléchargeable, utilisez un artefact.

Ne publiez pas de secrets dans les résumés. Pour un contenu fourni par un utilisateur, échappez les valeurs insérées dans du Markdown et n'injectez pas des propriétés d'annotation sans validation.

## 4. Contrôles obligatoires de branche

Les règles de branche ou rulesets peuvent exiger des checks avant fusion. Donnez aux jobs des noms stables et non ambigus.

Un workflow entièrement ignoré par des filtres de chemins peut laisser un contrôle attendu en attente. Concevez les filtres avec les règles de fusion, plutôt que de supposer qu'une absence d'exécution est une validation. [Contrôles obligatoires](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

Avec une merge queue, ajoutez l'événement adapté présenté dans [événements GitHub](17.evenements%20github.md).

## Exercice

Testez avec un README valide, puis vide. Comparez le statut, l'annotation et le résumé : ils décrivent le même contrôle mais remplissent des fonctions différentes.

Les checks et résumés n'ont pas été produits sur GitHub pendant cette rédaction.
