# Exécuter des commandes distantes avec SSH dans GitLab CI/CD

## Objectif

Adapter l'exemple Jenkins `sshagent { sh 'ssh ...' }` : connecter un runner à un serveur, y lancer une commande et récupérer son résultat. Compléter le transfert de fichiers du thème [7.artefact.md](7.artefact.md).

Les commandes de cette fiche sont des exemples à configurer ; elles n'ont pas été exécutées sur un serveur.

## 1. Correspondances et correction du support Jenkins

Le bloc `sshagent(...)` du support appartient au plugin **SSH Agent**. Le plugin **SSH Pipeline Steps** fournit d'autres étapes, comme `sshCommand`, `sshScript` et `sshPut`. Installer SSH Steps seul ne fournit pas `sshagent`. [SSH Agent](https://plugins.jenkins.io/ssh-agent/), [SSH Pipeline Steps](https://plugins.jenkins.io/ssh-steps/)

| Jenkins | GitLab CI/CD |
| --- | --- |
| Credential SSH identifié par un ID | Variable CI/CD de type File contenant la clé privée |
| Bloc `sshagent` | Agent OpenSSH lancé dans le job, ou clé passée directement avec `ssh -i` |
| Étape `sh` exécutant `ssh` | Commande `ssh` dans `script` |
| Configuration des hôtes connus | Fichier `known_hosts` vérifié et fourni au job |
| Agent Jenkins | Runner GitLab disposant du client SSH et de l'accès réseau |

Le runner exécute le **client SSH** ; la commande demandée s'exécute sur le **serveur distant**. Les outils distants doivent être installés sur ce serveur. Aucun plugin Jenkins n'intervient dans GitLab.

## 2. Prérequis

- Un runner Linux avec un shell POSIX, `ssh`, `chmod` et, pour le transfert, `scp`.
- Un serveur Linux joignable depuis le runner sur son port SSH.
- Un compte distant dédié, par exemple `deploy`, dont la clé publique autorisée se trouve dans `~/.ssh/authorized_keys`.
- Une clé privée dédiée à l'automatisation et un fichier de clés d'hôte vérifiées.

Avec un executor Docker ou Kubernetes, le client SSH doit être présent dans l'image du job. Avec Shell, il doit être installé sur la machine du runner. Un tag `linux` ou `ssh` ne l'installe pas.

### Préparer les deux identités SSH

| Élément | Fonction |
| --- | --- |
| Clé publique utilisateur dans `authorized_keys` | Autorise le compte CI à se connecter au serveur. |
| Clé privée utilisateur dans GitLab | Permet au job de prouver cette identité. |
| Clé publique du serveur dans `known_hosts` | Permet au job de reconnaître le bon serveur. |

Créez une paire dédiée depuis un poste d'administration de confiance, par exemple :

```sh
ssh-keygen -t ed25519 -f gitlab-ci-demo -C "gitlab-ci-demo"
```

Pour la variante directe de cette fiche, la clé doit pouvoir être utilisée sans saisie interactive de passphrase. Installez uniquement sa partie publique sur le compte distant. Les permissions habituelles sont `700` pour son dossier `.ssh` et `600` pour `authorized_keys`, avec le compte distant comme propriétaire.

Faites fournir la clé d'hôte par l'administrateur du serveur, ou relevez-la depuis un environnement de confiance et comparez son empreinte avec celle obtenue par un canal indépendant. `ssh-keyscan` seul collecte une clé sans authentifier son origine. Ne faites pas cette découverte automatiquement pendant le job. Pour un port différent de 22, l'entrée correspondante utilise la forme `[serveur]:port`. [Vérification des clés d'hôte](https://docs.gitlab.com/ci/jobs/ssh_keys/#verifying-the-ssh-host-keys)

## 3. Configurer les variables du projet

Dans **Settings > CI/CD > Variables** :

| Nom | Type | Valeur |
| --- | --- | --- |
| `SSH_PRIVATE_KEY` | File | Contenu complet de la clé privée dédiée |
| `SSH_KNOWN_HOSTS` | File | Lignes de clés d'hôte validées pour le serveur et le port |
| `SSH_HOST` | Variable | Nom DNS ou IP du serveur, sans `ssh://` ni port |
| `SSH_USER` | Variable | Compte distant, par exemple `deploy` |
| `SSH_PORT` | Variable, facultative | Port SSH ; l'exemple utilise `22` par défaut |

Une variable **File** contient, dans le shell, le **chemin d'un fichier temporaire** : `$SSH_PRIVATE_KEY` ne contient donc pas directement le texte de la clé. [Variables de type fichier](https://docs.gitlab.com/ci/variables/#use-file-type-cicd-variables)

La clé privée doit conserver ses sauts de ligne LF et se terminer par un saut de ligne. Le masquage GitLab ne convient pas à son contenu multiligne ; utilisez le réglage de visibilité prévu pour ce format, sans jamais afficher le fichier dans les logs. Une variable « Visible » n'est pas automatiquement affichée par le job. [Ajout d'une clé SSH](https://docs.gitlab.com/ci/jobs/ssh_keys/#add-an-ssh-key-as-a-file-type-variable)

Si les variables sont **Protected**, exécutez les essais sur une branche protégée autorisée, par exemple `main`. Avec une portée d'environnement limitée, le job doit aussi déclarer l'environnement correspondant ; pour ce diagnostic sans `environment`, utilisez une portée `*`.

## 4. Exemple complet : vérifier le serveur et exécuter une commande

Cet exemple ne modifie pas le serveur. Il affiche le compte connecté, le nom de la machine et son répertoire courant.

```yaml
variables:
  SSH_PORT: "22"

.ssh_base:
  before_script:
    - command -v ssh
    - test -n "$SSH_HOST"
    - test -n "$SSH_USER"
    - test -s "$SSH_PRIVATE_KEY"
    - test -s "$SSH_KNOWN_HOSTS"
    - chmod 600 "$SSH_PRIVATE_KEY"

diagnostic_ssh:
  extends: .ssh_base
  when: manual
  allow_failure: false
  timeout: 2 minutes
  script:
    - |
      ssh -T \
        -i "$SSH_PRIVATE_KEY" \
        -p "$SSH_PORT" \
        -o BatchMode=yes \
        -o IdentitiesOnly=yes \
        -o StrictHostKeyChecking=yes \
        -o "UserKnownHostsFile=$SSH_KNOWN_HOSTS" \
        -o ConnectTimeout=10 \
        "${SSH_USER}@${SSH_HOST}" \
        'set -eu; whoami; hostname; pwd'
```

`.ssh_base` est un modèle caché : il ne s'exécute pas comme un job. `extends` en reprend la préparation. Le nom `.ssh_base` n'est pas un mot-clé spécial.

1. Enregistrez le YAML sur la branche choisie.
2. Ouvrez **Build > Pipelines**, puis le pipeline.
3. Lancez `diagnostic_ssh`.
4. Vérifiez dans les logs les informations de la machine distante.

Le job est manuel et bloquant. Pour un diagnostic automatique à chaque pipeline autorisé, retirez `when: manual` ; les règles du thème [5.triggers.md](5.triggers.md) permettent de limiter ses déclenchements.

### Pourquoi ces options ?

| Option | Effet |
| --- | --- |
| `-i` | Sélectionne le fichier de clé privée. |
| `-p` | Sélectionne le port SSH. |
| `-T` | Désactive l'allocation d'un terminal distant. |
| `BatchMode=yes` | Échoue plutôt que demander un mot de passe interactif. |
| `IdentitiesOnly=yes` | Limite l'essai des identités aux clés configurées. |
| `StrictHostKeyChecking=yes` | Refuse un hôte inconnu ou une clé modifiée. |
| `UserKnownHostsFile` | Utilise le fichier d'hôtes fourni au job. |
| `ConnectTimeout=10` | Limite l'établissement de connexion, pas toute la commande distante. |

La durée totale est limitée séparément par `timeout` du job. N'utilisez pas `StrictHostKeyChecking=no` pour contourner une erreur de confiance. [Options OpenSSH](https://man.openbsd.org/ssh_config), [commande ssh](https://man.openbsd.org/ssh)

## 5. Plusieurs commandes : distinguer shell local et distant

Remplacez uniquement le `script` de `diagnostic_ssh` par ce fragment :

```yaml
script:
  - |
    ssh -T \
      -i "$SSH_PRIVATE_KEY" \
      -p "$SSH_PORT" \
      -o BatchMode=yes \
      -o IdentitiesOnly=yes \
      -o StrictHostKeyChecking=yes \
      -o "UserKnownHostsFile=$SSH_KNOWN_HOSTS" \
      -o ConnectTimeout=10 \
      "${SSH_USER}@${SSH_HOST}" 'sh -se' <<'REMOTE'
    echo "Utilisateur distant : $(id -un)"
    echo "Machine distante : $(hostname)"
    echo "Repertoire personnel distant : $HOME"
    test -d "$HOME"
    REMOTE
```

Le délimiteur cité `<<'REMOTE'` empêche l'expansion locale du bloc : `$HOME` et les commandes entre `$()` sont évalués sur le serveur. Les variables CI/CD ne sont pas automatiquement disponibles dans ce shell distant.

`sh -se` lit le script transmis et arrête les commandes simples en cas d'échec. SSH renvoie le code de sortie distant, ou généralement `255` en cas d'erreur SSH. Une commande finale réussie peut masquer une commande précédente échouée si l'on enchaîne sans contrôler les erreurs ; évitez aussi d'ajouter `|| true` sur une action obligatoire. [Exécution distante](https://man.openbsd.org/ssh)

Pour exécuter un script déjà présent dans le dépôt, on peut de même transmettre son contenu à `sh -se` avec une redirection d'entrée. Le script agit alors sur le serveur, pas sur le disque du runner.

## 6. Variante avec `ssh-agent`

`ssh -i` suffit pour les exemples précédents. Si un outil exige un agent, démarrez `ssh-agent` puis chargez la clé avec `ssh-add` dans le job. Cela se fait sans plugin GitLab.

Les variables `SSH_AUTH_SOCK` et `SSH_AGENT_PID` créées dans le shell principal ne sont pas conservées automatiquement dans `after_script`, qui utilise un autre shell. Ne comptez donc pas sur un simple `ssh-agent -k` dans `after_script` sans organiser la transmission de ces informations. Pour une variante à agent, prévoyez son arrêt dans le contexte qui l'a créé. [Contexte des scripts](https://docs.gitlab.com/ci/variables/#exporting-variables)

## 7. Relier les artefacts au transfert SSH

Gardez le fichier complet du chapitre 4, puis ajoutez ces deux jobs. Ils utilisent les stages GitLab par défaut `build`, `test` et `deploy` : le diagnostic reste dans `test`.

Prérequis supplémentaires : `scp` sur le runner et un dossier `ci-demo` déjà créé dans le répertoire personnel du compte distant, avec les droits d'écriture appropriés.

```yaml
preparer_fichier:
  stage: build
  script:
    - mkdir -p dist
    - 'printf "Pipeline %s\n" "$CI_PIPELINE_IID" > dist/message.txt'
  artifacts:
    paths:
      - dist/message.txt
    expire_in: 7 days

transferer_fichier:
  extends: .ssh_base
  stage: deploy
  when: manual
  allow_failure: false
  timeout: 2 minutes
  dependencies:
    - preparer_fichier
  script:
    - command -v scp
    - test -f dist/message.txt
    - |
      scp -B \
        -i "$SSH_PRIVATE_KEY" \
        -P "$SSH_PORT" \
        -o IdentitiesOnly=yes \
        -o StrictHostKeyChecking=yes \
        -o "UserKnownHostsFile=$SSH_KNOWN_HOSTS" \
        -o ConnectTimeout=10 \
        dist/message.txt \
        "${SSH_USER}@${SSH_HOST}:ci-demo/message-${CI_PIPELINE_IID}.txt"
```

Exécutez le diagnostic, puis le transfert. `dependencies` récupère le fichier du build ; l'ordre des stages conserve la barrière du diagnostic. Relancer le transfert du même pipeline peut remplacer son fichier distant.

Attention à la casse : **`ssh -p`**, mais **`scp -P`** pour le port. OpenSSH récent utilise normalement SFTP pour `scp` ; le serveur doit fournir le sous-système adapté. [Commande scp](https://man.openbsd.org/scp)

Pour un JAR, remplacez le producteur et le fichier par ceux de [7.artefact.md](7.artefact.md). Un transfert ne redémarre pas un service. Une commande d'administration distante nécessite les droits du compte ; si `sudo` est prévu, son mode `-n` permet d'échouer au lieu d'attendre un mot de passe.

## 8. Dépannage

| Symptôme | Points à vérifier |
| --- | --- |
| `ssh: command not found` | Client absent de la machine ou de l'image du runner. |
| Variable vide / fichier de clé absent | Type File, branche protégée, portée d'environnement et droits du pipeline. |
| `Permission denied (publickey)` | Compte cible, clé publique installée, clé privée correspondante, permissions serveur. |
| `Host key verification failed` | Nom/IP exact, port et clé d'hôte validée ; investiguer un changement avant mise à jour. |
| `error in libcrypto` | Format de la clé et saut de ligne LF final. |
| Connexion refusée ou timeout | Service SSH, routage depuis le runner, pare-feu et port. |
| Commande introuvable à distance | Outil ou PATH du compte distant ; une session non interactive ne charge pas forcément la configuration habituelle. |
| Échec SFTP lors du transfert | Sous-système SFTP disponible sur le serveur. |

Ne publiez pas la clé privée dans un artefact ou dans un cache ; conservez les chemins d'archivage ciblés sur les seuls livrables. [Configuration SSH GitLab](https://docs.gitlab.com/ci/jobs/ssh_keys/)

## 9. Exercices

1. Exécutez le diagnostic et vérifiez qu'il affiche bien l'identité du serveur distant.
2. Essayez la variante multiligne et comparez le `$HOME` distant à celui du runner.
3. Dans un projet de test, remplacez la commande distante par `exit 7` : le job doit échouer.
4. Testez une copie du fichier d'hôtes ne contenant pas l'entrée attendue : la connexion doit être refusée, sans désactiver la vérification.
5. Transférez `message.txt`, puis vérifiez son contenu sur le serveur.

Les exemples ont été relus avec les documentations officielles. Aucun serveur n'a été contacté, aucune clé n'a été créée et aucun transfert n'a été effectué. Validez le YAML et les prérequis avant les essais sur votre environnement.
