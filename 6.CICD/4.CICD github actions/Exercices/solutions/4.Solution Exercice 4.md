# Solution 4 — Attente explicite et retry distinct

[Énoncé](../4.Exercice%204.md) · [Guide commun](../readme.md)

## 1. Workflow complet : deux passages

Créer `.github/workflows/exercice-4.yml` :

```yaml
name: Exercice 4 - Deux passages
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:

# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Définit les réglages par défaut des commandes run dans cette portée.
defaults:
  # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
  run:
    # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
    shell: bash

# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « premier » ; needs permet de préciser ses dépendances.
  premier:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Arrête le traitement si sa durée dépasse ce nombre de minutes.
    timeout-minutes: 5
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Premier passage
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie, propage aussi les erreurs dans les pipelines de commandes.
          set -euo pipefail
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          echo "Premier traitement"
          # Affiche l'heure demandée pour situer cette étape dans les journaux.
          date -u '+Fin du premier : %Y-%m-%dT%H:%M:%SZ'

  # Déclare le job « second » ; needs permet de préciser ses dépendances.
  second:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: premier
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Arrête le traitement si sa durée dépasse ce nombre de minutes.
    timeout-minutes: 5
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Attendre puis traiter
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie, propage aussi les erreurs dans les pipelines de commandes.
          set -euo pipefail
          # Affiche l'heure demandée pour situer cette étape dans les journaux.
          date -u '+Debut de attente : %Y-%m-%dT%H:%M:%SZ'
          # Attend le nombre de secondes indiqué en conservant le runner occupé.
          sleep 60
          # Affiche l'heure demandée pour situer cette étape dans les journaux.
          date -u '+Debut du second : %Y-%m-%dT%H:%M:%SZ'
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          echo "Second traitement"
```

## 2. Ce que garantit ce workflow

`needs` impose l'ordre. Après le succès du premier job et l'attribution d'un runner au second, celui-ci attend 60 secondes. Le délai total peut être plus long à cause de la file et de l'initialisation.

C'est une exécution de workflow avec deux traitements, pas deux exécutions du workflow. `timeout-minutes` est une limite, pas une temporisation ni un retry. Un échec du premier job fait ignorer le second.

GitLab place un job différé dans son ordonnanceur sans occuper le runner pendant le délai. Ici le runner reste occupé durant `sleep` ; réserver cette technique à une courte démonstration. Un minuteur d'approbation d'environnement a un autre rôle et dépend de l'offre. [Dépendances et durées](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds)

## 3. Extension distincte : deux tentatives au maximum

Le fragment suivant est **une étape** à placer sous `steps`, pas un workflow autonome. Il simule un premier échec puis une réussite ; pour un vrai usage, remplacer le test dans le `if` par une commande adaptée et idempotente.

```yaml
- name: Retry local de demonstration
  # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
  shell: bash
  # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
  run: |
    # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie, propage aussi les erreurs dans les pipelines de commandes.
    set -euo pipefail
    # Répète ce bloc pour chaque valeur de la liste, dans l'ordre indiqué.
    for tentative in 1 2; do
      # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
      printf 'Tentative %s\n' "$tentative"
      # Choisit la suite du traitement selon le résultat de ce test.
      if test "$tentative" -eq 2; then
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        echo "Operation reussie"
        # Termine cette tentative avec succès ; les instructions suivantes ne seront pas exécutées.
        exit 0
      else
        # Prépare une valeur locale au shell ; elle ne devient pas automatiquement disponible dans un autre job.
        statut=$?
      fi
      # Choisit la suite du traitement selon le résultat de ce test.
      if [[ "$tentative" -eq 2 ]]; then
        # Écrit le diagnostic sur la sortie d'erreur pour distinguer l'erreur des résultats normaux.
        echo "Deux echecs : abandon" >&2
        # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
        exit "$statut"
      fi
      # Attend le nombre de secondes indiqué en conservant le runner occupé.
      sleep 60
    done
```

Le `if` capture un échec sans que `set -e` interrompe prématurément la boucle. Si la commande échoue deux fois, son dernier code est renvoyé. Si elle réussit dès la première fois, aucune seconde tentative n'est faite. Pour tester ces cas, remplacer temporairement `test "$tentative" -eq 2` par `true`, puis `false`.

Jenkins possède `retry` et GitLab une clé `retry` de job. GitHub ne possède pas de clé de job équivalente dans ce corrigé ; une boucle, une action spécialisée ou une relance du workflow ont des portées différentes.

## 4. Vérifications

Comparer les horodatages du workflow principal. Faire échouer le premier job pour vérifier que le second est ignoré. Dans l'extension, contrôler les trois cas : succès immédiat, succès à la deuxième tentative, deux échecs.

Un événement cron GitHub ne convient pas à une fréquence d'une minute ; l'intervalle minimal documenté est de cinq minutes. [Planification](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
