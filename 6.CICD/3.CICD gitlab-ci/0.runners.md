# Utilisation des runners dans un pipeline GitLab CI/CD

## Objectif

Comprendre l'équivalent des agents Jenkins et choisir où les jobs GitLab CI/CD s'exécutent.

## 1. De l'agent Jenkins au GitLab Runner

Un **GitLab Runner** exécute les commandes des jobs définis dans le fichier `.gitlab-ci.yml`, placé à la racine du dépôt.

Dans Jenkins, la directive `agent` choisit l'environnement d'exécution du pipeline ou d'un stage. Dans GitLab CI/CD, la sélection se fait au niveau de chaque **job**, notamment grâce à ses `tags`.

| Jenkins                            | GitLab CI/CD                        | Nuance                                                                                   |
| ---------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------- |
| Agent Jenkins                      | GitLab Runner                       | Exécute les tâches du pipeline.                                                          |
| `agent { label 'linux' }`          | `tags: [linux]`                     | Le runner doit posséder le tag demandé.                                                  |
| `agent none` puis agents par stage | Sélection du runner pour chaque job | Il n'existe pas de directive `agent none` : chaque job de script est confié à un runner. |

Un stage GitLab regroupe des jobs ; il ne possède pas lui-même de runner. Deux jobs d'un même stage peuvent s'exécuter sur des runners différents.

## 2. Prérequis

- Disposer d'un projet GitLab et du droit d'y modifier les fichiers.
- Disposer d'au moins un runner en ligne, autorisé à exécuter les jobs du projet et de la branche utilisée.
- Consulter les runners disponibles dans **Settings > CI/CD > Runners**.

Les exemples suivants sont des variantes : remplacez le contenu de `.gitlab-ci.yml` par l'exemple à tester.

## 3. Équivalent pratique de `agent any`

Le runner doit être configuré pour accepter les jobs sans tags (**Run untagged**).

```yaml
demo_runner:
  script:
    - echo "Execution sur un runner disponible"
```

1. Créez le fichier `.gitlab-ci.yml` à la racine du dépôt.
2. Ajoutez cet exemple puis enregistrez-le dans un commit.
3. Ouvrez **Build > Pipelines**, puis le job `demo_runner`.
4. Consultez son journal : l'en-tête indique le runner et l'executor utilisés, puis la commande affiche le message.

**Résultat attendu :** le job s'exécute sur un runner éligible acceptant les jobs sans tags. Sans runner compatible, il reste en attente (`pending`).

## 4. Équivalent de `agent { label 'linux' }`

Prérequis : un runner Linux disponible pour le projet porte le tag `linux`.

```yaml
demo_linux:
  tags:
    - linux
  script:
    - echo "Execution sur un runner Linux"
    - uname -a
```

**Résultat attendu :** GitLab sélectionne un runner portant le tag `linux`.

Les tags sont des étiquettes définies lors de la configuration du runner : le mot `linux` n'installe pas Linux et ne vérifie pas automatiquement le système. Il faut attribuer ce tag à un runner adapté.

Si un job demande plusieurs tags, le runner doit les posséder **tous**.

## 5. Équivalent de `agent none` avec des agents différents

Dans GitLab, chaque job sélectionne son runner. Pour reprendre l'exemple Jenkins avec un build Linux et un test Windows :

```yaml
stages:
  - build
  - test

build_linux:
  stage: build
  tags:
    - linux
  script:
    - echo "Build sur Linux"
    - uname -a

test_windows:
  stage: test
  tags:
    - windows
  script:
    - echo "Test sur Windows"
```

Prérequis : des runners adaptés portant respectivement les tags `linux` et `windows` sont disponibles pour le projet.

**Résultat attendu :** le job `build_linux` s'exécute d'abord ; après sa réussite, `test_windows` s'exécute sur un runner portant le tag `windows`.

Ces jobs n'ont pas de répertoire de travail partagé garanti. Le transfert des fichiers produits sera traité dans le thème consacré aux artefacts.

## À retenir

- **Runner** : exécute le job.
- **Tags** : permettent de sélectionner les runners compatibles.
- **Executor** : détermine comment le runner exécute les commandes, par exemple avec Shell, Docker ou Kubernetes.
- Un runner adapté doit déjà être disponible : écrire un tag dans le YAML ne crée pas de runner.
