# GITHUB_TOKEN et permissions des jobs

## Objectif

Utiliser l'identité automatique du job pour accéder à GitHub avec les droits nécessaires.

## 1. Une identité créée pour le job

GitHub fournit `GITHUB_TOKEN`, également accessible via `github.token`. Il ne faut pas créer manuellement un secret portant ce nom. Son accès est limité au dépôt du workflow et sa durée de vie à celle autorisée pour le job.

GitLab propose `CI_JOB_TOKEN`, mais ses ressources et règles d'accès diffèrent. Le modèle GitHub s'appuie sur un jeton d'installation GitHub App et une déclaration `permissions`. [GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token)

## 2. Choisir les permissions

| Permission | Exemple d'usage |
| --- | --- |
| `contents: read` | Checkout du dépôt |
| `actions: read` | Lire les runs et leurs artefacts |
| `issues: write` | Créer ou modifier une issue |
| `packages: write` | Publier dans un registre GitHub autorisé |
| `id-token: write` | Demander un jeton OIDC |
| `attestations: write` | Publier une attestation |

Déclarer certaines permissions met les autres à `none`, sauf exceptions documentées. `permissions: {}` désactive les droits configurables. Une politique d'organisation ou le contexte d'une PR peut restreindre les droits effectifs. [Syntaxe des permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)

## 3. Exemple complet en lecture seule

Fichier `.github/workflows/token.yml`. Le runner Ubuntu hébergé fournit GitHub CLI.

```yaml
name: Consulter les executions
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « inspect » ; needs permet de préciser ses dépendances.
  inspect:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
    permissions:
      actions: read
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Lire les cinq derniers runs
        # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
        env:
          GH_TOKEN: ${{ github.token }}
          GH_REPO: ${{ github.repository }}
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          gh api --method GET "repos/$GH_REPO/actions/runs" \
            -f per_page=5 \
            --jq '.workflow_runs[] | [.id, .name, .status] | @tsv'
```

**Résultat attendu :** les identifiants, noms et états des dernières exécutions. Aucun checkout n'est nécessaire pour consulter l'API.

`GH_TOKEN` est le nom attendu par `gh` ; `github.token` fournit sa valeur. Le jeton n'est jamais affiché. [Authentification dans les workflows](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token)

## 4. Actions et confiance

Une action peut accéder au jeton via le contexte GitHub même si aucun input nommé `token` ne lui est fourni. Réduire les permissions du job et choisir des actions de confiance est donc plus important que simplement retirer une ligne `with`.

Pour accéder à un autre dépôt privé, utilisez une identité explicitement autorisée, par exemple une GitHub App avec les permissions et installations adaptées. `contents: write` sur le dépôt courant ne donne pas accès à tous les dépôts de l'organisation.

## 5. Déclenchements issus du jeton

Un push effectué avec `GITHUB_TOKEN` ne déclenche généralement pas un nouveau workflow `push`. Les dispatchs explicites sont des exceptions.

La documentation actuelle prévoit aussi des runs soumis à approbation pour les événements PR `opened`, `synchronize` et `reopened` produits par ce jeton. Il serait donc inexact d'affirmer qu'aucun workflow ne peut jamais être déclenché par `GITHUB_TOKEN`. [Règles de déclenchement](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)

## Exercice

Dans un dépôt d'essai, exécutez le workflow puis retirez `actions: read`. Comparez les droits effectifs et l'erreur éventuelle, particulièrement pour un dépôt privé.
