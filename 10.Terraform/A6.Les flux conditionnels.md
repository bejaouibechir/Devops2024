# Atelier 4 : Flux Conditionnels dans Terraform

## 1. Introduction

## Pourquoi utiliser des conditions ?

Dans les ateliers précédents, les ressources étaient créées de manière fixe.

Exemple :

```hcl
resource "local_file" "report" {
  filename = "report.txt"
  content  = "Rapport Terraform"
}
```

Mais dans un vrai projet, on veut souvent adapter le comportement selon un contexte :

```text
Si environment = dev       → créer un rapport simple
Si environment = prod      → créer un rapport plus strict
Si enable_debug = true      → créer un fichier debug
Si create_extra_files = true → créer des fichiers supplémentaires
```

Terraform propose plusieurs façons d’exprimer ces conditions :

- Opérateur ternaire

- Count conditionnel

- for_each conditionnel

- expressions for avec if

- locals conditionnels

- dynamic conditionnel

Parmi les cas d'utilisation:

- utiliser l’opérateur ternaire

- créer une ressource conditionnellement avec count

- créer plusieurs ressources conditionnellement avec for_each

- filtrer une collection avec for

- centraliser des décisions dans locals

- comprendre la limite de dynamic avec le provider Local

- éviter les pièges fréquents des conditions

## Contrainte de l’atelier

On utilise uniquement le provider **Local** :

```text
hashicorp/local
```

Cela permet de travailler sans compte cloud, sans clé API et sans authentification.

# 3. Étape 1 : L’opérateur ternaire

## 3.1 Objectif

Utiliser une condition pour choisir une valeur.

La forme générale est :

```hcl
condition ? valeur_si_vrai : valeur_si_faux
```

Exemple :

```hcl
var.environment == "prod" ? "production" : "non-production"
```

Cette expression signifie :

```text
Si environment vaut prod, retourner production.
Sinon, retourner non-production.
```

---

## 3.2 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Environnement cible.
# Valeurs autorisées : dev, test, prod.
variable "environment" {
  type        = string
  description = "Environnement cible : dev, test ou prod."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment doit être dev, test ou prod."
  }
}

# Active ou désactive le mode debug.
variable "enable_debug" {
  type        = bool
  description = "Active ou désactive le mode debug."
  default     = false
}
```

---

## 3.3 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# Crée un rapport dont le contenu dépend de conditions.
resource "local_file" "environment_report" {
  filename = "environment-report.txt"

  content = <<EOT
Rapport environnement

Environnement : ${var.environment}

Type d’environnement :
${var.environment == "prod" ? "production" : "non-production"}

Niveau de sécurité :
${var.environment == "prod" ? "strict" : "standard"}

Mode debug :
${var.enable_debug ? "activé" : "désactivé"}
EOT
}
```

## 3.9 Questions pédagogiques

**Quelle condition permet de détecter l’environnement prod ?**
`var.environment == "prod"` — c’est une comparaison d’égalité qui retourne `true` si la variable vaut exactement `"prod"`, `false` sinon.

**Quelle valeur est retournée si la condition est vraie ?**
La valeur à gauche du `:` dans le ternaire. Exemple : `var.environment == "prod" ? "production" : "dev"` retourne `"production"` si vrai.

**Quelle valeur est retournée si la condition est fausse ?**
La valeur à droite du `:`. Dans l’exemple ci-dessus, `"dev"` est retourné si la condition est fausse.

**Quelle différence entre une variable bool et une condition de comparaison ?**
Une variable `bool` (`var.enable_debug`) est déjà `true` ou `false` et peut être utilisée directement comme condition. Une condition de comparaison (`var.environment == "prod"`) évalue une expression et produit `true` ou `false` au moment du plan. Les deux peuvent s’utiliser dans un ternaire, mais la comparaison est plus flexible car elle peut tester n’importe quelle valeur.

---

## 3.10 Points clés

**Ternaire** : permet de choisir entre deux valeurs.

**Condition booléenne** : expression qui retourne **true** ou **false**.

**var.enable_debug** peut être utilisé directement comme condition.

---

## 3.11 Astuces

Pour une condition simple, l’opérateur ternaire est très lisible.

Exemple :

```hcl
var.enable_debug ? "debug activé" : "debug désactivé"
```

Pour une condition longue, il vaut mieux utiliser **locals** plus tard dans l’atelier.

---

## 3.12 Attention

Les deux branches du ternaire doivent produire des valeurs compatibles.

Correct :

```hcl
var.environment == "prod" ? "strict" : "standard"
```

À éviter :

```hcl
var.environment == "prod" ? "strict" : 3
```

# 4. Étape 2 : Conditions avec count

## 4.1 Objectif

Créer ou ne pas créer une ressource selon une condition.

Le mécanisme **count** accepte un nombre entier. Il peut donc être utilisé avec une condition qui retourne :

1 → créer la ressource

Terraform précise que **count** permet de créer plusieurs instances d’une ressource avec un entier, chaque instance ayant son propre objet d’infrastructure associé. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/meta-arguments/count?utm_source=chatgpt.com "count meta-argument reference | Terraform"))

## 4.10 Questions pédagogiques

**Pourquoi `count = 0` empêche-t-il la création ?**
Terraform crée autant d’instances d’une ressource que la valeur de `count`. Si `count = 0`, Terraform crée zéro instance — la ressource n’existe pas. Si `count = 1`, une instance est créée. C’est le mécanisme utilisé pour conditionner l’existence d’une ressource.

**Pourquoi l’adresse devient-elle `local_file.debug_report[0]` quand count est utilisé ?**
Dès qu’une ressource utilise `count`, Terraform la traite comme une liste d’instances indexées. Même si `count = 1`, l’instance unique est accessible à l’index `[0]`. Sans `count`, l’adresse serait simplement `local_file.debug_report`.

**Pourquoi faut-il écrire `local_file.debug_report[0].filename` dans l’output ?**
Parce que `local_file.debug_report` avec `count` est une liste, pas un objet unique. Écrire `local_file.debug_report.filename` sans l’index provoquerait une erreur car Terraform ne sait pas de quelle instance extraire l’attribut. L’index `[0]` désigne la première (et unique) instance.

---

## 4.11 Points clés

**count conditionnel** sert à créer ou supprimer une ressource.

Forme classique :

```hcl
count = var.enable_resource ? 1 : 0
```

Quand **count** est utilisé, la ressource devient une liste d’instances.

---

## 4.12 Attention

Ce code serait incorrect si la ressource n’existe pas :

```hcl
local_file.debug_report[0].filename
```

Il faut protéger l’accès :

```hcl
var.enable_debug_file ? local_file.debug_report[0].filename : "debug non créé"
```

## 5.4 Créer le fichier main.tf

```hcl

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# for_each utilise une liste filtrée.
# Seuls les environnements présents dans enabled_environments sont conservés.

  filename = "env-${each.key}.txt"

  content = <<EOT
Rapport environnement

Environnement : ${each.value}
Statut : activé

EOT
}
```

## 5.11 Points clés

**for_each** est très adapté aux ressources identifiées par un nom.

La condition est souvent appliquée avant **for_each** avec une expression **for** filtrante.

Forme utilisée :

```hcl
for_each = toset([
  for env in var.environments :
  env if contains(var.enabled_environments, env)
])
```

---

## 5.12 Attention — Les clés de for_each doivent être connues avant apply

Terraform a besoin de connaître les clés de `for_each` **au moment du plan**, avant de créer quoi que ce soit. Si une clé dépend d'un attribut calculé après création (comme un `id` généré par un provider), Terraform ne peut pas construire son graphe de dépendances et refuse d'exécuter.

---

### Cas correct — clés issues d'une variable connue avant apply

```hcl
variable "environments" {
  type    = list(string)
  default = ["dev", "prod"]
}

# Les clés sont "dev" et "prod" : connues dès le plan.
resource "local_file" "rapport" {
  for_each = toset(var.environments)
  filename = "env-${each.key}.txt"
  content  = "Environnement : ${each.key}"
}
```

`terraform plan` affiche immédiatement :

```text
+ local_file.rapport["dev"]
+ local_file.rapport["prod"]
```

Les clés sont connues avant que la moindre ressource soit créée.

---

### Cas erroné — clés basées sur un attribut calculé après création

```hcl
resource "local_file" "source" {
  filename = "source.txt"
  content  = "source"
}

# ERREUR : local_file.source.id est calculé après création de source.txt.
# Terraform ne connaît pas encore cette valeur au moment du plan.
resource "local_file" "dependant" {
  for_each = toset([local_file.source.id])  # interdit ici
  filename = "dep-${each.key}.txt"
  content  = "dépendant de ${each.key}"
}
```

`terraform plan` retourne :

```text
Error: Invalid for_each argument
The "for_each" map includes keys derived from resource attributes
that cannot be determined until apply, so Terraform cannot determine
the full set of keys that will identify instances of this resource.
```

**Pourquoi** : `local_file.source.id` n'existe pas encore au moment du plan. Terraform ne peut pas savoir combien d'instances de `local_file.dependant` il va créer ni comment les nommer.

---

### Règle à retenir

```text
Clé for_each autorisée  → variable, locals, valeur littérale
Clé for_each interdite  → attribut computed d'une autre ressource (id, arn, etc.)
```

# 6. Étape 4 : Blocs dynamic conditionnels

## 6.1 Objectif

Comprendre ce que permet **dynamic** et pourquoi il ne s’applique pas au provider **Local** utilisé dans cet atelier.

## Ce qu’est un bloc dynamic — sans jargon

Dans Terraform, certaines ressources acceptent qu’on répète un même sous-bloc plusieurs fois à l’intérieur de ces ressources. 

Imaginez une ressource comme un formulaire : certains formulaires ont une section "ajouter une pièce jointe" qu’on peut remplir autant de fois qu’on veut. Ce sous-bloc répétable, c’est exactement ce que `dynamic` permet de générer automatiquement à partir d’une liste.

Exemple visuel avec une ressource hypothétique qui a un sous-bloc `tag` répétable :

```hcl
# Sans dynamic : on répète le bloc tag à la main pour chaque valeur.
resource "exemple_serveur" "web" {
  nom = "serveur-web"

  tag {
    cle   = "projet"
    valeur = "terraform"
  }

  tag {
    cle   = "equipe"
    valeur = "infra"
  }

  tag {
    cle   = "env"
    valeur = "prod"
  }
}
```

```hcl
# Avec dynamic : Terraform génère les blocs tag automatiquement depuis une liste.
resource "exemple_serveur" "web" {
  nom = "serveur-web"

  dynamic "tag" {
    for_each = {
      projet = "terraform"
      equipe = "infra"
      env    = "prod"
    }

    content {
      cle    = tag.key
      valeur = tag.value
    }
  }
}
```

Les deux codes produisent exactement le même résultat. `dynamic` évite la répétition quand le nombre de sous-blocs varie selon la configuration.

**Ce qui est important à retenir** : `dynamic` ne fonctionne que sur des **sous-blocs** (des blocs imbriqués à l’intérieur d’une ressource), pas sur des arguments simples comme `filename = "..."` ou `content = "..."`.

---

## 6.2 Essayons avec dynamic — et observons ce qui se passe

Vous venez de comprendre que `dynamic` génère des sous-blocs répétables. Une réaction naturelle : *"Et si j’utilise `dynamic` pour générer plusieurs lignes dans mon fichier ?"*

Testez-le pour voir ce que Terraform répond.

### Créer un dossier de test temporaire

```bash
mkdir -p ~/terraform-dynamic-test && cd ~/terraform-dynamic-test
```

Créez `main.tf` :

```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.0"
    }
  }
}

resource "local_file" "rapport" {
  filename = "rapport.txt"

  dynamic "content" {
    for_each = ["ligne 1", "ligne 2", "ligne 3"]

    content {
      value = content.value
    }
  }
}
```

### Lancer la validation

```bash
terraform init
terraform validate
```

**Ce que Terraform affiche :**

```
│ Error: Unsupported block type
│
│   on main.tf line 13, in resource "local_file" "rapport":
│   13:   dynamic "content" {
│
│ Blocks of type "content" are not expected here.
```

Terraform refuse. La ressource `local_file` ne connaît pas de sous-bloc `content` — `content` est un **argument** (une valeur simple, comme un paramètre). `dynamic` ne peut générer que des **sous-blocs que la ressource accepte nativement** ; ici il n’y en a aucun.

```
# Ce que local_file accepte :
filename        → argument simple (une chaîne)
content         → argument simple (une chaîne)
file_permission → argument simple (une chaîne)
# Aucun sous-bloc répétable → dynamic n’a rien à construire.
```

### Nettoyer le test

```bash
cd ~
rm -rf terraform-dynamic-test
```

## 6.3 La solution : construire le contenu avec `join` et `for`

Pour écrire plusieurs lignes dans un fichier, on assemble le texte **avant** de le passer à `content`, avec `join` + `for` :

```hcl
resource "local_file" "rapport" {
  filename = "rapport.txt"

  # join assemble la liste en une seule chaîne.
  # for génère chaque ligne à partir de la liste.
  content = join("\n", [
    for ligne in ["ligne 1", "ligne 2", "ligne 3"] :
    "- ${ligne}"
  ])
}
```

**Résultat dans rapport.txt :**

```
- ligne 1
- ligne 2
- ligne 3
```

`join` + `for` remplace `dynamic` pour le provider Local : on construit le texte complet en une expression, puis on le donne d’un coup à l’argument `content`.

---

## 6.4 Résumé des alternatives au provider Local

Avec `local_file`, pour du contenu conditionnel et répétitif, on dispose de :

- `join` — assembler une liste de lignes en une seule chaîne
- `for` — parcourir une liste et transformer chaque élément
- ternaire `condition ? a : b` — choisir entre deux valeurs
- `if` dans un `for` — filtrer les éléments d’une liste

## 6.12 Forme conceptuelle d’un dynamic conditionnel

Cette syntaxe devient utile avec un provider qui expose un vrai bloc imbriqué répétable :

# 7. Étape 5 : Conditions avancées dans locals

## 7.1 Objectif

Centraliser les décisions conditionnelles dans un bloc **locals**

Quand les conditions deviennent nombreuses, les écrire directement dans chaque ressource rend le code difficile à lire.

Les **locals** permettent de calculer des valeurs intermédiaires réutilisables.

## 7.3 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Environnement cible.
variable "environment" {
  type        = string
  description = "Environnement cible."
  default     = "dev"

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment doit être dev, test ou prod."
  }
}

# Active ou désactive le debug.
variable "enable_debug" {
  type        = bool
  description = "Active le mode debug."
  default     = false
}

# Liste des services possibles.
variable "services" {
  type        = list(string)
  description = "Liste des services."
  default     = ["api", "web", "worker"]
}
```

## 7.4 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# locals centralise les décisions conditionnelles.
locals {
  # Détermine si l'environnement est production.
  is_prod = var.environment == "prod"

  # Définit le niveau de sécurité selon l'environnement.
  security_level = local.is_prod ? "strict" : "standard"

  # Le debug effectif est interdit en production.
  effective_debug = local.is_prod ? false : var.enable_debug

  # En production, seuls api et web sont documentés.
  # Dans les autres environnements, tous les services sont documentés.
  enabled_services = local.is_prod ? ["api", "web"] : var.services

  # Nom du fichier final.
  report_filename = "final-${var.environment}.txt"
}

# Rapport global.
resource "local_file" "final_report" {
  filename = local.report_filename

  content = <<EOT
Rapport final

Environnement : ${var.environment}
Production : ${local.is_prod}
Niveau de sécurité : ${local.security_level}
Debug demandé : ${var.enable_debug}
Debug effectif : ${local.effective_debug}

Services documentés :
${join(", ", local.enabled_services)}
EOT
}

# Fichiers par service activé.
resource "local_file" "service_report" {
  for_each = toset(local.enabled_services)

  filename = "service-${each.key}.txt"

  content = <<EOT
Rapport service

Service : ${each.key}
Environnement : ${var.environment}
Niveau de sécurité : ${local.security_level}
EOT
}
```

**locals** permet de centraliser les décisions.

Une condition écrite une seule fois est plus facile à maintenir.


## 7.11 Astuces

Utiliser **locals** quand :

```text
la même condition revient plusieurs fois
une condition devient longue
une décision doit être réutilisée dans plusieurs ressources
```

## 7.12 Attention

**locals** ne sont pas des variables d’entrée.

Ils ne se passent pas avec **-var**.

Ils sont calculés à partir du code et des variables.

# 8. Comparaison et bonnes pratiques

## 8.1 Tableau récapitulatif

| Mécanisme                 | Sert à                                | Exemple                              |
| ------------------------- | ------------------------------------- | ------------------------------------ |
| **Ternaire**              | Choisir une valeur                    | prod ? strict : standard             |
| **count conditionnel**    | Créer zéro ou une ressource           | create ? 1 : 0                       |
| **for_each conditionnel** | Créer plusieurs ressources filtrées   | for item in list : item if condition |
| **for avec if**           | Transformer et filtrer une collection | garder seulement les éléments actifs |
| **locals**                | Centraliser les décisions             | local.security_level                 |
| **dynamic**               | Générer des blocs imbriqués           | rule, setting, ingress               |

---

## 8.2 Bonnes pratiques

| Situation                                            | Recommandation                |
| ---------------------------------------------------- | ----------------------------- |
| Choix simple de texte                                | **Ternaire**                  |
| Création optionnelle d’une seule ressource           | **count = condition ? 1 : 0** |
| Création optionnelle de plusieurs ressources nommées | **for_each** avec filtrage    |
| Transformation de liste ou map                       | **for**                       |
| Condition utilisée plusieurs fois                    | **locals**                    |
| Blocs imbriqués répétables                           | **dynamic**                   |

---

## 8.3 Pièges fréquents

| Piège                                            | Problème                  |
| ------------------------------------------------ | ------------------------- |
| Utiliser **count** pour des ressources nommées   | Index instables           |
| Accéder à **resource[0]** quand count vaut 0     | Erreur                    |
| Utiliser **dynamic** pour un argument            | Incorrect                 |
| Mettre toutes les conditions dans les ressources | Code difficile à lire     |
| Faire des ternaires trop longs                   | Code peu lisible          |
| Oublier de filtrer avant for_each                | Ressources créées en trop |
