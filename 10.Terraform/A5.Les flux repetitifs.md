# Atelier 3 : Répétition dans Terraform – count, for_each, for et dynamic

## 1. Objectif de l’atelier

Cet atelier montre comment éviter la répétition manuelle dans Terraform.

Au lieu d’écrire plusieurs ressources presque identiques, Terraform permet d’utiliser plusieurs mécanismes :

**count** : répéter une ressource selon un nombre.

**for_each** : répéter une ressource selon une collection nommée.

**for** : transformer une liste ou une map.

**dynamic** : générer dynamiquement des blocs imbriqués quand une ressource le permet.

Dans cet atelier, on utilise uniquement le **provider Local**, pour rester simple et sans authentification.

# 3. Étape 1 : Répéter avec count

## 3.1 Objectif

Créer plusieurs fichiers locaux à partir d’un **nombre**.

Le mécanisme **count** est le plus simple à comprendre.

Il répond à la question :

**Combien d’instances dois-je créer ?**

---

## 3.2 Structure utilisée

```text
file_count = 3

local_file.count_demo[0] → count-demo-0.txt
local_file.count_demo[1] → count-demo-1.txt
local_file.count_demo[2] → count-demo-2.txt
```

---

## 3.3 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Nombre de fichiers à créer.
variable "file_count" {
  type        = number
  description = "Nombre de fichiers à créer avec count."
  default     = 3

  validation {
    condition     = var.file_count >= 1 && var.file_count <= 5
    error_message = "file_count doit être compris entre 1 et 5."
  }
}

# Préfixe utilisé dans le nom des fichiers.
variable "file_prefix" {
  type        = string
  description = "Préfixe utilisé pour nommer les fichiers."
  default     = "count-demo"
}
```

---

## 3.4 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# count répète cette ressource plusieurs fois.
resource "local_file" "count_demo" {
  count = var.file_count

  # count.index représente l'index de l'instance courante.
  # La première instance commence à 0.
  filename = "${var.file_prefix}-${count.index}.txt"

  # Le contenu change selon l'index.
  content = "Fichier généré avec count. Index = ${count.index}"
}
```

---

## 3.5 Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Affiche la liste des fichiers créés.
output "created_files" {
  value = local_file.count_demo[*].filename
}

# Affiche le nombre total d'instances créées.
output "created_count" {
  value = length(local_file.count_demo)
}
```

---

## 3.6 Exécuter Terraform

Exécuter dans **~/terraform-repetition-local** :

```bash
# Initialise le projet et télécharge le provider Local.
terraform init

# Reformate le code Terraform.
terraform fmt

# Vérifie la configuration.
terraform validate

# Affiche les actions prévues.
terraform plan

# Crée les fichiers.
terraform apply -auto-approve
```

---

## 3.7 Observer le résultat

```bash
# Liste les fichiers créés.
ls -l count-demo-*.txt

# Affiche le contenu des fichiers.
cat count-demo-0.txt
cat count-demo-1.txt
cat count-demo-2.txt

# Liste les ressources suivies dans le state.
terraform state list

# Affiche les outputs.
terraform output
```

Résultat attendu dans le state :

```text
local_file.count_demo[0]
local_file.count_demo[1]
local_file.count_demo[2]
```

---

## 3.8 Point à retenir

**count** est adapté quand on veut créer plusieurs ressources très similaires.

Il faut retenir :

```text
count = nombre d'instances
count.index = index de l'instance courante
```

Limite importante :

**count** repose sur des index numériques.  
Si l’ordre change, les index peuvent provoquer des remplacements inattendus.

# 4. Étape 2 : Répéter avec for_each

## 4.1 Objectif

Créer plusieurs fichiers à partir d’une liste d’environnements.

Le mécanisme **for_each** est plus robuste que **count** quand chaque élément a une identité claire.

Il répond à la question :

**Pour chaque élément nommé, quelle ressource dois-je créer ?**

---

## 4.2 Nettoyer l’étape précédente

Avant de remplacer le code, exécuter :

```bash
# Supprime les ressources suivies par Terraform.
terraform destroy -auto-approve

# Supprime les fichiers locaux restants.
rm -f *.txt
```

---

## 4.3 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Liste des environnements à gérer.
variable "environments" {
  type        = list(string)
  description = "Liste des environnements."
  default     = ["dev", "test", "prod"]

  validation {
    condition     = length(var.environments) > 0
    error_message = "La liste environments ne doit pas être vide."
  }
}
```

---

## 4.4 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# for_each crée une ressource par environnement.
# toset transforme la liste en ensemble de valeurs uniques.
resource "local_file" "environment_file" {
  for_each = toset(var.environments)

  # Dans un set de strings, each.key et each.value ont la même valeur.
  filename = "env-${each.key}.txt"

  content = <<EOT
Fichier d'environnement

Environnement : ${each.value}
Adresse Terraform : local_file.environment_file["${each.key}"]
EOT
}
```

---

## 4.5 Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Affiche une map environnement vers fichier créé.
output "environment_files" {
  value = {
    for env, file in local_file.environment_file :
    env => file.filename
  }
}
```

---

## 4.6 Exécuter Terraform

```bash
# Reformate le code.
terraform fmt

# Vérifie la configuration.
terraform validate

# Affiche le plan.
terraform plan

# Applique la configuration.
terraform apply -auto-approve
```

---

## 4.7 Observer le résultat

```bash
# Liste les fichiers générés.
ls -l env-*.txt

# Affiche leur contenu.
cat env-dev.txt
cat env-test.txt
cat env-prod.txt

# Liste les ressources dans le state.
terraform state list

# Affiche les outputs.
terraform output
```

Résultat attendu dans le state :

```text
local_file.environment_file["dev"]
local_file.environment_file["prod"]
local_file.environment_file["test"]
```

L’ordre peut varier, mais les clés restent stables.

---

## 4.8 Point à retenir

**for_each** est adapté quand chaque ressource possède une identité claire.

Il faut retenir :

```text
for_each = répétition par collection
each.key = clé de l'élément courant
each.value = valeur de l'élément courant
```

Avec **for_each**, l’adresse Terraform est plus lisible :

```text
local_file.environment_file["dev"]
```

# 5. Étape 3 : for_each avec map d’objets

## 5.1 Objectif

Créer plusieurs fichiers avec des contenus différents.

Ici, chaque fichier possède :

**un nom**,  
**un titre**,  
**un contenu**.

Cette situation est mieux adaptée à **for_each** qu’à **count**.

---

## 5.2 Nettoyer l’étape précédente

```bash
# Supprime les ressources suivies.
terraform destroy -auto-approve

# Supprime les fichiers générés.
rm -f *.txt
```

---

## 5.3 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Map de documents à générer.
# Chaque clé est une identité stable.
variable "documents" {
  type = map(object({
    filename = string
    title    = string
    content  = string
  }))

  description = "Documents à générer avec Terraform."

  default = {
    readme = {
      filename = "README.txt"
      title    = "Documentation principale"
      content  = "Ce document présente le projet."
    }

    ops = {
      filename = "OPS.txt"
      title    = "Guide exploitation"
      content  = "Ce document décrit les opérations courantes."
    }

    support = {
      filename = "SUPPORT.txt"
      title    = "Support"
      content  = "Ce document explique comment demander de l'aide."
    }
  }
}
```

---

## 5.4 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Crée un fichier par document.
resource "local_file" "document" {
  for_each = var.documents

  # each.value donne accès à l'objet associé à chaque clé.
  filename = each.value.filename

  content = <<EOT
Titre : ${each.value.title}

Identifiant Terraform : ${each.key}

Contenu :
${each.value.content}
EOT
}
```

---

## 5.5 Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Affiche les fichiers générés.
output "document_files" {
  value = {
    for key, file in local_file.document :
    key => file.filename
  }
}

# Affiche les clés des documents.
output "document_keys" {
  value = keys(var.documents)
}
```

---

## 5.6 Exécuter Terraform

```bash
# Reformate.
terraform fmt

# Valide.
terraform validate

# Prévisualise.
terraform plan

# Applique.
terraform apply -auto-approve
```

---

## 5.7 Observer le résultat

```bash
# Liste les fichiers générés.
ls -l *.txt

# Affiche le contenu.
cat README.txt
cat OPS.txt
cat SUPPORT.txt

# Liste les ressources dans le state.
terraform state list

# Affiche les outputs.
terraform output
```

Résultat attendu dans le state :

```text
local_file.document["ops"]
local_file.document["readme"]
local_file.document["support"]
```

---

## 5.8 Point à retenir

Avec une **map**, **for_each** donne une adresse stable à chaque ressource.

```text
each.key = readme, ops, support
each.value = objet complet associé à la clé
```

C’est plus lisible et plus sûr que des index numériques.

# 6. Étape 4 : Expressions for

## 6.1 Objectif

Comprendre que **for** ne crée pas directement de ressources.

Une expression **for** sert à transformer des données.

Exemples :

```text
liste → nouvelle liste
map → nouvelle map
liste → map
```

Différence essentielle :

```text
for_each crée des ressources
for transforme des valeurs
```

---

# 6.2 Transformer une liste en majuscules

## Nettoyer l’étape précédente

```bash
# Supprime les ressources suivies.

# Supprime les fichiers générés.
rm -f *.txt
```

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Liste des services à transformer.
variable "services" {
  type        = list(string)
  description = "Liste des services."
  default     = ["api", "web", "worker"]
}
```

---

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

resource "local_file" "services_report" {
  filename = "services-report.txt"

  content = <<EOT
Services originaux :
${join(", ", var.services)}

Services en majuscules :
${join(", ", [for service in var.services : upper(service)])}

Services préfixés :
${join(", ", [for service in var.services : "svc-${service}"])}
EOT
}
```

```hcl
}
```


# 8. Étape 6 : Combiner for et for_each

## 8.1 Objectif

Utiliser **for** pour transformer une liste en map, puis utiliser **for_each** pour créer les ressources.

C’est une pratique très utile.


```hcl
# Liste de rapports à générer.
variable "reports" {
  type = list(object({
    name    = string
    content = string
  }))

  description = "Liste des rapports."

  default = [
    {
      name    = "security"
      content = "Rapport sécurité"
    },
    {
      name    = "quality"
      content = "Rapport qualité"
    },
    {
      name    = "delivery"
      content = "Rapport livraison"
    }
  ]
}
```

---

## 8.4 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# for transforme la liste en map.
# for_each utilise ensuite cette map pour créer les fichiers.
resource "local_file" "report" {
  for_each = {
    for report in var.reports :

Contenu : ${each.value.content}
EOT
}
```

# 9. Étape 7 : Comprendre dynamic

## 9.1 Objectif

Comprendre ce que fait **dynamic**, sans l’utiliser de manière incorrecte avec le provider Local.

Le provider **Local** ne propose pas de ressource avec un bloc imbriqué répétable adapté à une démonstration réelle de **dynamic**.

Il faut donc retenir la règle :

**dynamic sert à générer des blocs imbriqués, pas des arguments.**

---

## 9.2 Exemple de structure dynamic

Voici la forme générale :

```hcl
dynamic "nom_du_bloc" {
  for_each = collection

  content {
    argument = valeur
  }
}
```

Ce type de bloc est utile dans des providers où une ressource accepte plusieurs blocs imbriqués, par exemple :

```text
rule {}
setting {}
ingress {}
egress {}
disk {}
container {}
```

---

## 9.3 Ce qu’il ne faut pas faire avec local_file

Le code suivant est volontairement incorrect :

```hcl
resource "local_file" "bad_example" {
  filename = "bad.txt"

  dynamic "content" {
    for_each = ["ligne 1", "ligne 2"]

    content {
      value = content.value
    }
  }
}
```

Pourquoi c’est incorrect ?

Dans **local_file**, **content** est un **argument**, pas un bloc imbriqué.

Et **dynamic** ne peut pas générer **content**.

---

## 9.4 Bonne solution avec le provider Local

Avec le provider Local, si l’objectif est de générer un fichier riche avec plusieurs sections, il faut utiliser **for**, pas **dynamic**.

---

## 9.5 Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Liste de sections à écrire dans un fichier.
variable "sections" {
  type = list(object({
    title = string
    body  = string
  }))

  description = "Sections du document."

  default = [
    {
      title = "Introduction"
      body  = "Ce document est généré avec Terraform."
    },
    {
      title = "Répétition"
      body  = "Terraform propose count, for_each, for et dynamic."
    },
    {
      title = "Conclusion"
      body  = "Avec le provider Local, for est le bon outil pour générer du contenu."
    }
  ]
}
```

---

## 9.6 Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

provider "local" {}

# Génère un document riche avec plusieurs sections.
# Ici, on utilise for pour construire une chaîne de texte.
resource "local_file" "rich_document" {
  filename = "rich-document.txt"

  content = join("\n\n", [
    for section in var.sections :
    "## ${section.title}\n${section.body}"
  ])
}
```

---

## 9.7 Créer le fichier outputs.tf

Créer le fichier **outputs.tf** :

```hcl
# Affiche le nombre de sections.
output "section_count" {
  value = length(var.sections)
}

# Affiche les titres des sections.
output "section_titles" {
  value = [for section in var.sections : section.title]
}
```

---

```bash

# Valide.
terraform validate

# Prévisualise.

# Applique.

```

---

## 9.9 Observer le résultat

```bash

# Affiche les outputs.

```

Résultat attendu :

---

## 9.10 Point à retenir

Avec **local_file**, on utilise :

```text
for pour générer du contenu
for_each pour générer plusieurs fichiers
count pour générer N fichiers
```

On n’utilise pas **dynamic** pour générer l’argument **content**.

# 10. Comparaison finale

| Mécanisme    | Rôle                        | Crée plusieurs ressources | Cas d’usage                           |
| ------------ | --------------------------- | ------------------------- | ------------------------------------- |
| **count**    | Répéter par nombre          | Oui                       | Plusieurs objets similaires           |
| **for_each** | Répéter par clé ou valeur   | Oui                       | Objets avec identité stable           |
| **for**      | Transformer des données     | Non                       | Construire listes, maps, contenus     |
| **dynamic**  | Générer des blocs imbriqués | Non directement           | Ressources avec sous-blocs répétables |
