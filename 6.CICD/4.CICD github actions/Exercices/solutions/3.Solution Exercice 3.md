# Solution 3 — Conditions de statut et bilan

[Énoncé](../3.Exercice%203.md) · [Guide commun](../readme.md)

## 1. Workflow complet

Créer `.github/workflows/exercice-3.yml` :

```yaml
name: Exercice 3 - Succes et echec
# Déclare les événements qui peuvent lancer ce workflow.
on:
  # Autorise le lancement manuel avec les inputs éventuellement déclarés.
  workflow_dispatch:
    # Déclare les paramètres attendus ; leur type et leurs contraintes définissent le contrat.
    inputs:
      # Définit le paramètre « provoquer_echec » et les contraintes de sa valeur.
      provoquer_echec:
        description: Faire echouer le traitement
        required: true
        type: boolean
        # Fournit la valeur utilisée si cet input n'est pas renseigné.
        default: false

# Limite les droits du GITHUB_TOKEN pour la portée du workflow ou du job.
permissions: {}
# Définit les réglages par défaut des commandes run dans cette portée.
defaults:
  # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
  run:
    # Choisit l'interpréteur des commandes ; adapter leur syntaxe si ce shell change.
    shell: bash

# Déclare les jobs ; leur ordre dans le fichier ne crée pas de dépendance.
jobs:
  # Déclare le job « traitement » ; needs permet de préciser ses dépendances.
  traitement:
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Arrête le traitement si sa durée dépasse ce nombre de minutes.
    timeout-minutes: 5
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Traitement
        id: operation
        # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
        env:
          EXO_ECHEC: ${{ inputs.provoquer_echec }}
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Le shell arrête sur une commande en échec hors tests conditionnels, refuse une variable non définie, propage aussi les erreurs dans les pipelines de commandes.
          set -euo pipefail
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          echo "Debut du traitement"
          # Déclenche l'échec volontaire demandé afin de vérifier les traitements de fin.
          if [[ "$EXO_ECHEC" == "true" ]]; then
            # Écrit le diagnostic sur la sortie d'erreur pour distinguer l'erreur des résultats normaux.
            echo "Echec volontaire" >&2
            # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
            exit 1
          fi
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          echo "Traitement termine"
      - name: Apres reussite
        # Exécute ce traitement seulement après les succès requis.
        if: ${{ success() }}
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        run: echo "Le traitement a reussi"
      - name: Apres echec
        # Exécute ce traitement lorsqu'un échec antérieur est détecté.
        if: ${{ failure() }}
        # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
        run: echo "Une etape precedente a echoue"
      - name: Bilan local
        # Autorise cette étape ou ce job même après échec ; le nettoyage reste soumis à la disponibilité du runner.
        if: ${{ always() }}
        # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
        env:
          EXO_RESULTAT: ${{ steps.operation.outcome }}
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Resultat de operation : %s\n' "$EXO_RESULTAT"

  # Déclare le job « bilan » ; needs permet de préciser ses dépendances.
  bilan:
    # Attend les jobs indiqués ; leurs outputs sont accessibles via le contexte needs.
    needs: traitement
    # Autorise cette étape ou ce job même après échec ; le nettoyage reste soumis à la disponibilité du runner.
    if: ${{ always() }}
    # Sélectionne la machine qui exécutera ce job.
    runs-on: ubuntu-24.04
    # Arrête le traitement si sa durée dépasse ce nombre de minutes.
    timeout-minutes: 5
    # Exécute les étapes de ce job dans l'ordre sur le même runner.
    steps:
      - name: Afficher le resultat du job precedent
        # Injecte des variables dans les commandes de cette portée ; ce n'est pas un stockage partagé entre jobs.
        env:
          EXO_RESULTAT: ${{ needs.traitement.result }}
        # Lance ce script dans le shell de l'étape ; un nouveau run ouvre un nouveau processus.
        run: |
          # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
          printf 'Resultat du job traitement : %s\n' "$EXO_RESULTAT"
          # Ajoute ces informations au résumé consultable dans l'interface de l'exécution.
          printf '### Bilan\nTraitement : %s\n' "$EXO_RESULTAT" >> "$GITHUB_STEP_SUMMARY"
```

## 2. Deux portées de résultat

`steps.operation.outcome` décrit une étape dans le job courant. `needs.traitement.result` décrit le job dont dépend le bilan. Le job de bilan dispose d'un autre runner ; il n'hérite pas du disque ni des variables shell du traitement.

`success()` est la garde implicite habituelle. `failure()` permet l'étape après échec et `always()` permet le bilan même si un prédécesseur a échoué ou été annulé. Cette condition ne garantit pas l'exécution après perte de machine ou arrêt forcé. Pour une tâche qui doit éviter l'annulation, préférer une condition fondée sur `!cancelled()`. [Fonctions de statut](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions)

Le bilan doit rester court : ne pas utiliser un `always()` pour lancer un nouveau déploiement après une annulation.

## 3. Comparaison des mécanismes

Jenkins rassemble ces comportements dans `post`. GitLab sépare les jobs de fin et `after_script`, ce dernier utilisant un nouveau shell. GitHub les exprime par des étapes et des dépendances : leur place dans le fichier ne crée pas à elle seule un ordre entre jobs.

`continue-on-error` n'est volontairement pas utilisé : tolérer l'erreur modifierait la conclusion de l'étape ou du job. Un message d'échec réussi ne répare pas une étape précédente échouée.

## 4. Résultats attendus

| Input | Traitement | Étape succès | Étape échec | Bilan | Workflow |
| --- | --- | --- | --- | --- | --- |
| `false` | Succès | Exécutée | Ignorée | Succès | Succès |
| `true` | Échec | Ignorée | Exécutée | Succès | Échec |

Consulter aussi le résumé de l'exécution. Pour tester une annulation, elle doit intervenir pendant une étape suffisamment longue ; ne pas interpréter l'absence de nettoyage après un arrêt brutal comme une garantie contredite.
