Langage HCL
Les 8 types de blocs
Chaque bloc a un rôle précis. Tous peuvent cohabiter dans un seul main.tf ou être répartis dans des fichiers dédiés.
terraform { }
Version minimale, backend, providers requis
terraform.tf
hcl
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.0"
    }
  }
  backend "local" {
    path = "terraform.tfstate"
  }
}
provider { }
Configure la connexion à une plateforme
providers.tf
hcl
provider "azurerm" {
  features {}
  # Lit automatiquement les variables :
  # ARM_SUBSCRIPTION_ID
  # ARM_CLIENT_ID
  # ARM_CLIENT_SECRET
  # ARM_TENANT_ID
}

provider "local" {}  # Aucun credential requis
variable { }
Paramètre d'entrée typé, validable, avec valeur par défaut
variables.tf
hcl
variable "environment" {
  description = "Environnement cible"
  type        = string
  default     = "dev"

  validation {
    condition     = contains(["dev","staging","prod"], var.environment)
    error_message = "Valeur : dev | staging | prod"
  }
}

variable "tags" {
  type    = map(string)
  default = {}
}
locals { }
Valeurs calculées internes — évite la répétition
locals.tf
hcl
locals {
  prefix      = "atelier"
  full_prefix = "${local.prefix}-${var.environment}"

  common_tags = merge(var.tags, {
    managed_by  = "terraform"
    environment = var.environment
  })
}

# Référence : local.full_prefix (singulier !)
data { }
Lit une ressource existante sans la créer
main.tf
hcl
data "azurerm_resource_group" "existant" {
  name = "rg-prod-shared"
}

data "azurerm_subnet" "snet" {
  name                 = "snet-default"
  virtual_network_name = "vnet-prod"
  resource_group_name  = data.azurerm_resource_group.existant.name
}

# Référence : data.azurerm_subnet.snet.id
resource { }
Crée, modifie ou détruit un objet d'infrastructure
main.tf
hcl
resource "azurerm_resource_group" "rg" {
  name     = "${local.full_prefix}-rg"
  location = var.location
  tags     = local.common_tags
}

resource "azurerm_storage_account" "st" {
  name                     = "atelierst${var.environment}"
  resource_group_name      = azurerm_resource_group.rg.name
  location                 = azurerm_resource_group.rg.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
}
output { }
Expose une valeur après apply — terminal, CI/CD, module parent
outputs.tf
hcl
output "resource_group_name" {
  description = "Nom du Resource Group"
  value       = azurerm_resource_group.rg.name
}

output "connection_string" {
  description = "Chaîne de connexion"
  value       = azurerm_storage_account.st.primary_connection_string
  sensitive   = true  # masqué dans les logs
}
module { }
Appelle un bloc réutilisable — local ou registre Terraform
main.tf
hcl
module "network" {
  source   = "./modules/network"  # chemin local
  # source = "Azure/network/azurerm" # registre public

  location            = var.location
  resource_group_name = azurerm_resource_group.rg.name
  environment         = var.environment
  tags                = local.common_tags
}

Organisation
Structure de projet
Convention adoptée par la communauté Terraform.
Style 1 — Compact (débutant / petit projet)
projet/
  main.tftous les blocs ici
  terraform.tfvars # valeurs des variables
  terraform.tfstate # généré automatiquement
Style 2 — Fichiers séparés (professionnel)
projet/
  terraform.tf     # bloc terraform
  providers.tf    # bloc provider
  variables.tf    # blocs variable
  locals.tf       # bloc locals
  main.tf         # resource, data, module
  outputs.tf      # blocs output
  terraform.tfvars # valeurs
  modules/
    network/
      main.tf outputs.tf variables.tf
Credentials Azure — obtenir les 4 valeurs
bash — Créer le Service Principal
# 1. Se connecter
az login

# 2. Voir et sélectionner l'abonnement
az account list --output table
az account set --subscription "MON_ABONNEMENT"

# 3. Créer le Service Principal (Contributor)
az ad sp create-for-rbac \
  --name "sp-terraform-atelier" \
  --role Contributor \
  --scopes /subscriptions/$(az account show --query id -o tsv)

# Résultat → appId, password, tenant
bash — Exporter les variables
# Linux / macOS / WSL
export ARM_SUBSCRIPTION_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export ARM_TENANT_ID="yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
export ARM_CLIENT_ID="zzzzzzzz-zzzz-zzzz-zzzz-zzzzzzzzzzzz"
export ARM_CLIENT_SECRET="xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"

# Vérifier la connexion
az login --service-principal \
  --username $ARM_CLIENT_ID \
  --password $ARM_CLIENT_SECRET \
  --tenant $ARM_TENANT_ID

Cycle de base, gestion du state, workspaces, et debug.
Cycle de base
terraform initInitialise le projet, télécharge providers
terraform init -upgradeMet à jour les providers
terraform validateVérifie la syntaxe HCL
terraform fmt -recursiveFormate tous les fichiers .tf
terraform planPrévisualise les changements
terraform plan -out=tfplanSauvegarde le plan
terraform plan -var-file=prod.tfvarsCharge des variables
terraform plan -target=TYPE.NOMCible une ressource
terraform applyApplique (avec confirmation)
terraform apply tfplanApplique le plan sauvegardé
terraform apply -auto-approveApplique sans confirmation (CI/CD)
terraform destroyDétruit toutes les ressources
terraform destroy -target=TYPE.NOMDétruit une ressource précise
Gestion du State
terraform state listListe toutes les ressources dans le state
terraform state show TYPE.NOMDétails d'une ressource
terraform state mv SRC DESTRenomme / déplace dans le state
terraform state rm TYPE.NOMRetire du state (sans détruire)
terraform state pullAffiche le state brut en JSON
terraform force-unlock IDDéverrouille le state bloqué
Outputs · Debug · Workspaces

terraform showAffiche l'état courant
terraform show tfplanAffiche un plan sauvegardé

Premier tour — séquence type d'un déploiement
bash
terraform init                         # 1. Initialise (une seule fois ou après changement de provider)
terraform fmt -recursive               # 2. Formate le code
terraform validate                     # 3. Vérifie la syntaxe
terraform plan -out=tfplan             # 4. Génère et sauvegarde le plan
terraform apply tfplan                 # 5. Applique le plan approuvé
terraform output                       # 6. Vérifie les outputs
terraform state list                   # 7. Contrôle ce qui est dans le state
# --- plus tard ---
terraform destroy                      # 8. Nettoie tout
Bonnes pratiques
À retenir absolument
Les erreurs fréquentes et les règles à intégrer dès le début.
Dépendances implicites
Préférez toujours les références directes azurerm_resource_group.rg.name plutôt que depends_on. Terraform construit le graphe de dépendances automatiquement.
depends_on — usage restreint
N'utilisez depends_on que quand Terraform ne peut pas détecter la dépendance seul — typiquement avec null_resource et local-exec.
Jamais de secrets dans les fichiers .tf
Les mots de passe et tokens passent par des variables d'environnement (TF_VAR_*, ARM_*), jamais dans terraform.tfvars versionné. Ajoutez *.tfvars et .env dans .gitignore.
plan -out avant chaque apply
Sauvegardez toujours le plan avec -out=tfplan puis appliquez ce fichier. Cela garantit que vous appliquez exactement ce que vous avez reviewé, sans surprise entre le plan et l'apply.
Plan B local — providers local + null
En cas de problème de connexion Azure, basculez sur provider "local" + null_resource. Même logique HCL, zéro dépendance réseau — idéal en formation ou pour tester la syntaxe.
terraform destroy ne supprime pas les fichiers locaux
Un local_file ou un dossier créé par local-exec n'est pas supprimé physiquement par terraform destroy — seule la référence dans le state est retirée. Supprimez manuellement si nécessaire.
-auto-approve en production
Réservez -auto-approve aux pipelines CI/CD avec revue de plan préalable. Ne l'utilisez jamais interactivement sur un environnement de production.
Compact → Multi-fichiers
Commencez avec un seul main.tf pour apprendre la logique. Dès que vous avez plus de 3 ressources ou plusieurs contributeurs, éclatez en terraform.tf / providers.tf / variables.tf / locals.tf / main.tf / outputs.tf.
