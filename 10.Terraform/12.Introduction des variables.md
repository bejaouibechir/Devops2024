# Atelier 2 : Découverte des Variables Terraform – Types, Emplacements et Précédence

## 1. Introduction

## Objectif général

Dans l’Atelier 1, les valeurs étaient écrites directement dans le fichier **main.tf**.

Exemple :

```hcl
filename = "demo.txt"
content  = "Bonjour Terraform"
```

Dans cet atelier, ces valeurs vont devenir configurables avec des **variables Terraform**.

Une variable Terraform permet de remplacer une valeur fixe par une valeur paramétrable.

# 

## Prérequis

Savoir exécuter :

```bash
terraform init
terraform fmt
terraform validate
terraform plan
terraform apply
terraform destroy
terraform state list
terraform show
terraform output
```

## Contraintes

Dans cet atelier :

**provider utilisé** : hashicorp/local  
**pas de cloud**  
**pas d’authentification**  
**pas de modules**  
**pas de workspaces**  
**pas de fonctionnalités avancées**

# 3. Étape 1 : Variables simples string, number, bool

## Objectif

Découvrir les types de base :

**string** : texte  
**number** : nombre  
**bool** : true ou false

Terraform distingue les types primitifs **string**, **number** et **bool**. Le type **string** représente du texte, **number** représente une valeur numérique et **bool** représente **true** ou **false**. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/expressions/type-constraints "Type Constraints - Configuration Language | Terraform | HashiCorp Developer"))

## Scénario

On veut créer un fichier local dont :

**le nom** vient d’une variable string,  
**le nombre de lignes simulé** vient d’une variable number,  
**l’activation du message détaillé** vient d’une variable bool.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Variable de type string.
# Elle contient le nom du fichier à créer.
variable "file_name" {
  type        = string
  description = "Nom du fichier local à créer."
  default     = "rapport-base.txt"
}

# Variable de type number.
# Elle simule un nombre de lignes dans le rapport.
variable "line_count" {
  type        = number
  description = "Nombre de lignes annoncé dans le rapport."
  default     = 5
}

# Variable de type bool.
# Elle active ou désactive un message détaillé.
variable "detailed_mode" {
  type        = bool
  description = "Active ou désactive le mode détaillé."
  default     = true
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# Crée un fichier local en utilisant des variables simples.
resource "local_file" "basic_report" {
  filename = var.file_name

  content = <<EOT
Rapport Terraform

Nom du fichier : ${var.file_name}
Nombre de lignes annoncé : ${var.line_count}
Mode détaillé activé : ${var.detailed_mode}
EOT
}

# Affiche le nom du fichier créé.
output "created_file" {
  value = local_file.basic_report.filename
}
```

## Commandes à exécuter

Exécuter dans **~/terraform-variables-local** :

```bash
# Initialise le projet et télécharge le provider Local.
terraform init

# Reformate les fichiers Terraform.
terraform fmt

# Vérifie la configuration.
terraform validate

# Affiche ce que Terraform prévoit de créer.
terraform plan

# Crée le fichier local.
terraform apply -auto-approve
```

## Observer le résultat

```bash
# Affiche le fichier créé.
cat rapport-base.txt

# Liste les ressources suivies.
terraform state list

# Affiche les outputs.
terraform output
```

Résultat attendu dans le fichier :

```text
Rapport Terraform

Nom du fichier : rapport-base.txt
Nombre de lignes annoncé : 5
Mode détaillé activé : true
```

## Questions à poser

Pourquoi **file_name** est-il de type **string** ?

Pourquoi **line_count** est-il de type **number** ?

Pourquoi **detailed_mode** est-il de type **bool** ?

Où les variables sont-elles définies ?

Où les variables sont-elles utilisées ?

## Points clés

**variable** déclare une entrée configurable.

**type** impose le type attendu.

**default** fournit une valeur si aucune autre valeur n’est donnée.

**var.file_name** permet d’utiliser la variable dans **main.tf**.

# 4. Étape 2 : Types complexes list, map, object

## Objectif

Découvrir les types complexes :

**list** : liste ordonnée de valeurs  
**map** : ensemble de paires clé-valeur  
**object** : structure composée de plusieurs champs nommés

Terraform classe **list**, **map** et **object** parmi les types complexes. Une **list** regroupe plusieurs valeurs du même type, une **map** associe des valeurs à des clés texte, et un **object** regroupe des attributs nommés avec leurs propres types. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/expressions/type-constraints "Type Constraints - Configuration Language | Terraform | HashiCorp Developer"))

## Scénario

On veut générer un fichier de description de projet.

Le fichier contiendra :

**une liste de technologies**,  
**une map de tags**,  
**un objet décrivant l’application**.

---

## Remplacer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Liste de technologies utilisées dans le projet.
variable "technologies" {
  type        = list(string)
  description = "Liste des technologies utilisées."
  default     = ["Terraform", "HCL", "Provider Local"]
}

# Map de tags.
# Chaque clé représente le nom du tag.
# Chaque valeur représente le contenu du tag.
variable "project_tags" {
  type        = map(string)
  description = "Tags descriptifs du projet."
  default = {
    environment = "dev"
    owner       = "training"
    managed_by  = "terraform"
  }
}

# Objet décrivant l'application.
# Chaque attribut possède son propre type.
variable "app_config" {
  type = object({
    name        = string
    version     = number
    enabled     = bool
    description = string
  })

  description = "Configuration principale de l'application."

  default = {
    name        = "demo-hcl"
    version     = 1
    enabled     = true
    description = "Application de démonstration pour les variables Terraform."
  }
}
```

## Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Le provider Local ne nécessite aucune configuration.
provider "local" {}

# Crée un fichier local à partir de types complexes.
resource "local_file" "complex_report" {
  filename = "rapport-types-complexes.txt"

  content = <<EOT
Rapport sur les types complexes Terraform

Application
-----------
Nom : ${var.app_config.name}
Version : ${var.app_config.version}
Active : ${var.app_config.enabled}
Description : ${var.app_config.description}

Technologies
------------
Première technologie : ${var.technologies[0]}
Deuxième technologie : ${var.technologies[1]}
Troisième technologie : ${var.technologies[2]}

Tags
----
Environnement : ${var.project_tags["environment"]}
Responsable : ${var.project_tags["owner"]}
Géré par : ${var.project_tags["managed_by"]}
EOT
}

# Affiche le nom de l'application.
output "application_name" {
  value = var.app_config.name
}

# Affiche la première technologie.
output "first_technology" {
  value = var.technologies[0]
}

# Affiche l'environnement.
output "environment" {
  value = var.project_tags["environment"]
}
```

## Commandes à exécuter

```bash
# Reformate le code.
terraform fmt

# Vérifie les types et la syntaxe.
terraform validate

# Affiche les changements prévus.
terraform plan

# Applique la configuration.
terraform apply -auto-approve
```

## Observer le résultat

```bash
# Affiche le fichier généré.
cat rapport-types-complexes.txt

# Affiche les outputs.
terraform output
```

## Résultat attendu

Le fichier doit afficher :

```text
Nom : demo-hcl
Version : 1
Active : true
Première technologie : Terraform
Environnement : dev
```

## Questions à poser

Pourquoi utilise-t-on **var.technologies[0]** ?

Pourquoi utilise-t-on **var.project_tags["environment"]** ?

Pourquoi utilise-t-on **var.app_config.name** ?

Quelle différence entre une **map** et un **object** ?

## Points clés

**list(string)** contient plusieurs valeurs du même type.

**map(string)** contient des clés texte et des valeurs du même type.

**object** permet de décrire une structure avec plusieurs champs de types différents.

**[0]** accède au premier élément d’une liste.

**["environment"]** accède à une valeur dans une map.

**.name** accède à un attribut d’un object.

# 5. Étape 3 : Différents emplacements de définition des variables

## Objectif

Comprendre la différence entre :

**définir une variable**  
et  
**donner une valeur à une variable**

Terraform permet de donner des valeurs aux variables via plusieurs méthodes : option **-var**, option **-var-file**, fichiers **.tfvars**, fichiers chargés automatiquement et variables d’environnement avec le préfixe **TF_VAR_**. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/values/variables "Use input variables to add module arguments | Terraform | HashiCorp Developer"))

## Idée simple

**variables.tf** déclare les variables.

**main.tf** utilise les variables.

**terraform.tfvars** donne des valeurs automatiquement.

**dev.tfvars** donne des valeurs seulement si on utilise **-var-file**.

**-var** donne une valeur directement dans la commande.

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Nom du fichier généré.
variable "file_name" {
  type        = string
  description = "Nom du fichier généré."
  default     = "default-report.txt"
}

# Nom de l'environnement.
variable "environment" {
  type        = string
  description = "Nom de l'environnement."
  default     = "default"
}

# Nom du formateur ou responsable.
variable "owner" {
  type        = string
  description = "Responsable du fichier."
  default     = "default-owner"
}

# Activation du mode détaillé.
variable "detailed_mode" {
  type        = bool
  description = "Mode détaillé activé ou non."
  default     = false
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Provider Local sans configuration obligatoire.
provider "local" {}

# Crée un fichier local avec les valeurs des variables.
resource "local_file" "report" {
  filename = var.file_name

  content = <<EOT
Rapport Terraform

Fichier : ${var.file_name}
Environnement : ${var.environment}
Responsable : ${var.owner}
Mode détaillé : ${var.detailed_mode}
EOT
}

# Affiche les valeurs réellement utilisées.
output "effective_values" {
  value = {
    file_name     = var.file_name
    environment   = var.environment
    owner         = var.owner
    detailed_mode = var.detailed_mode
  }
}
```

## Créer le fichier terraform.tfvars

Créer le fichier **terraform.tfvars** :

```hcl
# Ce fichier est chargé automatiquement par Terraform.
file_name     = "terraform-tfvars-report.txt"
environment   = "terraform-tfvars"
owner         = "valeur-depuis-terraform-tfvars"
detailed_mode = true
```

## Créer le fichier dev.tfvars

Créer le fichier **dev.tfvars** :

```hcl
# Ce fichier n'est pas chargé automatiquement.
# Il sera utilisé uniquement avec -var-file.
file_name     = "dev-report.txt"
environment   = "dev"
owner         = "valeur-depuis-dev-tfvars"
detailed_mode = true
```

## Exécution 1 — Utiliser terraform.tfvars automatiquement

```bash
# Initialise si ce n'est pas encore fait.
terraform init

# Valide la configuration.
terraform validate

# Applique avec terraform.tfvars chargé automatiquement.
terraform apply -auto-approve

# Affiche le fichier créé.
cat terraform-tfvars-report.txt

# Affiche les valeurs réellement utilisées.
terraform output effective_values
```

Observation :

Terraform utilise les valeurs de **terraform.tfvars**, car ce fichier est chargé automatiquement.

## Exécution 2 — Utiliser dev.tfvars avec -var-file

```bash
# Applique en utilisant explicitement le fichier dev.tfvars.
terraform apply -auto-approve -var-file="dev.tfvars"

# Affiche le fichier créé.
cat dev-report.txt

# Affiche les valeurs réellement utilisées.
terraform output effective_values
```

Observation :

Les valeurs de **dev.tfvars** remplacent les valeurs de **terraform.tfvars** pour les variables présentes dans les deux fichiers.

## Exécution 3 — Utiliser -var en ligne de commande

```bash
# Applique en écrasant certaines valeurs directement en ligne de commande.
terraform apply -auto-approve \
  -var="file_name=cli-report.txt" \
  -var="environment=cli" \
  -var="owner=valeur-depuis-var-cli"

# Affiche le fichier créé.
cat cli-report.txt

# Affiche les valeurs réellement utilisées.
terraform output effective_values
```

Observation :

Les valeurs passées avec **-var** ont une priorité plus forte que les valeurs de **terraform.tfvars**.

## Questions à poser

Quel fichier est chargé automatiquement ?

Pourquoi **dev.tfvars** n’est-il pas utilisé tout seul ?

Quelle option permet d’utiliser un fichier spécifique ?

Quelle option permet d’écraser une variable directement dans la commande ?

## Points clés

**variables.tf** déclare.

**main.tf** utilise.

**terraform.tfvars** fournit automatiquement des valeurs.

**dev.tfvars** doit être appelé avec **-var-file**.

**-var** permet une surcharge ponctuelle.

# 6. Étape 4 : Précédence des variables

## Objectif

Comprendre quelle valeur gagne lorsque la même variable est définie à plusieurs endroits.

C’est la partie la plus importante de l’atelier.

Terraform applique un ordre de priorité lorsque la même variable reçoit plusieurs valeurs depuis plusieurs sources. Les options **-var** et **-var-file** en ligne de commande ont la priorité la plus forte, tandis que la valeur **default** dans le bloc **variable** a la priorité la plus faible. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/values/variables "Use input variables to add module arguments | Terraform | HashiCorp Developer"))

---

## Tableau de priorité

Ordre du plus prioritaire au moins prioritaire :

| Priorité | Source                        | Chargement                 |
| -------- | ----------------------------- | -------------------------- |
| 1        | **-var** et **-var-file**     | explicite dans la commande |
| 2        | **.auto.tfvars**              | automatique, ordre lexical |
| 3        | **terraform.tfvars.json**     | automatique                |
| 4        | **terraform.tfvars**          | automatique                |
| 5        | **TF_VAR_nom**                | variable d’environnement   |
| 6        | **default** dans **variable** | valeur par défaut          |

Version simple à retenir :

```text
CLI gagne sur fichiers.
auto.tfvars gagne sur terraform.tfvars.
terraform.tfvars gagne sur TF_VAR.
TF_VAR gagne sur default.
default est le dernier recours.
```

Attention :

Quand plusieurs options **-var** et **-var-file** sont utilisées dans la même commande, Terraform les traite dans l’ordre donné. La dernière valeur fournie pour la même variable peut donc l’emporter dans ce contexte. ([HashiCorp Developer](https://developer.hashicorp.com/terraform/language/values/variables "Use input variables to add module arguments | Terraform | HashiCorp Developer"))

**environment**

---

## Créer le fichier variables.tf

Créer le fichier **variables.tf** :

```hcl
# Variable utilisée pour démontrer la précédence.
variable "environment" {
  type        = string
  description = "Valeur permettant de tester la précédence."
  default     = "01-default"
}
```

## Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {

      source  = "hashicorp/local"

    }
  }

# Provider Local sans configuration.
provider "local" {}

# Crée un fichier dont le nom et le contenu dépendent de la variable environment.

  content = <<EOT
Valeur finale de environment : ${var.environment}
EOT
}

# Affiche la valeur finale choisie par Terraform.
output "environment_final" {
  value = var.environment
}
```

## Créer le fichier terraform.tfvars

Créer le fichier **terraform.tfvars** :

```hcl
# Valeur chargée automatiquement par Terraform.
environment = "04-terraform-tfvars"
```

## Créer le fichier 10-auto.auto.tfvars

Créer le fichier **10-auto.auto.tfvars** :

```hcl
# Valeur chargée automatiquement par Terraform.
# Elle est plus prioritaire que terraform.tfvars.
environment = "02-auto-tfvars"
```

## Créer le fichier dev.tfvars

Créer le fichier **dev.tfvars** :

```hcl
# Valeur utilisée uniquement si -var-file est précisé.
environment = "01-var-file-dev"
```

## Étape 1 — Tester sans variable d’environnement et sans CLI

Nettoyer la variable d’environnement :


Exécuter :

Exécuter :

```bash
# Définit une variable d'environnement Terraform.
export TF_VAR_environment="05-env-var"
```

Exécuter :


## Étape 4 — Tester avec -var

Exécuter :

```bash
# Applique avec une valeur directe en ligne de commande.
terraform apply -auto-approve -var="environment=00-var-cli"

# Affiche la valeur finale.
terraform output environment_final
```

Résultat attendu :

```text
"00-var-cli"
```

**-var** est une valeur passée explicitement sur la ligne de commande.  
Elle a la priorité la plus forte.

## Étape 5 — Tester l’ordre entre plusieurs sources CLI

Exécuter :

```bash
# Ici, -var-file est lu puis -var arrive après.
terraform apply -auto-approve \
  -var-file="dev.tfvars" \
  -var="environment=00-var-cli-apres-var-file"

# Affiche la valeur finale.
terraform output environment_final
```

Résultat attendu :

```text
"00-var-cli-apres-var-file"
```

Pourquoi ?

Sur la ligne de commande, Terraform applique les options dans l’ordre fourni.

Maintenant inverser :

```bash
# Ici, -var arrive avant puis -var-file arrive après.
terraform apply -auto-approve \
  -var="environment=00-var-cli-avant-var-file" \
  -var-file="dev.tfvars"

# Affiche la valeur finale.
terraform output environment_final
```

Résultat attendu :

```text
"01-var-file-dev"
```

Pourquoi ?

Dans cette commande, **-var-file** arrive après **-var**.  
La dernière valeur CLI pour la même variable l’emporte.

# 8. Étape 5 : Bonne organisation des fichiers

## Objectif

Adopter une organisation simple et lisible.

## Structure recommandée débutant

```text
terraform-variables-local/
│
├── main.tf
├── variables.tf
├── outputs.tf
├── terraform.tfvars
└── dev.tfvars
```

## Rôle de chaque fichier

| Fichier              | Rôle                                             |
| -------------------- | ------------------------------------------------ |
| **main.tf**          | Ressources Terraform                             |
| **variables.tf**     | Déclaration des variables                        |
| **outputs.tf**       | Valeurs affichées après apply                    |
| **terraform.tfvars** | Valeurs chargées automatiquement                 |
| **dev.tfvars**       | Valeurs d’environnement à charger avec -var-file |

---

## Créer une version organisée

Créer le fichier **variables.tf** :

```hcl
# Nom du fichier de rapport.
variable "file_name" {
  type        = string
  description = "Nom du fichier généré par Terraform."

}

# Environnement cible.
variable "environment" {
  type        = string
  description = "Nom de l'environnement."
  default     = "default"
}

# Liste des technologies.

  type        = list(string)
  description = "Technologies utilisées dans l'atelier."
  default     = ["Terraform", "HCL", "Local Provider"]
}

# Configuration applicative.
variable "app_config" {
  type = object({
    name    = string
    version = number
    enabled = bool
  })

  description = "Configuration de l'application de démonstration."

  default = {
    name    = "demo"
    version = 1
    enabled = true
  }
}
```

Créer le fichier **main.tf** :

```hcl
# Déclare le provider Local.
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# Provider Local sans configuration.
provider "local" {}

# Ressource principale.
resource "local_file" "organized_report" {
  filename = var.file_name

  content = <<EOT
Rapport organisé Terraform

Environnement : ${var.environment}

Application
-----------
Nom : ${var.app_config.name}
Version : ${var.app_config.version}
Active : ${var.app_config.enabled}

Technologies
------------
- ${var.technologies[0]}
- ${var.technologies[1]}
- ${var.technologies[2]}
EOT
}
```

Créer le fichier **outputs.tf** :

```hcl
# Affiche le fichier généré.
output "file_name" {
  value = local_file.organized_report.filename
}

# Affiche l'environnement utilisé.
output "environment" {
  value = var.environment
}

# Affiche le nom de l'application.
output "app_name" {
  value = var.app_config.name
}
```

Créer le fichier **terraform.tfvars** :

```hcl
# Valeurs chargées automatiquement.
file_name   = "final-report.txt"
environment = "dev"

technologies = [
  "Terraform",
  "Variables",
  "Provider Local"
]

app_config = {
  name    = "local-variable-demo"
  version = 2
  enabled = true
}
```

## Commandes à exécuter

```bash
# Reformate les fichiers.
terraform fmt

# Valide la configuration.
terraform validate

# Prévisualise.
terraform plan

# Applique.
terraform apply -auto-approve

# Affiche le fichier.
cat final-report.txt

# Affiche les outputs.
terraform output

# Liste les ressources.
terraform state list
```

## Points clés

**variables.tf** ne donne pas forcément les valeurs finales.

**terraform.tfvars** surcharge les valeurs par défaut.

**outputs.tf** sépare les résultats affichés.

**main.tf** reste concentré sur les ressources.

# 9. Erreurs guidées à provoquer

## Erreur 1 — Mauvais type number

Dans **terraform.tfvars**, mettre volontairement :

```hcl
app_config = {
  name    = "local-variable-demo"
  version = "deux"
  enabled = true
}
```

Exécuter :

```bash
terraform validate
terraform plan
```

Observation :

**validate** peut passer, mais **plan** doit échouer lors de l’évaluation des valeurs.

Correction :

```hcl
version = 2
```

## Erreur 2 — Bool écrit comme texte

Dans **terraform.tfvars**, mettre :

```hcl
app_config = {
  name    = "local-variable-demo"
  version = 2
  enabled = "oui"
}
```

Exécuter :

```bash
terraform plan
```

Observation :

Terraform refuse la valeur, car **enabled** attend un **bool**.

Correction :

```hcl
enabled = true
```

## Erreur 3 — Élément manquant dans object

Dans **terraform.tfvars**, mettre :

```hcl
app_config = {
  name    = "local-variable-demo"
  version = 2
}
```

Exécuter :

```bash
terraform plan
```

Observation :

Terraform indique que l’attribut **enabled** manque.

Correction :

```hcl
app_config = {
  name    = "local-variable-demo"
  version = 2
  enabled = true
}
```
