# Atelier 1 : Découverte de la structure HCL avec Terraform et GitLab

## 1. Prérequis

Savoir exécuter les commandes Terraform suivantes :

```bash
terraform init
terraform validate
terraform plan
terraform apply
terraform destroy
terraform state list
terraform show
```

Avoir aussi :

**un compte GitLab**,  
**un token GitLab**,  
**Terraform installé**,  
**un terminal Ubuntu**.

Le token GitLab doit être fourni par variable d’environnement Linux, pas par variable Terraform.

Le provider `gitlabhq/gitlab` lit automatiquement la variable `GITLAB_TOKEN`. Il ne faut **pas** créer une variable Terraform `variable "gitlab_token"` ni utiliser `TF_VAR_gitlab_token`.

## Rendre le token persistant dans .bashrc

Ouvrir le fichier `.bashrc` :

```bash
nano ~/.bashrc
```

Ajouter à la fin du fichier :

```bash
# Token GitLab lu automatiquement par le provider Terraform gitlabhq/gitlab.
export GITLAB_TOKEN="glpat-votre-token-ici"
```

Recharger la session :

```bash
source ~/.bashrc
```

Vérification rapide :

```bash
# Vérifie que la variable d’environnement existe.
echo "$GITLAB_TOKEN"
```

Résultat attendu :

```text
glpat-votre-token-ici
```

Si la commande retourne une ligne vide, le token n’est pas chargé. Relancer `source ~/.bashrc` et vérifier.

Attention :

Ne jamais écrire le token directement dans **main.tf**.

# 3. Étape 1 : Lecture de la documentation officielle

## Documentation à consulter

Documentation officielle du provider GitLab :

**Terraform Registry → gitlabhq/gitlab**

La ressource **gitlab_project** permet de créer et gérer un projet GitLab. 

## Comment lire la documentation

Dans la documentation d’un provider, il faut repérer trois parties.

## 1. Resources

Les **resources** sont les objets que Terraform peut gérer.

Dans cet atelier, on utilisera :

```text
gitlab_project
gitlab_project_label
```

Cela signifie :

**gitlab_project** : gérer un projet GitLab.  
**gitlab_project_label** : gérer un label dans un projet GitLab.

## 2. Arguments

Les **arguments** sont les valeurs que nous écrivons dans le code.

Exemple :

```hcl
name             = "tf-hcl-demo"
description      = "Projet créé avec Terraform"
visibility_level = "private"
```

Ici :

**name** définit le nom du projet.  
**description** décrit le projet.  
**visibility_level** définit la visibilité.

## 3. Attributes

Les **attributes** sont les valeurs disponibles après création.

Certains attributs sont calculés par GitLab ou par le provider.

Exemples courants :

**id**,  
**web_url**,  
**http_url_to_repo**,  
**ssh_url_to_repo**.

À retenir :

**Argument** : valeur fournie dans le code.  
**Computed attribute** : valeur calculée après création.

# 4. Structure HCL à comprendre avant de coder

## Forme générale d’un block

```hcl
block_type "label_1" "label_2" {
  argument_name = expression
}
```

## Exemple avec GitLab

```hcl
resource "gitlab_project" "demo" {
  name             = "tf-hcl-demo"
  description      = "Projet créé avec Terraform"
  visibility_level = "private"
}
```

Lecture :

**resource** : type de block Terraform.  
**gitlab_project** : type de ressource fourni par le provider GitLab.  
**demo** : nom logique Terraform.  
**name**, **description**, **visibility_level** : arguments.  
**"private"** : expression de type texte.

# 5. Version 1 : Resource GitLab basique

## Objectif

Créer un premier projet GitLab avec Terraform.

## Notions ciblées

**resource**,  
**labels**,  
**arguments**,  
**provider**,  
**apply**,  
**destroy**.

Attention :

Chaque participant doit utiliser un nom de projet unique pour éviter les conflits GitLab.

Exemple :

```text
tf-hcl-demo-bechir-001
tf-hcl-demo-amine-001
tf-hcl-demo-sara-001
```

## Étape 1 — Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Le block terraform configure Terraform lui-même.
terraform {
  required_providers {
    gitlab = {
      source  = "gitlabhq/gitlab"
      version = "~> 18.0"
    }
  }
}

# Le provider GitLab utilise automatiquement la variable d'environnement GITLAB_TOKEN.
provider "gitlab" {}

# Ce block déclare un projet GitLab géré par Terraform.
resource "gitlab_project" "demo" {

  # Nom du projet GitLab.
  # Modifier le suffixe pour éviter les conflits entre participants.
  name = "tf-hcl-demo-v1-bechir-001"

  # Description visible dans GitLab.
  description = "Projet GitLab créé avec Terraform pour découvrir HCL."

  # Le projet reste privé.
  visibility_level = "private"
}
```

## Étape 2 — Initialiser

```bash
# Initialise le projet et télécharge le provider GitLab.
terraform init
```

Résultat attendu :

```text
Terraform has been successfully initialized!
```

**init** télécharge le provider **gitlabhq/gitlab**.

## Étape 3 — Valider

```bash
# Vérifie la syntaxe et la cohérence du fichier main.tf.

```

Résultat attendu :

```text

```

## Étape 4 — Vérifier le token avant de planifier

Avant de lancer `terraform plan`, vérifier que `GITLAB_TOKEN` est bien présent dans la session :

```bash
echo "$GITLAB_TOKEN"
```

Résultat attendu :

```text

```

Si la commande retourne une ligne vide, le token n'est pas chargé dans la session courante.

Corriger avec :


Si le fichier `main.tf` contient un bloc `variable "gitlab_token"`, Terraform va demander `Enter a value` en interactif et ignorera `GITLAB_TOKEN`. Il faut supprimer ce bloc et laisser le bloc `provider "gitlab" {}` vide.

## Questions et réponses

**Question 1 — Quelle est la différence entre `gitlab_project` et `demo` ?**

`gitlab_project` est le **type de ressource**. Il indique à Terraform quel objet gérer, ici un projet GitLab. Ce type vient du provider `gitlabhq/gitlab` et correspond à une API GitLab réelle.

`demo` est le **nom logique Terraform**. C'est un identifiant interne choisi librement par le développeur. Il sert à référencer cette ressource ailleurs dans le code, par exemple `gitlab_project.demo.id`. Il n'apparaît pas dans GitLab.

Résumé :

```text
resource "gitlab_project" "demo" { ... }
         ^               ^
         type            nom logique Terraform
```

---

**Question 2 — Quels sont les arguments écrits dans le code ?**

Dans ce `main.tf`, les arguments de la ressource `gitlab_project.demo` sont :

```text
name             = "tf-hcl-demo-v1-bechir-001"
description      = "Projet GitLab créé avec Terraform pour découvrir HCL."
visibility_level = "private"
```

Ce sont des valeurs **fournies par le développeur** dans le code. Terraform les envoie à l'API GitLab au moment du `apply`.

---

**Question 3 — Quels sont les attributs calculés après création ?**

Après `terraform apply`, GitLab calcule et renvoie des valeurs que Terraform enregistre dans le state. Ces valeurs ne sont **pas écrites dans le code**, elles sont produites par GitLab.

Exemples visibles avec `terraform state show gitlab_project.demo` :

```text
id                = "12345678"
web_url           = "https://gitlab.com/bechir/tf-hcl-demo-v1-bechir-001"
http_url_to_repo  = "https://gitlab.com/bechir/tf-hcl-demo-v1-bechir-001.git"
ssh_url_to_repo   = "git@gitlab.com:bechir/tf-hcl-demo-v1-bechir-001.git"
```

Ces attributs sont dits **computed** : Terraform ne peut pas les connaître avant la création.

---

## Points clés

**gitlab_project** est le type de ressource.  
**demo** est le nom logique Terraform.  
**name**, **description**, **visibility_level** sont des arguments.  
**id**, **web_url**, **http_url_to_repo**, **ssh_url_to_repo** sont des attributs calculés.

# 6. Version 2 : Ajout de plusieurs arguments

## Objectif

Enrichir la configuration du projet GitLab avec plus d’arguments.

## Notions ciblées

**arguments**,  
**modification**,  
**plan de changement**,  
**computed attributes**.

## Étape 1 — Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Configuration Terraform avec le provider GitLab.
terraform {
  required_providers {
    gitlab = {
      source  = "gitlabhq/gitlab"
      version = "~> 18.0"
    }
  }
}

# Configuration du provider GitLab.
provider "gitlab" {}

# Projet GitLab enrichi avec plusieurs arguments.
resource "gitlab_project" "demo" {

  # Nom du projet GitLab.
  name = "tf-hcl-demo-v2-bechir-001"

  # Chemin GitLab du projet.
  path = "tf-hcl-demo-v2-bechir-001"

  # Description visible dans l'interface GitLab.
  description = "Version 2 : projet GitLab enrichi avec plusieurs arguments."

  # Visibilité du projet.
  visibility_level = "private"

  # Active les issues dans le projet.
  # Valeurs possibles : "enabled", "disabled", "private", "public".
  issues_access_level = "enabled"

  # Active les merge requests dans le projet.
  merge_requests_access_level = "enabled"

  # Active le wiki du projet.
  wiki_access_level = "enabled"

  # Active les snippets du projet.
  snippets_access_level = "enabled"
}
```

## Étape 2 — Reformater

```bash
# Reformate le code HCL selon le style Terraform.
terraform fmt
```

**fmt** améliore la lisibilité du fichier.

## Étape 3 — Valider

```bash
# Vérifie que les arguments sont acceptés.
terraform validate
```

## Étape 4 — Prévisualiser

```bash
# Affiche les changements prévus.
terraform plan
```

Observation possible :

```text
Plan: 1 to add, 0 to change, 1 to destroy.
```

Pourquoi ?

Dans la version 1, Terraform gérait un projet avec un certain **name**.  
Dans la version 2, le **name** et le **path** changent.

Selon les changements, Terraform peut proposer une modification ou un remplacement.

## Étape 5 — Appliquer

```bash
# Applique la version 2.
terraform apply -auto-approve
```

## Étape 6 — Observer

```bash
# Affiche le state.
terraform show

# Inspecte la ressource.
terraform state show gitlab_project.demo
```

## Questions et réponses

**Question 1 — Quels nouveaux arguments ont été ajoutés ?**

Par rapport à la Version 1, quatre arguments ont été ajoutés :

```text
path                        = "tf-hcl-demo-v2-bechir-001"
issues_access_level         = "enabled"
merge_requests_access_level = "enabled"
wiki_access_level           = "enabled"
snippets_access_level       = "enabled"
```

`path` définit le chemin URL du projet dans GitLab. Si absent, GitLab le dérive du `name`. Le préciser explicitement évite des comportements inattendus lors d’une modification du nom.

Les quatre arguments `*_access_level` contrôlent la visibilité de chaque fonctionnalité. La valeur `"enabled"` les rend accessibles selon la visibilité du projet. Les valeurs possibles sont `"enabled"`, `"disabled"`, `"private"`, `"public"`.

---

**Question 2 — Pourquoi `terraform plan` est-il important avant `apply` ?**

`terraform plan` affiche exactement ce que Terraform va faire **avant** de modifier quoi que ce soit dans GitLab. C’est une prévisualisation sans effet de bord.

Dans cette version, le `name` et le `path` changent par rapport à la Version 1. Terraform ne peut pas modifier un nom de projet GitLab en place : il doit **détruire** l’ancien projet et **créer** un nouveau. Sans `plan`, on risque de supprimer un projet sans le savoir.

Le plan indique clairement :

```text
Plan: 1 to add, 0 to change, 1 to destroy.
```

Ce message signifie : l’ancien projet sera supprimé, un nouveau sera créé.

---

**Question 3 — Quels attributs ne sont pas écrits dans le code mais apparaissent dans le state ?**

Après `terraform apply`, `terraform state show gitlab_project.demo` affiche des attributs calculés par GitLab :

```text
id                  = "12345678"
web_url             = "https://gitlab.com/votre-compte/tf-hcl-demo-v2-bechir-001"
http_url_to_repo    = "https://gitlab.com/votre-compte/tf-hcl-demo-v2-bechir-001.git"
ssh_url_to_repo     = "git@gitlab.com:votre-compte/tf-hcl-demo-v2-bechir-001.git"
default_branch      = "main"
namespace_id        = "..."
```

Ces valeurs sont dites **computed** : Terraform ne les connaît pas avant la création. GitLab les calcule et les renvoie. Terraform les enregistre dans le state pour permettre de les référencer dans d’autres ressources.

---

## Points clés

**Arguments** : valeurs écrites dans le code.  
**Plan** : montre les conséquences d’un changement avant apply.  
**State** : mémorise l’état connu de la ressource GitLab, y compris les attributs calculés.

## Étape 1 — Remplacer le fichier main.tf

```hcl
# Configuration Terraform avec le provider GitLab.
terraform {
  required_providers {
    gitlab = {
      source  = "gitlabhq/gitlab"
      version = "~> 18.0"
    }
  }
}

# Provider GitLab.

# Ressource principale : projet GitLab.
```

```bash
curl --silent --header "PRIVATE-TOKEN: $GITLAB_TOKEN" \
```

## Questions et réponses

**Question 1 — Combien de blocks `resource` voyez-vous ?**

Il y a **4 blocks resource** dans ce fichier :

```text
resource "gitlab_project" "demo"              → 1 projet GitLab
resource "gitlab_project_label" "bug"         → label bug
resource "gitlab_project_label" "feature"     → label feature
resource "gitlab_project_label" "documentation" → label documentation
```

Chaque block `resource` déclare un objet distinct géré par Terraform. Terraform crée, modifie ou supprime chacun indépendamment, mais en respectant les dépendances entre eux.

---

**Question 2 — Pourquoi les labels référencent-ils `gitlab_project.demo.id` ?**

L’API GitLab exige qu’un label soit rattaché à un projet existant via son identifiant numérique (`id`). Cet identifiant n’est pas connu avant la création du projet : c’est GitLab qui l’attribue.

En écrivant `project = gitlab_project.demo.id`, on dit à Terraform :

```text
"Utilise l’id du projet gitlab_project.demo, qui sera connu après sa création."
```

Terraform comprend alors qu’il doit créer le projet **en premier**, puis utiliser son `id` pour créer les labels.

---

**Question 3 — Quelle dépendance Terraform comprend-il automatiquement ?**

Terraform détecte une **dépendance implicite** entre les labels et le projet.

Quand une ressource référence l’attribut d’une autre ressource (`gitlab_project.demo.id`), Terraform construit automatiquement un graphe de dépendances. Il en déduit l’ordre de création :

```text
1. Créer gitlab_project.demo  (le projet)
2. Créer gitlab_project_label.bug, .feature, .documentation  (les labels)
```

Il n’est pas nécessaire d’écrire `depends_on` manuellement ici. La référence suffit. C’est pourquoi on parle de dépendance **implicite** par opposition à la dépendance **explicite** déclarée avec `depends_on`.

---

## Points clés

**gitlab_project.demo.id** est une référence vers un attribut calculé.  
Cette référence crée une **dépendance implicite**.  
Terraform sait qu’il doit créer le projet avant les labels.  
Il n’est pas nécessaire d’écrire `depends_on` quand une référence directe existe.

# 8. Version 4 : Expressions simples avec interpolation

## Questions et réponses

**Question 1 — Où voyez-vous une interpolation ?**

Il y a deux interpolations dans ce fichier, toutes les deux dans les arguments `description` des labels :

```hcl
# Label terraform
description = "Label créé pour le projet ${gitlab_project.demo.name}"

# Label managed
description = "Projet géré par Terraform : ${gitlab_project.demo.web_url}"
```

La syntaxe `${...}` permet d’insérer la valeur d’une expression à l’intérieur d’une chaîne de caractères. Sans interpolation, il faudrait écrire la valeur en dur, ce qui perdrait le lien dynamique avec le projet.

---

**Question 2 — Quelle différence entre `gitlab_project.demo.name` et `gitlab_project.demo.web_url` ?**

`gitlab_project.demo.name` est un **argument** : c’est une valeur que l’on a écrite dans le code. Terraform la connaît dès la lecture du fichier, avant même de contacter GitLab.

`gitlab_project.demo.web_url` est un **attribut calculé** (computed) : GitLab le génère au moment de la création du projet en fonction du nom, du namespace et de la configuration du serveur. Terraform ne peut pas le connaître avant le `apply`.

Résumé :

```text
gitlab_project.demo.name     → connu avant apply  (écrit dans le code)
gitlab_project.demo.web_url  → connu après apply  (calculé par GitLab)
```

---

**Question 3 — Quel attribut est fourni dans le code ? Quel attribut est calculé par GitLab ?**

Fournis dans le code (arguments) :

```text
name             = "tf-hcl-demo-v4-bechir-001"
path             = "tf-hcl-demo-v4-bechir-001"
description      = "Version 4 : projet utilisé pour les expressions HCL."
visibility_level = "private"
```

Calculés par GitLab après création (computed attributes) :

```text
id
web_url
http_url_to_repo
ssh_url_to_repo
default_branch
namespace_id
```

La distinction est visible dans la documentation du provider : les attributs marqués **(Computed)** ne peuvent pas être écrits dans le code, ils sont uniquement disponibles après création.

---

## Points clés

**Interpolation** : insertion d’une valeur dans une chaîne avec `${...}`.  
**gitlab_project.demo.name** vient du code : connu avant `apply`.  
**gitlab_project.demo.web_url** est calculé après création par GitLab.  
Une référence entre ressources crée une **dépendance implicite**.

# 9. Version 5 : Bloc terraform avec required_providers

## Objectif

Mettre en évidence le rôle de **terraform {}**, **required_providers** et **provider {}**.

## Pourquoi `required_providers` et pas seulement `provider` ?

Le bloc `provider "gitlab" {}` dit à Terraform **comment se connecter** à GitLab, mais pas **quel plugin télécharger**. 

Sans `required_providers`, Terraform télécharge la dernière version disponible du provider au moment du `init`, ce qui peut casser le projet si le provider publie une version incompatible. 

`required_providers` verrouille la source et la version du plugin, garantissant que tous les membres de l'équipe et tous les environnements (dev, staging, prod) utilisent exactement le même provider.

 C'est aussi ce qui permet à `.terraform.lock.hcl` de fonctionner : sans `required_providers`, il n'y a rien à verrouiller.

## Notions ciblées

**terraform block**,  
**required_providers**,  
**source**,  
**version**,  
**provider block**,  
**authentification par variable d’environnement**.

## Étape 1 — Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Le block terraform configure Terraform lui-même.
terraform {

  # required_providers indique les plugins nécessaires au projet.
  required_providers {

    # gitlab est le nom local du provider dans ce projet.
    gitlab = {

      # source indique l'adresse officielle du provider dans le Terraform Registry.
      source = "gitlabhq/gitlab"

      # version limite les versions acceptées du provider.
      version = "~> 18.0"
    }
  }
}

# Le block provider configure l'utilisation du provider GitLab.
# Le token n'est pas écrit ici.
# Le provider lit automatiquement la variable d'environnement GITLAB_TOKEN.
provider "gitlab" {}

# Projet GitLab géré par Terraform.
resource "gitlab_project" "demo" {
  name             = "tf-hcl-demo-v5-bechir-001"
  path             = "tf-hcl-demo-v5-bechir-001"
  description      = "Version 5 : provider GitLab déclaré proprement."
  visibility_level = "private"
}

# Label GitLab lié au projet.
resource "gitlab_project_label" "hcl" {
  project     = gitlab_project.demo.id
  name        = "hcl"
  color       = "#AA00FF"
  description = "Label pour apprendre la structure HCL"
}
```

## Différence importante

**required_providers** répond à la question :

```text
Quel plugin Terraform doit être installé ?
```

**provider** répond à la question :

```text
Comment Terraform se connecte à GitLab ?
```

Ici, le block **provider "gitlab" {}** est vide parce que le token est lu depuis **GITLAB_TOKEN**.

## Questions et réponses

**Question 1 — À quoi sert `terraform {}` ?**

Le block `terraform {}` configure Terraform lui-même, indépendamment de tout provider ou ressource. Il peut contenir :

```text
required_version  → version minimale de Terraform acceptée
required_providers → plugins nécessaires au projet
backend           → configuration du stockage du state (remote ou local)
```

Sans ce block, Terraform télécharge n’importe quelle version du provider disponible, ce qui peut provoquer des comportements différents selon les machines.

---

**Question 2 — À quoi sert `required_providers` ?**

`required_providers` déclare les plugins dont le projet a besoin pour fonctionner. Il contient pour chaque provider :

```hcl
gitlab = {
  source  = "gitlabhq/gitlab"
  version = "~> 18.0"
}
```

Lors du `terraform init`, Terraform lit ce bloc et télécharge le bon plugin depuis le Terraform Registry. Sans ce bloc, Terraform ne sait pas quel plugin installer.

---

**Question 3 — Pourquoi ne faut-il pas écrire le token directement dans `main.tf` ?**

Trois raisons principales :

**Sécurité** : `main.tf` est souvent versionné dans Git. Un token écrit en clair dans le code peut être exposé dans l’historique Git, même si on le supprime plus tard.

**Portabilité** : chaque développeur a son propre token GitLab. Si le token est dans le code, il faut le modifier à chaque changement de personne.

**Bonne pratique** : les secrets doivent toujours être fournis par des variables d’environnement, un gestionnaire de secrets ou un vault, jamais par du code source.

Le provider `gitlabhq/gitlab` lit automatiquement `GITLAB_TOKEN` : le block `provider "gitlab" {}` peut rester vide.

---

**Question 4 — Quelle différence entre `source` et `version` ?**

`source` indique **où** télécharger le provider. Il pointe vers son adresse dans le Terraform Registry :

```text
source = "gitlabhq/gitlab"
→ https://registry.terraform.io/providers/gitlabhq/gitlab
```

`version` indique **quelle version** utiliser. L’opérateur `~>` signifie "compatible avec la version mineure" :

```text
version = "~> 18.0"
→ accepte 18.0, 18.1, 18.2 ... mais pas 19.0
```

Sans `version`, Terraform télécharge toujours la dernière version disponible, ce qui peut casser le projet si le provider introduit des changements incompatibles.

---

## Points clés

**terraform block** configure Terraform.  
**required_providers** déclare le plugin GitLab.  
**provider block** configure la connexion.  
**source** indique l’origine du provider dans le Registry.  
**version** limite la version utilisée et garantit la reproductibilité.  
**GITLAB_TOKEN** évite de mettre un secret dans le code.

## Étape 1 — Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclaration du provider GitLab.
terraform {
  required_providers {
    gitlab = {
      source  = "gitlabhq/gitlab"
      version = "~> 18.0"
    }
  }
}

# Provider GitLab utilisant GITLAB_TOKEN.

# Crée trois labels avec le meta-argument count.
resource "gitlab_project_label" "training" {

  name = "training-${count.index}"

  project = gitlab_project.demo.id

  # Couleur identique pour simplifier le premier exemple.
  color = "#3366CC"

}
```

## Questions et réponses

**Question 1 — Pourquoi les labels ont-ils des adresses avec `[0]`, `[1]`, `[2]` ?**

Quand `count = 3` est utilisé, Terraform crée **3 instances distinctes** du même block resource. Pour les différencier dans le state, Terraform ajoute un index numérique à l’adresse de chaque instance :

```text
gitlab_project_label.training[0]  → training-0
gitlab_project_label.training[1]  → training-1
gitlab_project_label.training[2]  → training-2
```

Sans `count`, une ressource n’a pas d’index : `gitlab_project.demo`. Avec `count`, chaque instance a son propre index : `gitlab_project_label.training[0]`.

Cela permet aussi de référencer une instance précise dans le code :

```hcl
gitlab_project_label.training[0].id
```

---

**Question 2 — Est-ce que `count` vient du provider GitLab ?**

Non. `count` est un **meta-argument Terraform**. Il est intégré dans le moteur de Terraform lui-même, pas dans le provider GitLab.

La preuve : `count` fonctionne avec n’importe quel provider (AWS, Azure, GitHub, etc.) et même avec `terraform_data`. Il ne dépend pas du type de ressource utilisée.

Les meta-arguments Terraform disponibles sont : `count`, `for_each`, `depends_on`, `lifecycle`, `provider`.

---

**Question 3 — Quelle est la différence entre argument et meta-argument ?**

Un **argument** vient du provider. Il décrit les propriétés de la ressource gérée :

```hcl
name        = "training-0"       # argument du provider GitLab
color       = "#3366CC"          # argument du provider GitLab
description = "..."              # argument du provider GitLab
```

Un **meta-argument** vient de Terraform lui-même. Il contrôle le comportement de Terraform sur la ressource, pas les propriétés de la ressource :

```hcl
count = 3   # meta-argument Terraform : crée 3 instances
```

Résumé :

```text
argument     → ce que la ressource contient  (vient du provider)
meta-argument → comment Terraform gère la ressource  (vient de Terraform)
```

---

## Points clés

**count** est un **meta-argument Terraform**, pas un argument du provider GitLab.  
Il permet de créer plusieurs instances d’une même ressource.  
Chaque instance reçoit un index numérique dans le state : `[0]`, `[1]`, `[2]`.  
`count.index` donne l’index courant, utilisable dans les expressions.
