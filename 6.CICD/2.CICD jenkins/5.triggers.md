# Les Triggers

### A) Repo Git minimal (GitHub ou GitLab)

- Branche `main` (et `dev` si tu fais les scénarios MR).
- Un `Jenkinsfile` à la racine (je te donne 7 variantes ci-dessous, tu en utilises une à la fois).
- Un petit script de build pour voir un “vrai” résultat (ex: test “factice”).

Créer le fichier **scripts/test.sh** :

```bash
#!/usr/bin/env bash
set -euo pipefail

# Petit test "factice" mais visible dans la console Jenkins
echo "OK - tests passed at $(date -Is)"
```

### B) Jenkins : job “Pipeline”

- Type : **Pipeline**
- “Pipeline script from SCM”
- SCM : **Git**
- URL : ton repo
- Credentials : token/SSH selon ton cas
- Branch specifier : `*/main` (ou `*/dev` selon scénario)
- Script Path : `Jenkinsfile`

---

# 1) Trigger `pollSCM` + intégration Git (GitHub/GitLab)

**Idée (1–2 lignes)** : Jenkins “sonde” le repo toutes les X minutes; si un commit arrive, il build.

**Input pour tester (dans GitHub/GitLab)**

- Modifie `README.md` et push sur `main`.

Créer le fichier **Jenkinsfile** :

```groovy
pipeline {
  agent any

  triggers {
    // Jenkins interroge le SCM toutes les 2 minutes
    pollSCM('H/2 * * * *')
  }

  stages {
    stage('Checkout') {
      steps {
        // Récupère le code depuis le SCM configuré dans le job
        checkout scm
      }
    }

    stage('Test') {
      steps {
        // Exécute un test simple et visible
        sh 'chmod +x scripts/test.sh'
        sh './scripts/test.sh'
      }
    }
  }
}
```

# 2) Trigger “périodique” (`cron`) + intégration Git

**Idée** : le pipeline tourne à heure fixe même sans commit (ex : build nocturne).

**Input pour tester**

- Attendre l’heure/intervalle, ou clique “Build Now” une première fois pour vérifier le pipeline.

Créer le fichier **Jenkinsfile** :

```groovy
pipeline {
  agent any

  triggers {
    // Ex: toutes les 5 minutes (pour tester rapidement)
    cron('H/5 * * * *')
  }

  stages {
    stage('Checkout') {
      steps {
        checkout scm
      }
    }

    stage('Nightly-like checks') {
      steps {
        sh 'chmod +x scripts/test.sh'
        sh './scripts/test.sh'
      }
    }
  }
}
```

# 3) Trigger “upstream” (Job B déclenché par Job A)

**Idée** : un pipeline “parent” déclenche un pipeline “enfant” après succès.

**Input pour tester**

- Lance le job A manuellement (Build Now). Il déclenche le job B.

### Job A : `app-build`

Créer le fichier **Jenkinsfile** (dans repo A ou même repo si tu fais 2 jobs sur 1 repo) :

```groovy
pipeline {
  agent any

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('Build') {
      steps {
        echo "Build OK"
      }
    }

    stage('Trigger downstream') {
      steps {
        // Déclenche le job B (nom exact dans Jenkins)
        build job: 'app-deploy', wait: false
      }
    }
  }
}
```

### Job B : `app-deploy`

**Important** : dans la config du job B, coche :

- **Build Triggers** → **Build after other projects are built** → `app-build`

Créer le fichier **Jenkinsfile** (job B) :

```groovy
pipeline {
  agent any

  stages {
    stage('Deploy') {
      steps {
        echo "Deploy triggered by upstream job"
      }
    }
  }
}
```

# 4) Trigger `githubPush()` (webhook GitHub)

**Idée** : un push GitHub appelle Jenkins via webhook (instantané, pas de polling).

**Inputs à configurer**

1. Jenkins → job → **Build Triggers** : coche **GitHub hook trigger for GITScm polling**

2. GitHub → repo → **Settings → Webhooks → Add webhook**
   
   - Payload URL : `http://JENKINS_URL/github-webhook/`
   - Content type : `application/json`
   - Events : “Just the push event”

3. Test : push un commit sur `main`.

Créer le fichier **Jenkinsfile** :

```groovy
pipeline {
  agent any

  triggers {
    // Active le hook GitHub (le vrai déclenchement vient du webhook)
    githubPush()
  }

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('Build/Test') {
      steps {
        sh 'chmod +x scripts/test.sh'
        sh './scripts/test.sh'
      }
    }
  }
}
```

# 5) Trigger GitLab Push (webhook GitLab)

**Idée** : GitLab envoie un webhook à Jenkins au push.

**Inputs à configurer (avec plugin GitLab recommandé)**

1. Installer plugin **GitLab** dans Jenkins

2. Jenkins → job → **Build Triggers** : coche **Build when a change is pushed to GitLab**

3. Jenkins fournit une URL de webhook (souvent du type) :
   
   - `http://JENKINS_URL/project/JOB_NAME`
   - - token si configuré

4. GitLab → repo → **Settings → Webhooks**
   
   - URL : celle fournie par Jenkins
   - Trigger : **Push events**

5. Test : push commit sur `main`.

Créer le fichier **Jenkinsfile** :

```groovy
pipeline {

    }
```

# 6) “Main change” : build seulement si `main` a changé (skip sinon)

**Idée** : même si le job est déclenché, on ne fait les étapes lourdes que quand `main` (ou certains fichiers) changent.

**Input pour tester**

- Push commit sur `main` qui modifie `README.md` (doit builder)
- Push commit qui modifie un autre fichier (selon règle) (doit skip les étapes protégées)

Créer le fichier **Jenkinsfile** :

```groovy
pipeline {
  agent any

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('Run only when important files change on main') {
      when {
        allOf {
          branch 'main'
          changeset "README.md"
        }
      }
      steps {
        echo "README.md changed on main -> running tests"
        sh 'chmod +x scripts/test.sh'
        sh './scripts/test.sh'
      }
    }

    stage('Otherwise') {
      when { not { allOf { branch 'main'; changeset "README.md" } } }
      steps {
        echo "No targeted change on main -> skipping heavy steps"
      }
    }
  }
}
```

# 7) Merge Request `dev -> main` (GitLab) / Pull Request (GitHub)

### 7A) GitLab Merge Request `dev -> main`

**Idée** : Jenkins build quand une MR est créée/mise à jour vers `main`.

**Inputs à configurer**

1. GitLab : créer branche `dev`
2. GitLab → créer **Merge Request** de `dev` vers `main`
3. Jenkins job : trigger GitLab (plugin) configuré pour MR events (selon plugin : “Merge Request events” / “Pipeline events”)
4. Test : push un commit sur `dev` → MR se met à jour → Jenkins build.

Créer le fichier **Jenkinsfile** :

```groovy
pipeline {
  agent any

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('MR checks (dev -> main)') {
      steps {
        // On fait simple : on exécute des checks systématiques sur l'événement MR
        echo "Running MR checks"
        sh 'chmod +x scripts/test.sh'
        sh './scripts/test.sh'
      }
    }
  }
}
```

### 7B) GitHub Pull Request (équivalent)

**Idée** : Jenkins build sur PR via webhook (souvent via Multibranch Pipeline + GitHub Branch Source).

**Inputs à configurer**

1. Jenkins : créer **Multibranch Pipeline**
2. Ajouter source : GitHub (GitHub Branch Source)
3. Activer découverte des PR
4. Test : créer PR `dev -> main` et push un commit sur `dev`.

Créer le fichier **Jenkinsfile** (même que ci-dessus) :

```groovy
pipeline {
  agent any

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('PR checks') {
      steps {
        echo "Running PR checks"
        sh 'chmod +x scripts/test.sh'
        sh './scripts/test.sh'
      }
    }
  }
}
```

Oui.
**Avec cette condition exacte**, le stage s’exécute **uniquement si les deux conditions sont vraies en même temps** :

- le build concerne la branche **`main`**
- **`README.md` a été modifié** dans le(s) commit(s) qui ont déclenché le build

👉 **Cas concrets :**

| Branche | Fichier modifié | Stage exécuté |
| ------- | --------------- | ------------- |
| main    | README.md       | ✅ Oui         |
| main    | src/app.py      | ❌ Non         |
| dev     | README.md       | ❌ Non         |
| dev     | autre fichier   | ❌ Non         |

---

### Détail important à connaître

- `changeset "README.md"` **ne déclenche pas le build**
  👉 il **filtre seulement l’exécution du stage**

- Le déclenchement vient toujours du trigger :
  
  - `pollSCM`
  - webhook GitHub / GitLab
  - cron
  - upstream

- Si le build démarre mais que `README.md` n’a pas changé sur `main`, **le stage est simplement ignoré**.

---

### Variante utile (si tu veux plusieurs fichiers)

```groovy
changeset "**/*.md"
```

→ le stage s’exécute si **n’importe quel fichier Markdown** change sur `main`.

---

### Variante fréquente (exclure README.md)

```groovy
when {
  branch 'main'
  not {
    changeset "README.md"
  }
}
```

Si tu veux, je peux te montrer **comment bloquer totalement le pipeline** (et pas seulement le stage) quand `README.md` est le seul fichier modifié — c’est un cas très courant en CI.

Oui.
**Avec cette condition**, le stage s’exécute **pour n’importe quel changement**, **tant que la branche est `main`**.

```groovy
stage('Run only when important files change on main') {
  when {
    branch 'main'
  }
}
```

### Ce que ça signifie concrètement

- ✔️ `main` + n’importe quel fichier modifié → **stage exécuté**
- ❌ autre branche (`dev`, `feature/*`) → **stage ignoré**
- ✔️ push, merge, MR/PR fusionnée vers `main` → **stage exécuté**

### Points importants à garder en tête

- Le **trigger** (webhook, pollSCM, cron…) démarre toujours le build
- Le `when` décide **si le stage s’exécute ou non**
- Un merge `dev → main` compte comme un changement sur `main` → le stage passe

### Nom du stage (optionnel mais plus juste)

Si tu veux être précis :

```groovy
stage('Run on any change on main') {
  when {
    branch 'main'
  }
}
```
