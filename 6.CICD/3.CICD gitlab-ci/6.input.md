# Validation manuelle et choix utilisateur : équivalents de `input`

## Objectif

Reprendre le scénario Jenkins : effectuer un build, demander une réponse `Yes` ou `No`, puis exécuter le traitement correspondant.

Les exemples sont indépendants et remplacent le contenu de `.gitlab-ci.yml`. Ils utilisent un runner Linux avec Bash ou `sh`, disponible pour le projet et acceptant les jobs sans tags. Sinon, ajoutez les tags adaptés. Les actions de build et de déploiement sont simulées.

## 1. Ce que fait réellement l'exemple Jenkins

L'étape `input` suspend le pipeline et renvoie la valeur choisie. Le support stocke cette valeur indirectement dans `currentBuild.description`, puis les conditions `when` la lisent pendant l'exécution.

**Choisir `No` puis valider n'annule pas le pipeline** : le stage `No` affiche son message et peut réussir. Le bouton d'abandon de l'étape `input` est une autre action. [Étape input Jenkins](https://www.jenkins.io/doc/pipeline/steps/pipeline-input-step/)

Dans GitLab, on démarre un **job manuel** ; on ne répond pas à une invite interactive à l'intérieur d'un script déjà lancé. Pendant cette attente, ce job ne réserve pas de runner.

| Besoin | GitLab CI/CD | Limite |
| --- | --- | --- |
| Attendre une action humaine | `when: manual` | Le job attend avant son exécution. |
| Bloquer les stages suivants | `allow_failure: false` | À préciser explicitement pour une validation obligatoire. |
| Afficher une confirmation | `manual_confirmation` | Ne retourne pas une valeur `Yes` ou `No`. |
| Demander un choix au lancement du job | `inputs` du job, ou variables manuelles | Disponibilité différente selon les versions. |
| Paramétrer dès le lancement du pipeline | `spec:inputs` | Ne pose pas une question après le build. |
| Utiliser la réponse dans d'autres jobs | Rapport dotenv et conditions dans les scripts | Les `rules` du pipeline existent déjà. |

## 2. Première variante : une validation obligatoire simple

`manual_confirmation` est disponible depuis GitLab 17.1.

```yaml
stages: [build, validation, suite]

build_application:
  stage: build
  script:
    - echo "Build simule termine"

approuver:
  stage: validation
  when: manual
  allow_failure: false
  manual_confirmation: "Confirmez-vous la poursuite de ce pipeline ?"
  script:
    - echo "Validation manuelle recue"

continuer:
  stage: suite
  script:
    - echo "La suite est autorisee"
```

Après le build, le pipeline attend sur `approuver`. Lancez ce job depuis la vue du pipeline, puis confirmez. Après sa réussite, `continuer` démarre.

Fermer ou annuler la confirmation laisse le job en attente ; cela ne choisit pas une branche `No`. [Confirmation manuelle](https://docs.gitlab.com/ci/yaml/#manual_confirmation)

### Manuel ne signifie pas toujours bloquant

| Déclaration du job manuel | Valeur implicite de `allow_failure` |
| --- | --- |
| `when: manual` hors de `rules` | `true` : facultatif |
| `when: manual` dans une règle | `false` : bloquant |

Écrire `allow_failure: false` évite cette ambiguïté. Le pipeline est bloqué jusqu'à la réussite du job. Cette barrière concerne l'ordonnancement présenté ici : des jobs indépendants utilisant `needs` peuvent suivre un autre chemin. [Jobs manuels](https://docs.gitlab.com/ci/jobs/job_control/)

## 3. Choix `Yes` / `No` avec un input de job

**Prérequis : GitLab 18.10 ou plus récent et GitLab Runner 18.9 ou plus récent.**

```yaml
stages: [build, decision]

build_application:
  stage: build
  script:
    - echo "Build simule termine"

choisir_action:
  stage: decision
  when: manual
  allow_failure: false
  inputs:
    approval:
      type: string
      description: "Approuver ou refuser la suite"
      options: ["Yes", "No"]
      default: "No"
  script:
    - |
      case "${{ job.inputs.approval }}" in
        Yes)
          echo "Build approuve : traitement Yes"
          ;;
        No)
          echo "Build refuse : traitement No, sans deploiement"
          ;;
        *)
          echo "Reponse inattendue"
          exit 1
          ;;
      esac
```

Dans la vue du pipeline, cliquez sur **le nom du job** `choisir_action`, renseignez son input, puis lancez-le. Le bouton d'exécution rapide peut utiliser les valeurs par défaut : ici `No`.

Chaque input de job exige un défaut. Les choix sont validés et peuvent être modifiés lors d'une relance du job. Ils sont locaux à ce job, et leur syntaxe est **`${{ job.inputs.approval }}`**, distincte de **`$[[ inputs.approval ]]`** pour les inputs de configuration. [Inputs de job](https://docs.gitlab.com/ci/jobs/job_inputs/)

Cette variante reproduit le choix métier dans un seul job. Avec `No`, le traitement de refus réussit : le pipeline peut donc être vert, comme dans le support Jenkins. Pour qu'un refus fasse échouer le pipeline, ajoutez volontairement `exit 1` dans le cas `No`.

## 4. Variante compatible : saisie manuelle et deux jobs de traitement

Sur une instance sans inputs de job, saisissez une variable lors du lancement du job manuel. Le script vérifie lui-même les valeurs autorisées.

Cet exemple sépare les traitements `Yes` et `No`, comme le support Jenkins, et transmet la décision par un rapport dotenv :

```yaml
stages: [build, decision, traitement]

build_application:
  stage: build
  script:
    - echo "Build simule termine"

saisir_decision:
  stage: decision
  when: manual
  allow_failure: false
  script:
    - |
      case "${DEMO_APPROVAL:-}" in
        Yes|No)
          printf 'DEMO_DECISION_RESULT=%s\n' "$DEMO_APPROVAL" > decision.env
          ;;
        *)
          echo "Saisir DEMO_APPROVAL avec exactement Yes ou No"
          exit 1
          ;;
      esac
  artifacts:
    reports:
      dotenv: decision.env

traitement_yes:
  stage: traitement
  needs:
    - job: saisir_decision
      artifacts: true
  script:
    - |
      case "${DEMO_DECISION_RESULT:-}" in
        Yes) echo "Traitement Yes : poursuite simulee" ;;
        No) echo "Traitement Yes non concerne" ;;
        *) echo "Decision absente ou invalide"; exit 1 ;;
      esac

traitement_no:
  stage: traitement
  needs:
    - job: saisir_decision
      artifacts: true
  script:
    - |
      case "${DEMO_DECISION_RESULT:-}" in
        No) echo "Traitement No : refus enregistre" ;;
        Yes) echo "Traitement No non concerne" ;;
        *) echo "Decision absente ou invalide"; exit 1 ;;
      esac
```

### Manipulation

1. Attendez la fin du build.
2. Cliquez sur le **nom** `saisir_decision`, pas sur le bouton d'exécution rapide.
3. Ajoutez la variable `DEMO_APPROVAL` avec `Yes` ou `No`, en respectant la casse.
4. Lancez le job et observez les deux traitements.

Sans saisie, le job échoue et la suite ne démarre pas. Ne préconfigurez pas les noms `DEMO_APPROVAL` ou `DEMO_DECISION_RESULT` dans les variables du projet/groupe ou du pipeline pendant cet exercice, afin d'éviter une valeur préexistante ou prioritaire.

Les variables saisies dans un job manuel ne sont pas des champs secrets : des utilisateurs autorisés peuvent les consulter ou les réutiliser lors d'une relance. [Saisie de variables manuelles](https://docs.gitlab.com/ci/jobs/job_control/#specify-variables-when-running-manual-jobs)

### Différence visuelle avec les stages Jenkins

Les deux jobs existent et démarrent après la décision. Celui qui ne correspond pas affiche un message puis réussit sans action métier. Il n'est pas marqué `skipped` : on branche **dans le script**.

Remplacer ces conditions par `rules:if` sur `DEMO_DECISION_RESULT` ne fonctionnerait pas : la décision n'existait pas quand GitLab a sélectionné les jobs. Le rapport dotenv partage une valeur d'exécution, sans recalculer le graphe. [Dotenv](https://docs.gitlab.com/ci/variables/dotenv_variables/), [évaluation des règles](https://docs.gitlab.com/ci/jobs/job_rules/)

Pour créer réellement un seul chemin après une décision tardive, une approche plus avancée consiste à générer la configuration d'un pipeline enfant. Elle dépasse ce premier exercice ; voir le principe des pipelines enfants dans [5.triggers.md](5.triggers.md).

## 5. Choix au lancement ou choix après le build ?

| Question | Mécanisme adapté |
| --- | --- |
| « Quelle cible utiliser pour ce pipeline ? » | `spec:inputs`, avant la création des jobs. |
| « Après inspection du build, puis-je continuer ? » | Job manuel bloquant. |
| « Quelle action choisir maintenant dans ce job ? » | Input de job, ou variable manuelle validée. |

Les inputs de pipeline de [2.environnement et params.md](2.environnement%20et%20params.md) restent fixes pour l'exécution. Ils peuvent sélectionner les jobs par `rules`, mais ne constituent pas une nouvelle question après le build. [Inputs de configuration](https://docs.gitlab.com/ci/inputs/)

De même, un input de job ne peut pas être utilisé pour recalculer `rules`, `stage` ou `include` du pipeline courant. Il sert aux champs pris en charge à l'exécution, notamment `script`. [Portée des inputs de job](https://docs.gitlab.com/ci/jobs/job_inputs/)

## 6. Validation de déploiement : qui peut approuver ?

Une confirmation est un geste utilisateur ; elle ne définit pas à elle seule les droits de déploiement. Pour un environnement précis :

```yaml
stages: [deploy]

deploy_production:
  stage: deploy
  environment:
    name: production
  when: manual
  allow_failure: false
  manual_confirmation: "Confirmer le deploiement simule en production ?"
  script:
    - echo "Deploiement simule autorise"
```

Ce YAML associe le job à l'environnement `production`, sans le rendre protégé. Avec **Premium/Ultimate**, configurez **Settings > CI/CD > Protected environments**, puis la liste **Allowed to deploy** pour limiter les utilisateurs autorisés. [Environnements protégés](https://docs.gitlab.com/ci/environments/protected_environments/)

Les **deployment approvals**, également Premium/Ultimate, permettent d'exiger des approbations dédiées. Elles sont distinctes du simple bouton manuel et de `manual_confirmation`. Après les approbations requises, le job de déploiement doit encore être lancé ; un rejet n'exécute pas automatiquement un job `No`. [Approbations de déploiement](https://docs.gitlab.com/ci/environments/deployment_approvals/)

## 7. Pièges à éviter

- Deux jobs manuels « Oui » et « Non » ne créent pas un choix exclusif : les deux peuvent être lancés. S'ils sont tous deux bloquants, la suite peut attendre les deux.
- Une commande shell `read` n'est pas un formulaire GitLab : les scripts CI ne doivent pas attendre une réponse interactive dans le journal.
- `timeout` limite le temps d'exécution du job ; il ne fournit pas un délai de réponse humaine équivalent à un `timeout` Jenkins autour de `input`.
- Annuler le pipeline, choisir `No` et échouer avec `exit 1` doivent rester des décisions explicitement différentes.
- Une relance peut changer la réponse et répéter une action. Pour les déploiements réels, utilisez les contrôles d'environnement et prévoyez les répétitions.

## 8. Exercices

1. Lancez la validation simple : vérifiez que `continuer` attend, puis démarre après approbation.
2. Comparez `allow_failure: false` et `true` sur ce job manuel.
3. Avec les inputs de job, choisissez successivement `Yes` puis `No` dans deux pipelines. Comparez les messages et le statut.
4. Avec la variante compatible, essayez une valeur vide, `Yes`, `No` puis `yes`.
5. Vérifiez que les deux jobs de traitement existent même si une seule action métier est réalisée.
6. Ajoutez `exit 1` au traitement de refus dans la variante à input de job et observez le changement de statut.

Les exemples ont été relus à partir des documentations officielles. Ils n'ont pas été exécutés sur GitLab. Vérifiez les versions indiquées et validez la configuration dans l'éditeur de pipeline avant les essais.
