# Exécuter des commandes distantes avec SSH

## Objectif

Adapter `sshagent { sh 'ssh ...' }` de Jenkins et la préparation SSH GitLab à un runner GitHub Actions.

## 1. Correspondances

| Jenkins                         | GitLab CI/CD           | GitHub Actions                         |
| ------------------------------- | ---------------------- | -------------------------------------- |
| Credential SSH identifié par ID | Variable de type File  | Secret contenant le texte de la clé    |
| Bloc `sshagent`                 | Agent SSH ou `ssh -i`  | Agent SSH ou `ssh -i`                  |
| `sh` lançant `ssh`              | Commande dans `script` | Commande dans `run`                    |
| Configuration des hôtes connus  | Variable File          | Secret/variable matérialisé en fichier |

Le bloc Jenkins `sshagent` appartient au plugin **SSH Agent** ; **SSH Pipeline Steps** propose notamment `sshCommand`. Ici, OpenSSH suffit, sans action tierce. [Plugin SSH Agent](https://plugins.jenkins.io/ssh-agent/), [SSH Pipeline Steps](https://plugins.jenkins.io/ssh-steps/)

Le runner exécute le client ; la commande distante s'exécute sur le serveur. Les outils et permissions du serveur sont donc distincts de ceux du runner.

## 2. Préparer les identités et le réseau

Prérequis :

- serveur Linux joignable depuis le runner ;
- compte dédié, par exemple `deploy` ;
- clé publique de ce compte dans `~/.ssh/authorized_keys` ;
- clé privée dédiée utilisable sans saisie interactive pour cet exemple ;
- clés d'hôte du serveur obtenues et vérifiées depuis un canal de confiance.

Depuis un poste d'administration, une paire dédiée peut être créée avec :

```sh
ssh-keygen -t ed25519 -f github-actions-demo -C "github-actions-demo"
```

La clé utilisateur authentifie le compte ; la clé d'hôte identifie le serveur. Ne remplacez pas cette vérification par `StrictHostKeyChecking=no`. `ssh-keyscan` collecte une clé mais ne prouve pas son authenticité ; faites vérifier son empreinte avant de la stocker.

Pour un port non standard, `known_hosts` utilise généralement `[serveur]:port`. Un runner hébergé n'a pas automatiquement accès à un serveur privé ; utilisez un chemin réseau autorisé ou un runner adapté.

## 3. Configurer l'environnement

Créez **Settings > Environments > production**, puis ses secrets et variables :

| Nom               | Catégorie | Contenu                                   |
| ----------------- | --------- | ----------------------------------------- |
| `SSH_PRIVATE_KEY` | Secret    | Texte complet multiligne de la clé privée |
| `SSH_KNOWN_HOSTS` | Secret    | Lignes de clés d'hôte vérifiées           |
| `SSH_HOST`        | Variable  | Nom DNS ou IP, sans protocole ni port     |
| `SSH_USER`        | Variable  | Compte distant dédié                      |
| `SSH_PORT`        | Variable  | Port, par exemple `22`                    |

Configurez les branches autorisées et, si disponible, les reviewers. Contrairement à une variable File GitLab, un secret GitHub ne devient pas automatiquement un fichier : le workflow doit l'écrire. [Secrets d'environnement](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets#creating-secrets-for-an-environment)

## 4. Workflow complet : diagnostic distant

Créez `.github/workflows/ssh.yml` sur la branche par défaut :

```yaml
name: Diagnostic SSH
on:
  workflow_dispatch:
permissions: {}
jobs:
  diagnostic:
    if: ${{ github.ref == 'refs/heads/main' }}
    runs-on: ubuntu-24.04
    environment: production
    timeout-minutes: 5
    env:
      SSH_HOST: ${{ vars.SSH_HOST }}
      SSH_USER: ${{ vars.SSH_USER }}
      SSH_PORT: ${{ vars.SSH_PORT || '22' }}
    steps:
      - name: Preparer les fichiers SSH
        shell: bash
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}
        run: |
          set -euo pipefail
          test -n "$SSH_PRIVATE_KEY"
          test -n "$SSH_KNOWN_HOSTS"
          umask 077
          printf '%s\n' "$SSH_PRIVATE_KEY" > "$RUNNER_TEMP/ci-ssh-key"
          printf '%s\n' "$SSH_KNOWN_HOSTS" > "$RUNNER_TEMP/ci-known-hosts"
          chmod 600 "$RUNNER_TEMP/ci-ssh-key" "$RUNNER_TEMP/ci-known-hosts"
      - name: Interroger le serveur
        shell: bash
        run: |
          set -euo pipefail
          test -n "$SSH_HOST"
          test -n "$SSH_USER"
          ssh -i "$RUNNER_TEMP/ci-ssh-key" \
            -p "$SSH_PORT" \
            -o BatchMode=yes \
            -o IdentitiesOnly=yes \
            -o StrictHostKeyChecking=yes \
            -o UserKnownHostsFile="$RUNNER_TEMP/ci-known-hosts" \
            -o ConnectTimeout=10 \
            "$SSH_USER@$SSH_HOST" 'sh -se' <<'REMOTE'
          whoami
          hostname
          pwd
          REMOTE
      - name: Nettoyer les fichiers temporaires
        if: ${{ always() }}
        shell: bash
        run: |
          rm -f -- "$RUNNER_TEMP/ci-ssh-key" "$RUNNER_TEMP/ci-known-hosts"
```

**Résultat attendu :** après passage des règles d'environnement, les logs indiquent l'utilisateur, le nom et le répertoire du serveur.

Le délimiteur cité `'REMOTE'` empêche l'expansion locale des variables dans le script transmis. `sh -e` arrête le script distant sur une erreur non traitée. `ssh` transmet normalement son statut au job ; une erreur de connexion produit un statut distinct.

`-i` sélectionne la clé sans démarrer `ssh-agent`. Si vous choisissez un agent, son socket doit être rendu disponible aux étapes qui en dépendent : les shells des étapes ne partagent pas automatiquement leurs exports. [Manuel OpenSSH](https://man.openbsd.org/ssh)

## 5. Copier un artefact avant une commande distante

Dans un workflow possédant un job `build` qui publie l'artefact `application`, ajoutez `needs: build` au job SSH. Après la préparation des clés et avant le nettoyage, insérez ces étapes :

```yaml
- uses: actions/download-artifact@v8
  with:
    name: application
    path: reception
- name: Copier le JAR
  shell: bash
  run: |
    test -f reception/app.jar
    scp -i "$RUNNER_TEMP/ci-ssh-key" \
      -P "$SSH_PORT" \
      -o BatchMode=yes \
      -o IdentitiesOnly=yes \
      -o StrictHostKeyChecking=yes \
      -o UserKnownHostsFile="$RUNNER_TEMP/ci-known-hosts" \
      reception/app.jar "$SSH_USER@$SSH_HOST:/srv/monapp/incoming/app.jar"
```

Prérequis : `/srv/monapp/incoming` existe et le compte a le droit d'y écrire. SCP utilise `-P` pour le port, SSH `-p`. Ce fragment copie le fichier ; une vraie livraison doit aussi prévoir validation, activation, supervision et retour arrière adaptés à l'application. [Manuel SCP](https://man.openbsd.org/scp)

## 6. Diagnostic des erreurs

| Symptôme                        | Vérification                                                    |
| ------------------------------- | --------------------------------------------------------------- |
| `Permission denied (publickey)` | Compte, clé publique autorisée, clé privée, droits côté serveur |
| `Host key verification failed`  | Nom/port et entrée `known_hosts` vérifiée                       |
| Timeout                         | Routage, pare-feu, VPN, port et disponibilité du serveur        |
| Clé illisible                   | Format multiligne, fins de ligne LF, clé complète               |
| Secret vide                     | Environnement ciblé, nom du secret, origine de l'événement      |

Le nettoyage `always()` n'est pas garanti après disparition de la machine. Sur un runner autonome, prévoir aussi une gestion du cycle de vie des répertoires temporaires. Ne mettez jamais les clés dans les artefacts.

## Exercice

Commencez par le diagnostic, puis provoquez un échec distant avec `false` avant la dernière commande. Vérifiez que le job échoue et que l'étape de nettoyage est prévue malgré cet échec.
