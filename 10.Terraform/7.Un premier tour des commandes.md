

# Atelier — Les commandes (Une première découverte)

## Contexte général

Dans cet atelier, on reste volontairement sans :

**provider cloud**,  
**variables**,  
**workspaces**,  
**modules**,  
**backend distant**.

On utilise uniquement :

**terraform_data** : ressource logique intégrée à Terraform  
**local-exec** : commande exécutée sur la machine locale  
**state local** : mémoire locale de Terraform

Le but n’est pas d’apprendre l’infrastructure cloud maintenant.  
Le but est de comprendre les **commandes Terraform** dans des scénarios concrets.

---

# Scénario 1 — Cycle de vie minimal

## Chaîne de commandes

```text
init → plan → apply → show → destroy
```

## Objectif

Découvrir le cycle Terraform le plus simple :

**initialiser**, **prévisualiser**, **exécuter**, **inspecter**, **supprimer**.

---

## Préparation du scénario

Exécuter sur la machine **Ubuntu Terraform** :

```bash
# Créer un dossier isolé pour ce scénario.
mkdir -p ~/terraform-commandes/scenario-01-cycle-minimal

# Entrer dans le dossier du scénario.
cd ~/terraform-commandes/scenario-01-cycle-minimal
```

Créer le fichier **main.tf** :

```hcl
# Déclare la version minimale de Terraform attendue.
terraform {
  required_version = ">= 1.4.0"
}

# Ressource logique utilisée pour simuler une ressource gérée par Terraform.
# Elle ne crée aucune ressource cloud.
resource "terraform_data" "cycle_minimal" {
  input = "scenario-01-cycle-minimal"

  # Commande exécutée localement pendant terraform apply.
  provisioner "local-exec" {
    command = "echo 'Scenario 01 : ressource créée' > scenario-01-result.txt"
  }
}

# Output affiché après terraform apply.
output "scenario_name" {
  value = terraform_data.cycle_minimal.input
}
```

---

## Étape 1 — Initialiser

Exécuter dans **scenario-01-cycle-minimal** :

```bash
# Prépare le dossier Terraform.
terraform init
```

**init** prépare le projet Terraform.

Résultat attendu :

```text
Terraform has been successfully initialized!
```

---

## Étape 2 — Découvrir le plan

```bash
# Affiche ce que Terraform prévoit de créer.
terraform plan
```

**plan** ne crée rien.  
Il affiche seulement ce que Terraform prévoit de faire.

Résultat attendu :

```text
Plan: 1 to add, 0 to change, 0 to destroy.
```

---

## Étape 3 — Exécuter

```bash
# Applique le plan.
terraform apply
```

Terraform demande :

```text
Enter a value:
```

Taper :

```text
yes
```

**apply** exécute réellement les actions prévues.

---

## Étape 4 — Vérifier le fichier créé

```bash
# Vérifie le fichier créé par local-exec.
cat scenario-01-result.txt
```

Résultat attendu :

```text
Scenario 01 : ressource créée
```

---

## Étape 5 — Inspecter le state

```bash
# Affiche l'état Terraform lisible.
terraform show
```

**show** affiche ce que Terraform connaît dans le **state**.

---

## Étape 6 — Supprimer

```bash
# Supprime la ressource logique suivie par Terraform.
terraform destroy
```

Taper :

```text
yes
```

**destroy** supprime la ressource suivie par Terraform.

Remarque importante :

Le fichier **scenario-01-result.txt** peut rester présent, car il a été créé par une commande shell **local-exec**.

# Scénario 2 — Workflow propre avant exécution

## Chaîne de commandes

```text
init → fmt → validate → plan → apply
```

## Objectif

Montrer une chaîne plus professionnelle :

**préparer**, **formater**, **valider**, **prévisualiser**, **exécuter**.

---

## Préparation du scénario

Exécuter sur la machine **Ubuntu Terraform** :

```bash
# Créer un dossier isolé pour ce scénario.
mkdir -p ~/terraform-commandes/scenario-02-workflow-propre

# Entrer dans le dossier du scénario.
cd ~/terraform-commandes/scenario-02-workflow-propre
```

Créer le fichier **main.tf** :

```hcl
# Déclare la version minimale de Terraform attendue.
terraform {
  required_version = ">= 1.4.0"
}

# Ressource logique utilisée pour simuler une exécution propre.
resource "terraform_data" "workflow_propre" {
  input = "scenario-02-workflow-propre"

  # Cette commande écrit une trace locale après application.
  provisioner "local-exec" {
    command = "echo 'Workflow propre exécuté' > workflow-propre.txt"
  }

output "workflow_status" {
  value = "workflow-propre-valide"
```

```bash
# Initialise le dossier Terraform.
terraform init
```

```bash
terraform fmt
```

**fmt** applique le style standard Terraform.

```text

```

S’il n’affiche rien, cela signifie que le fichier était déjà correctement formaté.

## Étape 3 — Valider

```bash
# Vérifie la validité de la configuration.
terraform validate
```

**validate** contrôle la syntaxe et la cohérence de base.

Résultat attendu :

```text
Success! The configuration is valid.
```

---

## Étape 4 — Prévisualiser

```bash
# Affiche les actions prévues.

```

**plan** permet de vérifier avant d’exécuter.

---

## Étape 5 — Appliquer

```bash
# Applique sans confirmation pour gagner du temps en atelier.

```

**-auto-approve** évite la saisie manuelle de **yes**.

---

## Étape 6 — Vérifier

```bash
# Vérifie le fichier créé localement.
```

Résultat attendu :

```text
Workflow propre exécuté
```

# Scénario 3 — Inspection après création

## Chaîne de commandes

```text
init → apply → output → state list → state show → show
```

## Objectif

Montrer comment explorer ce que Terraform a créé et mémorisé.

Ici, l’objectif principal est le **state**.

---

## Préparation du scénario

Exécuter sur la machine **Ubuntu Terraform** :

```bash
# Créer un dossier isolé pour ce scénario.
mkdir -p ~/terraform-commandes/scenario-03-inspection-state

# Entrer dans le dossier du scénario.
cd ~/terraform-commandes/scenario-03-inspection-state
```

Créer le fichier **main.tf** :

```hcl
# Déclare la version minimale de Terraform attendue.
terraform {
  required_version = ">= 1.4.0"
}

# Ressource logique à inspecter après création.
resource "terraform_data" "inspection" {
  input = {
    scenario = "scenario-03-inspection-state"
    role     = "inspection"
    niveau   = "debutant"
  }

  # Crée un fichier local pour matérialiser l'exécution.
  provisioner "local-exec" {
    command = "echo 'Inspection Terraform terminée' > inspection.txt"
  }
}

# Output simple.
output "scenario" {
  value = terraform_data.inspection.input.scenario
}

# Output plus explicite.
output "role" {
  value = terraform_data.inspection.input.role
}
```

---

## Étape 1 — Initialiser

```bash
# Initialise le projet.
terraform init
```

---

## Étape 2 — Appliquer

```bash
# Crée la ressource logique et les outputs.
terraform apply -auto-approve
```

---

## Étape 3 — Afficher les outputs

```bash
# Affiche tous les outputs.
terraform output
```

**output** affiche les valeurs explicitement exposées par le code Terraform.

Résultat attendu :

```text

```

---

## Étape 4 — Lister les ressources du state

```bash

```

**state list** affiche les adresses Terraform.

## Étape 5 — Inspecter une ressource précise

Dans un pipeline sérieux, on peut séparer :

**génération du plan**,  
**lecture ou validation du plan**,  
**application du plan validé**.

---

## Préparation du scénario

Exécuter sur la machine **Ubuntu Terraform** :

```bash
# Créer un dossier isolé pour ce scénario.
mkdir -p ~/terraform-commandes/scenario-04-plan-sauvegarde
```

```hcl
# Déclare la version minimale de Terraform attendue.

  required_version = ">= 1.4.0"
}

resource "terraform_data" "plan_sauvegarde" {
  input = "scenario-04-plan-sauvegarde"

  # Écrit une trace locale seulement au moment de l'application.
  provisioner "local-exec" {
    command = "echo 'Plan sauvegardé appliqué' > plan-sauvegarde.txt"

  value = "plan-sauvegarde"
```

**plan -out** crée un fichier de plan réutilisable.

Résultat attendu :

```text

```

## Étape 4 — Lire le plan sauvegardé

```bash

```

**show tfplan** permet de consulter le plan avant application.

## Étape 5 — Appliquer le plan sauvegardé


**apply tfplan** applique le plan déjà généré.

## Étape 6 — Vérifier

# Scénario 7 — Renommage dangereux d’une ressource

## Chaîne de commandes

```text
apply → renommer ressource → plan → constater add + destroy
```

## Objectif

Montrer qu’un changement d’adresse Terraform peut être interprété comme :

**ancienne ressource à supprimer**,  
**nouvelle ressource à créer**.

---

## Préparation du scénario

Exécuter sur la machine **Ubuntu Terraform** :

```bash
# Créer un dossier isolé pour ce scénario.
mkdir -p ~/terraform-commandes/scenario-07-renommage-ressource

# Entrer dans le dossier du scénario.
cd ~/terraform-commandes/scenario-07-renommage-ressource
```

Créer le fichier **main.tf** version initiale :

```hcl
# Déclare la version minimale de Terraform attendue.
terraform {
  required_version = ">= 1.4.0"
}

# Ressource avec son premier nom logique.
resource "terraform_data" "app" {
  input = "ressource-app"

  # Écrit une trace locale.
  provisioner "local-exec" {
    command = "echo 'Ressource app créée' > rename-demo.txt"
  }
}

# Output lié à la ressource initiale.
output "resource_name" {
  value = terraform_data.app.input
}
```

---

## Étape 1 — Appliquer la version initiale

```bash
# Initialise le projet.
terraform init

# Applique la version initiale.
terraform apply -auto-approve

# Liste les ressources connues.
terraform state list
```

Résultat attendu :

```text
terraform_data.app
```

---

## Étape 2 — Renommer la ressource

Créer le fichier **main.tf** version renommée :

```hcl
# Déclare la version minimale de Terraform attendue.
terraform {
  required_version = ">= 1.4.0"
}

# Même idée fonctionnelle, mais nouvelle adresse Terraform.
resource "terraform_data" "app_renamed" {
  input = "ressource-app"

  # Écrit une nouvelle trace locale.
  provisioner "local-exec" {
    command = "echo 'Ressource app_renamed créée' > rename-demo.txt"
  }
}

# Output lié à la ressource renommée.
output "resource_name" {
  value = terraform_data.app_renamed.input
}
```

---

## Étape 3 — Observer le plan

```bash
# Observe l'effet du renommage.
terraform plan
```

Résultat attendu :

```text
Plan: 1 to add, 0 to change, 1 to destroy.
```

Explication :

Terraform suit une ressource par son **adresse**.

Avant :

```text
terraform_data.app
```

Après :

```text
terraform_data.app_renamed
```

Pour Terraform, ce sont deux adresses différentes.

---

## Étape 4 — Appliquer

```bash
# Applique le changement.
terraform apply -auto-approve

# Liste les ressources dans le state.
terraform state list
```

Résultat attendu :

```text
terraform_data.app_renamed
```

```text
graph.png
```

# Scénario 10 — Nettoyage final

## Chaîne de commandes

```text
destroy → rm fichiers → ls
```

## Objectif

Faire la différence entre :

**terraform destroy** : supprime ce qui est suivi par Terraform  
**rm** : supprime les fichiers locaux générés

---

## Exécution

Depuis chaque dossier de scénario où une ressource existe encore :

```bash
# Supprime les ressources suivies par Terraform.
terraform destroy -auto-approve
```

Puis supprimer les fichiers générés selon le scénario :

```bash
# Supprime les fichiers générés localement.
rm -f *.txt
rm -f tfplan
rm -f graph.png
```

Vérifier :

```bash
# Affiche les fichiers restants.
ls -la
```

Résultat possible :

```text
main.tf
terraform.tfstate
terraform.tfstate.backup
.terraform.lock.hcl
```

Explication :

**terraform.tfstate** garde l’état actuel.  
**terraform.tfstate.backup** garde l’état précédent.  
En backend local, le backup précédent peut être remplacé au prochain apply.

# Synthèse courte pour l’animateur

Le message principal à transmettre :

```text
Terraform ne s’apprend pas par une liste de commandes.
Terraform s’apprend par des scénarios.
```

Chaque commande a un rôle :

**init** : préparer le projet  
**fmt** : nettoyer le style du code  
**validate** : vérifier la configuration  
**plan** : découvrir les actions prévues  
**apply** : exécuter  
**output** : afficher les valeurs exposées  
**show** : inspecter le state ou un plan  
**state list** : lister les ressources suivies  
**state show** : inspecter une ressource précise  
**plan -destroy** : prévisualiser une suppression  
**destroy** : supprimer les ressources suivies  
**providers** : voir les providers utilisés  
**modules** : voir les modules utilisés  
**graph** : visualiser les dépendances
