# Actions après exécution : équivalents de `post` dans GitLab CI/CD

## Objectif

Reprendre les conditions Jenkins `always`, `success` et `failure`, en distinguant les actions après un job des actions à la fin du pipeline.

Les exemples YAML sont indépendants : copiez un exemple complet à la fois dans `.gitlab-ci.yml`. Ils nécessitent un runner Linux avec Bash ou `sh`, disponible pour le projet et acceptant les jobs sans tags. Sinon, ajoutez les tags de votre runner.

## 1. Pourquoi la traduction n'est pas directe

Dans Jenkins, `post` peut être placé dans un stage ou au niveau du pipeline. Ses conditions sont évaluées selon le résultat du stage ou du pipeline concerné. Les blocs conditionnels suivent un ordre défini par Jenkins. [Référence Jenkins](https://www.jenkins.io/doc/book/pipeline/syntax/#post)

GitLab répartit ce comportement entre plusieurs mécanismes :

| Besoin | Mécanisme GitLab |
| --- | --- |
| Actions après le script d'un job | `after_script` |
| Distinguer réussite et échec de ce job | Lire `CI_JOB_STATUS` dans `after_script` |
| Actions après les stages ordinaires | Job avec `stage: .post` |
| Exécuter après réussite des stages précédents | `when: on_success` |
| Exécuter après échec d'un stage précédent | `when: on_failure` |
| Exécuter malgré la réussite ou l'échec précédent | `when: always` |

Le stage `.post` indique une position ; `when` indique une condition. **`.post` seul ne signifie pas `always`.**

## 2. Adapter le `post` global de votre exemple Jenkins

```yaml
# Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
variables:
  FORCE_FAILURE: "false"

# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages:
  - build

# Déclare le job « build_application » et sa configuration propre.
build_application:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: build
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Simulation du build"
    # Choisit la suite du traitement selon le résultat de ce test.
    - if [ "$FORCE_FAILURE" = "true" ]; then exit 1; fi

# Déclare le job « bilan_toujours » et sa configuration propre.
bilan_toujours:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: .post
  # Exécute ce traitement même après un échec ordinaire ; un arrêt forcé peut l'empêcher.
  when: always
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Bilan execute apres le build, reussi ou echoue"

# Déclare le job « bilan_succes » et sa configuration propre.
bilan_succes:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: .post
  # Exécute ce traitement si les étapes antérieures requises ont réussi.
  when: on_success
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Les stages precedents ont reussi"

# Déclare le job « bilan_echec » et sa configuration propre.
bilan_echec:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: .post
  # Exécute ce traitement lorsqu'un échec antérieur non toléré le justifie.
  when: on_failure
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Un job des stages precedents a echoue"
```

`.post` existe sans déclaration dans `stages`. Il faut conserver au moins un job dans un stage ordinaire : un pipeline composé uniquement de `.pre` et `.post` ne s'exécute pas. [Stage .post](https://docs.gitlab.com/ci/yaml/#stage-post)

### Résultats attendus

Modifiez `FORCE_FAILURE` dans le fichier pour comparer ces deux exécutions :

| Valeur | Build | `bilan_toujours` | `bilan_succes` | `bilan_echec` | Pipeline attendu |
| --- | --- | --- | --- | --- | --- |
| `"false"` | Réussit | Exécuté | Exécuté | Ignoré | Réussi |
| `"true"` | Échoue | Exécuté | Ignoré | Exécuté | Échoué |

Le bilan d'échec réussi ne répare pas le build échoué.

### Différences avec les blocs Jenkins

Les jobs de `.post` peuvent s'exécuter en parallèle. L'ordre de leur déclaration n'impose pas l'ordre des messages. Ce sont des jobs séparés, avec leurs propres runners et répertoires de travail.

Dans cet exemple, `bilan_succes` décrit les stages **précédents**. Il peut réussir même si `bilan_toujours` échoue ensuite dans le même stage. Ce n'est donc pas une notification garantie du statut final, après toutes les actions du pipeline.

Pour inclure un contrôle final dans le bilan, placez ce contrôle dans un stage ordinaire avant `.post`. Évitez `needs: []` sur un bilan de fin : cela autoriserait son démarrage immédiat. [Ordonnancement des pipelines](https://docs.gitlab.com/ci/pipelines/), [dépendances needs](https://docs.gitlab.com/ci/yaml/needs/)

## 3. Actions après un job : `after_script`

Pour un rapport local au job, utilisez cet exemple :

```yaml
# Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
variables:
  FORCE_FAILURE: "false"

# Déclare le job « demo_apres_job » et sa configuration propre.
demo_apres_job:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Écrit ces données dans le fichier indiqué pour une étape ultérieure.
    - echo "Debut du traitement" > trace.txt
    # Prépare une valeur locale au shell ; elle ne devient pas automatiquement disponible dans un autre job.
    - export MESSAGE_LOCAL="Cree dans script"
    # Choisit la suite du traitement selon le résultat de ce test.
    - if [ "$FORCE_FAILURE" = "true" ]; then exit 1; fi
    # Écrit ces données dans le fichier indiqué pour une étape ultérieure.
    - echo "Traitement termine" >> trace.txt
  # Exécute le traitement de fin dans un nouveau shell, sans les variables locales créées par script.
  after_script:
    - |
      # Sélectionne le cas correspondant à la valeur ; la branche de repli traite les valeurs non prévues.
      case "$CI_JOB_STATUS" in
        success) echo "Le script du job a reussi" ;;
        failed) echo "Le script du job a echoue" ;;
        canceled) echo "Le job a ete annule" ;;
        *) echo "Etat non traite : $CI_JOB_STATUS" ;;
      esac
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - 'echo "Variable locale : ${MESSAGE_LOCAL:-absente}"'
    # Écrit ces données dans le fichier indiqué pour une étape ultérieure.
    - 'printf "Etat observe dans after_script : %s\n" "$CI_JOB_STATUS" > bilan.txt'
  # Conserve les fichiers ou rapports du job pour consultation ou transmission.
  artifacts:
    # Définit selon quel résultat du job les artefacts seront collectés.
    when: always
    # Sélectionne les fichiers du workspace à publier comme artefacts.
    paths:
      - trace.txt
      - bilan.txt
```

`CI_JOB_STATUS` décrit **ce job**, pas l'ensemble du pipeline. Un bilan placé dans un nouveau job ne doit pas utiliser cette variable pour deviner le résultat du build précédent. [Variable CI_JOB_STATUS](https://docs.gitlab.com/ci/variables/predefined_variables/)

### Contexte du shell et conservation des fichiers

`after_script` utilise un nouveau shell et revient au répertoire de travail initial. L'export `MESSAGE_LOCAL` n'y est pas conservé ; le fichier `trace.txt` reste accessible dans le répertoire du job. Les variables définies dans le YAML ou les réglages CI/CD sont réinjectées. [Portée des variables](https://docs.gitlab.com/ci/variables/#exporting-variables)

L'ordre est : **`before_script` et `script` → `after_script` → envoi des caches et artefacts**. Ainsi, `bilan.txt` peut être collecté. Le statut observé précède ces dernières opérations ; il n'est pas nécessairement le résultat final après leur exécution. [Cycle d'exécution d'un job](https://docs.gitlab.com/ci/jobs/job_execution/)

`artifacts: when: always` demande la collecte après réussite ou échec normal. Il ne provoque pas l'exécution du job et ne garantit pas la collecte après un dépassement du délai total. Téléchargez les artefacts du job pour lire les deux fichiers ; leur transfert sera détaillé dans la fiche dédiée. [Artefacts](https://docs.gitlab.com/ci/jobs/job_artifacts/), [condition de collecte](https://docs.gitlab.com/ci/yaml/#artifactswhen)

## 4. Mutualiser avec `default:after_script`

```yaml
# Applique ces réglages aux jobs qui ne les redéfinissent pas.
default:
  # Exécute le traitement de fin dans un nouveau shell, sans les variables locales créées par script.
  after_script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - 'echo "Fin du job $CI_JOB_NAME, etat $CI_JOB_STATUS"'

# Déclare le job « job_a » et sa configuration propre.
job_a:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Traitement A"

# Déclare le job « job_b » et sa configuration propre.
job_b:
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Traitement B"
  # Exécute le traitement de fin dans un nouveau shell, sans les variables locales créées par script.
  after_script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Action finale propre au job B"
```

Le défaut s'applique à chaque job qui en hérite : il ne s'exécute pas une seule fois pour tout le pipeline. Ici, `job_b` remplace le défaut ; les deux listes ne sont pas fusionnées. [Référence after_script](https://docs.gitlab.com/ci/yaml/#after_script)

## 5. Un contrôle obligatoire doit pouvoir faire échouer le pipeline

Si `script` réussit, un échec ou un dépassement du délai propre à `after_script` ne fait pas échouer le job. Une vérification obligatoire doit donc être exécutée dans `script`, éventuellement dans un job distinct. [Référence after_script](https://docs.gitlab.com/ci/yaml/#after_script)

Exemple volontairement en échec :

```yaml
# Fixe l'ordre des groupes de jobs ; les jobs d'un même stage peuvent s'exécuter en parallèle.
stages: [build, verification]

# Déclare le job « build_application » et sa configuration propre.
build_application:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: build
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Build simule"

# Déclare le job « verification_finale » et sa configuration propre.
verification_finale:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: verification
  # Exécute ce traitement même après un échec ordinaire ; un arrêt forcé peut l'empêcher.
  when: always
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Verification obligatoire simulee"
    # Renvoie un statut non nul pour conserver l'échec dans le résultat du job.
    - exit 1

# Déclare le job « bilan_echec » et sa configuration propre.
bilan_echec:
  # Place ce job dans le groupe indiqué, qui détermine son ordre par défaut.
  stage: .post
  # Exécute ce traitement lorsqu'un échec antérieur non toléré le justifie.
  when: on_failure
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Le build ou la verification finale a echoue"
```

La vérification échoue, puis le bilan s'exécute. Pour illustrer la différence, placez plutôt un `exit 1` dans l'`after_script` d'un job dont le `script` réussit : ce seul échec ne rendra pas le job rouge.

## 6. Cas limites à connaître

### Échec autorisé

Avec `allow_failure: true`, l'échec est toléré pour l'ordonnancement : il ne déclenche pas les jobs `when: on_failure` des stages suivants. Il ne reproduit donc pas exactement la condition Jenkins `post { failure { ... } }`. [Conditions when](https://docs.gitlab.com/ci/yaml/#when)

### Annulation

`when: always` traite les issues réussite/échec ; il ne force pas un job de bilan à démarrer après annulation du pipeline.

Sur les versions compatibles, `after_script` peut s'exécuter lorsqu'on annule un job pendant son `before_script` ou son `script`. Ce comportement est généralement disponible depuis GitLab 17.3 et nécessite GitLab Runner 16.11.1 ou plus récent. Il ne garantit rien pour un job jamais démarré, un arrêt forcé ou un runner indisponible. [Annulation et after_script](https://docs.gitlab.com/ci/yaml/script/#skip-after_script-commands-if-a-job-is-canceled)

### Délais d'exécution

Un dépassement du délai total du job empêche normalement `after_script`. Réservez du temps au script final et à l'envoi des fichiers :

```yaml
# Déclare le job « demo_delais » et sa configuration propre.
demo_delais:
  # Limite la durée du job ; ne crée ni attente ni nouvelle tentative.
  timeout: 10 minutes
  # Définit les variables de cette portée ; les valeurs de projet ou de pipeline peuvent être prioritaires.
  variables:
    RUNNER_SCRIPT_TIMEOUT: "6m"
    RUNNER_AFTER_SCRIPT_TIMEOUT: "2m"
  # Exécute ces commandes dans l'ordre sur le runner attribué au job.
  script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Traitement principal"
  # Exécute le traitement de fin dans un nouveau shell, sans les variables locales créées par script.
  after_script:
    # Produit du texte sur la sortie standard, ou dans le fichier destinataire si le bloc est redirigé.
    - echo "Finalisation du job"
```

Ces réglages sont interprétés par GitLab Runner. Ici, les plafonds des scripts laissent une marge théorique pour les autres opérations ; le téléchargement du dépôt et la préparation consomment aussi du temps. Le délai maximal du runner peut limiter celui demandé par le job. [Configuration des délais](https://docs.gitlab.com/ci/runners/configure_runners/#set-script-and-after_script-timeouts)

## 7. Exercices

1. Lancez le premier exemple avec `FORCE_FAILURE="false"`, puis `"true"`. Comparez les bilans exécutés.
2. Ajoutez `allow_failure: true` au job de build en échec. Observez le changement des bilans sélectionnés.
3. Dans l'exemple `demo_apres_job`, vérifiez que `MESSAGE_LOCAL` est absente dans `after_script`, mais que les fichiers sont conservés.
4. Comparez un `exit 1` dans `after_script` avec le même échec dans le `script` de `verification_finale`.
5. Dans l'exemple `default`, vérifiez que `job_b` affiche seulement son action finale personnalisée.

Les exemples ont été relus à partir de la documentation officielle ; ils n'ont pas été exécutés sur une instance GitLab. Validez-les dans l'éditeur de pipeline avant les essais avec les runners du projet.
