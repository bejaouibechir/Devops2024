

# Atelier 1 : Découverte de la structure HCL avec Terraform et GitLab

## 1. Prérequis

Savoir exécuter les commandes Terraform suivantes :

```bash
terraform init
terraform validate
terraform plan
terraform apply
terraform destroy
terraform state list
terraform show
```

Avoir aussi :

**un compte GitLab**,  
**un token GitLab**,  
**Terraform installé**,  
**un terminal Ubuntu**.

Le token GitLab doit être fourni par variable d’environnement Linux, pas par variable Terraform.

Exécuter sur la machine **Ubuntu** :

```bash
# Définit le token GitLab dans la session courante.
# Remplacer la valeur par votre vrai token GitLab.
export GITLAB_TOKEN="glpat-votre-token-ici"
```

Vérification rapide :

```bash
# Vérifie que la variable d'environnement existe.
echo "$GITLAB_TOKEN"
```

Attention :

Ne jamais écrire le token directement dans **main.tf**.

# 3. Étape 1 : Lecture de la documentation officielle

## Documentation à consulter

Documentation officielle du provider GitLab :

**Terraform Registry → gitlabhq/gitlab**

La ressource **gitlab_project** permet de créer et gérer un projet GitLab. 

## Comment lire la documentation

Dans la documentation d’un provider, il faut repérer trois parties.

## 1. Resources

Les **resources** sont les objets que Terraform peut gérer.

Dans cet atelier, on utilisera :

```text
gitlab_project
gitlab_project_label
```

Cela signifie :

**gitlab_project** : gérer un projet GitLab.  
**gitlab_project_label** : gérer un label dans un projet GitLab.

## 2. Arguments

Les **arguments** sont les valeurs que nous écrivons dans le code.

Exemple :

```hcl
name             = "tf-hcl-demo"
description      = "Projet créé avec Terraform"
visibility_level = "private"
```

Ici :

**name** définit le nom du projet.  
**description** décrit le projet.  
**visibility_level** définit la visibilité.

## 3. Attributes

Les **attributes** sont les valeurs disponibles après création.

Certains attributs sont calculés par GitLab ou par le provider.

Exemples courants :

**id**,  
**web_url**,  
**http_url_to_repo**,  
**ssh_url_to_repo**.

À retenir :

**Argument** : valeur fournie dans le code.  
**Computed attribute** : valeur calculée après création.

# 4. Structure HCL à comprendre avant de coder

## Forme générale d’un block

```hcl
block_type "label_1" "label_2" {
  argument_name = expression
}
```

## Exemple avec GitLab

```hcl
resource "gitlab_project" "demo" {
  name             = "tf-hcl-demo"
  description      = "Projet créé avec Terraform"
  visibility_level = "private"
}
```

Lecture :

**resource** : type de block Terraform.  
**gitlab_project** : type de ressource fourni par le provider GitLab.  
**demo** : nom logique Terraform.  
**name**, **description**, **visibility_level** : arguments.  
**"private"** : expression de type texte.

# 5. Version 1 : Resource GitLab basique

## Objectif

Créer un premier projet GitLab avec Terraform.

## Notions ciblées

**resource**,  
**labels**,  
**arguments**,  
**provider**,  
**apply**,  
**destroy**.

Attention :

Chaque participant doit utiliser un nom de projet unique pour éviter les conflits GitLab.

Exemple :

```text
tf-hcl-demo-bechir-001
tf-hcl-demo-amine-001
tf-hcl-demo-sara-001
```

## Étape 1 — Créer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Le block terraform configure Terraform lui-même.
terraform {
  required_providers {
    gitlab = {
      source  = "gitlabhq/gitlab"
      version = "~> 18.0"
    }
  }
}

# Le provider GitLab utilise automatiquement la variable d'environnement GITLAB_TOKEN.
provider "gitlab" {}

# Ce block déclare un projet GitLab géré par Terraform.
resource "gitlab_project" "demo" {

  # Nom du projet GitLab.
  # Modifier le suffixe pour éviter les conflits entre participants.
  name = "tf-hcl-demo-v1-bechir-001"

  # Description visible dans GitLab.
  description = "Projet GitLab créé avec Terraform pour découvrir HCL."

  # Le projet reste privé.
  visibility_level = "private"
}
```

## Étape 2 — Initialiser

```bash
# Initialise le projet et télécharge le provider GitLab.
terraform init
```

Résultat attendu :

```text
Terraform has been successfully initialized!
```

**init** télécharge le provider **gitlabhq/gitlab**.

## Étape 3 — Valider

```bash
# Vérifie la syntaxe et la cohérence du fichier main.tf.
terraform validate
```

Résultat attendu :

```text
Success! The configuration is valid.
```

## Étape 4 — Prévisualiser

```bash
# Affiche ce que Terraform va créer dans GitLab.
terraform plan
```

Résultat attendu :

```text
Plan: 1 to add, 0 to change, 0 to destroy.
```

## Étape 5 — Appliquer

```bash
# Crée réellement le projet GitLab.
terraform apply
```

Quand Terraform demande confirmation :

```text
Enter a value:
```

Taper :

```text
yes
```

## Étape 6 — Observer

```bash
# Liste les ressources suivies par Terraform.
terraform state list

# Affiche le détail du projet GitLab dans le state.
terraform state show gitlab_project.demo
```

Observation attendue :

Terraform affiche des attributs calculés par GitLab, par exemple :

```text
id
web_url
http_url_to_repo
ssh_url_to_repo
```

## Questions à poser

Quelle est la différence entre **gitlab_project** et **demo** ?

Quels sont les **arguments** écrits dans le code ?

Quels sont les **attributs calculés** après création ?

## Points clés

**gitlab_project** est le type de ressource.  
**demo** est le nom logique Terraform.  
**name**, **description**, **visibility_level** sont des arguments.  
**id** et **web_url** sont des attributs calculés.

# 6. Version 2 : Ajout de plusieurs arguments

## Objectif

Enrichir la configuration du projet GitLab avec plus d’arguments.

## Notions ciblées

**arguments**,  
**modification**,  
**plan de changement**,  
**computed attributes**.

## Étape 1 — Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Configuration Terraform avec le provider GitLab.
terraform {
  required_providers {
    gitlab = {
      source  = "gitlabhq/gitlab"
      version = "~> 18.0"
    }
  }
}

# Configuration du provider GitLab.
provider "gitlab" {}

# Projet GitLab enrichi avec plusieurs arguments.
resource "gitlab_project" "demo" {

  # Nom du projet GitLab.
  name = "tf-hcl-demo-v2-bechir-001"

  # Chemin GitLab du projet.
  path = "tf-hcl-demo-v2-bechir-001"

  # Description visible dans l'interface GitLab.
  description = "Version 2 : projet GitLab enrichi avec plusieurs arguments."

  # Visibilité du projet.
  visibility_level = "private"

  # Active les issues dans le projet.
  issues_enabled = true

  # Active les merge requests dans le projet.
  merge_requests_enabled = true

  # Active le wiki du projet.
  wiki_enabled = true

  # Active les snippets du projet.
  snippets_enabled = true
}
```

## Étape 2 — Reformater

```bash
# Reformate le code HCL selon le style Terraform.
terraform fmt
```

**fmt** améliore la lisibilité du fichier.

## Étape 3 — Valider

```bash
# Vérifie que les arguments sont acceptés.

```

## Étape 4 — Prévisualiser

```bash
# Affiche les changements prévus.

```

Observation possible :

```text
Plan: 1 to add, 0 to change, 1 to destroy.
```

Pourquoi ?

Dans la version 1, Terraform gérait un projet avec un certain **name**.  
Dans la version 2, le **name** et le **path** changent.

Selon les changements, Terraform peut proposer une modification ou un remplacement.

## Étape 5 — Appliquer

```bash
# Applique la version 2.
terraform apply -auto-approve
```

## Étape 6 — Observer

```bash
# Affiche le state.

# Inspecte la ressource.

```

## Questions à poser

Quels nouveaux **arguments** ont été ajoutés ?

Pourquoi **terraform plan** est important avant **apply** ?

Quels attributs ne sont pas écrits dans le code mais apparaissent dans le state ?

## Points clés

**Arguments** : valeurs écrites dans le code.  
**Plan** : montre les conséquences d’un changement.  
**State** : mémorise l’état connu de la ressource GitLab.

# 9. Version 5 : Bloc terraform avec required_providers

## Objectif

Mettre en évidence le rôle de **terraform {}**, **required_providers** et **provider {}**.

## Notions ciblées

**terraform block**,  
**required_providers**,  
**source**,  
**version**,  
**provider block**,  
**authentification par variable d’environnement**.

## Étape 1 — Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Le block terraform configure Terraform lui-même.
terraform {

  # required_providers indique les plugins nécessaires au projet.
  required_providers {

    # gitlab est le nom local du provider dans ce projet.
    gitlab = {

      # source indique l'adresse officielle du provider dans le Terraform Registry.
      source = "gitlabhq/gitlab"

      # version limite les versions acceptées du provider.
      version = "~> 18.0"
    }
  }
}

# Le block provider configure l'utilisation du provider GitLab.
# Le token n'est pas écrit ici.
# Le provider lit automatiquement la variable d'environnement GITLAB_TOKEN.
provider "gitlab" {}

# Projet GitLab géré par Terraform.
resource "gitlab_project" "demo" {
  name             = "tf-hcl-demo-v5-bechir-001"
  path             = "tf-hcl-demo-v5-bechir-001"
  description      = "Version 5 : provider GitLab déclaré proprement."
  visibility_level = "private"
}

# Label GitLab lié au projet.
resource "gitlab_project_label" "hcl" {
  project     = gitlab_project.demo.id
  name        = "hcl"
  color       = "#AA00FF"
  description = "Label pour apprendre la structure HCL"
}
```

## Différence importante

**required_providers** répond à la question :

```text
Quel plugin Terraform doit être installé ?
```

**provider** répond à la question :

```text
Comment Terraform se connecte à GitLab ?
```

Ici, le block **provider "gitlab" {}** est vide parce que le token est lu depuis **GITLAB_TOKEN**.

# 10. Version 6 optionnelle : Meta-argument count avec labels

## Objectif

Créer plusieurs labels GitLab avec **count**.

## Notions ciblées

**count**,  
**count.index**,  
**instances multiples**,  
**adresses indexées**.

## Étape 1 — Remplacer le fichier main.tf

Créer le fichier **main.tf** :

```hcl
# Déclaration du provider GitLab.
terraform {
  required_providers {
    gitlab = {
      source  = "gitlabhq/gitlab"
      version = "~> 18.0"
    }
  }
}

# Provider GitLab utilisant GITLAB_TOKEN.
provider "gitlab" {}

# Projet GitLab principal.
resource "gitlab_project" "demo" {
  name             = "tf-hcl-demo-v6-bechir-001"
  path             = "tf-hcl-demo-v6-bechir-001"
  description      = "Version 6 : démonstration du meta-argument count."
  visibility_level = "private"
}

# Crée trois labels avec le meta-argument count.
resource "gitlab_project_label" "training" {
  count = 3

  # Chaque label reçoit un nom différent grâce à count.index.
  name = "training-${count.index}"

  # Tous les labels sont liés au même projet.
  project = gitlab_project.demo.id

  # Couleur identique pour simplifier le premier exemple.
  color = "#3366CC"

  # Description dynamique avec interpolation.
  description = "Label numéro ${count.index} créé avec Terraform"
}
```

## Questions à poser

Pourquoi les labels ont-ils des adresses avec **[0]**, **[1]**, **[2]** ?
